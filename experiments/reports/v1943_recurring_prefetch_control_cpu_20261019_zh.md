# 常态调度与预取事务 CPU 降本

日期：2026-10-19。基线为 main 的 `fc9fea7`。
GPU 实验保持暂停，未启动 SGLang、CUDA 请求、真实分配或 DMA。
本轮修改在 main，原引擎补丁和下一轮 24-root 候选配置未变。

## 实现

没有 final-stage、tool、JOIN 或 completion 预测记录时，维护入口直接返回，
不再检查周期或创建空扫描结果；没有命令过期时跳过清理与零计数写入。
新记录仍受原图版本和周期维护，动作提交仍实时验证，不延长授权有效期。
因此空扫描计数不再累加，零过期计数也可能不出现在快照，分析时按零读取。

关闭采样且上次已读空时，事件通道在进入接收循环、创建 delivery 列表前
检查 socket 就绪。突发接收结束时立即记录已经读空，避免下轮再分配接收
缓冲并捕获一次相同的空读取异常。新事件仍在下一次 poll 立即接收，
有消息时沿原解码、顺序、去重、ACK 和拒绝路径处理；开启采样时保留采样。

物理事务登记将池名称、数值类型、重复池、字节对齐和求和合为一次遍历，
避免为每个 child 建立字典、多个集合和生成器。单 child 使用已验证的发布
元组，多个 child 保留交叉重复与重叠检查。节点上限、在途所有权、会话身份、
epoch、取消、超时与完整 ACK 校验均保留；失败登记不留下部分预留。

五个物理提交入口统一使用惰性随机命名空间、实际进程号和递增序号，
包括 PREPARE、单节点 H2D、JOIN/tool burst 及 handoff。仅首次迁移生成
随机命名空间，避免每个节点调用 UUID。序号不受 ledger 更换、历史回执
淘汰或取消影响，没有固定宽度回绕；实际 PID 区分 fork 后继承的实例。
命令 ID 为不透明字符串，原生接口与项目分析路径不按 UUID 格式解析。

## 常态控制与登记

V1941 采用 151 个样本、20 个预热样本，交替测量线程 CPU 时间。
基线完整冻结 runtime、observer、physical 和 event_channel，避免两侧
误用相同的优化后 socket 实现；候选源码均绑定 SHA256。

38 组计时包括真实空 Unix socket、12/24-root 与历史规模 156-workflow
的控制场景、8/48-running、0/16 在途命令、采样开关和维护到期状态。
这些是受控库存与频率，不是新的在线负载或已经观测到的频率。
整轮控制包含 scheduler_step、dispatch_after_forward 和 on_batch_completed；
不包含真实引擎外围调用。另有 36 组登记差分，合法与非法池输入的接收、
拒绝及物理预留结果与基线相同。

线程 CPU P50，单位 us：

| 场景 | 基线 | 候选 | 降幅 |
| --- | ---: | ---: | ---: |
| 空 socket，采样关闭 | 0.793 | 0.643 | 18.88% |
| 24-root/8-running，空预测库存，维护未到期 | 6.442 | 5.469 | 15.11% |
| 同上，强制维护到期 | 8.773 | 5.450 | 37.88% |
| 24-root/8-running，16 在途命令，维护未到期 | 6.972 | 5.797 | 16.86% |
| 登记 64 条 FULL 命令 | 241.224 | 165.561 | 31.37% |
| 登记 64 条 Mamba 命令 | 240.343 | 164.848 | 31.41% |
| 登记 64 条混合命令 | 273.589 | 195.558 | 28.52% |

空 socket 开启采样时为 0.902→0.933us，多约 0.03us；没有把这组计为收益。
24 组完整常态控制场景 P50 改善 4.02%–40.48%，12 组登记场景改善
23.57%–38.19%。维护强制到期不能按全部 decode 调用频率累计收益。

## 完整提交与依赖

V1942 使用 101 个样本、10 个预热样本，真实运行 Python 观察、规划、
来源重验和事务登记，native enqueue 使用 CPU stand-in。重置、状态核对
和 cProfile 不计入时间，诊断打开时只写内存，未模拟实际文件 I/O。
所有 24 组的恢复节点、顺序、必要状态、pending 数量与字节、预算一致。

原生预算、诊断关闭，线程 CPU P50，单位 us：

| 完整提交 | 基线 | 候选 | 降幅 |
| --- | ---: | ---: | ---: |
| JOIN，4 节点 | 423.884 | 399.503 | 5.75% |
| JOIN，16 节点 | 728.404 | 681.068 | 6.50% |
| JOIN，64 节点 | 2383.750 | 2177.131 | 8.67% |
| 工具，4 节点 | 398.250 | 384.151 | 3.54% |
| 工具，16 节点 | 786.708 | 733.721 | 6.74% |
| 工具，64 节点 | 2378.834 | 2168.002 | 8.86% |

全部完整提交场景改善 2.94%–8.86%，明显小于单项登记的百分比。
9 组 prefill 依赖检查的准入结果、原生检查对象、频率和 pending 状态相同。
但其中 64-command、相关 context、状态就绪场景为 25.633→27.245us，
多 1.61us，不能宣称所有路径均变快。

为检查随机命令命名空间和字典布局的影响，V1944 为每个依赖场景创建
12 份独立实例与命令布局；每布局 51 个样本、10 个预热样本，每样本
100 次调用，交替测量。保留 V1942，不以复测覆盖慢样本。各布局先算 P50，
再对 12 个 P50 取等权均值：

| 依赖检查 | 基线 us | 候选 us | 变化 |
| --- | ---: | ---: | ---: |
| 64 在途命令，相关 context，状态就绪 | 26.463 | 26.652 | +0.189us / +0.71% |
| 64 在途命令，相关 context，状态未就绪 | 26.147 | 26.067 | -0.080us / -0.31% |

108 组依赖检查的目标与结果均相同。先前 1.61us 差距未稳定复现，但这
不能证明全部由某个具体因素引起，也不将依赖路径算作已取得改善。

## 验证与剩余工作

最终代码 1384 项 CPU 检查、2 个 subtest 通过，覆盖事件通道、预测维护、
物理所有权/过期/部分 ACK、observer、runtime、PREPARE、JOIN、工具、
handoff、部分恢复、最终重验和服务依赖。新增检查包括多 child 的非法
池输入原子拒绝、空库存后新记录清理、空过期不触发清理、真实过期释放、
突发后即时新事件、采样运行时切换、跨实例与进程编号唯一性、历史回执
淘汰及 64 位边界后不回绕。图变化检查保留一个真实待维护记录，避免把
空扫描计数当作维护是否生效的依据。

最新完整提交剖析中，原生操作核算、事务登记、闭包观察和数量边界后的
再次规划仍占较多 CPU。64-node 场景触及事务数量边界，仍按原路径重新
规划；不以移除边界校验或来源证明来提速。本轮没有消除全部控制成本。

本轮局部时延不能乘以全部历史调度次数，也不代表传输、提前复用、预测
精度、吞吐或 JCT 改善。V85d 的 1811270 次 post-forward 与 558 次受控
完成属于不同频率；下一轮在线效果仍须在用户恢复 GPU 实验后验证。
