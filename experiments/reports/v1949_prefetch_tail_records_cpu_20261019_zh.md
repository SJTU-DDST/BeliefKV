# 预取核算、逐节点记录和尾部规划 CPU 优化

日期：2026-10-19。基线为 main 的 `00d1114`。
继续按用户要求暂停 GPU 实验。没有启动 SGLang 服务、模型请求或 DMA；
原引擎补丁、预测触发和 24-root 候选工作负载均保留。

## 实现

完整提交的步骤与本次选定计划一致、且其 FULL 总量等于不可变快照中
全部缺失 FULL 时，尾部容量检查可以直接结束。原来即使恰好提交全部
64 个节点，也会因为规划达到数量边界而重新规划整个闭包。本轮省去
这类空尾部的节点索引、集合及重复规划。

来源仍须有效，并且仍有在途命令。等式仅证明本快照中没有剩余 FULL
需要尾部规划，不表示传输、Mamba、ACK 或执行就绪。部分提交、超过
64 个节点的实际尾部，以及输入边界外的输出都继续经过原安全计划。
数量上限与 checkpoint_plan 原语义保留，没有扩大预取范围。

纯 FULL H2D 核算将 ID、创建时间和单池数量的重复遍历合并为标量核对，
减少临时 tuple、生成器、集合和比较字典。严格整数/布尔区别、非有限
时间拒绝、native 索引长度、Host 池几何、额外池和总字节核对保留；
混合状态与派生 sidecar 继续使用原通用数量/索引/字节校验。

PrefetchLoadStep、PhysicalChildExpectation、PhysicalActionExpectation
采用固定字段，删除每实例属性字典，继续保留原字段、创建时间与 Host
目的索引。dataclass 复制、值序列化及 pickle 往返均检查；原生引用、
所有权、取消和 ACK 生命周期保留。

## 原生核算与记录存储

V1948 从合格引擎 `HybridCacheController` AST 提取原生
`_num_tokens_by_pool`、`_transfer_num_bytes`，绑定完整源码 SHA256。
索引使用 CPU tuple，不运行真实 controller/分配器。H2D/D2H 各六组
FULL、混合、Mamba 和派生 sidecar，151 样本、20 预热样本，每样本
100 次调用，交替测量线程 CPU 时间。两侧 expectation 的身份、池字节、
总字节和 metadata 均相同。

保留被计时 step 前另行预热类共享字典，使字典实例与固定字段实例按
稳态形态比较；内存采样在计时外执行。V1945 是这个预热明确化前的
初测，最终采用 V1948，不将初始较大实例字典当作稳态内存收益。

线程 CPU P50，单位 us：

| 核算 | 基线 | 候选 | 降幅 |
| --- | ---: | ---: | ---: |
| H2D，FULL 2 token | 7.214 | 5.740 | 20.43% |
| H2D，FULL 4096 token | 7.163 | 5.707 | 20.32% |
| H2D，FULL 4096 + Mamba 1 | 11.343 | 10.463 | 7.76% |
| H2D，仅 Mamba 2 | 11.223 | 10.316 | 8.09% |
| H2D，混合状态 + FULL sidecar | 13.246 | 12.296 | 7.17% |
| H2D，Mamba + Mamba sidecar | 13.504 | 12.607 | 6.65% |

D2H 六组仅改善 1.51%–2.23%，不宣称它也获得约 20% 的 CPU 改善。
其收益主要来自同样使用的 child/action 记录，D2H 核算算法未改。

每个 H2D 步骤的三份记录浅层存储：

| Python 记录 | 基线 bytes | 候选 bytes |
| --- | ---: | ---: |
| PrefetchLoadStep | 176 | 80 |
| PhysicalChildExpectation | 176 | 80 |
| PhysicalActionExpectation | 192 | 96 |
| 合计 | 544 | 256 |

这是实例本体加实例字典，不含引用的 key、字符串、tuple、索引、共享
类元数据与 allocator 开销，不能当作总堆内存，更不是 Host/HBM 容量。
D2H 的 ShadowBackupStep 未改，child/action 合计减少 192 字节。

## 完整提交路径

V1946/V1947 各 40 组：JOIN/tool、4/16/64/65/96 节点、诊断开关及
原生/回退预算。101 样本、10 预热样本，线程 CPU 计时顺序交替。
真实运行 Python 观察、规划、来源重验和登记；native enqueue 为 CPU
stand-in，重置、状态检查和 cProfile 不计入时间，诊断写入内存。

65/96 节点场景实际只提交 64 条命令，并保留尾部。工具场景额外提供
两侧相同的受控 FULL 服务样本，使在 Mamba checkpoint 前截断的纯 FULL
前缀有形状支持；这是 fixture，不是新采集的在线数据或生产策略更改。

V1946 提供尾部回收入口。全部 40 组的恢复目标、顺序、必要状态、
pending 数量/字节和预算相同，P50 改善 2.90%–17.63%。

| 完整提交 | 计划节点 | 实际提交 | 基线 | 候选 | 降幅 |
| --- | ---: | ---: | ---: | ---: | ---: |
| JOIN | 4 | 4 | 312.524 | 299.923 | 4.03% |
| JOIN | 16 | 16 | 674.218 | 625.973 | 7.16% |
| JOIN | 64 | 64 | 2170.401 | 1836.429 | 15.39% |
| JOIN | 65 | 64 | 2183.821 | 2011.749 | 7.88% |
| JOIN | 96 | 64 | 2427.766 | 2265.484 | 6.68% |
| 工具 | 4 | 4 | 376.963 | 364.294 | 3.36% |
| 工具 | 16 | 16 | 719.500 | 679.088 | 5.62% |
| 工具 | 64 | 64 | 2138.821 | 1846.123 | 13.69% |
| 工具 | 65 | 64 | 2176.326 | 2021.058 | 7.13% |
| 工具 | 96 | 64 | 2411.788 | 2272.469 | 5.78% |

新剖析中，64-node 场景仅调用一次规划器，65/96-node 仍调用两次。
对应边界检查确认真实尾部仍按原 FULL 数量、预留和排除集合回收；
即使全部合法输入计划已提交，只要还有范围外 FULL，仍由安全计划
区分它是否可复用，不直接用全部闭包字节驱动回收。

V1947 不提供尾部回收入口，40 组完整路径改善 0.97%–9.84%。
例如 64-node JOIN 为 1992.308→1837.632us，工具为
2015.336→1854.090us。该对照说明核算/记录优化也能降低没有尾部入口的
控制成本，但不能用两个报告的绝对时间相减来估算尾部优化的独立贡献。

V1946 的 9 组 prefill 依赖检查判定、原生对象/频率和 pending 状态相同。
小场景存在正负波动，例如 4-command 已就绪检查 4.121→4.147us，
不宣称每条路径均变快，也不将这些局部波动转换为系统收益。

## 验证与剩余成本

合计 1750 项 CPU 检查、2 个 subtest 通过。首次扩展检查为 1734 通过、
16 项缺少合格引擎环境而跳过；补充显式 SGLANG_SOURCE_CHECKOUT，
CUDA_VISIBLE_DEVICES=99999 后，16 项真实 CPU radix/分配/回收均通过。
未启动 GPU、真实 DMA 或 serving，也未以跳过作为通过。

新增 36 项检查覆盖 63/64/65/96-node 边界、真实非输入 FULL 尾部、
严格节点/时间类型、非法/额外池以及固定字段复制/序列化。
原 observer、runtime、物理 ACK、PREPARE、工具、JOIN、handoff、
部分恢复、驻留、最终重验、telemetry 和策略检查仍通过。

闭包观察在 96-node 剖析中已成为最大的单项自身成本；原生操作核算、
登记和实时来源验证仍有成本，真实尾部也仍需规划。本轮没有消除所有
控制成本。受控节点分布不是实际 workload 频率，局部微秒不能乘以全部
decode 次数；没有据此证明预测精度、提前复用、吞吐或 JCT 改善。
