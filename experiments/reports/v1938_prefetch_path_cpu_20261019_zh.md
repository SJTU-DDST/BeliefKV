# 预取提交与尾部规划 CPU 优化

日期：2026-10-19。基线为 `main` 的 `3381a0e`。
GPU 实验继续暂停，本轮没有启动 SGLang、GPU 请求或 DMA。

## 改动

纯 FULL H2D 操作仍经过相同的来源、索引长度、控制器计数、池尺寸和总字节
核对，但不再为不存在的辅助传输建立尺寸缓存、来源索引、派生列表和排序
结果。池名、索引长度的无状态检查移出每次调用的闭包。Mamba、混合操作
和依赖 FULL/Mamba 索引的 sidecar 继续走通用核算。

`inspect_session_h2d_opportunity` 的有界规划如果自然结束，且未先按容量
截断，保留已经生成的 steps 和已计算的 FULL/Mamba 代价。报告阶段显式
请求的完整计划同样保留。在原有提交后尾部容量核算中复用这份同一快照
的结果，避免第二次执行相同的 `plan_prefetch_gpu_steps`。

这不增加工具/EOS 的规划深度。触及数量边界时无法证明规划自然结束，
仍走原来的重新规划；容量回收、分裂和重新捕获会使用新的 opportunity。
这里的完整结果表示规划器已穷尽本次可恢复步骤，不代表输入所有状态
可恢复，更不代表实际 DMA 完成、已有请求准入或可立即执行。

## 核算微基准

V1935 从固定引擎候选的 `HybridCacheController` AST 读取
`_num_tokens_by_pool` 和 `_transfer_num_bytes` 原方法，仅以 CPU 索引
stand-in 调用。绑定完整控制器源码 SHA，不导入模型、CUDA 或 serving。
每个场景交替测量基线与候选：151 个样本、20 个预热样本、每样本 100 次。

线程 CPU P50，单位 us：

| 操作 | 基线 | 候选 | 降幅 |
| --- | ---: | ---: | ---: |
| 纯 FULL，2 token | 12.88 | 9.54 | 25.88% |
| 纯 FULL，4096 token | 12.45 | 9.24 | 25.80% |
| FULL 4096 + Mamba 1 | 14.85 | 14.56 | 1.93% |
| 仅 Mamba 2 | 14.64 | 14.56 | 0.58% |
| 混合状态 + 依赖 FULL 的 sidecar | 17.42 | 17.07 | 2.03% |
| Mamba + 依赖 Mamba 的 sidecar | 17.24 | 17.03 | 1.24% |

六个场景的冻结 expectation、每池字节、总字节和身份一致。
混合/sidecar 场景只有小幅波动，不宣称同等幅度的改善。

## 完整 CPU 预取路径

V1936/V1937 运行真实 Python 观察、规划、重验和登记；native enqueue 使用
CPU stand-in，前后都不运行真实 allocator 或传输。每组 101 个样本，
10 个预热样本，顺序交替；计时不含重置、状态核对或 cProfile。

V1936 提供与当前引擎相同的尾部回收入口。在选取完整计划且全部提交时，
只需证明没有剩余安全 FULL 尾部，无须再遍历同一规划。24 组 JOIN/tool、
4/16/64 节点、诊断开关和原生/回退预算的 P50 降低 7.56%–13.92%。
恢复目标、顺序、状态选择、pending 数量与字节、预算及原生读取数量一致。

诊断关闭、原生预算下的线程 CPU P50：

| 场景 | 基线 us | 候选 us | 降幅 |
| --- | ---: | ---: | ---: |
| JOIN，4 节点 | 368.84 | 334.05 | 9.43% |
| JOIN，16 节点 | 864.93 | 744.56 | 13.92% |
| JOIN，64 节点 | 2724.84 | 2452.35 | 10.00% |
| 工具，4 节点 | 450.82 | 413.31 | 8.32% |
| 工具，16 节点 | 913.88 | 796.53 | 12.84% |
| 工具，64 节点 | 2798.57 | 2415.52 | 13.69% |

4/16 节点场景省掉一次相同计划的遍历；64 节点触及现有 64-command 边界，
仍保留第二次规划，改善主要来自纯 FULL 核算。基准不将全部改善归给复用。

V1937 不提供尾部回收入口，用来检查额外快照元数据是否抵消核算收益。
同样 24 组的 P50 降低 1.93%–13.40%。例如原生预算、诊断关闭下：
16 节点 JOIN 795.05→727.55us、工具 1101.62→1019.95us；
64 节点 JOIN 2531.27→2240.50us、工具 2567.87→2260.63us。
不同报告的绝对时间受本机运行条件影响，只使用各自交替对照的变化。

另有 9 组 prefill 依赖检查，相关/无关 context、必要状态就绪/未就绪及
legacy 情况的准入判定、原生检查和 pending 状态均相同。

## 验证与限制

最终代码共 1292 项 CPU 检查通过，覆盖 observer、物理事务、运行时、
工具迁移、JOIN、handoff、部分恢复、最终重验和服务子集。
新增 39 项检查针对：

- 有界规划自然结束、恰好触及上限、容量截断和显式完整计划的区别。
- 驻留变化和在途加载后的重新捕获。
- 已全部提交或仍有尾部时的计划复用与原 fallback，核对实际回收目标。
- 纯 FULL 操作的错误数量、零/布尔尺寸、错误总字节、索引不匹配和非法
  未使用池键；这些不能被快速路径放过。

6 组核算、24 组有尾部入口、24 组无尾部入口和 9 组 prefill 共 63 组
受控对照。这些数量和 token/节点分布不是当前 workload 的在线频率。
CPU tuple 不能代表 CUDA 索引开销；没有测得传输、复用、GPU 吞吐、JCT
或预测精度改善，也不将这些本地百分比当作端到端收益。

本轮继续保留原生最终物理检查、部分传输后剩余容量处理和恢复依赖。
24-root 动态委派工作负载仍为暂停后的候选，没有自动启动实验。
闭包观察和真正原生分配/传输的成本仍需继续分析。
