## 修改与边界

`_register_backed_pressure_nodes` 原本在每次新闭包观察后，重复计算已有
候选的前缀长度，再次调用登记。现在仅当既存记录持有同一个不可变 key
对象、且 node ID 和 creation time 均相同时，省去这一无状态变化的操作。
这不是跨调用复用原生状态，也不授予回收或恢复许可。

替换过的候选表仍会重建组索引；新节点、代际变化、同值但不同对象的 key、
新 epoch 和缺失登记继续走原路径。仅在确有新记录需要前缀核对时才构造
节点映射。输入范围、冷尾部条件保持原值。发布及原生回收仍检查当前锁、
引用、Host 副本、在途传输和设备叶子，不跳过物理安全检查。

## CPU 对照

最终 V1970 使用冻结的完整旧 event_channel/observer/physical/runtime，
与候选交替测量。72 组登记场景覆盖 4/16/64/256 节点，全部备份、部分
备份、没有备份，以及首次登记、重复登记、节点替换、同值不同 key、
新 epoch、缺少中间登记。完整顺序、组索引、位置、代际和计数相同。

另有 12 组完整 JOIN PREPARE 调度，24 个 synthetic workflow、running 8，
保留原生式稀疏设备叶子和 Mamba LRU 索引，覆盖控制交付、native 拒绝及
全部已有备份。传输目标、发布列表、原生读取次数、计数与 pending 核算相同。
没有将缺少索引的全表扫描替身当作实际原生路径。

每组 151 个样本及 10 次预热，普通函数固定时钟；重置、比较在计时外。
以下为线程 CPU P50，单位 us：

12 组完整调度均改善，P50 降幅 4.6%–14.4%。72 组局部登记中 26 组
P50 回退，主要为首次登记、同值不同 key 和新 epoch；最大增加约
20.99us，不能宣称所有登记场景更快。V1969 的第一版结果与完整代码差分
保留，第二版只是省去初始空候选表的逐节点查找，没有删除回退场景。

该基准使用 CPU 闭包及原生式索引替身，enqueue、controller 和 writer
也为 CPU 替身；没有实际 allocator/DMA、writer I/O、模型或完整 GPU
调度器。不能从场景频次推算实际累计 CPU、迁移机会、吞吐或 JCT。
