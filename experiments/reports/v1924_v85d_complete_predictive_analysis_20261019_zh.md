# V85d：12root 长上下文实验全程分析

分析日期：2026-10-19（北京时间）。GPU 实验保持用户要求的暂停状态。

## 结论与证据边界

本轮确认了长上下文、多轮动态委派、Host 备份及 JOIN 预恢复可以共同运行。
12 个 workflow、67 个 agent 全部自然结束，没有 error、incomplete 或 guard
强制完成；全部 agent 的平均实际输入都超过 100000 token。

本轮仍没有完成同配置 native 对照。native 在接续启动后被用户明确暂停，
其部分轨迹不能与完整 predictive 计算吞吐/JCT 改善，也不能使用旧 SWE
任务集 native 的吞吐代替本轮基线。任务正确性没有独立评分。

目前证据指向四个限制：

1. H2D 的实际频率仍低。38.415 GB 只有 71 个物理控制器批次，stream
   累计约 1.160 秒，88.04% 的字节发生在第二批 root 到达前。
2. JOIN 恢复能被消费，但主要使用 EOS 后的协议窗口。完成前启动且随后复用
   的 FULL 为 2.868 GB；真正早于模型 EOS 的只有 2 个 JOIN、85.463 MB。
3. 大恢复计划仍受 HBM 可用 FULL 页和安全回收条件限制，工具预取没有产生
   实际传输。增加 root 数需要同时检查有用备份损失和安全冷页的实际存在性。
4. 长输入的重复前端处理、混合 checkpoint 可用性及工具尾段，比本轮 H2D
   stream 时间呈现出更大的观测成本。尚不能将这些成本全部归因于 BeliefKV，
   或把观测时间直接视为可消除的 JCT。

| agent类型 | 数量 | 每 agent 平均输入再等权的均值 | 最大观测上下文 |
|---|---:|---:|---:|

1728 次实际输入范围 115976–228612 token，全部超过 100000；
67 个 agent 的生命周期平均输入也全部超过 100000。这比“只提高配置上限”
提供了更强的工作负载证据。

按独立 FULL 估算，root 均值输入约 3.396 GB，child 均值约 2.989 GB，
但实际存在共享：每个 context 首请求共 9.129M 输入 token，其中
4.909M 未缓存，约 46.23% 已由 Device/Host 命中。不能把 67 份完整
逻辑上下文直接相加当 HBM 占用。
首请求的 4.909M 未缓存 token 约占全程 6.591M prefill 输入的 74.48%，
说明本轮 prefill 很大一部分来自新 context 的初始化与分支恢复。

没有触发 95% 压缩：普通输入最大 228612 小于 249036，内部摘要 agent 为零。
所以本轮验证了配置与长输入路径，未验证压缩触发后的端到端行为。
最大单次实际输出 9377 token，没有 length 终态回调，未碰到 16384 上限。

55 个 child 均返回，create→return 的 P50 108.757s、P90 301.004s、
最大 937.129s；这些时长包含工具和调度等待。child 平均约 20.95 次模型
请求，root 平均 48 次；2048 图步骤预算没有造成本轮 incomplete。

## JOIN 预恢复的实际效果

172 个受控 FULL 节点动作均取得首次服务复用证明，FULL 合计 6.702 GB，
没有观测到这些 FULL 在首次服务前再次被原生加载。该比例是已执行动作
的命中情况，不包括所有未执行机会，也不是时机预测准确率或吞吐收益。

| 边界 | 复用FULL | 事件口径 |
|---|---:|---|
| 模型EOS之前已经启动 | 0.085 GB | 2 个独立 JOIN，5 个节点动作 |
| 客户端JOIN完成之前已经启动 | 2.868 GB | 25 个独立 JOIN |
| 客户端JOIN完成之前已经ACK就绪 | 1.741 GB | 上一行的子集 |
| JOIN完成→parent客户端提交之间启动 | 3.670 GB | 9 个 JOIN |
| parent客户端提交→原生入队之间启动 | 0.164 GB | 5 个 JOIN |

不同阶段的 JOIN 事件可以重叠，同一 JOIN 可以分批恢复，事件数不能相加。
各阶段字节可按动作分开。这里的 JOIN 完成为客户端 join_satisfied；
它晚于模型 EOS，不能把两个边界都叫成 child RETURN。

完成前的 25 个已复用恢复批次，实际提前量 P50 125.299ms、
P90 523.987ms，最早约 6.864s；完成前启动不等于完成前已全量就绪。
提前量来自真实提交到已观测完成边界，不是模型预测误差。

目前可见机制主要由终态事件及协议窗口驱动。显式通知覆盖不足：
55 个 child 中 16 个调用 announce_completion_intent；runtime 记录
15 次通知、12 次阶段接受、11 次最终请求绑定，报告长度校准样本 10 个。
只有 2 个 JOIN 实际由报告服务进度在模型 EOS 前启动恢复。不能据此
宣称已经在新域证明高精度的 RETURN 墙钟预测。

34 个独立 JOIN 中，31 个完成前曾有正 FULL 计划，25 个形成提前启动并
复用；该计数转化率约 80.65%。但大对象覆盖仍不足：

- 完成前最大观测计划按事件相加约 20.342 GB，实际提前复用仅 2.868 GB。
  前者有共享、时机和容量约束，不能当作可实现字节上界。
- JOIN 后继请求仍记录约 25.853 GB 原生 FULL Host 命中。
- 7 个观测计划至少含 16 节点的 JOIN，占剩余原生 FULL 命中的
  19.458 GB；其中仅 3 个有提前复用。
- 整个 JOIN 周期有 18 个事件记录 FULL 容量预算限制，完成前已有
  15 个事件出现该限制。不能据“16节点以上”直接判定存在固定16节点截断。

一个真实拒绝样本中，Device FULL 自由页为 4071 token，预留为 4105；
可用于预取的预算为零。回收扫描 22 个叶子，20 个未有 Host 副本，
2 个仍有 session 引用，未选中安全候选。这解释了为什么 Host FULL
尚有空间时，parent 仍可能无法恢复。重复探测的 unbacked 计数不等于
同样数量的不同 agent，也不证明这些页面都可安全卸载。

## 工具计时与 PREPARE

1820 次工具调用中有 408 次物理 shell 命令。排除退出 124/137 的候选后，
401 次自然结束命令的时长 P50 0.201s、P90 2.124s、P99 2.516s、
最大 3.967s。另有 7 个退出 124/137 的候选，分布在 2 个 workflow，
累计执行约 533.548s。退出 137 仍保留超时/OOM/其他 SIGKILL 的歧义。

工具预取为零。完整生命周期审计有 868 个工具等待 episode，
其中 867 个出现 no_host_backed_missing_copy，1 个出现 FULL 容量限制。
868 不是所有工具调用数：它是运行端实际观察并归属到等待上下文的 episode。
工具续接仍有约 2.233 GB 原生 FULL Host 命中；等待时没有缺失副本不能
证明服务前绝不发生驱逐。需要结合驻留变化，而不能将零预取全部归咎于
时长预测误差或断言没有任何潜在工具机会。

本轮多数命令很短，长工具等待又主要集中在少数尾部任务。应先验证下一轮
长等待与容量压力是否同时存在，再判断更主动卸载的净收益。

PREPARE 共 386 个节点 ACK、23.965 GB，全部为 FULL：
354 个 JOIN 准备节点、32 个工具准备节点。119 个准备节点可以关联到
后续恢复，其 ACK 体积约 6.206 GB；267 个节点、17.759 GB 没有关联恢复。
这是节点/池最新 writer 的归因，不表示 6.206 GB 全部被 forward 读取，
也不能把未关联部分全算作重复传输或浪费。本轮没有观察到这些准备对象
后来又发生同节点同池 D2H，历史的重复写回问题没有在该口径下重现。

## 池压力与重算

Host FULL 高水位 83.201 GB / 160.000 GB，约 52.0%；
Host Mamba 达到 40.050 GB 上限，记录 1054 次驱逐、67.866 GB。
FULL 也有约 2.505 GB 的驱逐/释放记录，不能因为池没满就把它们删掉，
但这些记录可能包含终态回收，不能直接视为容量不足造成的有用 KV 丢失。

1661 个有前次服务输入的同 session 请求，已服务公共前缀约 265.943M token，
首服缓存计数中缺失 60212 token，即 0.02264%。这是小的同 session 前缀
缺口，不能外推成所有重算、所有层或所有冷启动的精确重算率。
被驱逐 Host 对象仍有未匹配生命周期，不能把未匹配项补零。

另有不同的混合前缀问题：11 个新 context 的首请求中，完整 FULL 匹配
比实际 Device+Host 可用前缀合计多 1.340M token；7 个是 child，4 个是
root。相应单请求 prefill worker 区间合计 61.173s。10 个请求的差距超过
100K token，另一个约 4585 token。
这属于“有 FULL 匹配但完整混合 checkpoint 不能直接使用”的观测，
不是同 session 有用 KV 丢失；61.173s 包含这些请求全部 prefill 工作，
不能作为可消除时间。应进一步核对原生 Mamba 分支选择与安全 checkpoint
可用性，不能直接归因为 Host Mamba 驱逐。

## 前端、prefill 与控制成本

1728 次请求的服务端 chat conversion，包含模板渲染和 tokenization：
P50 374.069ms、P90 502.931ms、累计 676.813s。API receipt→原生队列
登记 P50 414.772ms、P90 552.091ms。
对于 JOIN 后继，客户端提交→原生登记的 P50 为 470.046ms，其中
chat conversion P50 为 368.920ms。

这是原生服务路径上重复处理 100K 以上输入的观测成本，不能全部记作
BeliefKV 新增开销；多个请求与 GPU 执行可重叠，676.813s 也不能从
总 JCT 相减。它仍值得在相同语义和两侧同版本条件下检查前缀处理复用。

2944 个 prefill worker 区间共 334.738s；138546 个 decode 区间共
1347.249s。小于 512 token 的单请求 prefill 为 814 批，共 18.814s，
P50 17.133ms、P90 43.426ms。它们是 worker 墙钟，不是独占 GPU kernel
计时。本轮没有同配置 native，不能再沿用旧短 prefill 慢 2 倍的结论。

共享路径细粒度计时关闭，因此没有全程同步控制成本总量。后台 writer
只有每64条的处理采样，不能乘64当作精确全程成本，不能将 wall-CPU
差值直接称为 GIL 等待。本轮也不能宣称控制开销已经测清或完全消除。

## 对下一轮24root的含义

暂停保持有效，下面是配置与验收建议，不启动实验：

1. 扩展到 24 个不同的原始长任务，保留相同上下文、超时和输出预算。
   root 数与 running 上限分开；优先用 24root/running8 观察更多等待
   context 是否形成恢复机会，避免同时改变多个维度。
2. 到达安排应让第二批加入时仍有足够活跃任务。仅按 8+4/900s 的比例
   外推不能保证持续压力；本轮第二批之前已经完成 6/8 个初始 workflow。
3. 同时验收原生需求 H2D、完成前已就绪 FULL、恢复→服务等待和有用
   Host 副本损失。24root 可能增加 Host 压力，不能只追求更多传输字节。
4. 将 EOS 前、EOS→JOIN、JOIN→parent提交三个窗口单独报告。
   显式通知覆盖只有约29%，大恢复容量和完整 checkpoint 可用性也要分别查。
5. 重点核查长输入前端重复处理和新 context 混合前缀缺口。若改到原生共用
   路径，随后必须用相同版本的 native 对照，不能沿用旧实现的基线。
6. 首先判断新增压力是否暴露了可改善的请求关键路径，再决定预取与调度
   方案的价值；单纯增加迁移量不会自动产生吞吐提升。
