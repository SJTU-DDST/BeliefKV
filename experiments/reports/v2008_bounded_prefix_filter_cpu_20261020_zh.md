# 后台前缀归因的两级筛选与 CPU 验证

日期：2026-10-20（北京时间）。基线 `ce2fd8f`。
新 GPU 实验最早仍为北京时间 06:00，本轮没有启动 GPU。

## 问题与修改

V1999 保存的 V85d 后台采样中，22 个 Host 驱逐样本的线程 CPU 均值为
6.285ms，26 个请求重访样本为 6.343ms。采样每 64 条一次，不能据此乘
64 估算全量时间或断言 GIL/JCT 影响。CPU profile 将长输入的 BLAKE2
更新定位为值得削减的工作。

同轮 `server/eviction_attribution.jsonl` 的 SHA256 为
`01c6e46c20978175afd9df8393b5e1bf0a192fb4ffd4b9d38c17f301501d3427`。
335 次 FULL 驱逐的前缀最小 116224、P50 153856、最大 187392 token。
1058 次 Mamba 驱逐中，56 次前缀不超过 32768，922 次超过 65536。
两池均无 4096 以内的驱逐，驱逐 namespace 共一个。这是已记录驱逐的
长度分布，不能当每次查询的候选分布、短过滤命中率或计时加权。

原实现按终端前缀之前的 power-of-two 前缀建立路由，候选长度不超过 32
时直接计算所有完整前缀。长输入即使与库存无关，也可能先哈希 64K/128K
token，或直接哈希整个输入。

最终实现先计算最多 4096-token 的短前缀。不存在对应短过滤器时直接
排除该范围；命中后仍沿用原长路由，只有长路由匹配的终端才计算完整
namespaced HMAC。完整 HMAC、事件记录、归因类别与真实 pending 身份
均保持原值。短过滤器只作必要条件，不能用于确认复用或重算。

短过滤器的引用按长路由维护，而非每个终端维护另一份长度索引。多个
终端共用长路由、FULL/Mamba 共用同一完整前缀时不会重复增加短引用。
最后一个长路由删除后才清理其短过滤引用；整批精确匹配同步清空。
索引仍受原 32768 个 pending 身份上限约束。
候选不超过 32 个且最长前缀不超过 4096 时，继续原直接计算路径，
避免为已有廉价查询强行增加路由工作。

## 保留的取舍与原型

V2001 只保留短路由。无关输入查询很快，但共享长源码的 187392-token、
512 候选场景约从 1.536ms 回退到 2.695ms，故未采用。

V2003 加回长路由后，共享源码场景恢复，但按终端维护两份长度索引，
512 个部分匹配的清理开销增加约 0.15--0.21ms。V2006 改为按长路由分组
引用，不将这一原型的结果写成已部署结果。

V2007 补查发现 1K 少量真实匹配的线程 CPU P50 多约 14.9us。
恢复短前缀直接路径后，V2010 的同类差异为约 6.1us；8K 少量匹配仍
多约 13.6us，记录这一取舍，不宣称所有场景加速。

V2006 和最终 V2011 保留 1024/16384/65536-token 上限的同场控制。更短上限
对早分歧更便宜，更长上限可更早排除某些共享头部；4096 是有界首轮
筛选的工程选择，没有依据这些受控场景宣称其对真实 workload 最优。

## 最终长前缀对照

最终 V2011 每组 31 个样本、10 次预热，按新旧及上限变体交替执行。
两侧读取同一只读请求数组；建库、状态重置、输出和索引核对在计时外。
共 60 组，覆盖 131072/187392-token、1/16/64/256/512 候选、早分歧、
共享 4K/32K/64K 源码、部分匹配和全部匹配。

单位为线程 CPU ms，P50：

| 输入 token | 候选 | 场景 | 基线 | 最终候选 |
| ---: | ---: | --- | ---: | ---: |
| 131072 | 64 | 无关输入 | 1.515659 | 0.071358 |
| 187392 | 1 | 无关输入 | 2.152059 | 0.068422 |
| 187392 | 16 | 共享 4K 后分歧 | 2.168138 | 1.514101 |
| 187392 | 64 | 共享 32K 后分歧 | 1.514402 | 1.516857 |
| 187392 | 512 | 部分匹配 | 6.403043 | 6.419721 |
| 187392 | 512 | 全部匹配 | 8.788462 | 8.809337 |

60 组完整事件文本、完整 HMAC、pending 身份、近期长度和分池计数相同；
另外核对派生路由、短过滤引用和有序长度表与仍存身份一致。
最大线程 CPU P50 回退为 0.7415%/40.767us，发生于 256 候选全部匹配。
全部原始样本及上限控制保留，未只筛选改善的场景。

最终 V2010 的 42 组另外核对短输入、不同 namespace、32 个分支、全部
匹配以及 4096/16384 项直接建库的有界溢出与部分消费。短 8K 数组的
少量匹配为 333.787→347.400us，32768-token 大库存无关查询为
287.891→148.478us，压力下新增驱逐为 482.115→486.159us。
未修改的 context 比较同样作为控制保留，不据其微小波动声称改善。
V2006 的 51 样本长前缀记录和 V2007 的补查也独立保留。

## 检查与运行约束

最终 V2009 在冻结 V88 引擎的正确 import 路径下，2266 项 CPU 检查通过，
没有 failure/error/skip。新边界覆盖短路由后分歧、长路由分歧、完整
HMAC、两池、namespace、近期长度截断以及长路由最后引用的清理。

V2004 首次扩大检查有两项 worker 失败。原因是从 `python -` 的 stdin
中调用 pytest.main，multiprocessing spawn 不能重新导入 `<stdin>`。
仅将入口改为正式 `python -m pytest` 后，V2005 全部通过；没有跳过
worker 检查或修改生产 worker。原失败 JUnit 保留。

本轮是后台证据收集的 CPU 对照，不含并发 writer/scheduler、队列、磁盘、
GIL 争用、原生 allocator、DMA、CUDA 或 GPU 吞吐/JCT 测量。
这条后台路径对 native/predictive 共用，不能视为预取策略的独立收益。

V88 引擎、补丁和 24-root 配置保持不变。提交 main 后重新发布 CPU 资格
及冻结源码；原独立等待进程仍只在北京时间 06:00 之后、GPU 空闲且最新
资格一致时启动 predictive，再运行 native。旧 V85d native 不恢复。
目标继续以去长尾吞吐、平均 JCT、有用迁移和相对 native 的收益验收。
