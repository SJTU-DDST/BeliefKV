## 已定位的范围

V2101 的相同 root 到达 0–900s 窗口里，GPU 利用率为 96.427%/
96.403%，不能继续沿用旧轮“大量新增 CPU 等待导致 GPU 空置”的结论。
这不证明控制成本为零。前端转换 P50 为 24.326/378.201ms；该差异
来自已约定的不同前端开关，转换累计区间不是可直接扣除的 JCT。

V2102 的 300–600s 中，直接 worker 均值有 3.44% 差距；按 batch、
2048-token 平均上下文分桶及相邻执行阶段匹配后，描述性加权均值为
14.951/14.783ms，约多 1.13%。上下文分桶仍不是相同工作量的严格回放。

V2103/V2104 的短 prefill，在 512-token 工作量、2048-token 前缀和
相邻阶段的粗分桶中，47/46 个样本的加权 worker 均值为
19.849/19.813ms，比例 1.0018。16-token 和精确工作量分桶样本不足，
保持未匹配，不宣称全部短 prefill 差距消失。

物理 H2D 为 predictive 0.897GB、native 93.119GB。native 的大部分
迁移发生在早期，而双方中后段都以驻留命中为主。不能据此把迁移量差异
归为 0.501GB 的受控恢复独立收益。V2093 的 35 条 JOIN 命令只对应
一个完成后、客户端提交前的恢复事件；一次工具恢复才是在完成前启动。
首服复用证明与命令数、物理批次及提前边界继续分开。

## 修复容量准备与计时估计的耦合

V91b 开启可借用 parent headroom，但最终计数有 136 次
`report_service_transfer_size_unsupported`，未记录
`critical_parent_headroom_checks`。代码在没有大小兼容的 H2D 估计时
直接跳过，导致临近最后一个 child 返回时，连安全容量准备也被挡住。
这些是累计检查次数，不能说成 136 个独立可预取事件或对应的损失字节。

现在只在原来的有效最终阶段、实际 child 服务进度及正恢复计划下，
用已有预取最大提前量限定容量准备时机；有估计时维持原来的时间窗口。
缺少估计只允许形成容量需求，继续计入 FULL/Mamba 恢复和原生输入/
decode 预留。等待状态 PREPARE 与原生回收仍重新检查副本、引用、锁和
在途命令，不抢占活跃 LLM、不永久锁住保留区。没有 H2D 计时支持时，
仍不创建传输 ticket 或发出 DMA。

V2106 固定 `ccc18bf` 的真实方法复现：在 100ms 剩余工作、缺少计时
支持的 CPU 场景，旧版没有容量需求，新版形成 104105 FULL token/
3 Mamba 槽的需求，同时无 ticket、无物理命令；有支持、较远阶段、
关闭开关和无恢复计划四组保持原有结果。其他 runtime AST 相同。
这证明逻辑修复，不证明线上一定能找到冷页或改善吞吐。

V2105 的 582 项相关检查通过。V2108 对当前源码重跑 1118 个不同
用例，1116 通过、2 个真实 tokenizer 用例因缺少显式路径跳过；
V2109 显式指定本地 tokenizer 后两项均通过并替代旧的跳过结果，
故 1118 个不同用例通过。两项 passing subtests 不另加为独立用例，
真实 SWE Docker 场景未选。
