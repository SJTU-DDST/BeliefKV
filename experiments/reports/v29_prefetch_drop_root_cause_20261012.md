# V29 提前 FULL 预取复用下降原因

核对日期：2026-10-12。比较完整 V27/V29，同一模型、workload、
物理配置和 500 ms lead；运行代码和引擎补丁不同。

| 完成前独立事件口径 | V27 | V29 |
| --- | ---: | ---: |
| JOIN 等待事件 | 194 | 197 |
| JOIN 有正 FULL 计划 | 163 | 164 |
| JOIN 进入启动阶段 | 129 | 147 |
| JOIN 实际提交 | 92 | 25 |
| JOIN 提前传输且下一请求确认复用 | 90 | 25 |
| 工具等待事件 | 18,476 | 20,269 |
| 工具有正 FULL 计划 | 1,856 | 1,416 |
| 工具进入启动阶段 | 504 | 17 |
| 工具实际提交 | 484 | 17 |
| 工具提前传输且下一请求确认复用 | 479 | 17 |
| 上述 JOIN/tool 提前复用 FULL 合计 | 9.581 GB | 1.330 GB |

主要损失发生在传输前。V29 已发出的 JOIN/tool 正 FULL 节点命令
48/73 条全部确认复用；节点命令数与独立等待事件数不同。需求
handoff、Mamba 和完成边界后才启动的恢复不混入提前 FULL。

工具侧观测到的完成前 FULL 计划总量约 114.53/113.89 GB，而各
独立事件最大可容纳计划的合计从 14.129 降至 2.542 GB。V117
将下一批原生输入和 decode 增长预留纳入 fit/reclaim，改变了
容量口径。不能以旧版 fit 快照当作新版空间证明，不能把这些
计划字节当作全部可预取需求或 oracle 性能上界。

V29 有 1,239 个正计划事件被启动窗口拦过，293 个随后成为
无 detail 的零计划。这与预算裁剪形态一致，但旧日志没有
no_step_reason，无法逐条确认拒绝原因。约 165-180 ms 的实际
启动窗口与临近完成时的回收、重规划一起压缩机会；两轮启动
窗口中位数相差十余毫秒，不能单独解释工具事件数的大幅变化。
FULL-only 工具启动快照也由 377 降至 3，值得检查状态依赖。

JOIN 已进入启动阶段却未提交的事件由 37 增至 122，其中 V29
36 个随后记录服务进度不可用，原因与容量等可以重叠。后续
V30 的独立 EOS 审计显示 49 个完整自然 ALL JOIN 中 7 个
EOS 到 RETURN 超过旧 250 ms 信号寿命；此为另一批事件，不能
将这些比例直接套到 V29。正常 EOS 证据有效期已在 5c1a646
修正，并部署 V31；FULL 回收无需等待无关 Mamba 备份的修订
0046741 同样已部署。

V131 又复现满批 decode 占满 request row 时的额度问题：缓存
恢复不分配 request row，旧预算却被归零。4f4567f 在独立
followup 允许一个有容量的恢复上下文，继续保留池、字节、
输入/decode 增长预留和原生执行准入。JOIN/tool 正例旧版失败、
新版提交且未分配请求行；容量不足及非满批无行负例保留。
380 项相关检查通过。该修订尚未部署 V31；现有旧日志不能
计算它在 V29 中的损失比例。

V31 的 13:12 封存前缀仍有容量/准入阻塞，其完整 300-600 秒
开发窗口仍落后于固定 native。结论是继续改善机会到实际提交
的转换和控制成本，不能以修复存在、ACK 增长或扩大 lead 宣称
系统收益已达标。

v131_v31_sealed_prefetch_20261012.json.gz 及其摘要、
