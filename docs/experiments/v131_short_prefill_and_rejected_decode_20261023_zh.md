继续使用正在运行的冻结对照，不将 main 的 CPU 候选注入 GPU 服务。
Full 已完成，native_matched 尚在运行，随后仍为 JOIN-only 和关闭后台

## 捷径为什么未采纳

候选在请求完成过 prefill 或首次 decode 后设置本运行时专用标记。
已服务过的纯 decode 批次可以跳过其他恢复记录的首次服务发现；
只有恢复记录数量超过当前批次请求数时才启用该捷径。

V3012 的 14 个 CPU 场景都通过既有状态、记录、回执和锁的对照，
其中 8 个场景的线程 CPU 中位耗时更低。诊断关闭时的部分结果：

| 同时跟踪的回执 | 原路径每回调 | 候选每回调 |
| --- | ---: | ---: |
| 0 | 1.154us | 1.215us |
| 8 | 4.601us | 4.672us |
| 42 | 5.373us | 4.513us |
| 168 | 8.286us | 4.656us |
| 512 | 15.686us | 4.737us |

512 为压力场景。真实 trace 的登记事件分布不是回调频率或时间加权分布，
不能将合成百分比或微秒乘以 trace 计数后宣称 JCT、吞吐改善。

随后补充的生命周期反例暴露了语义差异：请求已经完成 prefill 后，
新加入一条与其匹配、尚未收到 ACK 的恢复记录。原路径会在下一次
decode 回调记录该命令的服务见证；候选的请求标记仍然有效，
因而漏掉新记录。该见证用于 ACK 后判断是否还应建立驻留保护。
这个 CPU 反例不证明线上出现了多少次此顺序，却足以否定
“请求服务过即可永久跳过新恢复记录”的前提。

## 同工作量的短 Prefill 差距

V3018 分别使用每组首个实际 native API 回执后第 300–2700 秒的
诊断窗口，完整行封存并验证 audit 前缀。两组集合分别包含
4146/4271 个 prefill、143792/147713 个已知几何 decode。
窗口内的请求组成仍可能不同；这是路径诊断，不删除任何 workflow JCT
尾部，不比较截断后的整体吞吐。

V3021 进一步按同一源请求、实际输入增量、实际前缀长度、
输出进度、批次成员及顺序、CUDA graph 标志逐项配对：

| 精确请求与几何配对 | 配对数 | Full worker 均值 | native worker 均值 | 比值 |
| --- | ---: | ---: | ---: | ---: |
| 全部 | 3355 | 36.094ms | 34.838ms | 1.036 |
| 短单请求，输入增量小于 512 | 1914 | 13.247ms | 11.133ms | 1.190 |
| 长单请求，输入增量至少 512 | 1441 | 66.440ms | 66.325ms | 1.002 |

重复几何身份为零；保留完整逐对数值和两组未匹配覆盖。
worker 区间包含提交、依赖与干扰，不是纯 CUDA kernel 时间。
相同请求和几何也不代表运行邻居、恢复来源、显存压力和内核历史相同。
因此这里支持“短 prefill 路径仍需优化”，不支持将约 2.114ms 的
平均差额全部解释为新增 Python 控制或直接从 JCT 扣除。

## 下一步控制降本的边界

V3023 使用 36 workflow、running8、64 节点正恢复计划和真实 issuance
观察器，在 CPU 上对同一运行时代码作规模检查。单次正恢复分发约
1.94–2.49ms，profile 的主要工作包括原生操作账目冻结、事务登记、
活性校验和 issuance 记录。它没有 DMA 或真实 allocator；
profile 成本不能外推到每个线上短 prefill。

下一步需将完整 native、JOIN-only 和关闭后台 prepare 的实际结果，
与短 prefill 的具体恢复/备份活动及阶段覆盖一起核查。保留逐命令的
身份、容量和 ACK 验证；优先减少重复规划、没有实际目标的扫描以及
可合并的诊断构造，不凭少数合成场景直接删去正确性依赖。

主要证据均位于 `experiments/reports/`：
V3012、V3014 保留未采纳候选的原始结果；V3015/V3016 为反例与候选补丁；
V3017/V3022 为最终资格及源码绑定；V3018–V3021 为封存配对诊断；
V3023 为单独的 CPU 规模 profile。工作目标保持 active。
