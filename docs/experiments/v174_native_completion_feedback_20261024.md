## Completion feedback

Keep child-local bounded recovery: try a different substantive action, then, if
still blocked, return an honest child report with evidence and unfinished work.
The parent continues. Preserve the intervention flag and do not relabel an
assisted report as an unassisted natural return.

The shared prompt now explicitly separates a final report from a response that
contains another ordinary tool call. Add adjacent, persisted tool-result feedback:

- A successful all-completed todo update reminds the model to give its final
  report next if its assignment is complete or blocked, instead of printing or
  updating completion again.
- A successful literal shell print explains that it only printed supplied text
  and did not inspect files or validate the task.

Both feedback paths leave tools available, execute the actual tool, preserve
status and todo state, and allow substantive work to continue. The feedback
does not decide success or directly terminate a root or workflow. Native semantic
and soft graph guards remain observe-only; safety fuses remain explicit.
Use the same common feedback for native capture and the workload later replayed
on Full. No online semantic model, additional inference, per-token scan or
GPU-scheduler work is introduced.

Literal-print recognition is deliberately narrow and shared with progress
accounting. It accepts print-only `&&` chains, optionally after one `cd`.
Substitution, redirection, pipes and chains containing actual commands retain
their original handling. An inability to classify shell effects is not evidence
that a command is inert.

## Decode batch and capacity

The actual server information confirms `max_running_requests=24` and 805198
logical FULL tokens. The limit bounds admission; it is not a minimum batch size.
V3555 observes 80695 decode forwards with mean batch 6.834, P50 7, P90 9 and
maximum 14. The sum of logical sequence lengths in a decode batch has P50
738881 tokens, P90 788186 and maximum 801784. Shared prefixes can make this sum
differ from unique physical residency, so it is not an exact HBM allocation.

With 48 FULL layers, 4 KV heads, head dimension 128 and BF16, each token uses
98304 bytes. An independent 100000-token context uses about 9.83 GB of FULL KV;
24 such resident contexts exceed the approximately 79.15 GB FULL pool.
These observations support a substantial capacity constraint; the configured
24-request limit was not reached. Smaller decode batches can reduce batching
efficiency, but their size alone does not measure GPU efficiency or the benefit
of increasing a cap. Blocked tool/JOIN work, capacity admission, prefill and
restoration need separate accounting.

The later V3563 observation of the new V174 trajectory has 20620 decode forwards,
mean batch 10.742, P50 10, P90 16 and maximum 23, with the same configured
24-request upper bound. These are different live windows and generated demands;
their difference is not a scheduling speedup. It illustrates why a configured
limit and an actual batch distribution must be reported separately.

V3553 refines the earlier sealed prefix-loss window using completed requests.
Five requests miss 453334 previously served common-input tokens, about 13.0%
of the eligible completed cohort's observed logical prefill input work.
The earlier 0.411% ratio used repeatedly referenced common-input tokens as its
denominator. Neither ratio is a GPU-time or JCT fraction; do not describe that
loss as negligible recomputation or silently increase root concurrency.
