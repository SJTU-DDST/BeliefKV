## 能与不能解释的部分

本轮的原始观测是平均 JCT 较低、P95 与全程时长变差、全程输出吞吐较低。
因此即使先不考虑轨迹差异，吞吐验收也没有达到。不能将 JCT 改善单独
当作整个目标完成，更不能从预取确认复用量推导模块净收益。

总请求数接近，但逐 workflow 的输出、请求数、输入对称相对差中位数为
23.83%、34.33%、35.61%；没有一对三项同时在 10% 内。
这些是在完整总体上报告的诊断，不是另设一个有利 JCT 子集。
Full 的总输入、输出更多，native 的 JOIN 和嵌套更多；工作在 workflow
之间的分配及完成资格也不同，不能仅凭总 token 或 JCT/token 做归因。

V2927 在双方 600–1800 秒窗口中进一步核查：82 个共同 decode 分桶，
配对权重 64383，Full/native 的加权 worker 区间为 13.366753/13.436980ms。
这支持该窗口的匹配 decode 基本持平；它不匹配完整请求和整个生命周期，
也不能排除区间之外的调度、prefill、恢复或结果处理影响。

全程平均 decode batch 的差距提示应优先检查 batch 利用程度、完成顺序、
尾部及实际输入组成。由于轨迹不同，目前不能把较低 batch size 唯一
归因于 Full 的优先级，也不能反推改变排序必然改善吞吐。
短 prefill 的窄分桶样本不足，保留未知，不沿用旧版本的倍数。
