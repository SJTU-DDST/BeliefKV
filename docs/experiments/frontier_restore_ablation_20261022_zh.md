# 普通执行前沿恢复的独立消融

日期：2026-10-22，北京时间。本文记录可单独关闭的候选，不宣称 GPU 收益。
V122 的冻结源码、输入配置和进行中的 Full/JOIN-only/native 顺序不修改。

## 为什么先删除这一条路径

最新完成的 V122 Full 中，普通执行前沿恢复提交 14093 条命令，传输
57.777GB FULL，确认首次服务复用 29.458GB；7257 条、27.341GB 在首次服务前
失去已观察驻留。后者并不全是已证明的重复传输或无效传输。当前 Full
也没有启用 resident-first，不能把现象直接归因为两个排序策略冲突。

V2734 的 217 个采样 prefill 总依赖等待 P50/P90 为 0.100/0.296ms，
只有 7 个样本能够明确区分前置状态与后续层等待。这是已准入样本的
残余等待，不是删除前沿恢复的反事实，也不测容量阻塞或额外 CPU 工作。

普通前沿恢复在 PrefillAdder 最终输入、chunk、容量检查之前额外规划。
先关闭该路径，可以同时检查额外控制、提前占用容量、首次服务前驻留
损失与必要状态恢复先行的净作用，而不改变 EOS 的确定性窗口。

## 独立开关

| 项目 | 保留前沿恢复 | 删除前沿恢复候选 |
|---|---|---|
| `BELIEFKV_TOOL_RESTORE_MODE` | `execution` | `execution` |
| `EXECUTION_FRONTIER_RESTORE` | `1` | `0` |
| `BELIEFKV_ENABLE_FRONTIER_RESTORE` | `1` | `0` |
| 工具预测预取 | 关闭 | 关闭 |
| `EXECUTION_HANDOFF` | `0` | `0` |
| `JOIN_LAST_CHILD_PRIORITY` | `0` | `0` |
| `PARALLEL_WAIT_PREFETCH` | `1` | `1` |
| `WAIT_PREFETCH_CONTEXTS` | `2` | `2` |

`arm_environment` 接收 `EXECUTION_FRONTIER_RESTORE`，生成规范的 runtime
环境；直接启动脚本也接收该开关并导出规范环境。规范环境变量优先。
原来未指定开关的 execution 模式仍默认开启前沿恢复，保持冻结主对照的
既有行为；speculative 模式不受前沿开关影响，调度-only/native 强制关闭。

关闭候选不做普通前沿的额外排序、session anchor 检查、恢复规划或 H2D
提交，也不增加 admission 等待。工具预测预取由 restore mode 独立决定，
不能因为前沿关闭而重新打开。执行中有待处理的物理操作不能据此开关
被强行取消；本消融通过启动新进程生效，不在运行中的 V122 热切换。

保留以下功能：

- 同一有界 JOIN parent 排序、普通请求老化以及原生准入与逐层依赖。
- JOIN/EOS 提前恢复，以及它使用的状态先行和 FULL 分档传输能力。
- spawn 增量备份、冷 FULL 后台备份和工具等待卸载。
- 原有终态 child 容量回收、Host 副本与物理引用的正确性依赖。

启动元数据增加 `execution_frontier_restore_requested`。监控将请求值、
工具 restore mode 与实际 `execution_frontier_restore` 一起核对；发现
生效值偏离请求时拒绝继续，不仅检查环境字符串。旧 trace 缺少该字段时
保留原 execution 默认值的校验语义。

## 验证和比较

定向 CPU 回归 285 项通过，覆盖关闭后不触发原生检查、不提交 H2D、
不创建等待 ticket、不回退工具预测、保留 EOS/备份调度，以及真实 launcher
和 runtime 状态的开关一致性。

V2735 对全部 110 个保留及新增模块回归，3875 项和 2 个 subtest 通过，
无 skip；沿用此前明确排除的一个 Docker 沙箱测试。V2737 绑定源码并核对
V2730 的全部 3846 个身份均保留，新增 29 项，不据此宣称全仓测试已覆盖。

V2736 保留正常 GC、每种情况全部 101 个样本，测量 4/16/64 节点下的
新 context、驻留、容量不足和可提交恢复。以下为 16 节点的路径墙钟 P50：

| 情况 | 开启 | 关闭 |
|---|---:|---:|
| 新 context | 13.65us | 1.57us |
| 已驻留 | 30.12us | 1.55us |
| 容量不足 | 193.82us | 1.65us |
| 可提交恢复 | 665.36us | 1.60us |

关闭 fixture 的原生读取、物理提交和探测维护均为零。开启与关闭使用
各自的独立 fixture，固定顺序测量，不是交替配对样本；原生传输为 scalar
stand-in。开启的正例提交了真实控制层的恢复命令，关闭则没有，故不能
据其差值断言整个请求完成更快，也不能忽略普通需求恢复路径的新增工作。

下一项实验是新的 Full/no-frontier 进程。复用完整采集的 V122 Full、
JOIN-only 和工程对齐 native 作为开发对照；必须等待这些对照正常结束、
核验 GPU 空闲和最新候选资格后再启动。当前没有登记或启动新的 GPU 进程。
应用版本较 V122 更新，差异需要明确记录，不伪称严格同版本消融。
引擎仍为资格树 `1fd609df4835e1b7cace5ea4e7d45f2b0061d259`。

保持 36 root 同时到达、running/batch8、seed21、256K/95% 压缩、
Host200GB80:20、write-back、同一任务、prompt、工具 180s 上限和输出预算。
暂不同时启用最后 child 优先、改变 KV 保护或调整容量。

比较原始平均 JCT、统一去长尾 JCT 和共同忙时吞吐，并报告输出 token、
请求/工具/spawn 数量、guard、失败和任务正确性尚未独立评分的限制。
同时检查 JOIN 严格提前复用、原生需求 H2D、重算、实际恢复等待和容量
阻塞。CPU fixture 的时间和传输字节不能直接从 workflow JCT 中扣除。

若删除路径在相当工作量和有效完成口径下不损害 JCT/吞吐，并减少控制
或重复恢复，应将其移出默认机制；若退化，应定位必要状态先行或启动
时机的贡献，保留有证据的部分，不能仅以复用字节较多为理由恢复全部路径。
