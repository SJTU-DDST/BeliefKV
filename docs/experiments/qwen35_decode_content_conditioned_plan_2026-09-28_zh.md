# Child RETURN 的流式内容与长度联合预测：开发结论和下一阶段门禁

## 当前模型实际做了什么

这不是语义大模型、hidden-state probe，也不读取尚未生成的 token。
`scripts/pilot_child_stream_content.py` 对每个 child 的实际流式回调，
在首个正文 chunk、累计正文跨越 32、64、128 字符后按 128 字符
里程碑取最新 128 字符（大 chunk 可以越过多个里程碑）；转小写后
抽取词、符号和相邻词对，统计词频并归一化。词表必须在至少两个
**不同训练 workflow** 中出现该词；训练只用训练项目。这个
bag-of-words 代理只能识别类似“仍需检查”与“答案收束”的词形，
不理解因果、整个上下文、代码围栏闭合或跨语言同义表达。

长度特征是截至快照累计正文字符数的 `log(1+chars)`，**不是**
事后已知的最终长度，也不是输出 token 数。训练目标分别是
“这轮自然无工具 RETURN，而非继续工具调用”和“在 2 秒内自然
RETURN”；后一目标把最终报告的过早片段也标为负例。模型对
正负类按 workflow 均衡求平均向量，差向量与当下快照做内积，
用训练项目的请求级错误候选最大分数 P95 选触发阈值。
每个请求只计首次触发。此前直接拼接词形与长度会由长度主导。

新增的**长度条件化内容**消融用训练集拟合每个词形维度关于
常数项和长度的加权线性投影，减去该投影后得到内容残差；
将长度分数和残差分数分别除以训练集各自的标准差，再按
`长度分数 + 0.5 × 内容残差分数` 相加。`0.5` 是固定的
开发试验权重，不是由独立测试选择的最优超参数；投影、均值、
方差和阈值均不得用留出项目拟合。这让“长度之外有没有内容
信息”成为可检验的增量问题，仍不构成高级语义理解。

## 分阶段目标和停止条件

1. **可识别性与数据契约**：仅使用在线已送达的正文及其变化，
   以 `request_id`、child/context epoch 绑定自然 RETURN，
   区分同轮 tool_calls、纯文本后继续工具、异常和删失。
   扩大项目来源并预先冻结训练/校准/未见项目清单；至少收集
   100 个自然 RETURN、30 个 JOIN-last 和 100 个有足够
   正文的工具负例，分布在多个 workflow、至少 4 个项目。
   同时报告全部工具轮次及可评分轮次；若正文可见率仍很低，
   在**训练侧预注册**更早的 32/64 字符快照，同时评估由此
   引入的误报。不能拿 1318 个未达 128 字符门槛的旧负例
   给内容模型虚增精度。
2. **无工具终态 + 临近窗口**：把
   `P(本轮无工具地 RETURN | 已见正文、进度、上下文)`
   与 `P(将在可传输窗口内 RETURN | 本轮会 RETURN)`
   分开拟合与报告。只用训练项目选内容表示、融合权重和
   请求级首次触发门槛，再用独立项目校准。留出项目必须
   分别报告 0.5–2 秒窗口召回、工具误报、最终报告过早
   触发、JOIN-last 覆盖，按 workflow 聚类报告不确定区间。
   **候选晋级条件**：独立项目上较长度基线的窗口召回
   至少提高 10 个百分点且各项目不退化；有正文工具轮次
   误报率不超过 5%，最终报告过早触发率不超过 10%，
   workflow 聚类差值区间支持正增益。任一条件不满足则
   保持只读，不能由当前 Sphinx 单侧增益晋级。
3. **时钟和物理条件**：训练的目标是 child 自然 RETURN，
   不是受 HBM 调度影响的 parent 首次服务。将剩余生成
   服务量/可观测 decode 速率与无服务等待、工具等待分解；
   线上只用截至快照已知的服务进度，不用未来等待标签
   作为特征。只有当预期可用窗口覆盖实测 control +
   H2D 完成 P95 且目标 Host 副本、HBM 空间、身份及消费
   机会均成立时，调度器才决定是否预取。允许放弃动作；
   成功必须以物理 ACK、首次 GPU 服务复用、节省阻塞和
   其他 workflow 干扰的配对结果判断。
4. **信号升级**：先比较当前词形、结构状态/局部语义、
   长度和阶段变化，不因单侧 pilot 结果直接接入 runtime。
   再对同一请求的 EOS 候选概率/熵随时间变化做有条件、
   只读对照；它预测本轮生成结束，不能单独推出 child
   自然 RETURN。若内容和分布仍不足，并能证明额外
   服务开销低且不会改变解码行为，才评估轻量 hidden-state
   probe。每一步都要相对固定长度基线证明独立增益，
   否则停止增加在线复杂度。

这些门槛是下一批实验的**预定目标**，不是已取得的指标。
工具返回时间另由工具运行进度与等待时钟预测；child 解码
内容不应被拿来假装能预测任意外部工具完成。

负例数量，应在未看密封结果前追加来自其他项目的冻结任务，
不得靠重复快照膨胀样本数。0.5–2 秒只是一个诊断窗，最终
可行动提前量必须按实际目标 KV 字节、PCIe 并发和
control + H2D 完成分布设置；结束太早会占用 HBM，太晚会
退化为响应式 H2D。即便离线指标达标，仍需物理容量/ACK/
首次复用和配对吞吐证据，才能接入 predictive 行动。

## 自然 RETURN 的时钟分解与报告内容陷阱

对上述 31 次自然 child RETURN，按 request_id 关联已交付的
首段/末段正文、同一请求的 `llm_result`、正式 `return` 事件：

| 区间 | P10 / P50 / P90（ms） |
| --- | ---: |
| 首段正文到末段正文 | 5313 / 7965 / 14421 |
| 末段正文到 LLM 结果回调 | 46 / 163 / 411 |
| LLM 结果回调到正式 RETURN | 155 / 226 / 381 |
| 首段正文到正式 RETURN | 5715 / 8840 / 14944 |

每个样本中“首段至末段正文”占“首段至 RETURN”的比例
中位数为 94.6%；各段的中位数不能直接相加。最终可见
正文字符数中位数为 2150。首段到末段是含 GPU 调度、
可能停顿的生成**墙钟**时间，当前采集不能精确拆为
GPU 计算与排队，更不能从这些数声称 GPU 被独占。
正文相邻快照间隔的 P50/P90/P99 分别约
438/1178/2241 ms（561 个间隔，78 个超过 1 秒）。
对这个最终 LLM 请求，首段之后没有需要等待的工具调用；
前一轮工具所花的时间并未算入 8.84 秒。

部分自然 child 最终报告首段就写有
“Analysis Complete”/“Findings Summary”，但之后仍持续
输出证据、代码和建议。因此静态关键词“已完成”不能作为
可确认的 RETURN 提前通知。运行时要求 child 在完成或
确定受阻时以自然语言回答；图的真实结束边界是模型
**不再发起工具调用**而产生的最终消息，随后 `task` 工具
完成才有正式 RETURN；`llm_result` 的 provisional
completion-intent 已落在最后一段正文之后，无法解释或
隐藏首段到末段的约 8 秒。因此接下来的预测必须利用
**在线可观察的阶段变化/解码进度**判断剩余生成服务量，
并分别报告模型判断不再调用工具的错误和窗口时机误差。

替代“每项目无退化”的预定晋级条件；四项目均已用于
研发，不具备独立校准/密封资格。保持 shadow-only，
不开放 predictive H2D。

下一步先验证“内容和 EOS 预测剩余**生成工作量**”与
“在不同排队/服务节奏下达到 RETURN 的墙钟时间”是否
可分解：从可配对的最终报告离线构造截至快照的剩余
可见字符标签，只在训练项目上确定工作量表示与窗口
变换；若要声称剩余实际服务 token 的精度，须补逐请求
decode 服务证据，不能把字符数冒充 GPU 服务 token。
项目隔离且未被这些消融反复观察的新任务需另行冻结。
只有新项目上的请求级首次触发收益与物理容量/ACK/首次
KV 复用门槛同时成立，才讨论预测性传输。若继续无稳定
增益，优先利用确定性的 child 完成通知和 JOIN 交接。

作为不拟合模型的可识别性检查，在每个自然 RETURN 的
最终正文快照取得最终可见字符数，仅作为**离线标签**；
从在线可见快照中取首次满足 `0 < 剩余字符 <= 256` 的
时间点，再量其到实际 child RETURN 的墙钟间隔。
四项目分别有 Astropy 80、Django 47、Pytest 71、
Sphinx 37 条可配对样本，首次进入时剩余字符中位数
分别为 231.5、224、233、219；对应的墙钟间隔
P10/P50/P90（秒）分别为：

| 项目 | P10 | P50 | P90 |
| --- | ---: | ---: | ---: |
| Astropy | 0.67 | 1.92 | 17.36 |
| Django | 0.36 | 1.36 | 7.15 |
| Pytest | 0.79 | 1.65 | 18.45 |
| Sphinx | 0.79 | 1.17 | 2.34 |

这是按事后最终长度**筛选观测点**的分析，不能把剩余字符
当作线上已知特征，也不能据此断言长尾都是 GPU 排队；
可见字符与模型 token、实际 decode 服务量不同。其意义
仅是说明即使落在相近的输出工作量区间，RETURN 墙钟时间
仍有很大项目差异。下一次模型设计应在新冻结项目上分别
检验无工具自然终态、剩余生成工作量与服务/等待映射；
若要声称服务时间可预测，先取得逐请求服务证据，再训练
和检验转换误差。不可直接用这些开发集的最终长度构造
在线 256 字符触发器，也不能绕过 Host/HBM 容量与 ACK
门禁进入预测性 H2D。

## sampled-EOS 与真实 decode 服务的时钟对齐诊断

只读脚本 `scripts/audit_child_eos_decode_service.py` 在上述两个完整
开发批次上按同一 request、child invocation、context/epoch 关联
已交付的首次 EOS 快照、服务端逐请求 decode 样本及 `llm_result`。
服务端使用墙钟，客户端事件使用单调钟；分别由两批 9725 和
8280 对 submit/result 锚点约束偏移范围，区间宽度为 42.54 和
65.38 ms。判断服务端已结束或尚未结束时，在偏移上下界之外
另留 100 ms；不能直接比较原始时间戳。
报告位于 Astropy/Sphinx 批次的
`eos_decode_service_audit_dev.json`，只存聚合数据。

以下固定 EOS 概率阈值 0.05 用于解释旧开发结果，**未重新
拟合或校准**；分母为已交付正文的自然 RETURN 和工具轮次：

| 项目 | RETURN / 工具 | 窗口命中 / 过早 >2s / 工具误报 | 过早中服务端已先结束 / 时钟不确定 / 后结束 | 窗口命中中服务端已先结束 |
| --- | ---: | ---: | ---: | ---: |
| Django | 47 / 1153 | 12 / 4 / 0 | 3 / 1 / 0 | 11/12 |
| Pytest | 71 / 2850 | 18 / 6 / 0 | 6 / 0 / 0 | 16/18 |
| Astropy | 80 / 1855 | 18 / 14 / 0 | 11 / 2 / 1 | 13/18 |
| Sphinx | 37 / 1587 | 12 / 2 / 0 | 2 / 0 / 0 | 10/12 |

**关键发现**：26 次过早触发中，22 次在客户端交付 EOS
线索前 GPU 请求已结束、3 次位于时钟保护区间、只有 1 次
确定仍在服务。60 次表面上处于 0.5--2 秒 RETURN 窗口的
触发中，至少 50 次 GPU 请求也已经结束。过早触发中仅
2/26 在触发后到 RETURN 前能对齐新的 decode 服务样本；
只凭其余请求没有后续样本，不能反推确切 GPU 空闲时长，
但独立的服务端完成事件使其中多数的“已经结束”可判定。
在这 22 条确定已结束的过早触发中，按项目计算
“服务端结束至客户端 EOS 线索交付”的**保守下界**中位数
分别为 Django 94.10 秒（3 条）、Pytest 64.98 秒（6 条）、
Astropy 97.65 秒（11 条）、Sphinx 21.90 秒（2 条）。
抽查 Django 同一 request 的服务端 submit/result、
客户端首段正文、EOS 线索和最终结果，确有服务端已完成
约 20--199 秒后客户端才收到线索的样本；不是将不同
request/epoch 混接。进一步核对四条过早触发请求：
客户端 submit 到服务端 submit 约 0.3--0.6 秒，服务端
submit 到完成约 5.9--10.2 秒；**首段正文其实在服务端
完成前 4.6--8.1 秒已经交付**，不是首字节本身晚到。
相反，首段正文到客户端 EOS 线索相隔约 4.7--207 秒，
对应服务端已经提前结束。问题集中在之后的流式交付/
消费链，尚不能将延迟具体归因到 HTTP 输出缓冲、
客户端读取、token callback 还是其线程调度，也不能把
它泛化成正常网络或 GPU 排队时延。它使客户端按词形/
EOS 预测 GPU 剩余生成时间的因果前提尤其值得质疑。
两个批次在触发前 2 秒有至少两条安全 decode 样本的
请求仅 41/99（阈值 0.05 下已触发的自然 RETURN）；
服务进度不能无条件假定为每次在线触发都有的特征。

因此先前按“EOS 快照到 RETURN”量到的秒级提前量，
多数**不是剩余生成时间**：客户端获取/处理流式内容及
模型结果、child 退出协议仍可能占据该窗口。这不意味着
窗口完全不能用于 parent KV 的 H2D，但不能以此证明内容
模型已预测生成停止时刻，也不能把后验服务端结果或
RETURN 当作在线特征。下一步先把服务端最终 decode
完成、流式 chunk 的实际交付、客户端 `llm_result` 和正式
child RETURN 分段量化；优先辨别首段之后的服务端 flush、
HTTP 传输和客户端逐 token callback 是否因背压分离，
并确定该延迟是否稳定、可提前
观测；再单独检验“服务尚未结束”的请求里内容/解码证据
相对于长度基线的收益。若可行动的提前量主要由完成后的
交付产生，应优先试可确定通知和 JOIN 交接，而不是继续
加大预测剩余 decode 工作量的模型复杂度。此批数据仍是
反复使用过的开发集，不替代项目隔离校准或物理 H2D 验证。

完整且零丢失。EOS 轮 16/16 workflow 完成、测量有效；
纯内容轮为 15/16：`django__django-14500` 的 3 个 child
均自然 RETURN，JOIN 满足，没有 deadline 到期或 guard
干预；root 长时间重复分析后以自然语言终止，但没有形成
要求的 workflow 结构化终态，故结果为 incomplete。
这条 workflow 的 child 传输仍可用于请求级诊断，不能
冒充有效的端到端 workflow 结果。两轮 task 正确性均
未通过，不应从此对照推断任务质量没有变化。

按原始 HTTP 块的首末时间计，EOS 轮有正文的自然 RETURN
流在 Django/Pytest 分别有 8/27、3/29 条超过 30 秒；
纯内容轮分别为 0/29、0/27。EOS 长流中两次原始拉取
之间的客户端消费间隔占总拉取+间隔时间的中位数约
99%/98%，长流原始拉取等待中位数约 0.91/0.96 秒；
工具流的长尾也存在（EOS 35/671 和 28/1206，
纯内容 0/585 和 0/1078）。这把长尾主要定位在
**字节返回给迭代器之后、下一次拉取之前**，不等于
证明全部开销来自 SDK 解析或 callback：该间隔还包含
线程调度、回调及下游处理。

可复现的聚合文件为两轮各自的
`http_stream_transport_audit.json`；配对程序
`scripts/compare_child_http_stream_runs.py` 的结果为
纯内容轮的 `paired_http_stream_audit.json`。每轮有 56
条具备完整 HTTP 计时的自然 child RETURN；按 task 与
child invocation 身份相交 53 条，但其中 35 条两侧
delegation role 不同。角色相同的 18 对中，排除纯内容
轮无效 workflow 后只有 **16 对有效，分属 10 个
workflow**（Django/Pytest 各 5 个）；16 对的正文
长度均在另一侧的 0.5--2 倍内。其 EOS/纯内容的原始
流字节数中位数分别约 1.05/0.13 MB，消费间隔中位数
约 5.58/1.31 秒；原始拉取等待中位数约 1.74/7.61 秒，
两对的 EOS 原始流长于 30 秒而纯内容不长。
相同身份不等于相同输入或相同 decode：多数 role 已
分叉，16 对内工具与内容轨迹也可能不同；这些关联不能
当作 top-20 logprobs 的独立因果估计。字节量差异和
长尾支持优先优化 EOS 观测路径，而非把已有的客户端
延迟当成模型预测的提前窗口。

纯内容轮已有的 **开发集** 32 字符快照消融：
在 Django 的 29 条 RETURN 中，0.5--2 秒首次命中
长度/进度基线为 7/9，长度条件化内容为 6；JOIN-last
对应为 3/3 对 1。在 Pytest 的 27 条 RETURN 中，
长度/进度为 2/1，长度条件化内容为 5；JOIN-last
为 0/0 对 1。Django 的 29 条包含无效 workflow
里的 child，且门槛仍在训练项目内部选取，这些不能
称作独立泛化收益；尤其不能把只有 16 对同角色孩子
的观察外推为预测式 H2D 的净收益。

另以 `scripts/audit_child_live_decode_window.py` 对两轮
全部有正文自然 RETURN 计算**离线可观察上界**：
只在 RETURN 前 0.5--2 秒已有正文快照、同一请求的
服务端结果尚未结束（时钟区间外另留 100 ms），且
此前 2 秒有身份一致的正 token decode 样本时才计数。
服务端终态只用于事后判别，不提供在线特征；最近
有 decode 样本不证明触发瞬间一定在执行。结果为：

| 项目 | 纯内容：有效 RETURN 中符合上界 | EOS：有效 RETURN 中符合上界 | 纯内容 / EOS 的 JOIN-last |
| --- | ---: | ---: | ---: |
| Django | 16/26 | 7/27 | 6/7 / 5/8 |
| Pytest | 20/27 | 10/29 | 7/8 / 5/8 |

纯内容轮无效 root 的 3 个 child 均被有效分母剔除。
不筛选具体模型阈值，仅看内容快照是否存在，纯内容
有效样本中至多 36/53 条 RETURN、13/15 条 JOIN-last
能在该窗口利用**尚未完成请求的近期 decode**；
EOS 轮为 17/56 和 10/16。EOS 轮的服务端完成到
child RETURN 中位数 Django/Pytest 约 5.55/3.64 秒，
纯内容轮约 0.49/0.47 秒（后者的 Django 29 条包括
无效 root）；较长的表观提前量很可能落在服务完成
后的流交付/消费中，而不是剩余生成工作量。由于两轮
agent 轨迹显著分叉，差异不能直接归因为 logprobs 的
因果效应；更不能把 36/53 当作真实预测召回率。

**下一步门禁**：先让 child 信号以低开销、可证明早于
服务完成的方式抵达 runtime；top-20 整段 logprobs
只能保持诊断用途。再用服务端完成时钟保护过滤已经
结束的触发，比较仅在请求**仍在 decode**期间的
内容、长度/进度和候选低开销 EOS 信号，统计请求级
首次触发、JOIN-last 与有正文工具负例。服务端完成
只用于离线判别，线上不得读取未来事件。只有跨项目
独立校准通过，再检验 parent 的 Host 副本、HBM 容量、
实际 H2D ACK 和首次服务复用；本批结果不开放
predictive H2D。
