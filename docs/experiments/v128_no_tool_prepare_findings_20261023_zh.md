## 备份瓶颈

V2880 复用 V2878 的封存输入，后台参数仍为 200ms、单批最多 512MiB、
最多 32 个节点，策略为 all：

- 5722 个后台批次，全部 ACK 对齐，累计 FULL 166807654400 字节。
- 每批 FULL 平均 29.15MB、P50 11.80MB、P90 72.37MB、最大 336.86MB；
  没有批次达到字节上限，仅 1 批达到节点上限。
- 已发出批次间隔 P50 406.21ms；这不等于检查间隔。
- 原生设备 stream 计时 P50 0.629ms，提交到 ACK P50 8.866ms。
  两者都不能当作 scheduler 关键路径时间。
- 6358 个原生检查在扫描节点前就因 Host 预算不足返回，末次仍有 3541 个
  dirty 节点。当前实现已在这条失败路径避免遍历整个 dirty 表。
- 49 次容量检查记录 unbacked 拒绝，其中只有 11 次之前的 Host 快照显示
  可用空间至少容纳一个后台批次；Host 空闲字节的样本 P50 约 20.11MB。
  快照最多约 998ms 前，不能当作检查时的精确可用容量。

这支持优先核查 Host 容量和备份对象选择，而非直接扩大批量或缩短间隔。
unbacked 仍不证明节点已冷或可安全回收；也不能由此认定 all 策略的净收益
为负。要与同版 Full 及原生对照，核对实际容量释放、恢复等待、重算、
工作量和完整 JCT，再决定是否采用已有的 cold 选择策略。
