## 对下一项优化的含义

普通执行前沿恢复的独立关闭候选已在 main 实现，提交 `53aa53a`，
V2735/V2737 对应 3875 项 CPU 通过及源码绑定。新 Full/no-frontier
保持 JOIN/EOS、备份、卸载和相同排序，暂不叠加最后 child 优先。

实际 runtime 记录确认 `parallel_wait_prefetch=true`、
`wait_prefetch_contexts=2`。不能将非并行分支的“任一未结束 H2D 阻塞新
预取”直接套用到本轮；当前容量上下文数量达到 2、同 context 已在传输
或物理命令额度不足时仍会返回 busy。普通前沿恢复可能消耗这些额度，
但尚未量化它与 EOS 的实际冲突次数和净延迟，不能仅凭代码路径宣称
这是本轮吞吐差距的根因。删除候选也保留并行模式及 2 个 context 的额度。

当前证据说明 Full 尚未证明优于最简单强基线，继续优化的验收目标不变。
等待本轮 native 正常采集后，优先运行独立删除前沿恢复的 Full，复用这轮
合格对照，记录应用版本差异；不为重复 native 消耗额外 GPU 时间。

## 最新短 Prefill 的分桶与阶段证据

V2739 使用两组同一预定忙时窗口，按实际 native 准备的输入和前缀几何
匹配 worker 区间。共同 prefill 分桶需两侧各至少 32 个 batch，并匹配
batch 大小、512-token 输入工作分桶及 2048-token 平均前缀分桶。
13 个共同分桶全部为 batch1、实际新增输入小于 512 token；Full 的均值
为 JOIN-only 的 1.31--1.84 倍。这是值得继续拆分的观测；
分桶仍不等于相同请求、完全相同输入或纯 CUDA kernel 计时，也不能排除
桶内输入几何、执行路径及实际工作量差异。

V2740 复用已测试的 prefill turnover 分析器，读取 V2739 封存的精确 audit
前缀，按时钟域、forward_iter、顺序请求身份和 native 几何配对。
Full/JOIN-only 分别有 134/163 个短单请求 prefill 采样；各有一个缺失服务
配对的观测保留为未知。以下为采样阶段墙钟 P50：

| 阶段 | Full | JOIN-only |
|---|---:|---:|
| selection | 10.151ms | 9.091ms |
| run_batch | 39.842ms | 36.921ms |
| post-launch physical | 1.623ms | 0.007ms |
| result processing | 7.137ms | 7.307ms |
| run 返回至 result 开始 | 7.297ms | 2.999ms |

最后一项包含其他重叠阶段，不是可独立累加的额外 CPU 时间。run_batch
包含 CPU 提交和遥测；GPU stream span 也包含提交间隙和依赖，不能当作
纯 kernel。上述采样汇总尚未进一步匹配前缀分布，不能将所有差额直接
归因为自定义控制。仅 3/3 个短样本能配对到恢复等待，不能据此概括
所有短 prefill 的 H2D 等待，更不能将采样之和或差额从 JCT 中直接扣除。

post-launch physical 的实测成本支持优先消融普通前沿恢复；其他阶段
仍待按更细几何和下一相邻 batch 拆分，不跳过剩余瓶颈。

## 进一步缩小瓶颈范围

V2744 继续匹配连续 batch8 到 batch8、2048-token 上下文桶和明确的
graph 标志，共有 56 个两侧各至少 32 batch 的共同分桶。
每桶对两侧采用相同的 `min(left_count, right_count)` 权重，合计 76240。
平衡后的 worker 区间均值为 Full 12.523824ms、JOIN-only 12.518706ms，
Full 高约 0.041%。这里测量的是裁剪后的 worker 区间，不是纯 kernel；
但现有证据不支持把稳定满批次 decode 当成首要瓶颈。

同一 V2744 对短 prefill 采用更细的 16-token 新输入桶、2048-token 前缀桶、
loop 和明确 graph 标志，只有 7 个共同桶、共同权重 7；
没有任何桶能在两侧各保留至少 2 个样本。故当前短 prefill 的阶段采样
不足以给出可靠的细粒度匹配加速比，不能把前面的 1.31--1.84 倍直接归因
于自定义控制，也不能从边缘分位数之差推算可节约时间。

V2745 对同一共同忙时窗口做吞吐恒等式核对：

| 指标 | Full | JOIN-only |
|---|---:|---:|
| decode batches/s | 69.69785 | 71.91494 |
| 每 decode batch 输出 token | 7.14769 | 7.66459 |
| 已知几何 batch8 占比 | 75.44% | 86.62% |

两项比值 0.96917 与 0.93256 相乘，等于已观测吞吐比 0.90381。
这将后续检查重点收敛到批次填充、准入和阶段切换；它不是因果损失分解。
请求结束、不同生成轨迹、容量限制及额外控制都可能影响填充。
队列有等待请求也不证明这些请求当时都满足资源与数据依赖。

## 短 Prefill 相邻批次的间隔

V2746 使用 V2740 的封存输入，核对同一时钟域、精确相邻 forward 身份，
没有按最近时间戳猜测配对。全部短单请求样本中，下一次 `run_batch`
入口都早于当前结果处理入口；不能将整个结果交付间隔算作 GPU 空闲。

V2747 进一步只保留 decode 到短单请求 prefill 再到 decode 的样本，
Full 123 个、JOIN-only 161 个。测量从 prefill `run_batch` 返回到下一批
`run_batch` 入口的墙钟，已知阶段取裁剪区间的并集，避免重复相加。

| 均值 | Full | JOIN-only |
|---|---:|---:|
| 到下一批入口的间隔 | 5.929ms | 2.238ms |
| 已测 physical/barrier 阶段并集 | 2.843ms | 0.042ms |
| 未被这些阶段覆盖的间隔 | 3.086ms | 2.196ms |

这些样本尚未按相同前缀、输入和前后 batch 大小充分匹配。
入口也不是实际 CUDA launch 边界，未覆盖墙钟不等于 CPU 开销或 GPU 空闲，
已测物理工作也未证明全部可以删除。结果支持继续执行既有的普通前沿
恢复独立消融，不支持直接将均值差乘以请求数并从 JCT 扣除。

截至北京时间 14:29，native 已写出 32 个合格 workflow 的结果，仍在运行；
V123 watcher 存活并等待参考实验，尚未启动候选。以上四份分析报告没有
修改冻结应用或引擎，也没有改变排队候选的实验配置。
