# 执行前沿恢复的候选轮转

日期：2026-10-22，北京时间。仅 CPU 验证；GPU 性能待验收。

## 根因及影响范围

V120 等待启动时，检查新引入的 execution-frontier 恢复路径，发现
`plan.prioritized[:min(2, slots)]` 将“两次检查的 CPU 预算”实现成了
“永久只看最前两个请求”。即使有三个可用槽位，前两个请求已驻留或
已经进入退避，第三个有 Host-only checkpoint 的请求也无法被检查。
其他候选的到期状态还会使整队退避 shortcut 失效，继续建立无效规划。

使用真实 `join_priority` planner 的 CPU 复现中，三个请求顺序不变：
前两个驻留，第三个有正恢复计划和模拟可用容量。
在 10.0、10.051、10.251、10.501 秒四轮中，旧代码只读取前两个请求，
没有检查或发行第三个请求的恢复。

这是请求提交后、准入前沿恢复的新路径缺陷，不是完成前的 EOS 预取。
该路径在旧 V109 中尚未启用，不能把它称为历史 V109 落后的已证实根因。

## 修改

1. 先将候选限制在当前 request-slot 数量覆盖的语义前沿，再对到期候选
   计入检查预算。退避及已经成功发行的候选不消耗本轮检查额度。
2. 每轮仍最多检查两个到期候选，仍采用原有 50ms 调度节流和 200ms
   临时负例退避；成功发行仍为同请求 one-shot。
3. 队列含原生未标记请求或被计划过滤的请求时，复用现有
   `select_native_prefill_candidates` 计算实际位置，原生请求同样占用
   槽位。完整有效标记队列不重复运行这个选择器。
4. 未改变请求排序、running/batch 上限、EOS/关键 parent 优先级、
   物理容量/页有效性检查、原生依赖或 ACK 后保护策略。
   不为恢复暂停准入，不新增逐 decode 步扫描。

这里的槽位前沿不是 PrefillAdder 的最终准入证书；输入 token、
chunk、真实分配器和依赖仍由原生路径决定。

## CPU 证据

V2701 从冻结 main `9b5a5d1` 提取实际旧 dispatcher，与当前实现共享
其余 helper、身份类型和真实语义 planner。正常 GC，101 个交替样本，
每个样本调用 10 次，保留全部原始数据和负向差异。
以下为单次调用墙钟 P50，单位 us：

| 场景 | 队列 8，旧/新 | 队列 48，旧/新 | 队列 128，旧/新 |
|---|---:|---:|---:|
| 没有运行槽位 | 10.64 / 10.64 | 9.58 / 9.81 | 10.40 / 10.30 |
| 全部退避 | 25.64 / 25.30 | 67.80 / 67.55 | 161.86 / 162.64 |
| 首个候选到期 | 49.36 / 53.19 | 130.40 / 132.77 | 281.15 / 281.88 |
| 两次检查预算 | 55.37 / 55.62 | 134.74 / 135.30 | 284.85 / 285.80 |
| 第三个候选到期 | 46.96 / 56.48 | 127.07 / 134.85 | 277.58 / 285.92 |
| 第三个目标可模拟发行 | 46.38 / 98.59 | 128.68 / 183.67 | 279.66 / 331.88 |
| 第三个目标不在槽位前沿 | 49.10 / 46.28 | 126.65 / 126.70 | 278.82 / 276.04 |
| 另有一个原生请求占用槽位 | 48.90 / 66.36 | 126.73 / 198.33 | 278.40 / 453.58 |

第三个正目标场景每样本旧版本发行调用 0 次、新版本 10 次；每次调用前
刻意重置 one-shot 状态，用于比较同一正机会，不能把它当成实际十次迁移。
同样，首个候选和两次检查控制保持相同工作量；第三个目标带来的额外
读取及发行 CPU 工作没有被从新版本计时中扣除。

混合队列额外加一个未标记请求。新版本为了正确位置校验增加了 selector
成本，128 个标记请求场景约多 175us。这是负向结果，没有宣称所有路径
都变快。实际主实验的完整有效标记队列使用快捷路径。

使用标量 native cache；正计划和发行返回值是 stand-in，没有真实 native
allocator、DMA、GPU 执行或消费证据。每个样本比较 graph、visible、
session、pending 和临时 ticket 状态，图和外部逻辑状态保持一致。
V2700 是加入混合队列校验前的中间计时，继续保留；V2701 绑定最终源码。

定向回归覆盖真实 planner 顺序不变、前两个驻留后轮转到第三个、临时退避
及 one-shot 两种队首、有限槽位，以及混合原生/被拒绝请求的位置。
最终完整应用资格由封存报告绑定，不以定向测试替代。

V2702 完整应用回归 3790 项通过，保留 V2695 的全部 3781 项并新增 9 项；
无 skip，2 个 subtest 通过。与此前相同的一个 Docker 沙箱测试明确
deselect，不计通过。V2703 绑定当前应用源码。引擎及 canonical patch
未修改，复用 V2698 的完整 469 项资格，未声称本轮重新运行引擎测试。
