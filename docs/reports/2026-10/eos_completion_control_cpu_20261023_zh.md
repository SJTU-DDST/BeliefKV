# EOS 完成回调降本

日期：2026-10-23，北京时间。基线为 main 的 `4b43869`。

本轮修改 `NativeAdmissionRuntime.on_batch_completed` 的中间步统计条件。
正在运行和排队的 V128 继续使用冻结应用 `04191b0`，没有注入新代码。

## 多余路径及修复

此前，仅当 `_tool_timing_only` 或调度单独对照生效时，才会跳过没有
请求完成、也没有首次服务观察任务的 decode 统计。关闭工具模型后，
`_tool_timing_only` 变成 false，即使 JOIN 仅使用实际 EOS、也没有模型
或语义 worker 消费生成进度，仍会逐步读取可见请求并重写上下文计数。
V128/no_tool_duration_model 的冻结配置满足这条分支条件。

现在 EOS 模式且没有模型或语义 worker 时，也仅在完成后保存最终 token
计数。已存在的首次服务任务仍会进入原回调：包括 ACK 前首次服务、
驻留反馈、parent 容量交接、保护释放和真实 EOS 检查。不删除这些观察，
也不因生成进度停止更新而提前授予物理恢复或回收权限。

报告预测和旧 worker 模式保留实时生成进度。没有增加跨步缓存、失效
管理、扫描、计时或高频遥测。

## CPU 对照

V2881 的 355 项聚焦检查通过，覆盖新增中间步/完成计数、实时进度消费者、
首次服务反馈及原 EOS、调度和 KV 路径。

V2882 在正常 GC、101 个采样轮次、20 轮预热和交替执行顺序下，对照固定
旧源码与新源码的完整完成回调，共 32 个案例。保留所有样本，包括变慢
的情况。测试对象是 CPU 请求夹具，没有真实 GPU、DMA 或 Host 竞争。

完成 ID、可见身份、session、revision、pending 物理状态和最终计数相同。
明确允许变化的只有未完成且没有进度消费者时的中间计数；专项检查另验
原有旧 epoch 计数不被反复重写、完成后更新为正确的新计数。

工具模式和调度单独对照原本已有快速返回，成本大致持平；这些案例 CPU
变化范围为改善约 2.41% 至变慢约 3.22%。最大回退出现在 JOIN-only 的
batch8 单请求完成案例，约增加 0.145us，保留原样本。

当前 Full 的工具计时模式原本已跳过多数未完成请求，因此不能把 EOS
模式的约 67.7% callback 降幅归为 Full 整轮控制或 GPU 吞吐提升。其绝对
节省为微秒级，不能据此解释数十秒以上的 JCT 差异。
