## 二、成果说明

### 1. D1：选择哪些 agent 推进 workflow

在 ThunderAgent 工作集框架上，保留单个 agent 的执行身份，将 root 和
child 放回同一 workflow 的完成目标下评价。结合已观察的真实依赖、
剩余工作提示及容量约束，决定 ready-paused agent 的恢复与准入，
并支持同一阻塞 ALL-JOIN 下的 sibling 协同推进。

完成统一事件准入与周期容量协调，打通工具返回、资格恢复和后续模型服务。
R5 条件剩余工作与有界集合选择已实现并开展实验，但尚未建立稳定的独立
JCT 增益，不将整套系统收益归因于短 workflow 排序。

### 2. D2：为选中的 agent 周转 KV 容量

从真实待执行消费者的 KV 缺口出发，选择可以安全让出容量的阻塞 agent。
利用工具等待期预测、增量 Host 备份与 ACK 后释放，为消费者腾出实际 HBM；
结合 JOIN/EOS 信号提前恢复 parent，只加载后续请求需要的缺页。

将容量释放、恢复和实际执行绑定到同一消费者，避免仅授予逻辑资格、
但上下文或容量尚未就绪的问题。原生页分配、共享引用、锁和传输依赖继续
决定实际释放与执行权限。

### 系统整体的端到端结果

| 已完成匹配对照 | 平均完整 JCT | 共同窗口输出吞吐 |
| --- | --- | --- |
| 相同优化引擎下，Full 对 ThunderAgent acting-decay | 1083.13 s → 964.29 s，降低 10.97% | 提高 2.47% |
| 原默认引擎下，Full 对 native SGLang | 1215.27 s → 1052.99 s，降低 13.35% | 提高 1.63% |

两组均使用 56 个不同项目、200 GB Host、持续到达和固定 18 个测量成员，
保留每个测量 workflow 的完整正常尾部。每一行内部的工作量与资源匹配，
两行采用的引擎配置不同，不将收益相加或混作同一组实验。

Trace 采集、baseline 适配和评测建设作为上述结果的验证支撑，不单列成果。
这些数字属于整套系统，不能分别写成 D1 和 D2 各自的独立收益。
尤其上述 56 项目对照关闭了工作量排序，不能据此证明 R5 的性能收益。

### 3. 工程优化：工具替换检查的控制成本降低约一半

针对控制路径中大量没有有效配对的重复检查，实施 donor 预筛、
消费者需求与释放计划复用、普通 hint 刷新合并，以及后台重试节流。
保留工具返回、容量变化等真实事件的及时响应和动作前原生安全检查。

在相同 1583.26 秒共同窗口内，工具替换检查线程 CPU 从旧两轮的
47.10 / 54.85 秒降至约 25.48 秒，减少 45.9%–53.6%。
这是该项控制路径的成本下降，不是全部 CPU 开销下降，也不直接等于 JCT 收益。

## 三、口头汇报稿

本月围绕两个核心设计推进系统。第一，以完整 workflow 完成为目标，
结合剩余工作和 JOIN 依赖选择 agent 工作集；第二，面向真实执行需求，
协调工具等待期的 KV 卸载、增量备份与 JOIN 恢复，使所选 agent 获得
实际执行所需的容量和上下文。在已完成系统对照中，相对 ThunderAgent
的平均 workflow 完成时间降低约 11%，另一组相对 native SGLang 降低约 13%。
同时完成控制路径工程优化，将工具替换检查的 CPU 开销降低约一半。
下一阶段重点验证收益稳定性，以及工作量调度的独立贡献。

## 四、下一阶段

完成更强持续压力下的匹配对照，验证调度竞争、完整 JCT 和收益稳定性。
短 workflow 排序及新设计继续按端到端净收益筛选，不以预测准确率、
测试数量或实现完成替代性能成果。
