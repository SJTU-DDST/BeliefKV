# BeliefKV 近 30 天工作汇报

汇报周期：2026 年 10 月 9 日至 11 月 7 日，北京时间。
材料截止本次整理时已记录的结果，提交记录核对到 `1521c310`。

## 一、整体进展

本月围绕动态多 Agent 工作流的调度和分层 KV 管理，完成了从运行时机制、
真实轨迹与公平评测，到强 baseline 对照和性能优化的系统建设。研究主线收敛为：

1. 工作流完成导向的依赖感知工作集准入：决定哪些 agent 获得执行机会。
2. 执行需求绑定的 KV 容量周转：让选中的 agent 获得实际容量和上下文，并进入模型服务。

在已经完成的匹配对照中，系统相对 ThunderAgent acting-decay 的完整平均
workflow JCT 降低约 10%–11%；在另一组同负载 native SGLang 对照中降低
13.35%。同步控制优化使相同墙钟窗口内的工具替换检查线程 CPU 开销降低
约 46%–54%。

这些是指定负载上的阶段性结果，不是跨负载稳定收益或多轮统计显著性的结论。
短 workflow 排序的独立收益与整套系统收益分开报告。

## 三、主要量化成果

不同实验行的负载、资源或版本不同，不跨行相加收益，也不将公共引擎优化
或联合改动的整体结果归因于某个单独机制。

| 已完成对照 | 平均完整 JCT | 共同墙钟输出吞吐 | 说明 |
| --- | --- | --- | --- |
| 56 项目、200 GB Host，共同优化引擎：Full 对 ThunderAgent acting-decay | 1083.13 s → 964.29 s，降低 10.97% | 299.56 → 306.95 token/s，提高 2.47% | 固定 18 个测量成员，2819 个请求；两臂使用相同优化引擎。 |
| 56 项目、200 GB Host，原默认引擎：Full 对 native SGLang | 1215.27 s → 1052.99 s，降低 13.35% | 297.06 → 301.89 token/s，提高 1.63% | 同 token、到达表、工具时间、资源与测量组；native 保留公共测量扩展。 |
| 73 项目、400 GB Host，联合版本对 ThunderAgent acting-decay | 1190.93 s → 1061.91 s，降低 10.83% | 324.58 → 343.94 token/s，提高 5.97% | 固定 18 个测量成员，2991 个请求；包含预测、组合目标和控制优化。 |
| 73 项目、400 GB Host，Direct Global Oracle 对非排序 Full | 1081.53 s → 1061.03 s，降低 1.90% | 同一共同窗口下降约 0.55% | 这是独立排序对照，不能用上一行系统收益替代。 |

上述对照均保留固定测量组的完整正常尾部。部分 baseline 的有限背景到达表
没有覆盖到最后测量成员结束，且主要结果仍为单次完整配对，因此尚不能称为
已经验证稳态或重复性。部分首次服务指标也有回退，不声称所有指标同时改善。

### 控制成本

相同 1583.26 秒共同窗口内，工具替换检查线程 CPU 从旧两轮的
47.10 / 54.85 秒，降至联合版本的约 25.48 秒，减少约 45.9%–53.6%。
CPU 时间可能与 GPU 重叠，该差值不能直接作为可删除的 JCT。

最新 CPU 优化另将有效工具卸载授权的单次中位成本从 87.47 µs 降至
51.79 µs，减少约 40.8%。它是局部组件结果，不额外计算成完整系统收益。

### 预测与实际服务

扩充原始训练执行、引入排序目标并分离初始估计与执行进度后，固定开发组的
初始两两排序由 55.56% 提高至 66.67%。后续条件树使构造 ready 状态排序
由 70.78% 提高至 72.81%；这些开发数据已被多轮探索使用，不能当作独立盲测。

实际服务审计确认 Oracle 和联合策略改变的部分准入集合获得了对应请求的
原生模型服务，排除了“只改逻辑顺序、没有服务影响”的笼统解释。
但预测误差下降、更多成员获准入，都不自动保证完整 JCT 改善。

## 四、探索结果与设计收敛

- 保留预测工具卸载、JOIN/EOS 预取、prepare_host、active agent 连续性和
  sibling 支持，作为后续系统比较的基础。
- 工具预取在当前负载中没有建立净收益，已关闭，减少控制工作和容量干扰。
- 逐层卸载/加载 overlap 已完成多阶段实现和验证；当前机会及净收益不足，
  后续主配置保持关闭，不为制造机会而强迫频繁迁移。
- 多轮短任务排序、预测器与组合目标探索出现小幅改善和回退，均保留结果，
  不将单轮较优数字写成稳定收益。
- 第三个设计点仍在筛选。驻留工作集内的计算阶段编排具有研究价值，但
  现有工具关闭标记偏晚；备份节流与分支余量也尚未建立足够的净收益证据。

这些探索明确了应继续投入和应暂停的边界，减少后续无效参数扫描及 GPU 消耗。

## 五、当前进度与下一阶段

最新 83 项目候选复用七份已完成的原始采集，采用 20 个初始 workflow、
平均 60 秒持续到达、400 GB Host 和原固定 18 个测量成员。
其来源绑定、完整 CPU 验证和 Full/Oracle/ThunderAgent 配置准备已完成。
截至本报告记录，Full 已进入实际 GPU 对照，Oracle 按条件接续，
尚无这组负载的完整 JCT 收益结论。

下一阶段重点：

1. 完成更强持续压力下的匹配对照，确认短长候选同时可执行、容量不能全部
   容纳的竞争是否增加，以及新的选择能否持续转化为模型服务和完整 JCT 改善。
2. 继续合并成熟优化做完整验证，避免每个小改动单独消耗一轮 GPU 实验。
3. 新设计先用已记录轨迹和双向代价分析筛查；机会和在线可见性不足时不增加
   控制器，不把既有工作集切换或工程去重重新包装为贡献。

## 六、口头汇报稿

过去一个月主要完成了三方面工作。首先，打通动态多 Agent 的真实工具执行、
原始 trace 和公平评测链路，形成持续到达、固定成员完整 JCT 的实验方法，
工作负载扩展到数十个不同原项目。其次，围绕依赖感知工作集准入和执行需求
绑定的 KV 周转完善系统，在已完成对照中，相对 ThunderAgent 的平均 JCT
降低约 10% 到 11%，相对 native SGLang 的一组对照降低约 13%。
第三，系统性削减同步控制开销，工具替换检查的 CPU 成本下降约一半。
短 workflow 调度的独立 Oracle 收益目前约 1.9%，稳定性仍需验证；
下一阶段将重点检查持续压力下的真实竞争及收益，不继续盲目增加机制。
