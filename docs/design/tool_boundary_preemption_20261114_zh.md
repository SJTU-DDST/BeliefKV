# 工具边界的有成本 Oracle 让位

## 满参考窗口遗漏竞争候选的修复（2026-11-15）

旧有界Oracle完整2985次周期控制中，2578次可关联精确ready选择快照，
其中2130次有多个ready workflow、1044次有多个各自逻辑可放下的
workflow，434次存在集合装不下全部的逻辑竞争。832次有ready成员却
没有单个能放下。blocked-paused数量不能直接等同于可比较的候选数；
这些口径仍不是即时原生物理可执行性。

另有21次原规则参考集合已占满默认6个窗口，同时仍有单体逻辑可放下
的外部候选；8次外部workflow比全部参考成员更短，3次涉及测量组。
旧`_candidate_window()`在参考成员达到6个后直接返回，导致这些
已收集且合法的更高优先级候选没有机会进入前缀核对和集合比较。

修复保留完整参考集合与fallback。当参考有6或7个成员、当前已收集
候选中存在更高工作量优先级或JOIN优先级的可放下成员时，按需扩展
至现有8个上限。默认仍为6，不增加队列扫描、轮询、搜索时间预算或
物理权限。未知预测且没有优先级差异时不扩展；超过单体预算的成员
不触发扩展；完整8成员参考仍保留原窗口，不能声称覆盖全部竞争。
原JOIN权利、500微秒搜索超时fallback及动作前原生容量/锁/ACK检查
保持原样。后续与等待保护和空shadow复用合并验证，不单独重跑Full。

238项相关CPU检查全部通过，包括6/7参考成员的真实逻辑资格与原生
prefill候选选择，及无更优成员、单体超预算、旧选择器和完整8成员
参考的回退。复用全部39个满参考快照的元数据重放中，16次按需扩展，
7次使原来遗漏的更短workflow可见，包含全部3次测量候选。另1次原
参考超过8人，仍保留原回退。重放不补造前缀、物理可行性或JCT收益。

## Ready等待修正候选（2026-11-15）

完整旧有界Oracle的desktop021 epoch64是一个248379输入、93输出的
工具后继：提交到首次原生launch等待1231.345217秒，首次实际逻辑
授予在提交后1229.614748秒，授予后1.730469秒launch。Full同一请求
只等约21.013139秒。实际服务段仅相差0.611358秒。这是一个具体的
长时间未准入情形，不代表所有差异均由短优先策略单独造成。

同一406次完整搜索的CPU筛查保留候选、required JOIN、原生规划容量及
组合目标，以第一次观测到合法ready候选开始计算等待。沿用已有30秒
等待保护尺度，给base权重乘以`1 + ready_wait_ms / 30000`，上限为1。
52次集合变化中25次涉及测量成员，13次成员更少、1次更多；该请求在
11次候选观测中有8次会被新增选中。未重建反事实服务或完整JCT。
离线候选间的连续ready状态不完整，不把该筛查当作净收益上界。

后续默认关闭的`ready_wait_priority_ms`将上述修正落实到现有选择器：

- 只在已有共享准入边界维护当前合法ready-paused key，不扫描额外原生
  前缀，也不另开检查时钟。普通2秒边界及工具事件即时替换保持原样。
- 从第一次实际进入ready候选集合计时；提交、在等工具及JOIN时不提前
  累计。真实native_service后重置；新epoch/attempt/session不会继承，
  TOOL_START、JOIN_WAIT、RETURN及取消也清理对应invocation。
- 同一workflow只取当前ready候选中的最大等待，并对其成员使用同一
  权重，避免因fanout复制等待加分。历史最多512项，淘汰只丢失年龄，
  不新增资格或容量。候选截取、原生可执行性仍可能限制保护效果。
- 仅支持显式maximal short-work选择，参数为0或至多60000的正整数。
  当前候选使用30000，继承原等待保护尺度；没有按最终JCT调参。
- 保留required JOIN、所有容量和锁/ACK检查、active连续性及完整组合
  装入规则。它不抢占正在执行的模型请求，也不改变工具donor的工作量
  资格及迁移成本门槛，不能声称是SRPT最优或严格无饥饿保证。
- Oracle与学习版必须声明相同参数；审计拒绝未登记或不一致的等待
  配置。预测器本身与工具时长不变，没有按测量组身份改变优先级。

该实现继承同次空shadow结果复用；后续按合并版本进行GPU验证，不为
每个小控制修改分别重跑。0723f463正在运行的版本保持冻结，尚无本
等待修正的GPU结果。成本计价标签另留在CPU诊断，没有一并改变Oracle
的剩余工作定义。

231项相关CPU检查通过，包括实际eligibility到原生prefill选择、
真实服务重置、身份/epoch隔离、JOIN/工具阻塞清理、默认关闭及两侧
参数一致性。Owner索引后的元数据维护和至多8个权重/日志字段处理，
在6/32/128/512个ready key下中位为5.136/14.833/49.615/185.137微秒。
这不是完整控制器成本，也不是JCT收益；完整绑定CPU套件和GPU结果
另以本候选的实际证据验收。

## 已备份 donor 的有界规划修复（2026-11-15）

先在同一有界候选窗口中收集已有 settled Host 副本的实际释放计划，
检查是否有完整可行的单 donor 方案；只有没有这种方案时，才使用剩余
软预算捕获需要新增备份的候选。之后仍优先选择完整单 donor，最后才
考虑两个已备份 donor 的组合。没有延长2ms软预算，也不放宽容量、
工作量差、迁移预算、等待保护或动作前的原生身份/锁/ACK检查。

原实现按工作量从大到小逐个做昂贵的备份捕获，可能在第一个冷 donor
处耗尽预算，漏掉后面无需备份、足以让短请求执行的 donor。真实CPU树、
分配器及生产接口用例复现了这个选择缺口；慢捕获的时长使用可控时钟，
不能当作实测GPU成本或JCT收益。锁定备份的负例仍拒绝。

新增计数 tool_boundary_settled_plan_selections 与 tool_boundary_shadow_probes
分别记录直接使用已备份计划的选择及新增shadow捕获。完整性能仍需
原始固定测量组自然完成、fresh drain和真实退出后与匹配Full比较。

## 目标与实验顺序

先保持当前 133 个不同原项目、initial20、平均 60 秒泊松到达、
400GB Host 和固定 18 个测量成员。原来的 83 项目是历史人口，
不回退到旧到达表。复用已经完整完成的匹配非排序 Full。

先评估工具边界主动让位是否扩大有效服务机会，再判断完整 JCT 和共同
窗口吞吐。仅当机会仍不足时，才补充自然完成、模型调用轮数更少的短
workflow。不能根据完成结果重新挑选测量成员，也不截断长任务。

本候选默认关闭，必须在绑定的 Oracle 工作量 artifact 中显式声明。
现阶段不允许学习模型静默启用同名策略，不自动登记 R5 或基线。
这不是新的通用工作集切换创新声明，也不是最优 JCT Oracle。

## 与原工具卸载的关系

原有路径继续用在线工具剩余时间分布及 75% survival 门槛判断等待是否
足以覆盖必要 D2H、消费者 H2D、donor 恢复和控制余量。原路径不变。

新增路径允许真实 ready-paused 消费者 B 在缺少容量时，与实际在等待
工具、没有原生模型请求在执行的 A 配对。A、B 必须来自不同 workflow。
A 工具不必很长，也不要求存在工具预测；工作量读取现有同步 Oracle
进度缓存，不扫描未来 DAG，不读取未来工具时长，不进行语义推理。

## 评分及其边界

设 a、b 是剩余总模型工作量，s 是原 artifact 已冻结的秒/工作单位，
d 是必要备份成本，hB、hA 是 B 和 A 的恢复成本。新增路径要求：

```text
gain_ms = 1000*s*(a-b) - 2*d - hB - hA - margin_ms > 0
```

在单执行槽、两任务、无后续工具、固定服务率的局部模型中，把当前工具
当作已经返回，以上对应完成时间之和的改善；D2H 会同时延迟两者，故计
两次。实际工具剩余等待不用于提高分数。各迁移项使用原生在线传输估计，
缺少估计时沿用现有冷启动工程界限。控制余量首版为 400ms。

总模型工作量不是串行服务秒数。GPU 批处理、并行 sibling、未来工具、
其他 workflow 和后续容量变化都可能推翻局部评分。因此正分只是动作
筛选条件，不能累计成 JCT 收益，也不能保证这条路径优于原策略。

日志额外记录原有 forecast 资格及成本门槛此刻是否也会允许该配对。
新增路径执行的动作不全部等于相对旧实现新增的动作。

## 原生执行与容量安全

- 只消费现有真实等待请求，不预取工具未返回的请求。
- 消费者通过现有原生前缀、输入预算、增长预算、请求行和 running
  槽位检查。仍是有界单 donor 配对，不新增 ready-active 抢占。
- 优先复用 settled Host 副本；需要备份时，走原生 prepare 和逐项 ACK，
  ACK 前不释放 Device，也不计入物理可用容量。
- 缺少工具预测时，`tool_boundary` 备份及尾部规划资格仅在当前同步
  donor/consumer 配对内有效；身份、工具返回、锁、共享、Host 额度和
  consumer 消失仍须重验。不得伪造长期工具 hint 或扩大普通 donor 权利。
- 第一段实际释放可能已经使 A paused。继续释放仅允许同一请求配对，
  并在每次动作前重新判断需求；不得因为已经释放而免除安全检查。
- 完整释放后，重新读取真实容量，正常准入 B；记录实际释放和授予，
  之后按精确 request/attempt/session 身份核对原生服务和完成。
- JOIN/EOS、prepare_host、sibling、正在执行请求的连续性及原生权威保留。
  工具预取和逐层 handoff 仍关闭。普通 2 秒边界及 400ms 有界检查不变。

## 长任务保护与控制成本

同一 workflow 新路径成功让位后有 2 秒冷却。部分释放中的同一配对可以
继续，不因冷却失效。真实 ready 请求等待至少 30 秒并取得原生服务后，
保护紧随该服务请求的工具等待，不再被新增路径再次抢占。保护覆盖原有
路径导致的等待，不仅覆盖本机制暂停的对象；原有长工具卸载仍独立。

工具候选由 TOOL_START/END 事件维护，每轮最多读取八个。工作量读取
O(1) 缓存，传输估计在同一次判断内复用。正负资格或原 forecast 资格
改变才重复发布配对日志；历史表有界。工具结束和真实新请求可重新唤醒
现有有界控制器。

这些是防抖及等待保护机制，不是有容量约束时的无饥饿定理。

## 已有证据及待验收事项

完整 benefit Oracle 的封存轨迹含 3007 个周期控制。按压力协调后的真实
未折扣逻辑余额，335 个边界有单 donor/消费者配对，157 个边界出现局部
正分；274 个重复配对观测中 37 个以测量成员为消费者，81 个至少涉及一个
测量成员，去重后共 247 个配对。它们不是物理可行或增量机会证明。

首版 screen 将负逻辑余额截为零。独立 jq 检查发现 23 个负余额边界，
最小 -9744 token；修正版保留原值重新扫描完整封存输入，上述主要计数
未改变。两版源码和输出均保留。七个缺少结束观测的工具区间排除，
不假设其时长。共同窗口和完整测量跨度分别报告，重叠范围不能相加。

原生 CPU 用例使用真实树、分配器及生产准备接口，传输队列用 CPU
stand-in；不能据此宣称 CUDA 重叠、GPU 成本、真实模型吞吐或 JCT 收益。
保留最初短预测断言错误、dirty-index fixture 错误及准备规划入口缺口
对应的失败记录，不把它们冒充 GPU 实验失败或旧线上故障。

GPU 验收仍须同一固定 18 条自然完成、精确原始工作、fresh drain 和真实
退出；比较完整平均 JCT、共同墙钟窗口吞吐、实际新增配对服务、长成员
损益、控制 CPU、D2H/H2D 和重算。GPU 防抢占保持关闭，只能共享访问并
重新检查资源。现有协调器新增显式 `device_access_mode=shared`，要求旧
guard 已退出且 lease 为 released，保留每阶段的资源、源码、进程身份和
协调锁检查；不恢复 ACL 或重新启动 guard，不承诺共享 GPU 的独占顺序。
已停住的旧 reservation anchor 必须保持同一 PID/start 和 stopped 状态。

Oracle-only 配置完成后，协调器必须停在需要单独准备学习模型的状态，
不能自动把原来没有该动作空间的 R5 当作匹配后继。当前实现和 CPU
准备不构成整体目标完成。

## 有界工具边界调度的完善

用户于2026-11-14要求先完成可控实现及CPU分析，GPU仍被占用。原
2975685协调器在waiting_resources_oracle且GPU登记为空时收到SIGTERM，
已经真实退出；这是撤下尚未启动的旧版本，不是GPU实验失败。旧冻结树、
原始结果、共享GPU设置和stopped anchor均保留。本分支先完成CPU工作，
不自动恢复旧Oracle队列。

原v1在原生选批前比较真实ready-paused消费者和已经WAIT_TOOL的donor；
TOOL_START、真实新请求及备份ACK会唤醒有界检查，不必等普通2秒边界。
但v1的donor选择仍主要沿现有轮转，且工具返回即失去新增让位资格。
对于很短的工具，这个动作窗口可能在下一次原生调度前结束。

v2显式声明为tool_boundary_cost_bounded_schedule_v2，仍仅供Oracle
实验。短workflow的ready-paused请求存在且容量不足时，先按剩余工作
筛查长workflow，再检查完整容量和迁移成本。模型请求正在运行时不
抢占；工具实际开始后才产生边界资格，不用未来trace证明“它将调用工具”。

资格覆盖两个状态：

1. 正在等待一个工具、没有阻塞child的agent。
2. 工具已经返回，但紧接的同context、同session/generation、epoch加一
   的模型后继尚未分配原生执行资源。该资格只保留2000ms；实际服务、
   RETURN、取消、会话变化或其他工具/JOIN阻塞都不能沿用这项权限。

第二种状态使短工具的让位机会不会仅因TOOL_END先被处理而消失。它只
暂停尚未开始的后继，不中断已经分配/执行的prefill或decode。工具边界
优先绑定该owner最后实际服务的请求，避免控制事件晚到、latest已经
推进到新epoch时错误绑定。资格不授予物理容量；每次动作仍检查当前
consumer、donor、原生锁/共享/Host副本/会话和实际完整需求。

## 选择与迁移约束

最多查看64个轮转owner的缓存工作量，对其中较长的8个做原生检查；
消费者仍使用原来的JOIN/EOS优先及短workflow顺序。先做便宜的工作差
和逻辑容量过滤，再读取前缀和shadow。一次新增选择只服务一个真实
consumer，先找正收益且完整放得下的单donor；没有合适单donor时，
最多枚举两个donor的组合。两donor必须都已具备settled Host副本，不
同时为一个未准入consumer创建两份备份。

只在当前精确配对内，将上一epoch实际登记过的最多64个节点及创建时间
交接到同session的新后继；使用前重验会话代数、创建时间和原生所有权，
不推断新输入已经计算。释放计划最多检查64个节点，实际每次仍最多
释放16个节点。若有真实释放进展但尚未完整授予，下一原生边界立即
续接；无进展则保留原退避，避免反复空检查。

单donor可走原生prepare及ACK流程。组合在任何释放前检查完整计划；
实际释放逐项复核，最后重新读取真实容量后才授予。中途条件失效时
不伪造授予、不把已释放页当成仍被保留，也不回滚或丢弃Host中的有效
状态。已发生的部分释放计入迁移预算，同一consumer后续不能累积超过
两个不同donor；后续完整授予记录也保留之前的实际donor。

实际备份入队后，选中的未启动donor后继有最多2000ms的执行暂缓，
让ACK后的释放有机会接续；不改变其逻辑预算、不虚报已释放容量。
consumer消失、请求/会话变化、原生资源已分配或暂缓过期即失效。
该暂缓只属于已验证配对，不能推广为对所有active长请求的长期冻结。

设m为本次需要释放的donor数，a_i为剩余模型工作，b为consumer的剩余
模型工作，d_i和h_i为备份及恢复成本，h_B为consumer恢复成本。组合
筛查使用：

```text
gain_ms = 1000*s*(min(a_i)-m*b)
          -(m+1)*sum(d_i)-m*h_B-sum(h_i)-400ms
```

它在m=1时退化为旧两任务公式。m=2使用更保守的局部筛查，没有把B的
提前完成重复算作两份收益。它仍忽略GPU组批、其他workflow和未来依赖，
不是全系统收益界，正分不能累计为可消除JCT。

默认另有以下防抖约束；这些是显式工程参数，不能声称为数学最优值：

- donor剩余工作至少大于consumer的1.2倍，并通过有成本的正分门槛。
- 新路径成功授予之间至少间隔1000ms；同workflow让位后冷却30000ms。
- 60秒滑动窗口内限制迁移预算为4倍实际Device token池。实际释放按
  卸载及可能重载计两次，必要备份入队和consumer恢复预算另记；失败
  的部分释放也计入。它是控制预算，不是实际PCIe字节或带宽测量。
- ready等待至少30秒后获得服务的agent，其紧随的工具边界获得保护。
- 原生探测使用2ms软预算及8候选硬上限，不在检查中同步等待DMA。
  单次不可中断的原生调用可能超出软预算，必须记录实际CPU成本。

原75% survival工具预测卸载继续独立工作，上述冷却和预算不能被
描述成限制全部原生/旧路径迁移。JOIN/EOS预取、prepare_host、
sibling及正在执行请求的连续性保留，工具预取和逐层handoff仍关闭。

## CPU证据与收益解释

CPU正确性验证使用真实原生树和分配器，异步传输由stand-in完成。
需要覆盖单/双donor、完整计划不成立时不释放、ACK之前不释放、部分
失败及其预算、工具返回后的资格、已分配/正在执行请求保护、过期、
会话/epoch变化和旧路径回归。完整133项目配置还需通过真实构造函数。

完整封存Full与旧Oracle轨迹分别筛查全部2865和3007个实际周期控制，
保持相同18条测量成员，完整负逻辑余额也必须保留。工具返回后候选需
关联精确request/attempt/session，排除已有原生launch的请求。既有
周期快照不覆盖所有中间事件，且launch前已分配原生资源的状态没有
完整记录，因此这些是候选机会，不能当成全部实际可执行次数。

按旧测量关键路径统计被选请求尚未开始服务的等待，可得到“其他服务
不变、donor没有损失”条件下的乐观等待缩短量。必须按请求去重，保留
所有18条，不能把局部两任务正分之和作为平均JCT改善。该数也不是
整个新系统的严格上限，因为新的选择会改变后续候选、批次及关键路径。
CPU结果没有可靠刻画这些反事实变化时，应明确报告净JCT仍未知，而
不是给出伪精确的GPU收益百分比。
