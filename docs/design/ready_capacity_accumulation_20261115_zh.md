# 高优先级 ready 请求的有界容量积累

这是默认关闭的调度候选，尚无 GPU 净收益结论。它与即时工具替换的等待
保护修复合并验证，不改变原始任务、工具时间、到达表、固定测量成员或容量。

后续的等待权重修复见
[有界等待保护](bounded_ready_wait_priority_20261115_zh.md)。
该修复将容量累积的 30 秒准入门槛与 30 秒冷却时间从老化增长时间中分离，
因此调整工作量排序的老化参数不会同时改变本机制的计时。

## 问题与已有证据

133 项目、20 个初始 workflow、平均 60 秒到达、400GB Host 的完整
acc8926a Oracle 平均 JCT 为 1278.157774 秒，匹配 Full 为
1274.833468 秒。已有跨 workflow 竞争和改选后的实际服务，收益不足
不能仅解释成没有 paused 候选。

在该轮精确周期授予与 ready 快照中，有 40 次重复观察涉及 22 个不同
测量请求：更短的候选单独放不下，而同一时点新授予更长 workflow 的
完整逻辑预算合计覆盖其当前缺口。这些是观察到的额度竞争，不是
反事实 JCT 收益，也没有证明原生物理空间能立即满足该候选。

例如 desktop021 的 epoch42 有 248234 输入 token，提交到首次 launch
等待 584.371766 秒，launch 后完成仅 1.546251 秒。只提高可行子集内的
排序优先级，无法保证这类请求跨多个边界凑齐预算。

## 触发与边界

显式参数为 `ready_capacity_accumulation_ms`，允许 0、1000、2000。
0 保留原行为；启用时必须等于普通合并窗口，并同时使用 maximal
benefit 和已有 ready 等待保护。当前候选为 2000ms，等待保护为 30000ms。

只在周期恢复边界创建一个 focus，请求必须满足：

- 已有真实提交，依赖已满足，处于合法 ready-paused 状态。
- 精确请求、epoch、attempt、session 身份仍有效，预测受支持。
- 本次连续 ready 等待已观察至少 30 秒，期间尚未获得原生服务。
- 自身完整逻辑预算超过当前入口余量，但不超过总池预算。
- 原选集确实包含更低优先级的其他 workflow；可暂缓的新预算合计至少
  覆盖当前逻辑缺口。基础工作量优先级与等待调整后优先级都要更高。
- 已收集窗口内，原选集外不存在单独放得下的更高优先级、受保护 JOIN
  或同 workflow 成员；否则先由原组合选择器处理，不能因暂缓原选集
  而一并隐藏它们。这个检查也适用于已有 focus 的后续窗口。
- 当前实际 native running batch 至少有两个请求。

元数据只取已经收集的候选，最多 32 个；原选集最多 8 个，原生前缀搜索
和六/八候选组合搜索的上限不扩大。不新增队列、全图或 KV 扫描。

## 执行与结束

一次 focus 最多持续一个普通 2 秒窗口。该期间周期恢复和普通免费补位
仅暂缓原选集中较低优先级的跨 workflow 新准入。更高优先级、同 workflow
成员和受保护 JOIN 保留原权利；已有 active 不被暂停，也不增加任何逻辑
额度、物理空间、传输或备份权限。

JOIN/EOS 恢复和原预测式长工具 A→B 即时替换继续走已有及时路径，
不等待本窗口。工具替换已使用相同 ready 等待权重，但不被本暂缓动作阻挡。

免费补位不能自行启动 focus 或延长截止时间。一次开始后至少 30 秒
才能再次开始，事件不会反复刷新该冷却时间。

以下条件撤销暂缓，回到原选择器：

- 到达截止时间，或实际 running 数量不足两个。
- 当前完整逻辑预算已经能容纳 focus。
- 身份变化、依赖重新阻塞、预测失效、获得 JOIN 保护、终止或被忘记。
- 收到精确 focus 的原生服务回调。

额度足够只表示重新获得原选择器比较的机会，首版不强制把 focus 设为
required，不保证立即物理恢复或执行。原最大可行组合、输入、增长、
槽位、原生 allocator、引用/锁和 DMA 检查仍决定最终动作。

## 审计与验收

暂缓日志保留未经修改的原选集、所选子集、完整请求身份、两种权重、
观察等待、入口预算、running 数量以及固定开始/截止时间。离线重放
独立验证暂缓只删除合法低优先级的新授予，不能把该动作冒充组合搜索。

CPU 检查须覆盖：默认行为、相同 Oracle/R5 参数、JOIN 和高优先级保留、
超时和冷却、请求身份变化、精确服务撤销、免费补位不能延长窗口，以及
容量释放后的实际逻辑准入和 native prefill 选择。

GPU 验收仍是固定 18 条完整自然 JCT，目标相对匹配 Full 改善约 1%
或以上，共同窗口全部输出吞吐至少达到 Full 的 98%。另核对 focus 的
实际准入和服务、暂缓的低优先级请求代价、同步控制 CPU、迁移和重算。
局部逻辑预算可行、被暂缓次数或首批服务变化都不能替代完整 JCT。
