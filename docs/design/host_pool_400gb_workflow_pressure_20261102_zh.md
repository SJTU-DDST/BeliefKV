# 400GB Host KV 与增加 workflow 并发的可行性

状态：CPU 评估及候选实验设计；未修改启动器、分配 400GB、执行 CUDA
注册或启动新的 GPU 实验。保留现有 73 项目、200GB 配对结果。

用户允许本方向跨 NUMA 节点使用 Host 内存。评估目标是增加可保留的在途
workflow，让 HBM 容量释放时存在多个真实 ready 候选，检查短 workflow
排序能否改变实际服务并降低完整平均 JCT。

## 现有供给与竞争

证据位于
`experiments/reports/remaining_original_projects_20261030/useful_token_cost_r1/`
下的 `original73_background_substitution_full_review_r1/`：

- `gpu_idle_supply/report.json`：共同窗口 55.693--1638.955 秒，时间加权平均
  12.522 个在途 workflow、9.452 个 application-ready agent、
  8.635 个 active-ready agent、0.608 个 ready-paused agent。
  ready-paused 存在的时间占比为 28.703%。
- `periodic_decisions.json`：同一共同窗口有 772 次周期控制，其中 7 次
  跨 workflow application-ready 逻辑容量竞争。全程为 1805 次控制、
  27 次竞争；856 次有剩余额度却没有 application-ready paused 候选。
  全程 1302 个 ready 恢复授予均保留资格并有精确匹配的后续服务。
- `supply.json`：Host 高水位 200000077824 字节，最后使用率 99.604%。
  独立、非原子计数中的 Host 归因重算为 29122 token；不能报告为零重算。
- `demand.json`：480 秒时，15 个存活 workflow 的 pending/latest-served
  去重前缀代理为 1843153 token，仅为 HBM+Host 几何上限的 64.907%。
  全部周期样本中该代理最大为 2317672 token。它不是实时物理分配证明。

这些结果支持增加候选人口，但不能将 Host 满直接解释为有用存活 KV 已满。
Host 中还存在可驱逐或重复状态；只扩大 Host 池、保留原并发和到达表，不会
自动产生更多 ready 请求。最新窗口 GPU 采样利用率为 98.884%，本方向主要
检验容量竞争下的完成次序，而非恢复已经不存在的大段 GPU 空闲。

## 容量与内存

当前 FULL KV 每 token 为 98304 字节，HBM 为 805198 token。
按相同粒度向上取整的 400GB Host 估计如下；正式值以原生 census 为准。

| 项目 | 200GB Host | 400GB Host |
| --- | ---: | ---: |
| Host token 槽位 | 2034506 | 约 4069011 |
| HBM+Host token 槽位 | 2839704 | 约 4874209 |
| 相对现有总槽位 | 1.000 | 1.716 |

上述相加是几何容量上限。HBM/Host 重复备份、在途传输、增长预留、
不可驱逐状态和分配粒度都会降低实际可承载的独立存活状态。

2026-11-02 CPU 检查中，系统 `MemTotal` 为 528124296 kB，约 503.66GiB。
`MemAvailable` 一次观测为 458286080 kB，约 437.06GiB，包含可回收内存。
现有预检 `_node_capacity()` 对两个节点的保守可用量之和另一次观测为
384.444GiB。400GB 是十进制单位，约 372.529GiB；后一个估算扣除池后仅余
11.915GiB，尚未扣除新进程、CUDA 注册元数据及额外工作负载开销。
这支持把 400GB 作为待验证目标，不能证明完整模型一定能正常启动。

实际实施前必须验证完整原生 Host 分配、CUDA 注册、实际页面分布、
H2D/D2H 和释放。仅分配成功不等于注册成功。接受跨节点后，双方仍采用同一
显式内存策略并记录实际分布，避免旧 preferred1 结果中的页面比例差异。
现有单节点 `bind:1` 不适用于 400GB；双节点 placement 需要单独声明。

源码中仍有两个 200GB 上限：

- `scripts/launch_qwen35_native_v0520.sh` 拒绝 `HICACHE_SIZE_GB > 200`。
- `scripts/preflight_qwen35_host_pool.py` 的 `MAX_POOL_GB = 200`。

`beliefkv/experiments/host_numa.py` 的严格本地资格还绑定了 200GB 和单节点
完整驻留。新的跨节点容量不能沿用这份资格或通过直接清除检查宣称通过。

## 并发和到达方式

73 条完整原轨迹合计输出 1499356 token，平均每条 20539.123 token。
在假定任务混合不变时，到达间隔对应的平均新增输出负担为：

| 平均到达间隔 | 输出负担 / token/s | 相对旧 Full 实测 299.990 token/s |
| --- | ---: | ---: |
| 70 秒 | 293.416 | 0.978 |
| 65 秒 | 315.987 | 1.053 |
| 60 秒 | 342.319 | 1.141 |
| 45 秒 | 456.425 | 1.521 |

这仅是负载量纲检查，不是稳定性证明或吞吐上界；未计输入成本，且更高并发
会改变批次、重算和执行成本。旧实测来自有限共同窗口，不能作为严格稳态
服务率。因此不应直接将到达间隔缩为 40--45 秒并声称是稳定 serving。

建议先将初始 workflow 从 12 增至 20，平均到达间隔保留 70 秒；
平均在途人口以约 20--24 为诊断目标，不承诺初始 20 就能维持该人口。
初始积压消耗后，若 ready 候选仍不足，再依据新批次成本及完成能力调整
到达率。单纯增大初始批次不能建立稳态压力。

该分支保持 HBM、running/decode 上限 24、原工具时长和任务内容不变；
增加的是应用在途人口，不是 GPU 批大小。优先复用已有完整原轨迹，
仅重建预先固定的 warmup、测量组和到达表。重新核对背景是否覆盖所有
测量任务的完整尾部；不能因为加速提交使 73 个任务过早到完，就截断长任务
或将该轮称为稳定负载。新配对不能直接与旧 200GB 结果计算排序收益。

## 诊断与比较

先在 400GB、较高并发的非排序 Full 上检查：

1. ready-paused 数量、至少两个不同 workflow 同时 ready 的时间占比，
   以及分别可行但不能全部容纳的真实竞争；区分重复 tick 和独立决策对象。
2. HBM 的有用存活状态、可驱逐状态和增长预留，避免仅凭池分配率判断利用率。
3. Host 有用前缀丢失、实际额外 prefill 和内存开销；排队是否持续增长。
4. 容量释放到实际服务的时延、后半程候选供给和完整背景覆盖。

形成足够竞争后，在完全相同的 400GB 配置、任务、到达表和固定测量组上，
比较非排序 Full 与恢复/压力 oracle。保留 JOIN/EOS、工具预测卸载、
prepare_host、agent 连续性及 sibling 支持；工具预取和逐层 handoff 关闭。
已有计算服务候选仍为独立开关，不在这个容量诊断中同时启用。

不仅统计排序改变次数，还核对不同选择是否实际准入、保留并推进后续服务。
平均完整 JCT 包含所有固定测量成员，测量组全完成后停止背景；共同墙钟
窗口统计全部输出，另报长 workflow 和背景的等待，不能只选先完成者。
在同一配置内观察到可重复的约 1% JCT 改善后，再评价预测器和对应
ThunderAgent acting-decay 对照。单次正收益不证明稳定改善。

本方向可以创造原先缺少的选择机会，但不保证短任务排序必然获益。
若更多状态主要用于保存工具等待，或 oracle 仍只改变资格而不改变后续服务，
继续扩大 Host 池不能解决相应瓶颈。
