# 短 workflow 调度中的有界等待保护

## 已确认的问题

旧 `ReadyWaitPriority.weight()` 使用
`min(1, base_weight * (1 + ready_wait_ms / 30000))`。
这个上限只限制最终绝对权重，并未限制对原工作量权重的放大倍数。
等待两分钟可得到五倍权重；实际已完成的 133 项目 Oracle 日志中，
最大观测放大倍数达到 20.346771。对于当前约为 `1 / (1 + 剩余模型工作量)`
的基础权重，这足以把明显较长的 workflow 提到较短 workflow 前面。

老化使用精确请求首次被观测为 ready-paused 后的等待，不是 workflow
从到达开始的总时间。这里的修复也不修改 ThunderAgent 的工具 acting-decay。

## 新规则与参数

将等待保护限制为对原基础权重的相对加成：

```text
p = clamp((ready_wait_ms - grace_ms) / scale_ms, 0, 1)
weight = min(1, base_weight * (1 + (max_boost - 1) * p))
```

推荐的下一组匹配 Oracle/R5 配置为：

| 字段 | 数值 | 含义 |
| --- | ---: | --- |
| `ready_wait_priority_ms` | 120000 | 宽限期后，用两分钟逐步达到加成上限 |
| `ready_wait_priority_grace_ms` | 60000 | 前一分钟保持原基础工作量优先级 |
| `ready_wait_priority_max_boost` | 1.25 | 最多增加 25%，不会继续随等待放大 |

`ready_wait_priority_ms=0` 继续关闭此机制。只有显式 maximal short-work
selector 可以启用它。增长时间可设为 1 至 3600000ms，宽限期可设为 0 至
3600000ms；加成倍率允许 1 至 2，拒绝布尔值、非有限数和错误类型。
倍率设为 1 可以保留 ready 计时而关闭排序加成。

未填写新字段、但启用此机制的配置，在这份新源码中默认使用 60000ms
宽限期和 1.25 倍上限；增长时间读取原字段。因此运行源码及日志中的
`bounded_relative_ready_wait_v2` 是策略身份的一部分。冻结的旧源码和
历史日志仍使用原规则，不改写其含义。

对于当前近似逆工作量的基础权重，默认上限把可翻转的单体工作量差距
约束在约 25% 内。它仍允许工作量接近的较久等待者优先。组合选择还
考虑 JOIN、集合收益和容量，因此不能据此保证每次都选择全局最短的单体。
保留原有长期等待逃生机制；有限加成本身不提供任意持续负载下的无饥饿保证。

## 共享范围和计时

周期组合准入、普通补位、即时预测式工具 A→B 消费者排序，以及容量累积
候选比较，都使用同一个有界等待权重。每个 workflow 在同一次选择中
仍只有一份权重，不能通过多个 sibling 重复累加等待加成。

请求 epoch/attempt/session 身份改变时重新计时；精确 native 服务回调、
工具开始、JOIN 阻塞、终止或取消会清除对应历史。清除历史时同时使缓存的
workflow 年龄失效，避免当前快照残留旧加成。其他 sibling 的独立请求历史
仍保留，并在下一次候选收集时重建共同年龄。

容量累积原来把 `scale_ms` 同时当作最短等待和冷却时间。现在这两项独立
保持原候选的 30000ms，避免把增长时间调为两分钟时一并改变容量积累权限。
已有 2000ms 最长累积窗口、running 数量、基础和调整后优先级双重检查、
JOIN/同 workflow 保留和原生安全约束不变。

不增加同步扫描、定时器、预测调用、active 抢占或物理容量权限。一次权重
计算仍为常数时间，仍复用原有有界候选和 512 条精确请求历史。

## 匹配准备与部署边界

`scripts/prepare_bounded_ready_wait.py` 从已有匹配 Oracle/R5 配置生成新工作量
产物及配置，只修改上述等待参数、对应文件指纹与声明。模型预测参数、真实
任务、token、工具时间、到达表、测量成员、成本模型和容量均保持原值。
它不注册实验、不修改正在运行或排队的注册，也不重跑 Full。

CPU 验证覆盖明显长短差距、接近工作量的有限等待保护、真实逻辑准入与
native prefill、即时 A→B、JOIN 保护、独立容量计时、身份重置、参数验证、
历史日志重放及匹配产物。原先 60001ms 的非法增长时间用例，因现在允许
更慢增长而替换为 3600001ms 上界用例；60001ms 另有明确合法配置测试，
源码绑定报告应如实列出该单个历史测试身份的替换。

尚无新 GPU JCT 结论。下一轮应合并其他已完成改进验证，继续保留完整
测量 workflow 的自然 JCT、共同窗口吞吐、长任务等待和实际服务证据。
