# 当前目标：验证短 workflow 调度的实际收益

2026-11-02 用户重新设定目标：取消 Host 池必须在两个 NUMA 节点上均匀
分布的要求。后续以调度竞争和完整 workflow JCT 为主线，NUMA 页面分布
只作诊断，不再将其作为实验启动或结果有效性的硬门槛。

## 工作负载与配置

- 复用现有 73 个不同项目的完整原始轨迹、token、依赖和工具时长。
- Host 池 400GB；初始提交 20 个 workflow，后续泊松平均间隔 70 秒。
- HBM 805198 token，running/decode 安全上限 24，prefill chunk 2048，
  mixed 关闭；不通过改变请求批上限制造调度竞争。
- 保留 JOIN/EOS 预取、工具预测卸载、prepare_host、agent 连续性和
  sibling 支持。工具预取和逐层 handoff 继续关闭。
- 固定按到达序号选择 18 个测量成员，保留它们的完整 JCT；这些成员全部
  自然完成后即可停止背景。共同墙钟窗口统计全部服务输出。

## 执行顺序

1. 解除当前启动路径对 NUMA 均匀性和逐页计数完全相等的强制要求。
   保留实际池容量、CUDA 注册、传输正确性、原始 token 和停止条件检查；
   页面分布、计数差额和远端比例只记录为诊断。新的匹配控制使用同一内存
   策略，实际分布不必精确相等。已实现显式 `diagnostic` 模式，容量与页面
   均匀性独立判断；597 项相关定向检查全部通过，新压力控制已进入
   实际服务，历史失败不改判。
2. 运行一轮非排序 Full，检查真实 ready-paused 供给和恢复竞争：
   不同 workflow 的候选各自可执行，但不能全部装入。分别统计独立竞争、
   改变准入集合、保留资格和实际获得服务，不以重复 tick 或排序改变替代。
3. 在相同 Host、任务、到达表、测量组和执行配置上运行 oracle。
   第一阶段目标是可重复的约 1% 或更高平均 JCT 改善，同时共同窗口吞吐
   无明显下降，长任务和背景等待可解释。单次小幅正收益只作为继续依据。
4. 若竞争不足，优先缩短平均到达间隔或调整在途人口；一次只改一个配置。
   若已有竞争却无收益，先核对资源组合、准入到实际服务、decode 效率和
   控制成本。确有工作量区分不足时，再调整原始 workflow 的选择。
5. oracle 明确获益后再评估 R5 条件剩余工作分布预测器，并补相同配置的
   ThunderAgent acting-decay 对照。旧 200GB 结果不作为 400GB 的匹配对照。

## 控制验证成本

完整 400GB 原生分配、注册、有界双向拷贝和释放已有实际 GPU 成功证据，
见同一研究报告下的 `host400_native_registration_component_r5/` 和 `r6/`。
后续复用这些证据；只有分配或传输代码改变、实际组件出错时才补相应检查。
不因文档、观察器或非关键门槛调整重复运行全量组件和全部历史 CPU 测试。
对实际改动运行有针对性的检查，保留旧回归及失败启动的原始证据。
