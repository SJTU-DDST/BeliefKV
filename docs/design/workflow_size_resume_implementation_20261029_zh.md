# Workflow 剩余工作分档与 agent 恢复：实现状态

本实现对应
[R4 设计第 13 节](workflow_size_join_frontier_20261029_zh.md#13-当前方案剩余工作三档与原预算内恢复)。
实现日期为 2026-10-29（美国西部；上海时间 2026-10-30）。
算法与 CPU 验证不改变此前冻结实验。

**恢复选择器、后台分类器、真实 JOIN sibling 接入和训练/评估入口已实现。
当前训练出的模型尚不具备启用正式 GPU 对比的条件。**
这些是两个不同的验收项：代码按规则工作，并不能证明剩余工作预测有效，
也不能证明完整 workflow 平均 JCT 已下降。

## 1. 调度规则

以 ThunderAgent 的 agent invocation 为资格身份，workflow 为工作量预测
和最终 JCT 的统计单位。root 和全部 descendant 查询同一份 workflow
档位，不给每个 child 建立一个独立的“短任务”预测。

在原周期恢复边界，先沿原路径刷新已经实际生成的 token，再使用原
`remaining_capacity_with_decay(now)` 预算。候选资格过滤仍由原 reference
及真实 JOIN 阻塞过滤器决定。排序键为：

```text
原恢复类别 → workflow short/medium/long → 当前上下文 token → 原入队序
```

原恢复类别的具体顺序是：非 ACTING 的续调、首次 program、ACTING 后备。
short 只能在同一类别内提前，不能跨类别获取资格。档位缺失或不可信时
取 medium；没有有效 JOIN 协同的情况下，所有对象回退 medium 时的状态
变化与原 reference 一致。

扫描候选时按原来的 `context_tokens + buffer_tokens` 累加。遇到放不下
的对象继续向后扫描。预算 7、short 的 a1/a2 各占 3、medium 的 b 占 4、
long 的 c 占 2 时，选择 a1/a2；预算 5 时选择一名 a，再跳过另一名 a
和 b，最后用 c 填满。这里仍是逻辑预算，不是物理页分配。

资格恢复后，继续执行原来的不折扣容量压力处理：可以暂停 ACTING，
也可以将 REASONING 标记为在安全边界暂停。新选择器不指定 active
受害者，没有再加全额预算门禁，也不保证整轮结束后旧 active 集合不变。
原生物理 KV、锁、DMA、输入增长、请求槽位及选批检查继续拥有最终权限。

Full 候选继承上一轮选定的 **2000ms 控制周期**，ACTING decay 半衰期
仍是 1 秒；paper ThunderAgent 保持 5000ms。保留原请求等待 1800 秒
force-resume，不新增每秒老化或强制时间片。工具预取、普通 frontier
预取、物理逐层 handoff 均关闭。

## 2. JOIN sibling 协同

周期恢复只索引当前 paused、pending invocation 已有的 JOIN 关联，
不扫描离线未来图。只有已有 runtime 图中真实阻塞的 ALL-JOIN 才适用：

- parent 确实等待该 JOIN，JOIN 尚未满足；
- child 已提交当前请求，身份、context epoch 和 workflow 一致；
- child 当前可服务，未在工具中、未等待自己的阻塞 child；
- ANY、后台 SPAWN、推断出的 JOIN、已返回成员均不获得组资格。

同一原恢复类别、同一档位中的组，以原排序中最先出现的 ready 成员为
anchor，将其余 ready sibling 相邻安排。之后仍按原预算逐个扫描，
可以只选择能放下的子集，不等待未 ready 的成员。
新增的周期组内相邻恢复要求该 workflow 有受支持的模型判断；预测
回退时保留原周期恢复顺序，已有事件共同准入和原生共同选批照常工作。
预算不足时保留 reference 的快速返回，不编码任务或扫描恢复候选。

逻辑恢复后复用 `JoinSiblingService` 的原生共同选批、至多四名成员的
有界偏好、容量释放后的重试，以及 actual native first-service 证据。
它保留队首、久等请求、resident-first 及真实物理容量保护。两个成员
逻辑 active，不等于同一 GPU batch，也不等于已经获得服务。

## 3. 分类器与热路径

`WorkflowWorkWorker` 在后台线程中处理已观察事件、请求提交、每新增
128 个输出 token 的进展和原生请求完成。按 workflow 合并更新，最多
每 200ms 一轮。任务文本从首个 root 已提交输入的末尾提取，或来自真实
WORKFLOW_START 的显式任务字段；tokenizer 加载、文本提取、词袋编码、
同上下文前缀比较及模型推理都在后台执行。

初版模型是字符 2--4 gram TF-IDF（训练词表至多 4096 维），任务投影
64 维，与已观察数值状态投影相加，再经过 ReLU、32 维隐藏层和三类
输出。任务投影每 workflow 缓存一次。运行时加载 JSON 权重并校验
SHA-256，避免引入 pickle 或训练依赖。小矩阵使用 NumPy `einsum`，
不依赖新增的 BLAS 线程池。

输入只有任务指示和已观察进度：已完成调用、累计必要输入和实际输出、
已观察工具/child/JOIN 数、当前 ready/running/tool/JOIN 状态、最大
已观察 fanout/depth 及真实完成意图。它不读取录制的输出长度、未来
child、隐藏工具时间、完整未来 DAG 或原请求服务时长。

恢复选择入口读取已经发布的不可变预测，一轮内为同一 workflow 固定
同一预测快照。它不等待后台推理。以下情况回退 medium：

- 首次任务文本或缓存尚未就绪、词表不支持；
- 最大概率小于 0.6、校准不支持三类、模型未通过启用检查；
- 后台观察积压超过 2 秒、观察队列溢出或 worker 出错；
- workflow 已结束。结束标记会立即压过尚未发布的后台结果。

观察队列有 4096 条上限，最多维护 256 个 workflow。溢出只撤销预测，
不取消 runtime 请求或截断 workflow。相同逻辑调用重试不会重复增加
完成调用或输出。模型工作账本不是原生 allocator 的容量账本。

## 4. 当前工作量标签的准确边界

训练工具为每条完整、自然结束的历史 workflow 导出因果进度快照。
同一 context 后继请求只计算相对于此前完整已服务输入/输出的实际
token 公共前缀之外的输入，编辑或压缩后按实际差异计算。额外缓存
丢失和原生重排队不会被当作未来逻辑新增输入。

当前 CPU 原型的工作单位明确为：

```text
U = 0.01 × 同上下文必要输入 token + 实际输出 token
```

必要输入在完整模型调用结束时结算，输出按已经观察到的内容块更新。
这也是调用边界上的粗粒度进度模型，尚不是逐个 prefill chunk 的精确
服务账本。该限制和跨 context 共享成本的限制都需要在正式余量预测中
进一步验证。

它是冻结的逻辑 token 工作代理，**不是已校准的 GPU 秒数**，也没有按
跨 context 物理共享页并集估计 prefill。不同 context 的首次输入分别
计入，不假装已实现精确的跨 agent 前缀共享成本模型。预测不包含工具
等待、排队、迁移或丢失前缀的额外重算。

正式使用前还需要验证这个代理在 paused 竞争快照中的排序价值，并用
固定模型/硬件的必要 prefill/decode 成本补充或替换该换算。历史 V174
worker 区间的聚合 prefill/decode 单 token 成本比约 0.03994，明显不等于
这里的 0.01；该聚合还混有批次和上下文差异，不能直接冒充完整校准表。
目前没有凭这个原型作 GPU 性能结论。

## 5. 训练、隔离与实际结果

所有同一 workflow 的快照放在同一侧；同时隔离项目和相同任务文本
模板。词表、数值归一化、权重和工作档位阈值仅从训练 workflow 确定。
温度只由独立校准项目拟合。三档阈值使用训练初始总工作量的 1/3、
2/3 分位数，随后固定，不在线追随当前队列改变。

当前十八个测试项目全部排除后，同模型历史轨迹只有六个其他项目。
R1 使用 V168b/V171/V174，仅作诊断，包含部分早期受干预源；保留其
数据和负结果。R2/R3 只使用全部自然结束的 V171/V174：最终八条训练
workflow 来自四个项目，四条校准 workflow 来自另外两个项目，评估
仍为 V230 的十八个不同项目、14458 个观察快照。

R1 的校准集缺少 long 类项目；不能仅因拟合过温度就允许 short 决策。
R2 修复校准项目类别覆盖，并在每个 workflow 总权重相等的前提下平衡
类别。R3 维持相同权重与独立温度，明确增加仅使用校准项目的部署检查：
macro-F1 至少 0.50，long→short 比例至多 0.10，且三类都有项目支撑。
这些是初始保守检查，不是统计保证；通过也不能替代真实恢复竞争和 GPU
验收。本轮已经查看过评估结果，不将此开发集包装为永未使用的最终测试集。

R3 实测：

| 项目 | 结果 |
| --- | ---: |
| 校准 macro-F1 | 0.3274 |
| 校准 long→short（按 0.6 概率门槛） | 41.03% |
| 十八项目评估普通准确率 | 62.75% |
| 十八项目评估 macro-F1 | 0.3455 |
| 十八项目评估 long→short（未应用部署禁用） | 54.55% |
| 部署检查 | 不通过，回退 medium |

这些结果说明普通准确率会被大量 late/short 快照抬高。现有样本不足以
支持把任务文本与进展分类当成可靠的剩余工作排序。正式 preflight 会
拒绝此模型，避免花一轮 GPU 时间跑事实上全回退的“新策略”。
这不否定恢复规则，也没有证明它有 JCT 收益。

训练入口为 `scripts/train_workflow_work.py`，数据、源 SHA、模型和评估
均位于 `experiments/reports/workflow_size_join_frontier_20261029/model_r*/`。
这些输出保留独立身份，未覆盖早期失败或诊断结果。

## 6. CPU 开销与验证

`benchmark_r1.json` 使用真实权重、200 次恢复测量，候选规模为 8/64/256。
整轮 tick 包含相同的 program 副本构造；其中部分成本并非排序本身。
64 个候选的 thread-CPU 中位数约为原实现 159µs、新实现 261µs；
256 个候选的新实现约 787µs。缓存任务投影后的动态分类约 26.5µs。
100000 token 的同上下文前缀核算约 3.83ms，在后台进行。

这不是整轮控制总成本、GIL 干扰或 JCT 收益的测量。后台前缀核算仍会
使用 CPU/GIL，真实运行必须同时统计 enqueue、推理次数、累计 CPU、
P99 提交间隔和原压力循环开销，不能只引用分类函数微秒数。

CPU 测试覆盖原类别优先级、分档选择、跳过不合适大小、部分 sibling、
真实阻塞身份、随机 reference 回退等价、decay 后原压力暂停、重试去重、
无未来输入、置信度与校准回退、队列溢出、终态失效、配置隔离和正式
preflight 拒绝。完整保留前一轮 4859 个测试身份的执行结果，见同目录
`cpu_r1/evidence.json` 及后续保留其全部身份的 `cpu_r2`/`cpu_r3`。
最终 `cpu_r3` 实际通过 4903 个测试及 6 个子测试，无失败、错误或跳过，
保留上一版全部 4902 个身份，1974 个源输入和原生引擎在执行中未变化；
证据文件的实际结果是验收依据，局部测试的 native
fixture 跳过不算完整通过。最初一处 fixture 的 sibling 顺序断言错误
单独保存在 `cpu_initial_fixture_failure.json`，只修正了预期。

## 7. 与其余系统路径的关系

此次只修改周期 paused→active 的选择。新 program 的原生首次到达准入、
事件驱动 free-continuation、JOIN parent 的免费额度/逻辑让额路径，以及
已有 sibling 免费额度重试，都继续使用原规则，可能绕过新排序。
不把这些路径的 grant 计成分档策略作出的决定。

`workflow_size_resume_selection` 逐轮记录原预算、候选身份/档位/类别、
按优先级选中的成员、原压力处理后的 active/marked 状态和 CPU 时间。
预测器状态同时公开调用次数、回退、积压及资格状态。后续应从这些真实
paused 竞争样本评估排序，而不是把全部模型请求或温度拟合当成排序有效。

新配置为
`configs/migration/predictive_workflow_size_resume_20261029.json`。
它与前一轮冻结 Full 分离，当前明确标为“等待合格预测器”，未注册 GPU。
该配置与 2 秒/no-handoff Full 的原冻结执行及结果分别保留。

后续顺序为：完成并复核前一轮完整比较；补充项目隔离训练资料与工作
成本口径，先通过校准和真实竞争排序验证；再分别冻结、进行当前源的
位置/采样检查并运行同工作量 Full。最终比较完整 workflow 平均/P95
JCT、全程吞吐、正常长尾、实际 sibling 服务、重算/迁移及控制成本。
不能从模拟选择、逻辑 active 或 CPU 测试推断已经优于 ThunderAgent。
