# 新负载的机制条件与验收顺序

依据用户最新总结，先找到能检验机制的负载，再运行正式策略比较。
目标是固定到达测量组的完整平均JCT及共同测量窗口的系统吞吐。
负载选择不使用Full相对baseline的胜负或native重算量作为门槛。

## 条件及需要补充的口径

| 方面 | 目标与证据 |
| --- | --- |
| 持续到达 | 冻结独立到达表和测量窗口，按到达成员确定测量组；每名成员保留完整自然JCT，背景提交覆盖全部测量成员完成之前。 |
| 人口 | 每个workflow来自不同原项目，测量与背景来自同一声明的任务混合，大小与到达槽位独立；不靠复制项目增加压力。 |
| 异构工作 | 以必要模型工作分布检验长短，工具关键路径另列，不能用一次含排队的JCT分长短；短/长档都覆盖大、小上下文。 |
| 多轮短委派 | 多轮真实双/多成员ALL-JOIN；root保留实质实现、整合、验证；child负责具名路径/符号上的小交付物并自然报告。 |
| 就绪覆盖 | 热工作推进时有后继ready候选；容量释放后短长对象各自能容纳但不能全部容纳，并验证新准入确实获得服务。 |
| HBM压力 | 总有效KV超过HBM，同时热状态、下一恢复状态和增长预留可以协调；分别观察空闲页、安全冷页、锁定页及逻辑资格。 |
| Host可行性 | 有复用价值的存活状态原则上能由HBM与Host共同容纳。Host满可以是可回收重复备份占用；关注有用前缀丢失与实际额外重算。 |
| 工具分布 | 保留短、中、长混合，工具阻塞期间仍有其他计算可推进；分开记录工具执行、工具排队与LLM排队，避免全体同时阻塞。 |
| 恢复机会 | 存在已服务历史前缀的实际缺失和暴露恢复等待；新child首次cold prefill不算它自身的旧KV恢复。 |
| 比较与信息 | 所有方法同token/图/工具时间/容量/到达/停止条件；未来信息仅交给明确oracle，测量组身份不交给策略。 |

前几项用于选自然源，物理压力、暴露等待和服务覆盖需要小规模原生
采集/校准证明。校准是准备工作，不能被当作正式算法收益，也不能用
未验证的逻辑预算推断实际HBM有多少可安全卸载的页。

测量组应从统一预热之后的到达成员中选取。持续到达本身不代表稳态，
还要检查在途工作、ready候选及排队年龄是否持续增长。背景表及提交
截止时间提前冻结，各方案执行相同的完整序列；不能在各自测量组完成
时停止提交，从而让较慢方案面对更多背景工作。固定背景耗尽前仍未
完成的测量组保留完整JCT，但不能宣称其后续排空阶段有持续压力。

## 三点修正

**“child不主导”要分解看。**同时报告root工作、所有child合计及最大
单child占比，还要看JOIN关键路径。多轮短child的总量可能超过root，
这本身不等于错误；本轮希望root保留足够实质工作，并避免长child、
纯串行委派吸收绝大多数服务。不要通过给root添加无意义调用改善占比。

**空位及时补入依赖已有就绪工作及准入。**提高到达率只能增加供给机会，
不能保证每个空位出现时立刻有新外部workflow抵达。独立随机到达本来就
允许间隔；通过足够人口与计算/工具阶段交错维持候选，再量化释放到
准入、准入到服务的时延。不要偷偷改成完成触发到达的闭环负载。

**native重算应是结果。**各方法使用相同HBM/Host资源及正常实现。原生
缓存策略在该条件下自然造成更多重算，可以如实报告；不能为了比较
优势专挑native失败、Full成功的样本，也不能把Full绝对零重算作为
必须筛中的条件。若总存活有效状态超过HBM+Host，单靠调度不能承诺
无损保存全部状态，应调整人口/上下文/到达，而不是继续加压。

## 工作量及时间口径

当前离线工作代理为 `.01 * necessary_new_input + generated_output`，
按完整invocation归属求和，runtime内部调用另列；不把重复完整prompt、
工具等待或排队当作固有模型工作，也不称其为精确GPU秒数。root和全部
child的归属量应与完整工作量守恒。

工具是否“太长”按就绪覆盖和关键路径占比判断，不能只看P50/P90。
短到无法覆盖迁移成本时可借用窗口小；长到大部分agent同时等待时，
GPU缺少工作。保留真实分布/完整尾部，合成负载声明公开来源、类别和
固定抽样；不裁掉慢样本或乘缩放因子制造收益，隐藏采样时长不进入
可部署预测器。

工作量与KV规模应交叉覆盖，不能只提供小上下文短任务和大上下文长
任务。排序时模型服务需求、工具关键路径与KV容量成本需要分别可见，
不能把并行工具时间直接相加当作workflow长度。实际未来调用及采样
时长只允许用于显式oracle；可部署预测使用已知任务、委派、角色、
执行进度及历史工具统计，并单独评估误差。

“短任务优先应有收益”是合理假设，不是验收结果。必须看到同一准入
边界有竞争、选择不同、实际服务变化及全测量组JCT改善；大短任务
挤掉多个中任务、工具关键路径和batch效率可能抵消收益。保留长任务
服务年龄与尾部指标，不能用饿死背景任务换取测量组均值。

## 已有源的重新审查

## 后续顺序

1. 先收窄child任务及补充目标文件/符号上下文，让root承担实现、整合，
   将新的真实独立问题作为后续并行委派。保留4/8软目标，不改成2/4，
   不截断报告、固定完整DAG或为了轮数重复工作。
2. 以少量不同项目自然采集验证短/中/长实际差异及多轮多成员JOIN，
   形态不足则保留全部结果并修正任务组织，不直接扩到整组36/48。
   给child提供已经掌握的目标路径/符号及明确交付证据，避免每个child
   从全项目搜索开始；保留真实未知问题及root的实现、整合责任。
3. 补足背景人口，校准到达率及HBM/Host压力、ready候选和恢复缺口。
   保留JOIN/EOS预取；用户关闭的工具预取继续关闭。
4. 冻结完整测量组、背景表、工具映射和公共资源，再先Full、后
   ThunderAgent工具衰减版本；取得清晰可重复收益后才推进其他适用
   baseline。工作负载或到达改变后，旧性能结果不能充当匹配对照。

完整证据在 `experiments/reports/workload_requirements_20261030/`。
本轮只是离线审计与负载验收准备，没有新GPU采集或策略性能结论。

## 结构化六项目采集的后续结果

后续结构化采集已完整结束，805个请求、33,667,535个输入token、
111,073个输出token全部保留。模型工作P90/P10为2.237，child调用
P50/P90为16/28.6，27个JOIN中21个singleton、6个double，无嵌套；
root并行轮次仍全部为1。child合计工作占比中位数55.65%，最大单child
中位数15.26%。全部28个超8次child的第9次输入含软提醒，不能再将
这些长child简单解释为提示未送达。只读源码变化、patch解析错误均为零。

下一候选保持同任务与预算，只增加显式`parallel_tasks`提交接口，
使模型在一次工具调用中表达2--4个真实并发的小交付物。该候选先做
小规模自然形态验证，不启动正式策略比较。完整结果和边界见
`docs/research/structured_checkpoint_complete_and_parallel_api_20261030_zh.md`。

显式并行接口的六项目源也已完成：660个请求，模型工作P90/P10=3.561，
9个多成员组均有真实共享decode，root并行轮次中位数1.5；实际服务的
28个child调用P50/P90=16.5/23，仍达不到目标。另有两个不存在的角色被
错误提前记录为零服务child，现已修复caller角色/深度校验，原始记录
和失败审计全部保留。该源不进入正式比较，不因上述部分改善自动扩展。
