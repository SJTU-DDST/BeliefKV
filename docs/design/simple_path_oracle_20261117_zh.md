# 简化 Oracle：恢复旧版全局短优先

按用户要求，回到旧 83 项目 Oracle 的排序与装入方法，保留必要修复、
真实阻塞 JOIN 的 sibling 支持和工具边界抢占。不在 Oracle 中试验新的
公平性、效用加总或主动等待机制。新设计统一简称 **KV 背压（D3）**，
指延后新 child 的首次 KV 物化、保护已有有效 KV；当前 D3 GPU 实验继续运行。

## 一条普通准入规则

1. 保留通过活体检查的 JOIN/EOS 恢复权利和正在执行请求的连续性。
2. 其余真实 ready 候选按 workflow 剩余关键路径升序排列。路径使用
   原始固定轨迹中模型工作与工具等待的依赖图；并行分支取关键路径，
   不直接相加全部工具时间。沿用旧版模型时间系数，不另作三档加权。
3. 按序逐个检查完整预算，放得下就准入；放不下就继续检查后续候选。
4. 同一阻塞 ALL-JOIN 中已 ready 的 sibling 相邻推进。容量足够时共同
   准入；容量不足时允许部分推进，不等未 ready 成员，也不为等容量空转。

实际使用已有 `global_ready_remaining_path` 和 `DeferredFreeAdmission`，
`WORKFLOW_COMBINATION_ADMISSION=0`，不构造 R5 组合选择器。
普通窗口仍为 2 秒，原有及时工具替换和 JOIN/EOS 事件旁路保留。
事件补位新增与周期恢复一致的 ready sibling 相邻处理。

旧版仍需保留的修复包括 pending 索引更新、窗口到期时先协调 decay 与
完整容量、JOIN 身份和 epoch 检查、原生 Host 备份与 ACK、控制开销复用。
不倒退任务、工具时长、到达表、测量成员或传输安全修复。

## 关闭的排序干扰

- 30 秒尺度 ready 老化及其后续封顶变体。
- 1800 秒等待后的强制 active 绕过。
- 最大化候选集合效用之和，以及用请求成本作优先级分母。
- JOIN 平方或线性覆盖份额对 workflow 长短的修正。
- 主动积累容量和暂缓已可执行请求的机制。
- 工具边界中基于 ready 等待时长的 donor 保护。

准备器不复制这些运行配置；实际全局控制器也拒绝夹带老化、
效用和主动容量等待字段，避免仅在文档中声称关闭。
历史组合 Oracle 和 R5 实现保留用于重现实验，不是本候选的默认路径。

## 工具边界抢占

复用已有最多两个 donor 的安全交接实现，只在真实 ready 请求等待容量、
存在实际工具边界时尝试。消费者仍按同一剩余关键路径升序，
donor 按同一依据从较长者中筛选，禁止额外的模型总工作量排序覆盖它。

路径秒数换算成现有交接代码的工作单位，使原有 D2H、消费者 H2D、
donor 后续 H2D 的成本检查继续以毫秒计算。它是有迁移代价的局部筛选，
不是完整 DAG、共享 GPU 执行下的反事实 JCT 下界。

`min_work_ratio=1`，只有严格更短且差值覆盖迁移成本与控制余量才可交接；
不存在额外 1.2 倍或 1.5 倍的工作量门槛。控制余量及最小检查间隔复用
现有工具检查周期；单 workflow 冷却和工具返回交接有效期复用普通 2 秒窗口。
保留已有有界 native 探测与迁移总量限制，作用是限制搬运开销，不增加
某个长 workflow 的准入优先级。`ready_wait_protection_ms=0`。

仍须满足实际 Host 副本、session generation、私有页、锁、DMA、输入预留
和请求未在 GPU 执行等检查。释放计划不给容量信用，实际释放后才准入。
现有预测式工具卸载继续独立工作。

## 准备和验收

`scripts/prepare_simple_path_oracle.py` 从已完成的 133 项目 FULL 未排序产物
恢复排序，并核对旧 83 项目 Oracle 的路径定义、2 秒窗口和时间系数。
保持 400 GB Host、20 个初始 workflow、平均 60 秒到达、固定 18 个测量成员
及原始 tokens、工具和依赖。它不重跑 FULL、不启动 GPU、不插入正在运行的
D3 对比队列。

CPU 检查覆盖实际控制器、长等待绕过、含工具路径排序、周期及事件 sibling
准入到 native 可服务集合、真实原生页释放和工具边界路径反转。
CPU 结果只能证明策略语义和安全约束；完整平均 JCT 收益仍需后续匹配 GPU
实验验证，不将静态排序改变直接折算成性能收益。

已执行 164 项直接相关检查和 163 项共享路径回归，累计 327 项通过，
无失败、错误或跳过。真实 133 项目配置也已在 CUDA 隐藏的 CPU 环境中
完成生产构造、原生接口挂接和有效配置核对；确认没有组合选择器，工具
边界交接、JOIN/EOS、工具预测卸载和 prepare_host 保留。
证据位于本工作树的 `experiments/reports/simple_path_oracle_20261117/`。
初次新测试缺少 fixture 导入的三项 setup 错误保留在 `related_cpu_r1.xml`，
修复后报告为 `related_cpu_r2.xml`，未把旧失败改成成功。

## 后续用户修订：1800 秒执行兜底与实验顺序

2026-11-16 PST，用户在 D3 对照因客户端 `ReadTimeout` 停在 17/18 后，
要求保留明确的 1800 秒执行兜底，并改为先执行本 Oracle、再执行修改后的 D3。
上述“关闭 1800 秒绕过”描述保留原候选历史；新实验显式设置
`BELIEFKV_AGENT_READY_SERVICE_TIMEOUT_S=1800`。

连续 ready 且整个 workflow 没有实际原生 GPU 服务达到 1800 秒后，
每次只选择一个最早超时的精确请求，复用原有逻辑超时准入出口。
该出口允许单个请求临时突破逻辑工作集预算；它不增加物理容量信用，
不绕过原生分配、锁、DMA、JOIN 依赖及首次物化许可。
实际请求选批将其移到普通候选之前，保留已保护的关键队首。
获得逻辑额度、预取或进入 active 均不清零计时。
同 workflow 任一有效请求实际获得原生服务后才清除例外，
工具/JOIN 阻塞、身份变化和退休重置对应 ready 计时。
检查只发生在已有完整控制边界，不增加独立轮询。

这不是连续老化：1800 秒之前的剩余路径分数和装入规则不变；
超时出口与正常短优先的选择次数分别记录。
它提供防饥饿机会，仍不能承诺在物理资源不足时立即执行。
因此客户端读取超时也通过新注册显式设为 14400 秒，与现有四小时
测量观察上限一致；历史注册保留原值，失败的 17/18 记录不续跑、不删尾。
少量测量尾部缺少持续背景到达不再作为阻止实验的条件，保留该诊断。

用户随后要求客户端超时保持 **3600 秒**。实际运行的 Oracle r4 与待启动
D3 均采用该值；14400 秒只保留为此前准备与失败启动的历史记录。

新兜底、旧默认、全局 Oracle、R5、原生入口、控制协议等相关 CPU 回归
858 项通过、无失败或跳过。初次缺少原生源码环境的 3 项跳过、
扩展回归的 2 项旧假设/路径失败均保留，未改写原始报告。
这不代表 GPU 收益；新 Oracle 相对匹配 Full 的完整 fixed18 平均 JCT
至少降低 2% 仍是实测验收目标。

## 实验结束后整合的终结回调修复

真实原生回调在清除完成请求的 visibility 后才通知准入层，
因此执行兜底不能只用 visibility 确认最后一次 GPU 服务。
补充通过回调已确认的完成 ID、当前请求对象、latest key 和完整请求身份
确认终结服务；旧 attempt、epoch、session、替换请求对象和不在本批次完成
列表中的对象均不给计时清零。

修复保持普通短优先、1800 秒门槛和物理容量权限不变，
仅供本轮实验全部实际退出后的线性整合使用，不属于当前运行的
`61a55c95` 或待启动的 `e117908e`。

101 项相关 CPU 回归实际通过，无失败或跳过，覆盖真实回调、终结身份、
1800 秒前后行为、全局 Oracle 和参考免费续接准入。
报告为 `experiments/reports/terminal_service_integration_20261117/related_cpu_r2.xml`；
初次未设置 `SGLANG_SOURCE_CHECKOUT` 的 94 通过、7 跳过报告另行保留，
不作为完整通过证据。
