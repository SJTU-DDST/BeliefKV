## 当前决策

暂停继续训练 workflow 工作量预测器，保留当前已验证模型和配置。
最近连续效用、配对排序、真实决策状态适配三类共 12 个 CPU 候选，没有提供可采用的
排序提升。最新启用/关闭 R5 的同版本对照观察到平均 JCT 降低 4.807688%，但它包含
集合权重和 JOIN 组合决策的共同作用，不是预测精度的独立贡献；目前仍只有单轮结果，
关闭轮还存在 187.041518 秒背景到达覆盖不足。见
[完整对照与预测诊断](../research/ranking_disabled_and_prediction_diagnostics_20261104_zh.md)。

条件允许时可以重开预测研究：有新的独立任务信息，且实际竞争现场的排序有稳定改善，
并能改变会得到后续服务的可行集合。仅数值误差下降、更换损失或增大模型不足以重开
GPU 比较。现有同单位连续 oracle 在 133 次竞争中使 30 个集合改变、15 次涉及测量
成员，只证明仍有局部选择空间，不能从这些次数计算剩余 JCT 收益上限。

用户随后要求先寻找新的设计点，并暂停接下来一段时间的 GPU 实验。
当前只推进 CPU 理论和记录分析，中央启动保护已关闭自动恢复，等待新的明确释放。
[最新双向依赖筛查](../research/compute_frontier_two_sided_screen_20261104_zh.md)
已在最新完整 R5 运行评价全部 1918 个局部候选，补齐受延后 prefill 与 JOIN 尾部变化。
典型净投影余量很小且对成本敏感，少数长 prefill 段仍有较大机会。
它尚未重放共享 GPU 队列、token 步骤、批次变化或物理增长，不能认定 D3 已成立。
同轮筛查的多 child JOIN 后 prefill 等权暴露仅 0.344104 秒，不优先推进后继前缀
提前计算。历史下文的旧非排序数据继续保留其原人群和范围。

## 第三个候选的边界

| 层面 | 当前设计或候选 | 决策对象 |
| --- | --- | --- |
| D1 | workflow 完成导向的依赖感知工作集准入 | 哪些 agent 获得 active 资格 |
| D2 | 执行需求绑定的 KV 容量周转 | 为真实消费者保留、释放和恢复哪些 KV |
| 候选 D3 | 驻留工作集内的计算推进 | 下一段算力用于哪个阶段、推进多久 |

D3 不撤销 active、不交换工作集、不主动搬运 KV。它要处理的是：候选已经通过 D1，
上下文也已由 D2 准备好，但实际 prefill/decode 次序仍可能延后模型阶段结束，进一步
延后真实工具启动或依赖解除。这里只是待验证的区别，尚不足以宣称第三个贡献。

## 为什么筛查这里

已完成 original73/Host400 的旧非排序 Full 有以下证据：

| 观察 | 数值 | 解释边界 |
| --- | --- | --- |
| 固定 18 条平均 JCT | 1081.531 秒 | 最新联合版本的 JCT 为 1061.911 秒，不能混为同一运行 |
| 关键路径首次模型服务到原生完成 | 平均 657.706 秒 | 包含自身 worker、穿插和依赖，不是纯 GPU 时间 |
| 首次 decode 后与 prefill worker 相交 | 平均 174.759 秒 | 暴露量，不是可以直接删除的时间 |
| 固定共同窗口 prefill worker 占比 | 约 37.50% | prefill 是必要工作，不代表浪费 |

## 拟比较的动作

在自然 batch 边界，只比较下一份本来可执行的 prefill 与现有 running decode batch
的一小段推进。首版不增加 decode 子批、不启用 mixed、不改变原生锁和增长检查。
无真实可执行竞争时直接沿用原生次序。

概念目标为：

```text
净价值 = 预计提前的 workflow 完成时间之和
       - 预计被推迟的 workflow 完成时间之和
       - 额外执行和控制的代价
```

两侧都包括背景 workflow；测量组身份不能用于选择。D1 的权重可以提供评价输入，
但不能将“多输出几个 token”“当前最后一个 child”直接等同于 workflow 完成。
同一 workflow 多个分支的价值也不能按请求数重复累加。

在线输入限于已经观察到的 JOIN、agent 资格、当前输入/输出进度、已经生成的动作标记、
真实前缀与增长容量，以及已有 batch 执行成本。未来输出长度、下一次工具种类、
录制 RETURN 和未来工具时长仅能用于离线 oracle。当前 DeepAgents 路径在完整消息后
发布动作，增量标记观察本身也需要实现与成本核对。

例如，假设 A 再执行 0.1 秒就能启动 4 秒外部工具，B 的 prefill 需要 1 秒：

```text
先 B 后 A：B 的阶段在 1.0 秒结束，A 的工具在 5.1 秒结束。
先 A 后 B：B 的阶段在 1.1 秒结束，A 的工具在 4.1 秒结束。
```

只有当这些阶段变化确实传到各自完整 workflow，且后续服务和干扰保持不变时，
总 JCT 才改善 0.9 秒。这个算例只说明工具与计算重叠的机制；工具返回后若仍被
同一长 prefill 挡住，或该 child 不是 JOIN 瓶颈，收益可能消失。

## 当前反证与难点

不能据此立即进入实现和 GPU 扫描：

1. 上述 500ms oracle 筛查的去重局部暴露代理合计 205.906 秒，没有支付完整的
   prefill 推迟及后续干扰。它不是平均 JCT 改善或严格上界。
2. 已生成 `</tool_call>` 的强可见信号，只覆盖 187 条不同关键路径请求，
   对应去重局部代理约 27.747 秒，且剩余输出 P50/P90 均为 1。扩大覆盖需要新的
   阶段信息或预测；不能直接把 `<tool_call>` 开始当作即将结束。
3. decode 更多地穿插可能降低 prefill 效率、增加 forward 和控制次数，或让更多
   agent 同时增长而引发容量压力。仅 TBT 更平滑不证明 JCT 或吞吐改善。
4. 旧日志的 decode 样本缺少 attempt/session 字段，逻辑前后连续不证明全过程
   物理驻留。缺失证据保持未知，不能借此授予原生执行权限。
5. 如果只有准确知道未来输出长度时才有收益，而在线信号无法保留足够机会，
   应放弃这个候选，不立即转入新一轮长度预测器训练。

分支余量调度也暂不追加投入。已有筛查只有 8 个固有路径可容纳的局部替代，
仅 1 个竞争者来自测量组，而它提前 RETURN 并不直接推进自身 JOIN。当前执行中
工具单独提供足够余量的机会为零。它仍属于 D1 的深化，见
[分支诊断](../research/ranking_disabled_and_prediction_diagnostics_20261104_zh.md)。

## 与已有方案区分

Sarathi-Serve 已用 chunked prefill 与 stall-free batching，让现有 decode 与有
token 预算的 prefill 共批。因此固定 decode 优先、缩小 chunk 或启用 mixed 不能
成为本候选的新机制。论文来源：
[Sarathi-Serve](https://arxiv.org/abs/2403.02310)。

2026-09-07 提交的 SLOWeave 预印本，已根据 decode 的下一 token deadline 和迭代
成本模型选择最大可行 prefill chunk。单纯把 2048 token 换成目标毫秒数，
同样不足以构成本候选。来源：
[Deadline-Aware Adaptive Prefill Chunking](https://arxiv.org/abs/2609.07883)。

SGLang 官方参数还记录了面向 pipeline parallelism、用拟合函数保持各 chunk 执行
时间一致的 `--enable-dynamic-chunking`。它不是本机单 GPU 已实现相同机制的证据。
来源：
[Server Arguments](https://docs.sglang.io/docs/advanced_features/server_arguments)，
2026-11-04 核对。

本候选只有证明“根据真实 workflow 阶段推进价值，比较延后两侧的完整完成影响”
比这些简单强控制额外有效，才有独立成立的可能。目前没有完成新颖性或性能验证。
通用引擎优化应同样向 baseline 提供，不把统一升级产生的速度归于 D3。

## 下一步的验证条件

先补 CPU 机会筛查，不启动单独的 GPU 参数网格：

1. 同一完整日志中，比较“保持原次序”与“提前一小段 decode”，同时移动受影响的
   prefill，保留真实请求、token、工具时长、依赖和到达。两种次序采用相同成本假设。
2. 支付被推迟 prefill 及其他受影响 workflow 的代价，沿依赖重新传播到 workflow
   完成；背景状态和测量组完整尾部都保留。不相加相关局部机会冒充端到端结果。
3. 做成本敏感性检查，并分别核对 oracle 信息和在线可见信息的覆盖。固定批次成本
   不能自动外推到变化后的形状；没有真实页与增长证据时不宣称物理可执行。
4. 只有净机会足够覆盖成本模型误差，且不依赖新增高精度预测器时，才实现有界候选，
   随其他成熟改动合并做一次完整 GPU 验证。
5. 正式验收沿用固定 18 条完整 JCT、共同墙钟输出吞吐、E2E normalized
   interactivity、长任务等待、控制 CPU 与重算。不能用 GPU busy 或物理池满替代。

因此当前保留两个已实现设计，D3 仅列为优先筛查的研究假设。准备 Host 备份的节流、
重复检查去重、普通工作集切换、分支排序，以及 kernel 参数调优均按其真实边界
归入既有设计或工程优化，不为凑第三点另行命名。
