# 恢复 Oracle 的剩余工作量短优先语义

## 为什么需要单独纠正

用户指出，尾部 workflow 分析后，Oracle 加入了老化及其他附加规则。
这项质疑成立：这些规则改变了被测策略，不能继续把所有结果解释为
“准确知道剩余工作量时，短 workflow 优先的收益”。

历史提交顺序，北京时间：

| 提交 | 时间 | 改动 |
| --- | --- | --- |
| `05749d8a` | 2026-11-15 16:52:33 | 增加 30 秒尺度 ready 等待老化 |
| `acc8926a` | 2026-11-15 17:43:54 | 原参考集占满窗口时比较额外较短候选 |
| `17b31461` | 2026-11-15 19:57:06 | 即时工具 A→B 排序也使用等待老化 |
| `17a7d0fa` | 2026-11-15 20:27:59 | 增加有界主动等待，尝试积累较大请求的额度 |
| `d6d9aa1e` | 2026-11-15 20:43:41 | 容量累积前保留已经放得下的高优先级候选 |

| `72eae3a0` | 2026-11-16 01:37:19 | 线性 JOIN 份额、工具保留分组和连续权重回退修复 |

老化的直接背景是某个较大请求出现真实准入长等待，离线加成能使它
在更多快照中入选。这个局部见证不支持把长等待保护混入短优先的定义，
更不能证明它改善完整均值。上一轮限制老化强度仍允许工作量接近的
长者越过短者；本轮严格短优先候选直接关闭该机制。

原参考窗口修复、安全 donor 检查和控制开销复用仍有各自用途，
不因为发生在尾部讨论后就全部删除。到达、测量成员和背景覆盖属于
实验设计，不能用更改工作量排序掩盖缺失的背景供给。

## 已确认的策略偏离

1. `shortest_work_first_admission=true` 不保证调用短优先实现。
   `cost_aware_maximal_admission=true` 时，控制器先走 maximal 集合分支，
   最大化 workflow 加权收益之和。多个长 workflow 的收益可以超过
   单个短 workflow。该目标有组合优化含义，但不等于严格短优先。
2. JOIN 平方覆盖率会额外压低首次推进的分支。即使改成线性份额，
   分支收益仍除以未完成成员数，可能让短 workflow 的一个 child
   输给更长串行 workflow。分支份额不应再覆盖 workflow 长短排序。
3. ready 老化、组合评分 1% 的接近容差，会允许原参考集合中的较长者
   保持优先。严格排序时不使用它们改变工作量大小关系。
4. 主动容量累积包含最短等待、冷却和最长暂缓等额外状态，
   会改变准入时机。此机制不属于普通短优先，严格候选关闭它。
5. 原参考集合会保留所有前缀检查名额。已经有八个参考成员时，
   窗口不能再比较新的更短候选。选择集合与参考集合长度相同，
   也不能直接判断为没有竞争。
6. `join_priority_pending` 的成员身份不单独证明真实 JOIN 恢复权利。
   严格候选只保留通过现有 `_protected_join()` 活体检查的权利。
7. 公共 ThunderAgent 路由器的 1800 秒超时强制激活被 Full/Oracle 继承。
   它会绕过选择器并直接设置 active。该机制早于本次尾部优化，
   不是新加的 ready 老化，但仍与严格排序不一致。

## 新候选的规则

显式设置 `strict_remaining_work_admission=true`：

```text
1. 保留已经确认、仍有效的 JOIN 恢复权利及其完整预算。
2. 普通 ready 候选按 workflow 剩余模型工作量由小到大排列。
3. 逐个检查完整资源约束，放得下就加入；放不下则尝试后面的候选。
4. 同一 workflow 的已 ready sibling 尽量相邻，允许部分推进。
5. 继续装入可执行候选，直至当前候选窗口中再无可加入的对象。
```

当前有效权重为连续剩余工作量的单调变换。严格候选直接按该权重排序，
不加等待加成，不加总不同 workflow 的投票，不用请求成本或 JOIN fanout
改变优先级。只有基础工作量相等时才沿用类别、KV 和队列顺序作为次序。
这不是“先给一个短者权利，再用加总收益改掉其余短优先顺序”。

同一次选择中，一个 workflow 仍共享一份工作量；不会因 sibling 更多
就获得多个独立 workflow 的身份。真实分支就绪状态仍决定谁可以执行，
不能等待一个尚未 ready 的 sibling 或读未来轨迹伪造 JOIN。

策略配置拒绝同时启用老化、主动容量累积、maximal 加总选择、
额外工具边界 Oracle 抢占或工作量压力扩展。Oracle 必须使用连续模型
工作量提供者，不能静默切回三档或含工具关键路径。R5 也必须声明连续
工作量读出；两个提供者使用相同的策略，预测参数和标签定义不改变。

## 候选与回退

沿用 6 个普通候选、按需最多 8 个前缀检查以及 0.5ms 软预算。
先对现有逻辑候选使用已缓存的工作量排序，再决定前缀检查名额。
原参考集合只作为原样回退，不再要求其所有普通成员占据检查名额。
有效 JOIN 必须成员仍保留在窗口，并先计入其逻辑预算。

原集合中有成员未做新前缀检查时，日志显式记录
`reference_metadata_complete=false`，参考成本不可计算。替代选择必须
使用实际成功读取的候选及完整资源检查。原生信息不足、身份改变、
必须保留 JOIN 不可放入或搜索截止时，仍原样返回原参考集合，
不能把缺少的成员默默删掉，也不能把原参考成本编造为零。
审计核对原参考成员的精确请求身份，并重放实际截止回退。

超过八个参考成员时，本轮仍保留原参考集合，显式记录
`strict_reference_exceeds_prefix_budget`，不声称完成严格比较。
现有封存的 552 次实际搜索参考规模为 1 至 7，但该日志不能证明
所有未搜索控制都处于同一范围。当前 pending 采集范围外的请求
也不属于这次严格排序的全局最优保证。

## 长等待和论文对照

严格 Full/R5/Oracle 候选关闭 1800 秒强制激活，经过一次正常选择器
就可以明确核对谁被准入。公共 ThunderAgent 对照保留原超时行为，
通过默认允许的 hook 与 Full 严格模式区分，不热改论文方法。
有限自然工作负载继续完整排空测量成员。任意持续过载下的无饥饿保证
属于独立公平性设计，不能用这个候选宣称已经解决。

工具保留权重、预测式 A→B、Host 备份、JOIN/EOS 预取、原生锁、
ACK、输入及增长预留继续工作。正在 GPU 执行的请求和 chunk owner
保持原连续性；没有新增任意 GPU 请求抢占或 KV 迁移权限。
普通窗口仍为用户指定的 2 秒，真实及时事件沿用原旁路。

## 真实快照上的 CPU 检查

`scripts/audit_strict_workflow_priority.py` 复用已有封存输入：
552 次实际搜索全部精确重放。67 次实际搜索未完成，只保留重放结果，
不把旧枚举的截止次数套给不同复杂度的新算法。以下比较限于其余
485 次完整搜索，替代算法使用不截断的 CPU 策略比较时钟。

“可行前缀优先级反转”定义：较短候选未选入，更长普通候选被选入，
而较短者能与原必须保留 JOIN 及已选的等高或更高工作量优先级成员
共同放入。不把短者本来就放不下、或必须让位真实 JOIN 的情形算进去。

| 固定快照中的选择规则 | 有反转的选择数 | 候选成对反转数 | 相对原实测改选 |
| --- | ---: | ---: | ---: |
| 原实测：老化＋平方份额＋加总收益 | 96 | 202 | 0 |
| 关闭老化，保留平方加总 | 46 | 95 | 72 |
| 关闭老化，采用线性加总 | 46 | 80 | 90 |
| 严格剩余工作量优先 | 0 | 0 | 96 |

这说明只限制老化或只取消平方都不足以实现严格短优先。零反转证明
这些固定候选中的排序语义一致，不是新 JCT 轨迹，不模拟新窗口、
队列、工具、迁移、真实服务及完整完成时间。选中对象数量的变化
也不直接证明 GPU 利用率或吞吐变化。

## 验证与实验解释

`scripts/prepare_strict_workflow_priority.py` 已从上一轮匹配参数产物准备
Oracle/R5：关闭 ready 老化、主动容量累积和加总选择，启用严格排序。
预测参数、连续工作量参照、成本测量、原始 133 个不同项目、
20 个初始 workflow、平均 60 秒到达、400GB Host 和 fixed18 均保持原值。
准备不修改排队冻结注册、不重跑 Full、不自动启动 GPU。

产物位于既有 `ready_capacity_accumulation_r1/strict_priority_review_r1/`，
最新快照结果为 `same_state_r2/report.json`，完整 CPU 来源绑定为
`bound_cpu_r1/evidence.json`。CPU 覆盖真实准入和 native 可服务候选、
八成员参考集替换、必须 JOIN、stale JOIN、1800 秒绕过、同目标匹配、
异常组合拒绝、候选窗口及精确截止回放。

剩余工作量定义继续为 `0.01*必要新增输入+实际输出`，输入在请求完成时
结算，部分输出沿用已有 128 token 进度发布。工具时间另受 D1 管理，
不把工作量代理悄悄换成真实剩余墙钟时长。批处理效率、未抢占的 active
工作、native 选批与迁移仍会影响 JCT；此候选也不是可任意抢占的理想 SRPT
或完整 JCT 理论下界。完整测量尾部必须保留，不能靠剔除长者验证收益。
