# 12 初始、平均 70 秒：修复对照完成与 oracle 启动

## 实验选择

用户澄清“暂不进行长工具替换”指保持 trace 工具时长不变。运行时 A→B 预测卸载继续启用，它是已有工具预测卸载的一部分，不增加独立关闭开关。只有存在实际可执行消费者、真实释放及完整容量和原生安全检查都通过，才将空间交给消费者；普通两秒合并窗口不应额外延迟这条路径。

本次复用 56 个完整原项目及既有工具映射，使用 12 个初始 workflow、平均 70 秒的既有到达表，固定 12 warmup、18 measured、26 background。不重跑相同对照，不同时改到 80 秒，也不更换或缩放工具样本。

下一臂选择同一负载上的匹配 oracle，用于验证剩余工作量排序。两臂均保留相同 oracle 进度记账、工具感知工作集压力、实际卸载后的资格暂停、A→B 预测卸载、prepare_host、JOIN/EOS 和 sibling 路径。两份 artifact 仅在 `remaining_work_ranking_enabled` 上不同。普通合并窗口和完整控制均为两秒，普通补位兜底为 500 ms，A→B 兜底为 200 ms。工具预取、普通恢复租约、逐层 handoff 和 mixed chunk 保持关闭。

这是机制对照，不是论文 ThunderAgent 臂，也不是完整 R5 组合评价或最优 JCT 上界。当前负载有下述未通过项，oracle 结果只能作为相同有限容量与到达条件下的诊断，不能宣称已经完成稳态负载验收。

1. 背景最后到达为 3259.858610 秒，最后测量成员完成为 4415.851888 秒，存在 1155.993278 秒无新增背景到达的尾部。背景仍在执行与背景持续到达是不同条件。

CPU 下一请求可复用前缀并集在固定共同窗口内最大约为 HBM＋Host 的 64.68%，但全测量执行区间的规则采样峰值达到 108.6834%，位于 3120 秒；9 个规则采样点超过组合容量。这里只是未来信息辅助的离线诊断，不是在线保留策略或实际物理分配证明。后半程的容量问题不能再用早期 64.68% 的前缀报告排除。

因此不能因为 paused 供给和选择机会增加就宣布负载合格，也不能将 oracle 若出现的数值改善直接推广为稳态性能。两臂保留相同容量和到达表，本轮先回答排序在这组真实竞争下如何影响完整 JCT、吞吐、迁移和前缀丢失。
