# 组合准入成本分母的离线审计

2026-11-03。回答：是否应该取消
`Score(S) = sum(q_w F_w(S)) / (epsilon + C_hat(S))`
中的成本分母，以及是否存在短 workflow 的昂贵请求被长 workflow 的
便宜请求压后。只读分析两轮已完成 Host400 R5 64 步实验，没有修改
线上调度、启动 GPU 实验或重写历史结果。

结论：成本分母确实能压过正确的工作量排序，主要表现为惩罚长 prefill；
去掉分母提高了本地选择对真实较短 workflow 的覆盖。但不能从这些
固定现场的选择与观测等待，计算取消分母后的完整平均 JCT，也不能保证
取得 1% 改善。

## 实验与分析边界

两轮均使用相同 73 个原始项目、20 初始＋mean70 到达、400 GB Host、
805198 FULL token 池、running/decode24、prefill2048、mixed off、
固定 18 个测量成员，测量工作保持 2991 请求／362157 输出 token。
重新验证完整测量组自然完成、正常尾部、实际请求回执、新鲜 idle drain
和所有 owned-process 退出。非测量组仍允许原协议的右删失。

首轮实际平均 JCT 为 1066.070725 秒，确认轮为 1093.559954 秒；
共同非排序 Full 为 1081.530918 秒。原先 64 步改善没有在确认轮复现。
这些是已执行策略的结果，均不是本次无分母策略的结果。确认轮最后
测量尾部超过最后到达 87.177219 秒，原有背景覆盖失败继续保留。

先用冻结成本和实际 cutoff 精确重放原选择，包括未完成搜索。再仅对
完整搜索比较：

- 原成本比值目标。
- 仅最大化 `sum(q_w F_w(S))` 的目标。

候选、顺序、资源、输入与增长预留、共享 extent 去重、required JOIN、
原生准入权威都保持相同。保留 S0 为初始方案、原 bitmask 枚举顺序和
1% 相对改善门槛；没有在同分时暗中重新加入成本排序。

v6 仍按完整池几何容量规划，当前 free/cold 计数没有增加。规划可行不
保证立即物理可行，也没有撤销 active 资格或改变 acting decay。

真实剩余模型工作量沿用已有观测重建：完整逻辑总量减去当时已完成
工作和粗粒度已观察输出。单位为 `必要输入增量×0.01＋输出 token`，
包含 root 和 descendants，排除工具等待、排队、迁移、额外重算。
未来标签只用于离线诊断，不用于线上决策。

## 保留实际预测，只取消成本分母

| 项目 | 首轮 64 步 | 同配置确认轮 |
| --- | ---: | ---: |
| 全部组合入口 | 8368 | 7425 |
| 缺少可重放搜索元数据 | 7796 | 6876 |
| 未完成搜索，排除目标替换 | 42 | 41 |
| 完整可比搜索 | 530 | 508 |
| 普通跨 workflow 规划容量竞争 | 145 | 130 |
| 取消分母改变选择集合 | 38 | 37 |
| 其中集合变大／变小／同大小替换 | 17／1／20 | 20／1／16 |
| 改变涉及至少一个测量 workflow | 9 | 7 |
| 比值目标严格缩小 S0 | 20 | 21 |
| 无分母目标严格缩小 S0 | 6 | 3 |
| 竞争中选中真实剩余工作最少者：比值→无分母 | 102→113 | 93→105 |

对应的最短者覆盖为 70.34%→77.93%、71.54%→80.77%。
这里是“集合包含至少一个真实最短普通候选”，不是排序准确率、
实际原生服务成功率或完整 JCT 改善率。

同大小改变均为一个成员换一个成员的跨 workflow 替换。首轮 20 次
中，14 次替换为真实剩余工作更少者，6 次更多；确认轮 16 次中，
12 次更少，4 次更多。反向变化还可能来自模型权重误差、JOIN 覆盖
收益和同分保留 S0，不能全部称为预测分类错误。

## 隔离纯成本的反向选择

采用更严格的一换一检查：

1. 被拒对象所属 workflow 的真实剩余模型工作更少。
2. 两者均是独立单成员组；不改变 JOIN 覆盖、不撤销 required 成员，
   也不以成员数量差异解释结果。
3. 只用被拒对象替换已选对象，满足原现场所有规划约束。
4. 替换后分子增加超过 1%，但因成本更高，比值不能优于实际集合。

| 项目 | 首轮 | 确认轮 |
| --- | ---: | ---: |
| 严格反例所在决策边界 | 20 | 16 |
| 去重的完整 request/attempt/session 对 | 25 | 18 |
| 其中短侧与长侧跨越冻结的真实三档门槛 | 15 | 11 |
| 涉及不同昂贵短请求／短 workflow | 13／12 | 11／11 |
| 无分母完整选择确实选入该短请求的对数 | 20 | 16 |
| 短侧属于固定测量组 | 5 | 1 |
| 两侧同时属于测量组 | 0 | 0 |
| 长侧真实直接授予且保留资格 | 25 | 18 |
| 长侧先得到后续原生有效服务 | 21 | 13 |
| 长侧先服务的观测间隔 P50 | 22.146698 s | 12.204502 s |
| 长侧先服务的观测间隔 P90 | 130.901097 s | 32.655332 s |
| 两个替换方案都满足当前 free＋safe-cold 摘要 | 2 | 1 |
| 短侧替换方案满足当前 free＋safe-cold 摘要 | 3 | 6 |
| 短侧 prefill 成本代理更高 | 25 | 17 |
| 短侧 H2D 成本代理更高 | 3 | 1 |

“较短”首先按真实剩余工作量的相对大小判定，不把同档比较误称为
短档对长档；跨档的 15／11 对另列。

以上服务间隔只计完整身份匹配的新正进度批次，长侧必须有直接授予和
保留资格。补充扫描原始 native journal 后，没有发现这些首个精确
服务之前还有身份不全但可能匹配的正进度样本。一般样本中确有不少
缺失 attempt/session 字段的 decode 记录；没有将其升级为精确证据。

这些观测说明“评分压后”有真实后续服务顺序对应，但不足以归因整段
等待：后面还有新的容量、工具、控制与工作集事件。多个对还可能共用
同一个被压后请求，不能把各对服务间隔求和再除以 18 当作 JCT 收益。
确认轮唯一短侧测量组反例中，短侧实际反而先服务约 5.996 秒，更说明
逻辑选择不等于物理服务次序。

“昂贵请求”主要指恢复／prefill／上下文成本代理较高，不等于输出更长。
25／18 对中分别有 16／11 对的短侧当前请求录制总输出也更多；输出长度
只作离线诊断，未输入原比值或无分母选择器。

## 具体实例

首轮原始 journal 的 `raw_journal_sequence=137`（从零计数）包含两个
初始 root：

| 项目 | `python_web_blog_hard_076` | `python_system_networking_medium_063` |
| --- | ---: | ---: |
| 真实剩余模型工作 | 30438.84 | 36287.02 |
| 实际概率权重 q | 0.327226 | 0.272988 |
| 需要 prefill 的输入 | 101198 token | 87667 token |
| 整组成本代理，含已有 batch | 11.771296 s | 9.504284 s |
| 原始比值，按秒计 | 0.027798 | 0.028722 |
| 取消分母后的选择 | 选中 | 未选中 |
| 原策略的选择 | 未选中 | 选中 |

两者属于同一现场的真实逻辑容量竞争，且各自方案都满足当前
free＋safe-cold 摘要。短侧较高的工作量权重仍被长 prefill 惩罚压过。
原轨迹中长侧在决策后约 45.735 秒服务，短侧约 176.636 秒服务，
相差 130.901 秒；这不是该单次选择独占造成的可消除等待。

另一个测量组例子是 `python_web_cms_expert_002` 的初始 root。剩余
模型工作仅 8664.99，当前输入 211405 token，成本代理约 42.602 秒；
竞争的 `python_ml_training_medium_087` 剩余工作 32795.86，当前新增
输入 22 token，成本代理约 1.686 秒。权重 0.507176 对 0.274019，
比值仍选长 workflow 的便宜请求，无分母则选短侧。原轨迹中短侧后续
服务晚 44.613 秒，但短侧当时尚不满足当前 free/cold 容量摘要，需要
保留原生容量等待，不能声称取消分母就会立即服务。

## 排除预测误差后的敏感性

进一步把两种目标都代入同一套离线真实工作量权重，不改变资源与 JOIN。
三档仍使用冻结门槛和 `(1, 0.5, 0.25)`；连续权重为
`1/(1+remaining/short_threshold)`。它们都不预测完整工具关键路径。

| 权重 | 首轮最短者覆盖：比值→无分母 | 确认轮最短者覆盖：比值→无分母 |
| --- | ---: | ---: |
| 实际缓存概率 | 102→113 / 145 | 93→105 / 130 |
| 真实三档 | 105→114 / 145 | 92→104 / 130 |
| 真实连续工作量 | 113→131 / 145 | 98→116 / 130 |

即使工作量排序来自真实标签，成本分母仍能显著改变本地短 workflow
偏好。因此不能把问题全部归结为预测器。但连续权重、三档权重和覆盖
函数仍是启发式，以上数值不构成最优性或整轮收益证明。

## 设计判断

“最终都要执行”不意味着执行顺序无关紧要。即使总计算量固定，先后
顺序也会改变各 workflow 的等待和完成时间；在当前系统中，先恢复哪个
对象还可能改变重算、重复迁移、batch 速度和 active 对象的服务。

因此成本值得保留为容量约束、较近收益下的偏好和极端成本保护，但当前
把“完整当前请求的恢复／prefill＋固定 64 步 batch”直接除进主目标，
没有推导为 workflow 平均 JCT 的目标函数。它容易把较短 workflow
的一次长 prefill 当作应长期回避的对象。

建议下一步单独验证“分子主导”的完整对照，保留已有容量、增长、
active 连续性、JOIN 和原生物理安全。若保留成本作近似同分偏好，应当
独立声明；本次纯无分母比较没有增加这种新规则。不要为了提升被恢复
数量盲目填满，也不能把真实短作业覆盖上升当作平均 JCT 已改善。

固定现场分析无法给出无分母的完整平均 JCT：改变首个选择后，后续
batch、驻留、工具起止、请求就绪和候选集合都可能改变。当前没有经过
校准的完整系统反事实模拟器；本次没有补造一个消除这些反馈的 JCT。
