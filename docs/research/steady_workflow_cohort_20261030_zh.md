# 持续到达下的固定 workflow 测量组

用户提出在持续到达期间只统计预先选定的一批 workflow，其他 workflow
继续提供正常背景负载。该方法适合补充当前有限批次排空实验，但不会
消除真实 workflow 长尾，也不能仅凭固定到达率宣称系统达到稳态。

## 测量协议

1. 提前冻结任务、到达表、工具时间及测量成员。到达按独立开放过程进行，
   不等待一个 workflow 完成才补入下一个。
2. 使用统一预热规则。原型可先安排8个初始workflow；正式稳态开始时刻
   需由独立校准确定，不能直接将“8个已到达”等同于完成预热。
3. 预热之后按到达顺序固定18个测量workflow，保留它们从计划到达到自然
   完成的完整JCT。不得改成最先完成18个，也不得丢掉超出统计窗口者。
4. 后续背景workflow按同一冻结到达过程继续提交，至少覆盖测量组全部
   完成之前的区间。测量身份只在离线统计侧使用，不传给调度器。
5. 不因方法运行得慢而缩减测量成员或背景工作。所有方案使用相同完整
   测量任务、背景序列、到达前缀、token、工具时间及资源配置。
6. 固定背景库/提交截止时间耗尽时，若测量组尚未全部完成，标记“持续
   背景覆盖不合格”，仍保留完整结果；不能把后续排空阶段包装为稳态。
   新扩展协议必须供全部对照共同使用，不单独补救某个方法。

背景组自身也要保留结果、错误和服务年龄，避免只改善测量组而饿死背景
任务。未完成任务不能当作自然完成。若未来选择中止背景收尾，应另行
声明为基准终止，不能隐去其未完成状态；当前未实现这种中止。

## 指标

测量组的主指标为完整平均JCT，同时报告各workflow、分位数及首次服务、
ready服务间隔。18个完整workflow只是开发样本，不能支持稳定的尾部分位
或普遍收益结论。

吞吐在两臂相同、预先冻结的墙钟窗口中统计实际完成输出，包含背景组；
decode吞吐趋势和batch分布也在该窗口中报告。不要用测量组总输出除以
最后一名测量成员完成时间代替稳态吞吐。测量组JCT与系统吞吐必须明确
各自的统计总体和边界。

检查在途/ready-paused数量、可执行agent、逻辑预算、实际HBM/Host状态、
队列年龄及其时间趋势。稳定到达不保证这些指标稳定：低负载仍会空闲，
过载则积压持续增长。后者是有限时长过载实验，不能标为稳态服务。

## 当前36项目的边界

新准备保留原18个任务，加入18个不同原项目，共36个。全部项目的root/
child实际工具执行已通过CPU检查，没有修复任务测试或改动原项目。
这为增加持续到达提供了真实候选，但尚无该人口的完整自然trace和匹配
容量标定。

如果8个预热、18个测量，36总量仅剩10个背景workflow。历史同负载Full
的P95 JCT约2064s、最大2150s；若仍以约120--133s平均间隔作量级参考，
最后一名测量对象到达后，约需16--18个背景到达再加余量，10个未必够。
这些是旧burst测量提供的容量规划线索，不是新负载的可靠JCT预测。

因此36项目先用于负载和机制开发；正式持续背景测量要预先准备更大的
不同项目库，或先缩小测量组，并验证背景覆盖。48项目可作为8预热、
18测量、22背景的初始候选规模，仍须实测确认；不能为了满足固定总量
而重复同一个项目、缩短自然长尾或关闭背景压力。

## 已核对的相关工作

- **Parrot，OSDI 2024，8.2节、图12(a)**：为chain-summary应用加入不同
  速率的背景LLM请求，报告目标应用平均端到端延迟。支持“目标应用在
  背景流量下测JCT”的思路；背景是请求流，并非与我们完全相同的固定
  workflow测量组协议。
- **PackServe，arXiv:2609.33224v1，8.1节**：构造一小时会话负载，前10分钟
  预热缓存及调度历史，评价后50分钟到达的请求。它支持按到达窗口区分
  预热和测量；评价单位是请求，也不等于前N个完整workflow。
- **Open Versus Closed: A Cautionary Tale，NSDI 2006**：明确区分独立到达
  的开放系统与按完成触发后续提交的封闭系统，并展示调度评价可能因
  两种负载模型产生显著差异。当前建议保留独立workflow到达。

以上是实验方法依据，不是任何论文已经证明本项目的新调度有收益。
本文件为协议建议，本轮未据此启动新的GPU比较。
