# 高方差负载的调度设计与驻留计算份额筛选

## 本轮结论

保留 original56、初始12条、后续平均70秒到达、固定18条完整JCT的配置。
本轮新增三个CPU只读分析器，核对真实批次、输出进度、工具替换和关键路径，未改服务策略、
任务、到达、工具时长或测量组，未启动或排队新的GPU实验。

当前最值得保留的设计是**按下一阶段成本组织批次**：让已就绪、已有agent资格、
完整前缀实际驻留的短续接，与长prefill共享输入预算，保留正常decode批次。
它仍缺少历史等待时刻的物理驻留证明和多请求prefill的增量成本，暂不作为
已通过理论收益门槛的GPU候选。

另外实际筛选了**保持KV驻留，只对短workflow增加计算份额**的方案。
在本轮局部模型中，整段优先或周期增加短批次均没有显示足够收益；
即使使用当前阶段的真实剩余输出，仍未达到筛选所需的收益信号。
不能将该局部模型当作完整workflow JCT模拟或所有执行调度的上界。

另一个贴近KV管理的候选是**阻塞窗口与消费者下一释放边界配对**。
不能只追求整个agent在工具窗口内结束；需要判断它能否推进到下一次真正
可释放KV的工具、JOIN或终态边界。已完成实际窗口审计，但完整候选与物理
可行性证据不足，暂不登记其GPU对比。

后续[阶段替代审计](tool_stage_alternatives_and_window_screen_20261101_zh.md)已完成：
144次事件替换中已有66次消费者在窗口内到达潜在释放边界，
12次已发布可改序逻辑竞争仅有6次乐观phase-fit替代，仍未证明物理可行及
完整JCT收益，暂不进入GPU比较。

后续的物理检查和下游核对已记录于
[短续接原生验证](short_continuation_native_and_downstream_20261101_zh.md)：
CPU原型可检查真实原生联合预算，但34个有逻辑就绪观察的候选即使免费
提前prefill、免费加入后续decode，局部完成提前合计也仅约1.315秒；
每个prefill后增加一步decode同样未形成足够的早完成窗口。
因此短续接共批也暂不进入完整GPU实验。本节原先的候选优先级保留为
筛选历史，不能视为已通过后续收益门槛。

## 差异有多大，等待在哪里

使用原有完整56项目的模型工作量，P90/P10为4.480，P80/P20为2.931。
分类在分析前固定为全人口模型工作量中位数20,183.205单位，单位为
`必要新增输入/100 + 输出token`，没有用一次实验的JCT来定义大小。
该划分仅用于只读解释，不向在线策略提供未来信息。

固定18条测量任务中，有11条位于短半区、7条位于长半区。按相同完整
实际最后完成依赖链得到以下等权均值：

| 关键路径分量 / 秒 | 短半区，11条 | 长半区，7条 |
| --- | ---: | ---: |
| 完整JCT | 441.654 | 2013.673 |
| 模型请求提交至首次worker启动 | 35.289 | 251.917 |
| 首次worker启动至请求完成 | 267.737 | 1143.418 |
| 其中自身worker区间并集 | 196.426 | 742.530 |
| 其中自身worker区间以外 | 71.310 | 400.888 |
| 首次decode后与prefill worker相交 | 63.982 | 386.701 |

最后一行与前面的分量存在覆盖，不能再相加。worker区间包含公共批次、
主机提交和等待，不是纯GPU kernel时间；“自身worker以外”也不是
全都可以消除的空闲。工具、事件及其他因果延迟仍在完整JCT内。

这组证据说明，长短差异没有自动转化成大量短任务准入等待：
短半区提交至首次服务的路径等待只有约35.3秒。假设长半区完全不受影响，
整体平均JCT再改善5%，需要11条短任务平均各缩短约86.2秒，相当于其
完整JCT的19.5%。仅从短半区现有首次服务前等待直接扣除，最多对应
约2.05%的整体平均值变化。后一个数只是固定已观察路径分量的算术，
不是重排全部执行后JCT的全局上界。

因此，设计应同时检查阶段推进、其他workflow的延迟、批次效率和状态成本。
仅增加总工作量差异，或再次给paused恢复排序加权，都不足以形成收益证明。

## 候选一：KV保留与计算份额分开

这个方向与此前的paused到active排序不同：长agent继续保有原资格和KV，
只在已有驻留decode集合中，有界增加短workflow的执行机会。
长agent不因该偏好触发备份、卸载或恢复。

它针对已经一起执行的竞争，而不依赖出现新的paused准入竞争。
完整original56记录有145,004个graph decode批次，其中105,980个同时包含
全人口短、长半区workflow。它们是相关的重复批次，不是独立机会。
对本轮有精确完成回执的混合集合，按执行序列均匀选择128个不同请求集合
做局部筛选；包含已完成成员的600个首次集合观察没有进入该模拟。

### 一个明确的盈亏条件

考虑两个同质、闭合的当前集合：短组有`n_s`个workflow，长组有`n_l`个；
短组还需`q`步，长组均至少还需`q`步。混合批单步为`t_all`，单独短批为
`t_s`，单独长批为`t_l`。暂时固定后续工作，不加入新请求、工具和迁移。

与先混合执行到短组完成相比，先单独执行短组的完成时间总和节省为：

```text
gain = q * ((n_s + n_l) * (t_all - t_s) - n_l * t_l)
```

所以不能只看短组获得的加速，还要支付长组失去的并行推进。存在新的
备份、恢复或控制工作时，也必须计入。保持KV只消除了这里额外迁移的
直接成本，不会使额外forward、未来KV增长和其他请求等待免费。

例如`n_s=10, n_l=2, q=10, t_all=40ms, t_s=20ms, t_l=38ms`，
在这个假设模型内有正收益；把人数改为`n_s=1, n_l=10`就变成负收益。
若大小batch的单步成本完全相同，增加短批不会加速短任务，只会延迟长任务。
这些是数学算例，不是本机GPU性能数据。

### 已完成的局部筛选

`scripts/audit_resident_decode_partition.py`使用实际width、实际graph bucket、
上下文总量和最大上下文拟合非负worker成本。先对1,178个几何cell取中位数，
避免将同一次生成的相邻token视作大量独立任务；同一请求集合固定在同一
训练或保留分组中。训练样本115,838个，保留样本29,166个。
保留分组仍共享workflow，不是独立测试集。

保留样本的绝对相对误差P50为5.85%，P90为38.96%。这个精度不足以将
百分之零点几的模型变化解释成可靠性能收益。worker模型不是kernel模型，
也没有实际资格化新的subset批次。闭合集合排空时长只用于成本筛选，
不是全程吞吐。

分析比较了：

1. 短workflow当前集合先完成，再执行长组。
2. 每8步完整decode增加1步短组decode。
3. 每32步完整decode增加1步短组decode。

初次按整个workflow的大小分类，结果没有提供推广信号。随后
`scripts/audit_resident_phase_sensitivity.py`在完全相同128个集合和同一成本下，
用**当前已驻留成员的真实剩余输出**作更有利的敏感性分析：
每个workflow以当前成员的最大剩余输出分类，避免将同一workflow的多个
成员当成多个workflow权重。原闭合集合baseline逐请求完成时刻被精确复现。

| 当前阶段敏感性分析 | 局部frontier均值改善P50 | 闭合集合排空增加P50 |
| --- | ---: | ---: |
| 短组先完成 | -3.736% | 7.179% |
| 每8步完整decode增加1步短批 | -0.430% | 0.752% |
| 每32步完整decode增加1步短批 | -0.128% | 0.166% |

三种策略都没有任何一个样本同时满足“局部frontier均值改善至少5%、
排空增加不超过2%”。5%和2%只是本轮局部工程筛选尺度，不是完整
实验的收益保证。不能将128个相关集合相加，也不能把frontier称为
真实ALL-JOIN或完整workflow完成：未来分支、后继请求、工具、到达、
物理增长压力与控制成本均未模拟。

当前阶段的长度信息比整个workflow大小更贴近当前执行，但模型仍没有
提供明显收益依据。继续增加计算份额的GPU实验暂不启动。这个判断不
证明所有驻留计算策略均无效，也不重新开启已暂停的恢复Oracle搜索。

## 候选二：短续接与长prefill共批

这是更值得保留的结构性设计。长workflow的下一轮可能只有几十token新增
输入；短workflow也可能首次携带大上下文。选批时应使用实际下一步成本，
并将已经具备资格的阶段推进落实到原生批次。

已有冻结引擎先将chunk owner交给`PrefillAdder.add_chunked_req`，然后
再选择其他prefill。chunk可能耗尽整轮输入预算，延迟后面已经就绪的
短续接。当前56项目的旧审计记录92个测量关键路径短续接与长chunk相交，
其中32个在相交区间内有至少一个active且ready的逻辑观察点。对应的
等权等待重叠分别为41.427秒和25.387秒。

这些不是可消除JCT；32个逻辑观察也不证明整个等待区间物理可执行。
后续设计应保持以下边界：

1. 在现有原生prefill边界最多检查8个已有资格、依赖满足的候选。
   完整前缀必须在此时由原生缓存确认驻留，不从之后首次服务的命中倒推。
2. 只对短输入增量共享本轮预算，例如总量不超过预算的1/8；
   按实际需要的token和原生page对齐分配，不空留固定256token。
3. 让长chunk继续获得其余预算，decode保持正常集合。未知驻留、H2D未完、
   无请求行或增长空间不足时沿用原路径，不驱逐ready peer来制造机会。
4. 保留JOIN/EOS、共同sibling准入、正常agent资格、预测工具卸载和备份。
   不新增普通预取、恢复lease或逐token全队列扫描。
5. 同批完成短续接之后，后续decode、工具开始及JOIN推进也要计入实际
   因果路径；早一次prefill不是完整JCT收益的充分条件。

此方向的局部正收益条件，是短续接提前带来的完成收益超过新增共批计算、
控制、长chunk推迟及后续竞争的代价。维持批次与只分配实际增量可减少
候选一的拆批固定成本，但多请求prefill的真实成本仍需验证。
仅靠已有41.427秒或25.387秒等待重叠，不足以登记正式收益实验。

### 进入GPU验证前需要补齐的证据

首先在相同选批边界证明“已有agent资格、完整物理前缀、可用请求行、
新增输入与decode增长空间”同时满足，并记录实际可共批输入。
随后验证原生多请求prefill是否保留正确图执行、输出统计和数值结果，
比较真实增量批次成本；这与长chunk等待重叠是不同的证据。

若上述机会和成本支持继续，再只登记一个与保留Full匹配的候选：
同任务、到达、工具、容量和固定18条完整JCT；共同墙钟输出统计包括背景。
原有吞吐窗口之外才生效的机制需事前冻结附加诊断窗口，不能在结果出来后
选择有利片段。单独检查长workflow服务间隔、额外H2D、重算与控制成本。
通用prefill组批优化本身不能直接宣称为新的agent调度贡献。

## 候选三：工具窗口与下一释放边界配对

在不改动现有长工具卸载权限的基础上，消费者选择还可以考虑两种时间：

```text
W_A = A的工具条件剩余时间
H_B = B从恢复到下一次可安全释放KV边界的时间
```

边界可以是临时child完成、真实阻塞JOIN，或者满足现有安全卸载条件的
下一次长工具等待。只完成当前LLM请求、进入一个很短的工具，不能自动
视为容量已归还。长workflow也可能具有较短的`H_B`。

若同优先级内有多个真实ready候选，已有容量不能让它们全部推进，且
迁入及备份成本已经计入，则优先考虑：

```text
P(H_B + restore_cost + release_cost + margin <= W_A) 足够高的候选
```

必须同时检查该边界真实释放多少独占状态、该agent的后续恢复成本和
其他workflow被延迟的代价。`W_A`应使用已等待时间条件下的剩余分布，
不是工具类别的无条件P90；`H_B`包含该阶段的模型工作及工具关键路径，
不能只看完整workflow总工作量或当前输出长度。未知时沿用已有选择，
不为了凑窗口抢占ready peer，也不撤销现有JOIN保护。

这是对已有工作集切换的消费者选择约束，不能把“借出”本身包装成创新。
它试图减少A工具返回后与仍会占用容量的B之间的冲突，而不是强行让A
优先执行来转移等待。

### 已完成的窗口审计

`scripts/audit_tool_window_backfill.py`复用现有工具轮次身份与依赖审计，
在完整original56记录中对应144次实际事件替换。每次均找到了同一donor
请求的完整工具轮次和consumer实际返回：

| 实际观察 | 数值 |
| --- | ---: |
| donor工具剩余窗口P50 | 4.438秒 |
| donor工具剩余窗口P90 | 18.013秒 |
| consumer到实际返回的剩余墙钟时间P50 | 116.379秒 |
| consumer在donor工具窗口内返回 | 4 / 144 |
| consumer后续自身工具区间并集P50 | 31.140秒 |
| 后续自身工具区间并集已超过donor窗口 | 107 / 144 |

consumer墙钟时间包含排队，不能当作固有剩余工作。自身工具区间并集
避免重复计算并发工具，但尚未补齐未知工具轮次和嵌套child路径；它是
描述性核对，不冒充完整剩余关键路径。144是事件替换记录，不能称为全部
工具卸载或144个独立agent。工具轮次结束也不保证之后没有其他依赖。

这组数据不支持将“整个agent在窗口内结束”作为强制门槛；下一阶段应比较
`H_B`及其可释放状态。也不能据此声称换一个consumer就一定降低JCT。

额外的同文件只读核对找到32条已发布free-capacity选择记录。以同一
实际被授予请求、grant到替换之间0至50毫秒为对应规则，144次替换中有
18次能对应选择记录，12次带有可改序且无受保护JOIN的逻辑竞争。
结果保存在`backfill_choice_summary.json`。缺失记录不等于不存在其他候选；
这是有界候选观察及逻辑额度，仍不证明替代对象物理可执行。

因此，这个方向值得保留为阶段级KV管理设计，但需要先补齐候选的下一
释放边界、当时实际准入和回收成本。当前不为它重跑完整恢复Oracle或
启动新的GPU参数搜索。
