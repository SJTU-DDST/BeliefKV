## 周期维护的实测成本

真实实现每 100ms 最多处理 8 个等待上下文，每个上下文再按
150/500/1000ms 退避。相关历史修订可以提前触发重算。
等待上下文分组有缓存，统计刷新不逐次读取原生 KV 祖先路径。
这些限制约束重算量，不代表整个维护调用具有固定最坏耗时。

CPU 测量直接导入历史冻结应用，使用 110 个上下文、8 个活跃工具、
64 个已完成同类样本及真实固定 TraceLab prior。每个情形预热 25 次后
测量 300 次，使用调度线程 CPU 时钟；启用日志的情形使用真实异步写线程。

| 调用路径 | 调度线程 CPU P50 | P99 |
| --- | ---: | ---: |
| 未到维护时刻 | 0.894us | 2.903us |
| 到维护时刻，但各上下文仍在退避 | 62.938us | 79.333us |
| 重算 8 个预测 | 1.228ms | 1.326ms |
| 重算 8 个预测并提交真实异步日志 | 1.811ms | 2.041ms |

日志情形的回调 wall P50/P99 为 1.844/2.427ms，观测最大值
12.568ms。重新构建上下文索引的 8 预测情形 CPU P50/P99
为 1.246/1.450ms。

这是 CPU fixture，未包含原生缓存、DMA、物理卸载、非空恢复租约、
并发事件 drain 和整个调度器。策略单调时钟固定，真实 CPU/wall
计时正常；构造 fixture、历史和重置期限不计入回调。不能将这些
样本乘以历史调用次数，声称得到历史总成本或可消除 JCT。回调也可能
在提交 forward 后运行，其 CPU 时间并不等于 GPU 空闲。

历史完整运行未启用 shared scheduler profile。日志中
0.161ms/forecast 是后台写线程的采样 CPU 均值，不是预测器或
调度线程开销，不能用它替代上面的测量。

证据：
`experiments/reports/tool_online_refresh_20261027/measure_refresh_cpu.py/.json`。

## 同类工具为何会后来获得概率资格

当前合成网络场景的可观察类别为 WebFetch/WebSearch。冷启动时同类
调用共享 prior；后续还利用当前 workflow/run 已完成的同类工具历史，
以及已经等待多久仍未返回这一事实。没有利用某次采样的未来完成时间，
也没有从原始 execute 命令语义预测独立随机抽到的持续时间。

令类别生存函数为 S，已观察等待为 t，实际需要覆盖的迁移时间为 C，
相关量是：

```text
P(T > t + C | T > t, category) = S(t + C) / S(t)
```

例如某类 80% 在 0.2s 完成、20% 在 30s 完成。开始时继续等待
1s 的概率只有 20%；若 0.3s 仍未返回，剩下的样本全部属于长调用。
因此同一次工具可以后来才通过卸载概率门槛。这个概率对一般分布
不保证随 t 单调增加；历史更新也可能改变估计。类别、历史和已等待
时间相同的调用仍给出相同预测，不是逐调用语义识别。

完整日志记录 16773 份预测、2670 个实际等待组，其中 887 组有多份预测。
使用当前冻结 CDF 语义，在每份预测签发时检查“未来 1s 继续阻塞
概率至少 90%”，208 组从首次未通过变成后来通过。例如同一次等待
约 560.251ms 后，未来 1s 返回概率从 0.220761 降为 0.003036，
对应继续阻塞概率约 77.9% 到 99.7%。
同 scope 不能证明历史没有变化；这不是只由 elapsed 变化造成的
受控实验。

这个 208 仅是固定 1s、90% 的 forecast gate 变化数，不是完整
动态迁移成本、剩余尾部支持、Host/HBM 容量、所有权和 native 安全
检查的通过数，更不是 208 次实际或盈利卸载。

`NativeToolWaitHint.release_probability_within(now_ms=...)` 本来就会
对已有 CDF 按已等待时间重新条件化。因此仅为观察时间流逝，不需要
反复重建完全相同的预测。此前真实缺陷是 Full 没有续发预测，导致
1--2s TTL 后丢失有效授权。优化方向应保留修复，区分历史变化、
授权续期、尾部支持和概率查询。复用旧分布还必须验证 hybrid 混合、
fallback 及支持检查等语义，不能直接无限延长旧 hint。

证据：
`experiments/reports/tool_online_refresh_20261027/refresh_audit.py/.json`。

## 3.91% 到 3.44% 的实际变化

| 配置 | 平均 JCT (s) | 全程输出率 (token/s) | 相对 V345 JCT 改善 |
| --- | ---: | ---: | ---: |
| 准入前预测卸载，716ef9a3 | 1631.194643 | 238.499008 | 3.910794% |
| 离散 CDF 修复，c04a47e5 | 1635.620442 | 236.597296 | 3.650082% |
| 在线周期刷新，29c58c8b | 1639.208934 | 236.448501 | 3.438694% |
| ThunderAgent 工具衰减，V345 | 1697.583645 | 233.371801 | 对照 |

相对 3.91% 的一轮，刷新版平均 JCT 增加 8.014291s，即 0.491314%。
相对直接前驱 CDF 修复版，只增加 3.588492s，即 0.219396%。
因此前者不是刷新一项的干净消融；两次改动和执行顺序均影响比较。
每个配置只有一次完整执行，既不能把回落全部归因于刷新，
也不能在没有重复证据时直接称为噪声。

末次记录的累积状态计数如下。这些完整文件的最后 runtime snapshot
`final=false`；它们不是 shutdown-final 计数，但完整工作、实际成功退出
和 idle drain 有独立证据。

| 观测 | 准入前卸载 | CDF 修复 | 周期刷新 |
| --- | ---: | ---: | ---: |
| 接受的工具预测 | 2668 | 2679 | 16773 |
| 过期预测清理 | 881 | 881 | 52 |
| 工具预取扫描 | 3690 | 3939 | 13160 |
| 预测物理释放事件 | 41 | 64 | 179 |
| 预测物理释放累计 GB | 0.392724 | 0.786629 | 12.311593 |

新增预测会重置 `_tool_prefetch_next_ms`，是额外下游控制工作的候选来源；
这几轮没有实际工具预取复制，不能将增加扫描量解释为预取收益。
刷新相比直接前驱，完整 H2D 从 2629.177737GB 增到 2648.332960GB，
约多 19.155223GB；D2H 从 1109.291434GB 降到 1101.094158GB。
这是实际迁移变化，但复制总量/stream 时间不是暴露等待，
不能直接转换成 3.588s JCT 的归因。释放量增加本身也不是净收益。

现有证据支持“刷新修复了资格过期，并增加了控制工作与实际预测卸载”，
尚未支持“周期重算改善净 JCT”。下一步应核对当前联合 Full，
再决定低成本复用、按需重算及预取检查期限是否值得改变；
不能为归因而改动正在运行的冻结应用或提前再启动 GPU 实验。
