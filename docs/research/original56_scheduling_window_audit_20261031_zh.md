# 70秒控制的调度窗口与周期外准入

## 结论

用户指出调度窗口过小可能让paused候选来不及积压。源码与日志支持其中
一部分：当前Full在请求注册、模型完成、工具/JOIN返回等事件处立即
尝试补位，500ms只是兜底，2秒周期控制不是所有准入的唯一入口。
只用周期竞争次数判断整个系统选择机会不足，证据不完整。

这并不证明扩大到5秒会降低JCT。延迟可立即执行的请求，会增加自身
等待；相邻到达的多个请求也可能全部放得下，没有选择代价。实际要检查
的是同一决策时刻多个合法ready候选分别放得下、合起来放不下，以及
选择是否改变后续真实服务。不能把人为排队或paused表变长当作收益。

## 完整共同窗口的资格授予

范围保持原412.944491--1841.814938秒，未改变运行中的调度或到达表。
独立封存周期外与周期内明确记录的逻辑授予，结果如下：

| 入口 | 保留的资格授予人次 |
| --- | ---: |
| 普通事件/兜底补位 | 94 |
| sibling共同准入 | 45 |
| JOIN阻塞额度交接 | 24 |
| JOIN免费额度 | 12 |
| 周期恢复且压力处理后仍保留 | 104 |

周期外合计175次，周期内104次。它们是资格授予人次，不是唯一agent数、
物理分配、GPU首服务或独占收益，可能存在同一对象的再次授予。

窗口内119次首次注册在原注册记录时均为inactive，其中96次在下一次
周期控制前得到资格，约80.67%；随后授予路径为普通补位67次、sibling
29次、周期恢复23次。首次注册到资格授予中位数0.082859ms，P90约
644.758ms，95次小于1ms。完整注册后尚未观察到授予的记录为0。
首次注册处的短暂inactive不能直接称为持久积压；后续调用真正进入
paused的起点没有被这项统计重建。

原始策略的`others_waiting`还会看到inactive但未必application-ready的
其他program，因此首次注册标记为paused也不意味着存在多个真实ready
竞争者。必须结合后续事件与容量状态判断。

## 扩大窗口能证明什么

将已经发生的周期外授予时间，按固定窗口起点分别划入0.5/2/5秒桶：
含不同workflow接收者的桶分别为7/15/30个，对应17/34/77次资格授予。
扩大观察范围确实会把更多不同workflow放进同一桶。

但这只是时间重分桶：候选未必同时ready，期间容量也会释放，不能据此
断言它们在一个更长调度周期中会竞争，更不能把它当作5秒调度的JCT
模拟或oracle收益。这里没有执行新的GPU或调度周期实验。

## 源码行为和下一步

- `ReferenceFreeContinuationAdmission.registered/completed/events`均可立即
  调用补位；`tick`中的500ms检查只是兜底。单独改变2秒工作集控制周期，
  不会关闭这些即时入口，也会改变acting decay和预算回收时机。
- 当前8候选检查上限决定一次扫描能看到哪些等待者，本身不决定实际
  paused队列是否形成。它与时间窗口是两个参数，不能混称。
- 已实现、尚未在这份负载上取得GPU收益的全局oracle使用
  `DeferredFreeAdmission`：事件只置dirty并记住候选，在下一次native
  调度边界统一尝试。它没有强制等待整个500ms或2秒，JOIN优先及已有
  active连续性继续保留。
- 后续判断先覆盖首次注册、普通补位、sibling、JOIN与周期入口，
  检查真实有约束的选择与后续服务。不能继续把周期入口的0次竞争当作
  全系统0次选择机会，也不先把控制周期放大来制造积压。

12初始/平均80秒候选仍只是CPU准备；新的证据要求在推广该候选或更换
负载前，把周期外候选消耗一起审查。当前70秒实验保持冻结，固定18项
自然完成后再核对JCT及关闭。

证据：
`experiments/reports/remaining_original_projects_20261030/mean70_window_r1/scheduling_window_audit.json`，
保存所有119次首次注册的后续授予、入口统计、时间桶及独立JSONL前缀。

## 固定测量组完成后的复核

70秒控制已按原schema2协议完成18个测量workflow、2819个请求及362072个
输出token；平均JCT为931.500654秒，最后测量完成4425.261825秒。56个
workflow均已到达，51个自然结束，5个非测量workflow明确取消。独立
`verify_measured_execution`重验原token/停止回执、两份新鲜idle快照、
停止证书及实际进程退出通过。没有把原supervisor的预期中断改写成全56完成。

完成后的分阶段周期审计如下；这是同一次控制的不同观察范围，不能相加：

| 观察范围 | 周期控制 | 决策前有ready-paused | 跨workflow逻辑集合竞争 |
| --- | ---: | ---: | ---: |
| 原共同吞吐窗口412.944491--1841.814938秒 | 703 | 80 | 0 |
| 首个测量到达至全部测量完成 | 1957 | 657 | 34 |
| 共同窗口结束至全部测量完成 | 1254 | 577 | 34 |

因此不能将共同窗口的0次周期竞争推广到整个JCT阶段。共同窗口保持不变，
JCT仍包含后续全部执行；上述完成依赖的跨度只作诊断，不替换公平吞吐窗口。
背景最后到达3671.178788秒，仍缺少754.083037秒的测量尾部到达覆盖。
共同窗口ready-paused快照81/1384，即5.8526%；原验收拒绝仍保留。
最终9408份同session前缀探针的旧输入丢失代理为0；其他Host块重算
归因仍独立报告，不能由此声称绝对零重算。

## 已补充的有界准入观测

共享的免费额度授予在改变active状态前，观察实际dispatch检查的候选，
将普通补位、sibling、免费JOIN及通过此helper的交接分别关联至原授予。
直接授予没有实际dispatch窗口时，只检查pending索引前8名并明确标注；
选中成员始终列入。它不覆盖所有非免费donor交接，不能宣称全系统完整覆盖。

观测沿用原`_candidate`的只读合法性检查，保留完整预算、JOIN保护、
原选择次序和每轮授予上限，不改变资格或发起传输。只有出现跨workflow
候选分别可放入、总和超过预算时才增加冲突日志。单workflow键窗口直接
返回；未观察成员数通过有界成员查找计算，不遍历整个pending索引。
同一dispatch的多次grant按dispatch序号去重，warming/受保护JOIN与
普通ready竞争分开。逻辑冲突不证明物理容量、真正模型服务或JCT收益。

`audit_free_capacity_choices.py`校验观测与原grant的成员、容量和时钟，
重算冲突及保护分类，并在最终状态存在时核对累积计数。旧f6控制没有
新增观测，完成审计结果为`unobserved`，冲突数为null，不能伪装成0。
本次未为获得观测而改动运行中的冻结源，也未启动新GPU实验。

CPU微基准复用真实Full准入helper及真实异步writer，native缓存为CPU
stand-in，固定8名候选，每种配置3轮、每轮1000份记录及16次预热：

- 同workflow快速路径主线程中位额外开销2.16--2.92us。
- 跨workflow全部可容纳时103.19--107.41us。
- 存在容量冲突、追加关联日志时88.83--92.16us；含原授予/日志enqueue
  的整段主线程P99为133.62--138.28us。
- 含后台writer排空的总进程CPU差值原样保存。同workflow第一轮出现
  118.60us/次离群差值，另两轮为1.79/2.93us；不以单次微基准代替
  实际运行累计控制成本，也不隐去该离群值。

证据在同一父实验目录的`mean70_window_r1/free_choice_cost_cpu.json`及
`measured_cohort_complete_original56_mean70_r1/{cohort,periodic_phases,free_choices}.json`。
源码绑定回归结果另存`free_choice_bound_cpu_r1`，不能用这些CPU观测宣称
新的GPU负载已经通过或oracle已经改善JCT。

该源码绑定回归实际通过5964项及23个子测试，保留全部5933项此前身份，
无失败、错误或跳过；2225项源码输入及原生树在执行中未变化。早期定向
测试的12项失败来自测试writer缺少`close`，已修正fixture；后续源码
绑定结果覆盖修正后的完整实现，不将该失败解释为GPU或调度回退。
