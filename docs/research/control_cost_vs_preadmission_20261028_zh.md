# 最新分组版与准入前卸载版的控制开销核对

现有证据不足以把 JCT 回退的主因判为新增控制开销。更直接的观测是：
相近计算形态的 decode worker 均值基本一致，但关键请求参与的批次区间
和服务间隔变长，同时迁移行为发生变化。完整控制成本没有被历史运行
直接计量，因此也不能宣布控制开销已经排除。

本文比较准入前卸载版 `716ef9a3e4ad` 与最新已完成分组版
`913e3238b84b`，原生树分别为 `11b84f7c3198` 和 `2ce5e5389979`。
两者均为完整 18 项目、3674 请求、145565966 输入及 549671 输出 token，
V311 工具时间、相同容量、running/decode24、seed21 及原始停止；
保留全部正常长尾。18 条关键请求链也逐项一致。
当前新增 sibling service/capacity 候选尚未进行 GPU 实验，不属于这次回退。

## 24.98 秒的准确含义

这是关键路径上的 2973 个工具后继，分别求和后再按 18 个 workflow
等权平均的首次 `run_batch` 入口到 native 完成增量，不是单个请求
多耗时 24.98 秒，也不是整轮独占控制 CPU 时间。

| 工具后继关键路径分量/s | 准入前卸载版 | 最新分组版 | 增量 |
| --- | ---: | ---: | ---: |
| prefill 成员 worker 区间并集 | 16.118585 | 15.431237 | -0.687349 |
| decode 成员 worker 区间并集 | 624.327388 | 638.928906 | +14.601518 |
| 不属于该请求成员区间的时间 | 144.353003 | 155.420327 | +11.067325 |
| 首次 launch 到完成 | 784.798976 | 809.780470 | +24.981494 |

各行使用请求真实生命周期裁剪后的区间，并集避免交叠重复计费。
worker 区间包括运行时、依赖等待及交叠处理，不等于纯 GPU kernel。

全部关键请求的首次 launch 到完成增量为 22.483493 秒；提交到首次
launch 减少 6.046348 秒，其余事件净减少约 0.147351 秒，最终平均
JCT 从 1631.194643 增至 1647.484437 秒，即增加 16.289793 秒。
不能把工具后继的 24.981494 秒再加到这些整体分量上。

## 相近 decode 形态未显示普遍变慢

完整 decode worker 累计时间从 1576.540814 降到 1556.110380 秒；
worker 加权 batch 从 8.274797 增至 8.565581。固定输出下，全局
worker 输出率从 346.325953 增至 350.872925 token/s，但这不保证
每条 workflow 的关键路径更快。

重新读取并核验两轮全部原始 worker 行，按实际 batch 大小、
2048-token 平均上下文档位和实际 CUDA Graph 状态匹配。
每个共同档位对两侧使用相同的 `min(旧样本数, 新样本数)` 权重。

| 每侧每档最低批数 | 共同档数 | 共同 batch 权重 | 旧均值/ms | 新均值/ms | 新增量 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1 | 381 | 64198 | 16.750801 | 16.751261 | +0.002743% |
| 16 | 307 | 63610 | 16.726779 | 16.721043 | -0.034290% |
| 32 | 256 | 62443 | 16.696928 | 16.701475 | +0.027233% |
| 64 | 207 | 60224 | 16.676741 | 16.681681 | +0.029625% |
| 128 | 132 | 53294 | 16.142481 | 16.177680 | +0.218055% |

这不支持“所有 decode 步骤普遍被新增逻辑显著拖慢”的解释。它支持
先检查 batch 组成和服务落在哪些关键请求上。这里仍是粗粒度匹配的
描述性均值，并非相同批次、独立消融、纯计算时间或控制成本上界；
未匹配档位仍保留在完整指标中。

## 多出的服务间隔也不是直接测到的 CPU 空转

使用全部 100176/94898 个原始 worker 区间建立全局并集，再与每个
请求首次 launch 到完成的真实区间求交，最后扣除该请求自己的成员
区间。2973 个关键工具后继的新增 11.067325 秒全部落在其他 worker
记录区间之内；两轮这些生命周期内的全局 worker 并集之外时间均为零。

这只说明不能把这 11.07 秒直接标作“GPU 等控制逻辑的空白时间”。
其他 worker 的区间本身也可能含 CPU 处理、传输依赖或等待，不能
据此声称 GPU 一直在执行有效 kernel，或将它全部归因于公平性、
抢占或某一种服务策略。

## 历史控制计量的覆盖范围

两轮分别有 2237/2248 个控制状态快照，`profile_shared_path` 全部为
false，记录的细分 shared-path phase 数均为零。历史独占控制耗时
保持未知。后台写线程的采样计时不属于调度线程，不能用于替代。

原生 prefill turnover 探针确实记录了调度线程 CPU，排除独立启动
预热后，两侧分别有 235/237 个真实工作样本：

| 抽样阶段 | 准入前卸载 CPU 均值/ms | 最新分组版 CPU 均值/ms |
| --- | ---: | ---: |
| selection | 53.472004 | 59.479750 |
| post-launch physical | 0.440667 | 0.536311 |
| result processing | 63.483543 | 47.658766 |
| run_batch | 12.530145 | 9.019192 |

选批确实变贵，结果处理则变便宜。它们来自不同的稀疏 prefill 样本，
阶段存在嵌套，既不能相加当作独占总额，也不能外推全部 decode 步骤。
这不构成普遍控制回退的证据，也没有排除特定 JOIN/Host 检查的成本。

最后记录的预测接受数从 2668 增至 16750，维护 sweep 从 15694 增至
24872，预测卸载 context 检查从 166 增至 1456；工具预取检查则从
3690 降至零。这些说明控制工作分布变化，不等于已测 CPU 时间；
末次状态 `final=false`，也不是 shutdown-final 计数。

23 次分组 handoff 从 native pair-submit 时间戳到 journal 的 wall
总计为 22.954346ms，P50 0.925293ms。这一小段记录不支持单独解释
24.98 秒；它不包含此前的候选规划、失败检查或异步后续成本，
也不是完整提交路径的独占 CPU。

## 对下一步的影响

本轮比准入前卸载版多 73.381675GB H2D 和 142.161052GB D2H；
JOIN 后继的关键路径提交等待减少 54.159928 秒，工具后继对应等待
增加 52.094220 秒。局部 JOIN 推进与更高全局 worker 输出，未转化
为更低平均 JCT。

应优先核对服务集合变化及实际切换代价，特别是工具预测卸载是否为
真实等待消费者提供了容量、之后是否过早召回原 owner，以及 JOIN
恢复与其他 ready agent 的服务如何交错。不能靠强行提高工具后继
优先级解释或修复此问题，那会同时改变其他 agent 的服务。

下一次正式比较应同时记录低频、可扣除嵌套的控制 wall/thread-CPU
时间，并保留 forward 提交与完成边界，区分计算重叠期间的 CPU
工作和真正推迟下一次提交的 CPU 工作。当前 `HotpathTiming`
使用 `perf_counter_ns`；即使启用，也不是线程 CPU 或 GPU 空闲计量。
不能只打开一个 wall profile 就将所有记录值当作可消除的 JCT。

## 证据与执行

新增两份只读 CPU 算子均已完整执行，核对原始文件大小、SHA256、
时钟域、请求身份、关键链及分解守恒：

- `experiments/reports/tool_offload_before_admission_20261027/control_regression_audit.py/.json`
- `experiments/reports/tool_offload_before_admission_20261027/control_gap_activity_audit.py/.json`

第二份算子复用既有 `EnvelopeIndex`。系统 Python 的首次执行缺少其
传递依赖 numpy，随后在已有 CPU plotting 环境中完整通过，未安装
或更改 serving 依赖。没有启动 GPU、修改生产策略或创建新主版本号。
既有区间并集、请求生命周期及几何匹配检查共 45 项通过，记录在同目录
`control_regression_helpers_cpu.xml`。
这些单次组合比较不提供独立因果归因或重复性能验收。
