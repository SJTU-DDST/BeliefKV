# 最新 Mean60 Oracle 与 FULL 的 JCT 差距诊断

本报告针对截至 2026-11-15 最新完成的
`workflow_original133_host400_mean60_competitive_window_oracle_20261115_r1`，
参考组为 `workflow_original133_host400_mean60_full_20261113_r1`。
这是 133 条 workflow 的到达计划，不是此前的 83 任务实验。
两组均有 20 条预热、固定 18 条测量 workflow，其余为背景；平均到达间隔
60 秒，Host 400 GB，running/decode 24，prefill chunk 2048，
FULL 设备池 805,198 token。所有 18 条测量 workflow 均完整结束，未删除正常尾部。

## 结论

最新 oracle 的平均 JCT 比 FULL 长 **3.3243 秒，或 0.2608%**。
本轮能确认的是：准确的剩余模型工作量在受限准入选择中改善了一部分服务前等待，
但没有减少后续服务间隔和大上下文请求的容量竞争，最终收益被抵消。
这不是已证明的稳定显著回退，也不说明完整信息的最优调度不如 FULL。
当前 oracle 提供的是剩余模型工作量真值，不是最优端到端调度器。

不能用不同生成工作量解释这次差距。两侧固定测量请求均为 2,991 条、
362,157 个输出 token，逐请求的 workflow、invocation、context、epoch、
prompt token 数、output token 数一致。新增核验逐条对齐原生服务输出和完成收据，
并重算了两侧完整原生审计日志的 SHA-256，与已封存路径证据一致。
这不把固定逻辑工作量等同于相同物理恢复量或相同实际计算量。

| 指标 | FULL | 最新 Oracle | Oracle 相对变化 |
|---|---:|---:|---:|
| 测量平均 JCT / s | 1,274.8335 | 1,278.1578 | +0.2608% |
| 测量 P95 JCT / s | 3,417.2544 | 3,443.1429 | +0.7576% |
| 相同窗口系统输出吞吐 / token/s | 342.2093 | 338.0482 | -1.2160% |

公共吞吐窗口为到达时钟的 [47.7367, 1404.8184] 秒，含预热、测量和背景请求。
它是固定公共窗口，不代表全部测量 workflow 生存期的稳态。
JCT 则按完整测量生存期统计。两个范围不能混用。
背景到达计划的末次到达为 6757.87 秒，两侧最后测量完成分别为
5842.31 和 5966.47 秒，不能套用旧实验背景到达表过早结束的解释。

## 差距发生在哪里

沿每条 workflow 实际最后完成的依赖路径拆分，并对 18 条取平均：

| 路径组成 / s | FULL | Oracle | 差值 |
|---|---:|---:|---:|
| 请求提交到首次原生 launch | 292.4276 | 287.3097 | -5.1179 |
| 首次 launch 到原生完成 | 710.1071 | 721.6900 | +11.5829 |
| 其中：请求参与的 worker 区间并集 | 576.9802 | 575.5236 | -1.4566 |
| 其中：上述区间以外的完成前墙钟 | 133.1269 | 146.1664 | +13.0395 |
| 路径上的工具结束事件段 | 228.0508 | 224.8667 | -3.1841 |
| 其他事件和派发 | 44.2480 | 44.2913 | +0.0433 |
| 合计 JCT | 1,274.8335 | 1,278.1578 | +3.3243 |

两个“其中”行是第二行的分解，不能重复求和。
新增服务分解把明确包含该 request 的原生 worker 区间裁剪到首次 launch 至收据完成，
合并重叠区间后取并集。因此它计入共享 batch、引擎等待和控制，**不是 CUDA
独占计算时间**。补集可能包含其他 batch、prefill 交错、再次等待和完成处理，
不能直接全部命名为 paused、KV 传输或某一函数开销。

这个分解给出的明确定位是：平均首次服务前等待略有改善，
平均首次服务后、请求未参与任何 worker 区间的等待增加更多。
不能把 +11.58 秒全部解释为模型计算变慢或预测计算开销。

## 大上下文的容量准入问题

desktop_021 有两条可直接核验的长等待请求：

| 请求 | Prompt / token | 完整逻辑准入预算 / token | FULL 等待 / s | Oracle 等待 / s | Oracle 逻辑满足的观测 | 最终准入到首次 launch / s |
|---|---:|---:|---:|---:|---:|---:|
| epoch 42，输出 33 token | 248,234 | 248,334 | 70.864 | 584.372 | 6 / 262 | 1.706 |
| epoch 65，输出 75 token | 248,618 | 248,718 | 6.211 | 270.626 | 4 / 124 | 2.321 |

单条请求的完整逻辑预算约为设备 FULL token 容量的 30.8%。
两条等待期间分别有 97.71% 和 96.77% 的 ready-paused 控制观测不满足
单请求逻辑准入预算；这不是“物理 HBM 在这些时间里全被计算使用”的证明。

少数逻辑满足的时刻也不保证能被选中：第一条首次逻辑满足在提交后 43.43 秒，
第二条为 11.28 秒；它们还受物理前缀可恢复性、候选窗口、组合选择和 reference
回退约束，不能声称等到最后才首次有空间。第一条的 6 次逻辑满足中，
2 次搜索超时回退、1 次 reference 回退、2 次其他选择结果、最后一次获选；
第二条的 4 次逻辑满足中，前 3 次没有选它，最后一次获选。
这些记录不证明未选时它已经具备完整物理可行性。

两条最终都是由 oracle 组合选择加入 reference 以外的候选；
获得准入后很快开始服务。不能将数百秒等待归为“oracle 选中了，但 native
FIFO 一直没有执行”。这两条等待增长也不能直接相加当成 workflow 的净回退，
因为同一 workflow 的其他请求存在补偿；净服务前等待只增加 140.413 秒。

## 为什么有真值仍没有收益

实际执行配置为 `workflow_continuous_model_work_combination_oracle_v1`。
它使用所有剩余请求的输出工作和 0.01 权重的必要输入增量，连续更新模型工作量，
按 `1/(1+remaining_model_work)` 构造权重，并叠加 ready 等待老化。
当前排序不使用未来工具时长，也不优化真实剩余墙钟关键路径。
长上下文恢复、上下文对 decode 的影响、并行 JOIN 关键路径，以及未来 batch
之间的相互影响，都不能由一个准确的剩余工作标量自动解决。

执行策略是在现有准入边界选受资源约束的 maximal feasible set，
保留 JOIN 权利、active 连续执行以及原生容量判定。候选默认 6 个、最多 8 个，
子集搜索预算 0.5 ms。30 秒是老化权重的尺度，并非 30 秒后保证准入。
它没有全局 SRPT 的抢占或为大请求强制腾出容量的权限。

完整记录有 18,796 次组合调用，552 次实际搜索、267 次选集变化，
新增 279 个相对 reference 的被选 agent episode。其中 272 个来自周期准入、
7 个来自空闲派发，全部有对应的实际服务证据；这是 episode 数，不是 279 条
独立 workflow 或 279 个独立 JCT 收益机会。
2,927 次周期控制中有 932 次虽然存在 ready-paused 请求和剩余预算，
却没有单个 application-ready 候选满足完整逻辑预算。
准确排序能改变的只是部分控制时刻。

在共同窗口中，decode 服务时间加权 batch 为 15.8634 与 15.5204，
oracle 低 2.16%；decode worker 时间/输出为 1.7141 与 1.7465 ms/token，
oracle 高 1.89%。请求 active-ready 时间加权数量为 17.2782 与 16.4230，
ready-paused 为 3.5691 与 4.0840。排序改变并未转化为更多并行有效服务。
这些是观测到的组合与服务效率差异，不是仅凭 trace 得出的纯策略因果分摊。

## 已核对的其他解释

- 控制计算：共同窗口 oracle 组合控制 CPU 累计约 0.514 秒，
  workflow-size 控制约 1.203 秒，FULL 后者约 1.305 秒。
  tool-event replacement CPU 分别约 22.010 与 24.833 秒。
  某些计数相互嵌套，不能求和；这些计数没有覆盖所有系统成本，
  但不支持“oracle 排序额外计算了几百秒”作为解释。
- 原生重算：末次原生累计计数的已驱逐 FULL 再访问归因为
  FULL 重算 51,364 / 复用 57,653,247 token；
  oracle 重算 62,764 / 复用 59,744,979 token。
  重算占这些再访问归因 token 的约 0.089% / 0.105%，不能解释为大量失去前缀。
  这不是所有重算率；两组观察终点不同，不能用这些累计量做严格等窗口增量归因。
- 传输：末次累计 FULL H2D/D2H ACK token 为
  FULL 112,798,826 / 75,017,885，
  oracle 117,259,566 / 78,314,139。oracle 的累计传输更多，但生存期也更长；
  不能据此断言多出的迁移造成了多少秒 JCT 回退。
- native 选批：760 个完整观察的多 workflow 被选窗口中，664 个最短 workflow
  已在第一波得到服务。剩余 96 个窗口中最短者的相对首次服务延迟最大约 1.87 秒。
  这是重复窗口诊断，不能累计为独立可消除 JCT，但不支持普遍被 FIFO 阻塞。
- 比较范围：本次 FULL 与 oracle 的合同明确标记
  `matched_pair_changes_only_remaining_work_ranking=false`、
  `ranking_gain_isolated=false`。它们还包含组合、老化和候选窗口的变化，
  不能将全部差距归因于把预测改成真值。
- 单次运行：当前没有配对重复样本，不对 0.26% 的差距声明统计显著性。
  原始 133-task oracle 和 benefit oracle 的均值还分别比此 FULL 低
  3.17 秒和 5.29 秒，因此不支持“oracle 总是更差”的概括。

## 补充：为什么不违反短任务优先的最优性

上一版的路径分解定位了差距，但不足以解释 SJF/SRPT 理论与实验的关系。
最关键的补充是：本轮实际运行的策略不是严格 SJF 或全局可抢占 SRPT。

经典单服务器模型要求独立任务、固定且已知的处理时长、无切换代价和额外资源约束。
全部任务同时可执行时，SPT 最小化完成时间之和；动态到达时，可抢占的 SRPT
在经典模型下最小化平均响应时间。这里不能把“已知剩余 token 工作量”等同于
“满足该模型的已知剩余处理时间”。我们的 workflow 会等待工具和 JOIN，
有并行子任务；处理速率还随 batch、上下文和 KV 恢复而变化。

一个仅用于说明理论边界的构造例子：A 需要 GPU 1 秒、工具 100 秒、GPU 9 秒，
总 GPU 工作 10 秒；B 只需要 GPU 5 秒。两者同时到达，工具不占 GPU。
先完成短 GPU 工作 B，再启动 A，完成时间为 B=5、A=115，平均 60 秒。
先运行 A 的第一段，工具运行时执行 B，再运行 A 的末段，
完成时间为 B=6、A=110，平均 58 秒。
即使 GPU 工作量完全已知，按整个 workflow 的总 GPU 工作量排短者优先，
也没有最短平均 workflow JCT 的保证。这是构造反例，不是对本轮收益的估计。

本轮还有可以直接核验的真实策略反例。原生 journal 第 81,586 行的
`workflow_combination_selection`，单调时间 776773.0189655 秒，候选如下：

| 候选所属 Workflow | 剩余模型工作量 | 实际选择权重 |
|---|---:|---:|
| system_networking_027 | 12,540.58 | 0.000079735 |
| mobile_game_096 | 27,065.97 | 0.000036945 |
| system_automation_062 | 31,444.38 | 0.000044588 |
| desktop_development_021 | 48,072.26 | 0.000423245 |

前三者构成 reference 集合；实际只选了最后一个。最后一个等待了约 580.40 秒，
其基础权重为 0.000020802，乘以 `1 + 580.40/30` 后变为约 0.000423245。
这超过 reference 三者的 benefit 之和约 0.000161268，
因此 `maximal_benefit` 选择了更长者。该决策没有强制 JOIN 成员，
搜索完整结束，没有超时回退。
两个集合都有规划层面的有效 evaluation，不代表已证明两者都可立即物理执行。
这条记录证明实际策略不是严格短任务优先；它不单独证明整轮回退由老化造成。

实际代码的另一处区别是 `_evaluate` 使用
`sum(workflow_weight * JOIN_coverage)`，JOIN coverage 包含
`((active + selected)^2 - active^2) / unfinished^2`。
该组合 benefit 是启发式目标，没有最小化完整 workflow 完成时间之和的证明。

对照关系也应明确：已完成 FULL 的实际工作 artifact 中
`remaining_work_ranking_enabled=false`，环境中
`WORKFLOW_COMBINATION_ADMISSION=0`；
最新 oracle 分别为 `true`、`1`，并启用 maximal-benefit 和 30 秒尺度老化。
两组虽然都使用 oracle bookkeeping，但 FULL 不以其剩余工作量排序。
因此本轮比较的是参考调度与新增混合策略，不能称为同一调度器仅将预测替换成真值。
这些开关均从各自注册表指向的实际配置及工作 artifact 核对。

理论结论的参考为 Grosof、Scully、Harchol-Balter 在 Performance Evaluation 的
“SRPT for multiserver systems”（DOI 10.1016/j.peva.2018.10.001）对经典单服务器 SRPT
及多服务器边界的说明。上面的工具阻塞反例和真实选集记录独立于文献成立。

继续提高同一个剩余模型工作量标量的准确率，无法解决这轮已经由真值揭示的
容量准入和服务连续性问题。下一项优化应检验等待老化是否能在资源可行时兑现，
以及改变选集能否减少首服务后的间隔、维持有效 batch，并以相同代码只替换
learned/oracle 信息源做消融；不能把当前 oracle 当作系统性能上界。
