### 已确认的新旧控制差异

本轮不是“旧非排序 Full 仅减少了 CPU 检查”。实际冻结注册和第一份原生状态证明：

- 旧轮为 `WorkflowOracleAdmission`，禁用 remaining-work 排序，但仍使用
  `global_ready_remaining_path` 框架、2 秒窗口及窗口到期后的 decay/容量协调。
- 新轮为 learned `WorkflowSizeAdmission` 加 `WorkflowCombinationController`，
  只在 `select()` 入口返回参考集合 S0；预测器和新的共享准入框架继续运行。
  预测分布不参与压力暂停和工具替换排序，未发现这两条路径偷偷使用工作量偏置。
- 工具检查由 200ms 改为 400ms，普通 hint 刷新保留退避，昂贵检查进行了前置过滤
  和同次调用复用。真实新事件仍可 rearm；净时序影响不能只由间隔数值推算。
- 同窗口工具替换检查 CPU 从约 65.87 秒降到 27.32 秒，周期控制也下降。
  新轮预测 worker 仍消费约 26.84--26.92 秒线程 CPU；后台线程与旧路径的同步
  记账不能直接相加或扣成 JCT，GIL/唤醒干扰也没有独立测量。

还有一项容易忽略的参考语义差异。`WorkflowSizeWorkingSet::_resume` 在
`select_set is None or rank_before_category` 时才把已有 sibling 组排成相邻。
旧轮符合该条件；learned R5 的 S0 构造不符合。关闭组合改选后，它直接返回这个
S0，没有恢复旧周期路径的 sibling 相邻偏好。**事件级 sibling 准入和 native
sibling 选批支持仍然保留，不能把这项缺口说成全部 sibling 支持被关闭。**

用实际 `WorkflowSizeWorkingSet` 核心作了一个 CPU 反例：容量 7，三个 ready
候选 `a=2,b=3,c=5`，工作量权重完全相同，`a/c` 属于同一 JOIN。
按两种实际框架参数，旧参考选择 `{a,c}`、使用 7；R5 关闭后选择 S0 `{a,b}`、
使用 5。它证明即使没有工作量排序，两种参考策略也可能作出不同选择，
不证明旧集合总是更优，更不证明本轮有多少 JCT 由它造成。

窗口协调也不完全等价：旧 `WorkflowOracleAdmission::tick` 会在 2 秒窗口到期、
存在 pending 且周期尚未到期时前移 `next_tick`，先做 decay/容量协调。
learned 路径没有这一 override，而按常规周期加 deferred dispatch 推进。
不能仅凭两者配置都写 2 秒，就认为恢复机会及实际服务次序完全一致。

因此，目前能严格确认的是：**回退主要发生在首次服务前的排队，而不是已有证据
显示模型执行整体慢了 3.14%；新旧非排序参考路径存在真实行为差异。**
尚未把完整回退独占归因于 sibling、窗口协调、400ms、预测 worker 或随机执行波动。
后续若修订非排序参考路径，应先在相同 CPU 决策现场核对语义和受影响频次，
不为每一个差异分别追加完整 GPU 实验。

这一发现也进一步限制 4.81% 的表述：它仍是同版本 R5 集合决策对照的观察结果，
包括相对该 S0 的 JOIN 组合改选；不能单独称为“预测长短更准确”的贡献，
也不能将旧非排序到新关闭轮的差异全部归于 CPU 优化。
187.041518 秒背景覆盖不足继续保留为限制，不当作等量 JCT 回退的原因。

### 窗口协调的进一步核对与共享路径修复

用户追问“为什么新路径关闭了”后，进一步核对了完整调用链。此前说法需要明确：
**acting decay 没有关闭，缺少的是窗口到期与完整工作集控制之间的连接。**
这段连接原来只在 `WorkflowOracleAdmission::tick`，切到 learned
`WorkflowSizeAdmission` 时没有进入共享基类。`remaining_work_ranking_enabled=false`
只使组合选择返回 S0，不负责选择 adapter，也不控制这个连接；不存在有意为了 R5
而关闭它的性能设计理由。

两种动作不同：

- 完整工作集控制刷新真实上下文增长，按工具保留权重/decay 比较恢复候选，
  再强制检查未折扣总预算，必要时暂停安全的阻塞 owner。物理页和实际执行仍需
  原生 KV、锁和容量检查。
- 窗口免费分发只使用 `remaining_capacity()` 的未折扣空闲额度，不能把
  decay 折扣直接当成已释放的真实容量，也不自己完成阻塞 owner 的协调。

两个周期都为 2 秒，不代表相位相同。若一次完整控制在 1.8 秒执行，下次计划为
3.8 秒，而 B 在 1.9 秒才 ready、既有窗口在 2.0 秒到期，免费额度不足时，
旧路径可将本次完整控制前移到 2.0 秒；原 learned 路径只有免费分发，然后仍需等待
后续完整控制。这个算例说明调用顺序，不证明 B 当时物理可准入或提前量等于 JCT。

## 分支级调度的理论收益与风险

考虑同一 ALL-JOIN 的两个分支 A、B，以及其他 workflow 的候选 C。
在一个简化且资源不相互拖慢的例子中，A 尚需外部等待 8 秒，B 需 1 秒模型工作，
C 需 2 秒模型工作。先执行 B 再执行 C，C 在第 3 秒完成；
先 C 再 B，C 在第 2 秒完成，B 仍赶在第 8 秒前返回，JOIN 不推迟。
若 C 的完成确实决定其 workflow 完成，就存在 1 秒的总 JCT 改善。
这说明方向可行，但不能把这个算例当作当前负载的发生频率。

现有实际现场的收紧筛查为：

- 20 个保留其余选中成员的一对一跨 workflow 替代。
- 8 个竞争者完整 RETURN 路径可放入另一分支的理想余量，来自 4 个 JOIN。
- 只有 1 个涉及测量组竞争者；其余依然会影响背景竞争。
- 只依靠**当前已经执行中的工具**提供的余量，可完整容纳替代者的机会为零。
  所以 8 个机会依赖尚未发生的模型/工具阶段，预测难度更高。

用已知未来固有路径计算误差敏感性。记 A 为另一分支路径，B 为被推迟分支，
C 为替代者路径，M 为迁移和保护时间。若三方估计误差分别受相同比例 rho 限制，
下面的条件足以保留这个**固有路径**上的余量：

```text
(1 - rho) * A >= (1 + rho) * (B + C) + M
rho_max = max(0, (A - B - C - M) / (A + B + C))
```

这不是实际容量占用或 GPU 干扰的界。M=0 时，8 个机会中：

| 可同时容忍三方的相对路径误差 | 仍保留理想余量的机会 |
| --- | ---: |
| 10% | 7 |
| 25% | 6 |
| 50% | 3 |

中位容忍比例为 46.23%，最脆弱者只有 2.42%。
唯一测量竞争者的例子中，A/B/C 为 378.53/40.06/15.18 秒，
理想路径差很宽，可容忍约 74.53% 的误差；它的当前工具余量却为负。
它还没有证明竞争者 child 的提早 RETURN 会缩短完整 workflow。
不能把 8 次理想余量相加作为可削减 JCT。

因此，分支调度**不必在所有场合精确预测分支结束时刻**；较宽余量允许误差。
但当前能支持这种判断的样本很少，不能直接推广。

真正在线判断应使用：

```text
其他 sibling 的早侧完成界
  > B 的晚侧模型/工具需求
  + C 到实际安全释放容量的晚侧时间
  + 恢复与 batch 干扰保护量
```

C 的一次短模型请求不是 C 的容量占用时间；准入后保留 agent 连续性，
它可能继续执行后继请求。发现误判时，不能假定能免费撤销已经准入的 C。
工具 P90 也不能用作可供借用的等待时间，应使用工具返回的早侧界。
未来还未知的工具数量、分支轮次、嵌套 JOIN 和随机工具时长必须纳入不确定性。

若分别给 A/B/C 的一侧预测使用 90% 覆盖率，三者同时满足的保守保证
只有 70%，不能称为 90% 联合可靠性。用三个各 96.67% 的一侧界可通过
union bound 达到至少 90%，无需假定独立，但会显著放宽区间。
当前只有 12 个校准 workflow；对三个单独的一侧 split-conformal 界，
这个覆盖率甚至可能要求无限界。直接校准联合误差分数是另一条路，
仍需按完整 workflow 保留相关性，不能把数千个相邻快照当作独立样本。

当前建议是只保留为有界候选的保守偏好：在已有选择入口按事件更新，
只在明确余量和完成 frontier 价值均存在时改选，其余使用现有共同推进。
不增加新的全队列周期扫描，不为当前 8 个理想机会单独启动 GPU。
