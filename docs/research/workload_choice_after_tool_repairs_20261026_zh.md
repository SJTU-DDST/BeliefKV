## 建议

在选定项目的真实工具执行得到验证后，优先选择 LoCoBench-Agent 作为
完整一体化设计的主负载。理由是它允许本项目 runtime 直接观测实际
SPAWN、等待、工具参数、工具返回、原生完成与上下文生命周期，更接近
增量备份、阻塞卸载、JOIN 提前恢复和 agent 资格管理的共同输入。

这不意味着 LoCoBench 的工具天然更长，也不保证更容易超过所有 baseline。
正常工具时间、实际独占冷页、Host 可恢复缺口和恢复等待需要实测。
公平的选择标准应在比较结果出现前确定，不能反复筛选 Full 获胜的轨迹。

## 两种负载的能力

LoCoBench-Agent 提供可交互的软件任务和源码。本项目的多 agent 委派框架、
长前缀输入、真实 shell/test 工具及动态 SPAWN/JOIN 属于明确声明的适配。
不能称其原版天然具有本项目需要的多轮、嵌套和并行 JOIN。默认 minimal
初始化与本项目完整长源码输入也不同，应在论文中说明。

AgentX 提供实际会话衍生的请求长度、前缀 hash、时序和 subagent 标记。
它适合固定工作量、缓存压力和调度策略比较，完整发布会话的 JCT 有效。
但公开数据没有原 prompt、代码、工具参数和工具结果，重建的 JOIN
不是原始工具等待边界，合成终止 token 也不提供原始语义 EOS。
因此其当前保守路径不能完整验证旧的 EOS/语义工具预测设计。
重建 runtime 可以报告实际执行的等待，但需要单独的信息与计时声明，
不能补回缺失的原始工具语义。

## 对照方法

1. 在同一多 agent runtime 上自然执行候选任务，每个 root 来自不同原项目。
   提示词统一鼓励合理分工、多轮和嵌套；保留模型选择，不固定完整 DAG，
   不用硬截断制造短 child 或提前 JOIN。
2. 先采集健康的自然轨迹，保存实际请求输入输出 token、原始停止条件、
   创建与等待操作、工具身份与参数、真实耗时、压缩及生命周期事件。
   记录工具成功与任务正确性；正常长尾保留。
3. 以同一完整轨迹比较 native、Agentix、KVFlow、ThunderAgent、TokenCake
   和 Full。事件按实际执行时刻投递，模型服务由被测系统执行；不重放旧的
   GPU 服务时长，不把未来图、最终请求标签或已知结束时刻交给在线策略。
   另以自然执行抽查重放保留了预期机制与质量，不混合两种指标。
4. 同时校准真实压力与可优化机会：全部有效 KV 超过 HBM，但活跃计算与
   少量下一恢复状态有空间；Host 能保存必要状态，额外重算不失控。
   running/decode24 与同时到达 workflow 数分别控制。先按容量和恢复等待
   选强度，再看性能，不以让 baseline 抖动最大为选择标准。
5. 评测完整 JCT、完整运行输出吞吐、workflow 首次服务/就绪服务间隔、
   实际 GPU 恢复等待、有效预取首次使用、重复传输和重算。保持源码、种子、
   容量、请求/token、工具时间与在线事件信息一致，做重复运行。

目标仍是相对全部适用 baseline 同时改善 JCT 与吞吐。数据集选择不能
证明该目标已实现；若只在某种压力范围有效，应如实说明。

## 后续 Runtime 与 Trace 设计建议

2026-10-26。本节最初是待验证建议，现已按用户授权用于新 LoCoBench
负载准备。历史冻结人口和 baseline 源码保留；新 profile 需要独立
环境证据及匹配自然源，不沿用旧轨迹的性能结论。

### 明确收益假设

工具调用较长、父子等待较多，可能提供安全借出 HBM 的机会，但不能由此
断言一定超过 ThunderAgent。其论文已有 acting/reasoning 状态感知、
状态优先暂停和长工具等待的时间衰减。新方案需要证明：更及时地识别
可借出状态，并在其重新可运行前恢复必要前缀，减少实际恢复阻塞和重算，
同时不增加热请求驱逐、控制开销或正常任务工作量。

主要容量区间应满足：

`实际热工作集 + 下一恢复前缀的缺失页 + 原生增长余量 <= HBM KV 容量 < 总有效状态`

这些量按去重后的原生页核算，不能重复计算共享前缀。冷页须没有运行、
排队消费者或在途 DMA 的必要引用。长期不再使用的垃圾页不算有用冷状态。
不要求运行中一直保持高冷页占比；正确卸载后冷状态可能主要保存在 Host。
已有空闲 HBM 也能承接预取；需要的是可用或可安全借出的容量，而不是
必须人为制造大量 HBM 冷驻留。
全部 agent 同时等工具、GPU 没有其他工作时，预取也不能消除工具执行本身。

频繁新建短 child 的首次请求通常是冷 prefill，不存在该 child 的旧 Host
KV 可预取。该形态的主要恢复对象是反复等待、再唤醒的长上下文 parent，
以及工具返回后还需继续请求模型的 child。能否复用必须按实际 token
前缀和原生缓存页检查，不能用 child 数量代替机会量。

### 两类自然工作流

以下数值仅为首轮形态探索的建议，不是数据集已具备的分布或强制门槛。
LoCoBench-Agent 提供任务、项目和多轮工具环境；多 agent 编排和真实
shell/test/build 工具属于本项目明确声明的 runtime 适配。

| 候选 | 任务组织 | 首轮探索参数 | 主要可验证机制 |
| --- | --- | --- | --- |
| 多轮短 child | 每个 child 回答一个符号、调用链、测试结果或兼容性问题；parent 汇总后据新证据委派下一轮 | 比较每轮建议 2--4 与 4--8 个独立任务；child 主链目标约 2--6 次模型调用；有新工作时形成约 3--5 轮 | 长 parent 等待时借出 HBM，在下一轮 parent 请求前恢复 |
| 工具阻塞较多 | 真实的针对性测试、构建、类型检查、集成验证；结果决定下一轮操作 | 时长按实际观察分为 <=1s、1--10s、10--60s、>60s；不人为设置等待时长 | 工具开始后卸载，借助已观察进度或历史分布安排恢复 |

优先探索多轮短 child，保留普通短工具工作流作为参照。每个 child 的
工作描述要限定问题和交付证据，不把整个任务外包给一个长期执行的 child。
现有 child 24/32 次调用软预算不适合充当“短 child”的目标；候选可单独
声明更小的提醒/目标参数，但不得强制截断仍在运行的命令或生成。
多轮应由新的任务证据推动，不固定完整 DAG，不重复调查以凑轮次。

同一轮独立只读调查或独立测试可并行；并行修改必须使用不重叠写域，
否则由 parent 串行集成。先研究 root/child 两层，再对有真实需要的
嵌套单独统计；深层嵌套不是创造迁移收益的必要条件。
长上下文按实际任务输入分桶，不给每个 child 复制整份源码或填充无用文本。
保留真实共享前缀，分别记录每个 agent 的私有页与树内共享页。

工具频繁应同时报告“有工具的模型轮次比例”和“agent 生命周期中实际
工具阻塞的时间比例”。并行工具耗时不能直接累加后除以 workflow JCT。
另外统计工具等待时是否有其他已就绪模型工作，避免把纯工具等待误判为
GPU 调度收益空间。原测试正常执行但本来很快时，应接受该事实。

### 从实际执行记录状态

`SPAWN -> 实际 JOIN_WAIT -> child RETURN -> JOIN_SATISFIED`
由 harness 回调记录，分别保存创建者、成员、ALL/ANY 模式、超时和取消。
背景 SPAWN 不赋予 parent 驱逐权限。工具执行直接记录真实参数、开始、
进度和结束；排队执行与实际开始分开。请求提交、首次原生服务、首 token、
结束及客户端下一提交也分开，避免把排队写成工具耗时或剩余生成工作。
上下文关闭必须由显式生命周期证据触发，RETURN 本身不等于关闭。
一次性短 leaf 可由新应用契约在创建时声明 temporary，实际完成后显式
关闭上下文；持久 child 按明确句柄保留。所有方法执行相同生命周期，
不根据 trace 的最后一次使用事后决定，也不只为 Full 清理已结束 child。

纠正先前关于 AgentX 的宽泛表述：其依赖录制结束时间重建的 JOIN 只属于
私有回放依赖，不能传给在线调度器作为等待、卸载或预取授权。新自然轨迹
必须采集真实等待边界，不事后利用 child 结束时间反推。

每条事件至少关联：

- workflow、invocation、context、epoch、request、tool_run、join 身份。
- 单调时钟时间戳、时钟域、事件顺序、因果父事件和观测来源。
- 已完成请求的输入输出 token 与原始生成/停止参数，支持相同工作量回放。
- 实际可复用前缀、原生页所有权、HBM/Host 驻留及共享引用。
- 备份/恢复 issue、submit、ACK、实际首次消费和再次驱逐的关联。

在线控制器只接收已经发生的事件和当前输入，不读取未来轮数、最终输出
长度、最后请求标签或工具/child 的未来结束时刻。完整自然 trace 与未来
标签保存在离线评估侧，未来信息仅可用于明确标注的 oracle 分析。
短 child 可以在组织最终报告时发送已有收尾通知，随后自然报告并返回；
通知在全部比较方法中保持一致，记录缺失、改意和再次调用工具的情况，
不以通知当作完成事实。

高频记录采用有界异步缓冲；在线控制事件保留必要的顺序与可靠交付。
原始内容只保存必要的最终请求记录，decode 进度按已有低频采样，不在
每个 token 上重复解码文本、扫描整个图或同步写大日志。单独计量观测开销。

### 在跑正式比较前确认机会

先用候选自然 trace 统计以下结构与容量特征，按预先声明的标准选择强度，
不按 Full 相对 baseline 的胜负挑选任务。自然捕获仍每个 root 使用不同
原始项目；保持运行/decode24，与同时进入系统的 workflow 数分别调整。
固定工具执行资源并分开记录工具排队与实际执行，避免仅以 CPU 工具队列
拥塞拉长等待。不同 workflow 的模型和工具阶段需要有交错，不能让所有
workflow 同步停在一个工具屏障上。

| 必须回答的问题 | 证据 |
| --- | --- |
| 是否存在安全可借出的状态 | 等待 agent 的独占、无活跃引用、已备份原生页及其 byte-time |
| 是否存在真实恢复需求 | 后续请求实际缺失的已服务历史前缀；区分首次 prefill 与历史前缀重算 |
| 是否能减少暴露等待 | 请求关键路径上的原生恢复等待和层依赖阻塞；不以累计 DMA 时长代替 |
| 恢复是否及时消费 | 完成边界前启动的 H2D、必要页就绪、首次实际复用及其提前驻留成本 |
| 有没有挤掉更需要的状态 | 被驱逐页当时所有者状态、重复加载、额外 prefill 和就绪 agent 延迟 |
| 是否有端到端收益 | 完整 workflow JCT、同工作量吞吐、任务质量和控制路径开销 |

可借出冷状态、近期恢复需求和其他可推进计算应在时间上有交集。先做
不同自然工具形态和并发强度的画像；若恢复关键路径本来很小，即使完美
预测也难取得明显收益，应报告收益空间不足。若工具长尾主导 workflow，
更长工具也可能稀释 JCT 改善，不应继续单纯拉长等待。

冻结健康自然源后，全部方法执行相同请求、token、真实工具间隔、前缀、
依赖和终止条件，保留完整尾部。旧 AgentX 队列按最新用户要求提前终止；
新负载健康后重新登记适用 baseline 与 Full。正式对照按用户既定要求重复运行。取得清晰整体验证
后，再以相同调度关闭预测传输的消融确认预取增量，避免把调度变化全归功于
H2D。单纯“在 LoCoBench 上更快”不足以证明工作流预取机制有效。
