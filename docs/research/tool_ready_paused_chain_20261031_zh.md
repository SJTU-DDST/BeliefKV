# 工具返回、逻辑暂停与恢复准入链路审计

## 结论与状态边界

2026-10-31 对冻结的 `020527dd` oracle 与当前 Full 代码逐段核查。
不能把工具阻塞、逻辑 paused 和 KV 在 Host 上视为同一个状态。

| 状态 | 实际含义 | 由谁更新 |
| --- | --- | --- |
| `WAIT_TOOL` | 仍有真实工具调用未返回，不能发起有效模型续接 | RCCG 的 TOOL_START/TOOL_END |
| `program.active` | 当前 agent 是否持有模型请求准入资格 | agent 工作集控制 |
| KV 在 HBM/Host | 私有或共享前缀的物理位置，以及是否有已完成的副本 | 原生缓存与受安全条件约束的迁移 |
| ready-paused | 实际后继请求已经登记且可执行，但 agent 没有准入资格 | 实际请求、图依赖与逻辑资格共同判定 |

当前 `DemandAwareToolOffload` 只释放安全、已有已完成 Host 副本的物理页，
不会调用 `policy._pause()`。其 reference 分支只为已经持有资格、
且实际缺少物理容量的等待消费者寻找工具 donor；不能直接借出逻辑额度。
因此“预测还要等十秒 -> 立即 paused -> 十秒后 active”不是当前实现。
卸载过 KV 的 agent 可以仍是 active；实际工具返回后，其后继请求沿用资格，
需要时进行原生按需恢复，不经过 ready-paused 排序。

预测只决定备份/卸载是否值得。预测时间到达不等于实际工具返回，
也不自动创建后继请求、授予资格或启动工具预取。工具预取继续关闭。

## 当前暂停与恢复规则

`ThunderWorkingSet` 中的 `acting`、`pending`、`active` 分别表示模型调用间隙、
是否有未完成模型请求、是否持有资格。`acting` 不等同于已经观察到 TOOL_START。

逻辑暂停主要发生在以下入口：

1. 新 agent 首次请求不能取得完整预算，或已有等待对象时，首次准入排队。
2. acting-decay 工作集控制尝试恢复对象，随后按完整预算处理压力；
   先暂停 acting agent。正在执行模型请求的 agent 通常只做暂停标记，
   等该请求完成后才实际暂停。
3. Full 的观测 JOIN 交接向真实阻塞且安全的 donor 回收逻辑额度。
4. 全局 oracle 主动将首次普通准入送入统一选择窗口。

普通工具预测卸载本身没有增加第五个“物理卸载即暂停”的入口。

正常工具续接链路如下：

1. 原生模型请求完成：`pending=False`、`acting=True`，资格可以保留。
2. TOOL_START：图进入 WAIT_TOOL；预测及物理卸载可以独立发生。
3. 如果工作集将该 agent 暂停，工具执行期间它仍不可成为 ready-paused。
4. 真实 TOOL_END 到达：移除对应工具；仍有其他工具或 JOIN 依赖时保持阻塞。
5. 工具已结束且实际后继模型请求登记后，更新为 `pending=True`、
   `acting=False`。active 原值保留；inactive 对象成为恢复候选。
6. 候选获得逻辑资格后，原生容量、锁、DMA 与 KV 恢复检查仍决定实际服务。

TOOL_END 和原生后继登记通过不同路径到达，代码必须兼容两种先后顺序。
事件补位的 500 ms 是兜底检查；完整工作集控制的配置周期为 2 秒。
逻辑授予、物理恢复与首次有效 batch 的时间需要分别记录。

## 已复现的两个实现缺口

### 请求先登记、工具事件后到时漏掉事件补位

旧版事件补位在发现调用仍有 `active_tool_calls` 时，会将其从
`_dispatch_pending` 移除。后续 TOOL_END 虽然使图 READY，也触发补位，
却没有先重新索引该后继请求。500 ms 兜底只扫描现有 pending 索引；
完整工作集控制重新扫描请求前，该对象可能一直没有事件准入机会。
这是补位延迟，不是已证明的永久死锁。

修复在 TOOL_END/LLM_SUBMIT 后，对事件对应的最新请求重新核对
完整身份、pending、工具/child 阻塞与图状态，再加入 pending 索引。
不扫描全部 agent，不提前授予资格，仍有其他工具未结束时不能执行。
“工具先返回”和“请求先登记”、单工具和多工具四种情况均有真实 runtime 测试。

### 合并窗口与 acting-decay 控制错位

旧版 1 秒普通准入窗口关闭时，周期选择也被门控；窗口到期后，
事件补位却只使用完整、未衰减预算。如果 2 秒完整控制总在窗口尚未打开时
触发，acting-decay 释放逻辑额度的机会可能持续被错过。

可复现算例：池容量 500 token，等待工具的 active agent 计费 400+100，
另一 ready-paused agent 需要 100+100。工具等待一秒后衰减恢复预算为 200，
但完整预算仍为 0。周期控制在 100.5 秒运行、窗口在 101 秒到期时，
旧代码既不恢复等待对象，也不让工具 agent 退出集合。

修复只在显式 timed oracle 中启用：窗口到期且 pending 索引非空时，
先运行同一套工作集恢复与完整压力处理，再做普通 free dispatch。
这样恢复预算和暂停额度由同一次控制落实，没有把衰减量当作物理空闲页。
2 秒是配置的常规控制周期；有候选的窗口到期可以提前触发完整控制。
新增计数 `oracle_coalescing_reconciliation_ticks`，实际状态明确声明
`workflow_oracle_reconciles_decay_at_window_deadline`。

这会改变 timed oracle 的实际控制频率，不能只描述为纯排序改进。
默认零窗口、学习模型分支、纸面 ThunderAgent 策略不增加这个窗口控制。
JOIN/EOS 预取和已 ready JOIN 的绕过权限保留；不主动抢占 ready active 请求。

## 采样证据与解释范围

只读审计：
`experiments/reports/remaining_original_projects_20261030/oracle_mean70_window1s_r1/tool_readmission_capacity_prefix_r1.json`。
输入按完整 JSONL 前缀封存并记录哈希，实际 runtime 确认 Device 池为
805198 token，每个周期的完整预算之和与原日志压力后余额逐项核对。

固定共同窗口仍为 `412.944491--1841.814938` 秒，其中 704 次周期控制：

- 225 次存在被窗口挡住、衰减预算可容纳、完整预算不能容纳的 ready 候选。
- 对应 451 条重复 agent 边界观测，不是 451 个独立 agent。
- ready-active 为 3531 条、ready-paused 为 525 条重复观测。

这些证据说明不能仅凭少量周期授予便认定原始负载没有 ready 供给，
但不证明 225 次都具备物理准入空间，更不能乘以某个时长当作可回收 JCT。
工具返回事件乱序缺口在测试中可复现，尚未统计其在本轮的实际发生率。

同目录 `common_window_supply_r1.json` 用修订后的周期 reader 将“有恢复预算”
分成四种互斥情况，原计数保持不变：

| 共同窗口周期边界 | 次数 |
| --- | ---: |
| 应用本身没有 ready-paused | 436 |
| 有 ready-paused 但无对象能放入衰减预算 | 0 |
| 有能放入的对象，但全部被窗口推迟 | 253 |
| 至少一个能放入且窗口已允许的对象 | 15 |

不能把 253 次窗口等待合并到“没有应用候选”中。历史预计算报告没有新增
字段时保持 unknown，不能补成零。周期外存在真实竞争及实际服务，
也不能用周期竞争为零否定所有准入入口。
