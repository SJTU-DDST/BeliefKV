## 1. 研究结论

候选问题是：工作流结构持续生成、agent 反复等待外部工具或其他 agent 时，如何让
有限的执行额度与 FULL/Mamba 状态容量支持可执行分支推进，而不是形成大量已经
物化、尚不能执行、恢复后又失去驻留的状态？

预取是可能的辅助机制，主论证不依赖亚秒 RETURN 预测。收益必须来自少重复工作、
少无效状态占用、少恢复后再次加载及维持有效 batch，并转化为质量相当的工作流
JCT 和完成吞吐。修复本系统额外控制开销只是必要工程条件，不单列为论文创新。

这一问题不是现成的新颖性结论。动态 agent 调度、工作流感知缓存、程序级优先级、
缓存反馈准入都已有研究；本项目必须证明具体资源协议和可执行状态决策的增量。

## 3. 当前场景的证据和缺口

V1112 于北京时间 2026-10-16 19:15 封存 V73 已写入前缀，156 个 workflow 中
126 个已观测到 WORKFLOW_END；这是运行中观察，不是完整实验或任务质量结论。

- 502 个非内部 agent invocation，包含 346 个实际 spawn child。
- 最大 spawn 深度为 1，嵌套 spawn 为 0。
- 178 个 root JOIN 轮次，21 个 workflow 有多轮 root JOIN，非 root JOIN 为 0。
- 非终态逻辑 agent 时间中约 38.40% 为工具/依赖等待。RUNNING_LLM 含原生排队，
  该比例不是 idle HBM 字节时间，不可据此直接声称能释放 38.40% HBM。
- 72,841 个可观察机会快照中，18,434 个的 Mamba free list 为 0；93 个的 FULL
  free list 为 0。闭包观察超过当前 free list 的 FULL/Mamba/双池样本分别为
  15,872/1,446/9。它们是稀疏、策略选择的快照，不能等同完整请求拒绝次数。
- 有 FULL 空闲 14,118 token、Mamba 空闲 0 的观察，同时存在需要恢复一个 Mamba
  状态的对象。该现象首先是池配置/容量排查线索，不能证明需要新资源协议；
  必须先与合适的池配置比较，也不能由稀疏快照推算性能损失。

证据：
`experiments/reports/v1112_v73_workflow_progress_evidence_20261016.json`。
V1111 将不带 waiter 的 JOIN_CREATE 用作 parent 计数，相关 JOIN 归因无效；
V1112 改用独立 JOIN_WAIT(parent, join_id)，旧结果保留而不继续引用其轮次字段。

V1106 的固定 41 个工具事件中，存在 FULL 已提前复用、原生 FULL 恢复为零，
但到达后仍等待约 10.629 秒的请求；快照显示必要 Mamba 缺失和低池余量。
这证明 FULL 命中不能代替完整可执行性，但尚不能把全部等待归因于状态容量。
V1109/V1110 另识别混合 batch 的 Mamba COW 共享屏障；其当前采样规模和等待
量不足以独立支撑整篇论文，更不能把全部原生到达到服务间隔算成传输收益。

当前 harness 的 root 有 SubAgentMiddleware，child 没有委派工具。RCCG 和 adapter
已经能表达多层 parent、JOIN 和返回目标，应用构造却没有覆盖它们。因此目前不能

尚缺的关键证据：等待状态的唯一物理 HBM 字节时间；完整可执行预算下的排队阻塞；
同一数据恢复后的再次驱逐/重算；新机制相对正确 native 和强简单基线的增量。

## 4. 研究问题和可证伪假设

RQ1：按可执行状态而非 agent 数量准入，是否能在相同 GPU/Host 预算下减少资源
阻塞，同时保持 batch 填充？如果 agent 计数控制得到相同结果，向量预算不足以
成为贡献。

RQ2：动态嵌套 spawn 时，等待父节点与运行子节点的额度分离，能否改善推进与
公平性？不宣称 CONCUR 或其他系统存在死锁；比较时必须加入合理的 yield-on-wait
适配，不能以一个故意不释放父额度的错误实现作主要 baseline。

RQ3：将终态回收、完整恢复与 parent 首次消费组织为一个续接协议，能否减少恢复
后再次加载和未被执行消费的状态？如果收益只来自正确关闭 session 的小修复，
应把同样修复放进 native 对照，不能算为新算法收益。

## 5. 三个联合机制

### 5.1 动态执行分支准入

spawn 创建逻辑任务，不等于立即占有整段生命周期的 GPU 执行额度。READY/
RUNNING_LLM 的分支可以竞争执行；WAIT_JOIN、WAIT_CHILD、WAIT_TOOL 不继续
占有执行额度，仍保留各自逻辑状态和恢复责任。嵌套 parent 不能持有一个不可归还的
工作流许可证并等待被该许可证阻塞的 child。

决策基于当前已观察依赖、原生队列和状态成本，不使用未来 RETURN 或完整 DAG。
有可执行请求时继续补足原生 batch；低压不以固定小并发限制系统。公平老化必须
能让长 workflow 和新 workflow 获得服务，不给 root 身份无限优先权。

### 5.2 完整可执行状态预算

每个候选的新增资源需求至少是：

`(缺失 FULL + 下一 prefill chunk + decode 预留, 必要 checkpoint Mamba +
请求/追踪 Mamba 槽, 请求行)`。

FULL 以原生 page 对齐；共享 checkpoint 按实际物理身份去重；Mamba 当前必要状态
与请求活动/追踪槽分别计数。已经占用的 running 资源由原生 free list 体现，
不得重复扣除。unknown 保留为 unknown，交回原生判定，不伪装成零成本或永久拒绝。

该预算是规划，不取代 allocator、引用保护、数据依赖和现场准入检查。它的目标是
减少无法尽快执行的新增物化，而不是创造另一个每 decode 步扫描全部 context 的
控制器。FULL 的逐层就绪和必要 Mamba 的就绪分别处理，不能统一等待完整 FULL
ACK，也不能仅凭第一层就绪断定混合模型可执行。

### 5.3 父子续接的容量交接

child RETURN 后，只有已确认由原生 allocator 回收、且没有活跃共享/传输引用的
容量才可记为回收结果。parent 必须满足完整 JOIN 且请求可执行，才消费续接优先权。
较早 sibling 回收支持其他工作推进；最后 child 回收后的需求恢复不算预测 H2D。

交接绑定 workflow/context/epoch/session generation，消费、取消、压缩和新轮次
必须解除旧身份。优先权不能当作已经预留的物理页；别人已经分配的容量不得再次
记账。parent 没提交或暂不能执行时，额度可被其他 ready 工作使用，不长期空置 GPU。

## 6. 条件化性质与反例

可验证的性质包括：预算不超额；共享物理状态不重复收费；waiting parent 不阻断
descendant 准入；同一回收容量不被两个续接同时消费；在有限、可容纳请求和公平
调度的条件下，被延期的 ready 请求不会永久得不到一次原生准入尝试。

不承诺任意未知增长、无限 spawn、Host 同时耗尽或永不结束工具下的无条件完成。
资源不足时应安全排队、原生驱逐/恢复或保留失败事实，不通过截断任务伪造进展。

用于 CPU 验证的反例需明确标记为构造例：

1. 平坦生命周期许可证被所有等待父节点占用，child 无法取得额度。正确对照应
   yield-on-wait，本系统还须处理跨池状态预算，不能只修这个简单反例。
2. HBM FULL 容量 100 单位，两个请求分别需要完整 60 单位。各恢复 50 单位仍
   无法执行；按完整预算先推进一个不同于最大化已恢复字节。原生最终容量检查仍
   保留，比较的是前置决策成本与有用消费，而不是允许不完整数据执行。
3. FULL 有余量但 Mamba 请求/追踪槽不足。标量总字节控制或叶子片段 fits 不能
   证明整个请求可以推进；需与“简单分池 best-fit”强基线比较增量。

## 7. 工作负载调整

新增层级软件修复应用：root 负责最终编辑和验证，调查负责人可把代码路径、
复现/回归证据交给独立 leaf，汇总后返回 root。非 root 默认只读，避免新增嵌套
并发写同一 checkout 造成质量和轨迹混淆。根、负责人和 leaf 使用同样的模型、
通知协议、工具反馈和预算；所有对照使用完全相同的应用。

委派由具体问题决定，不要求每个节点必须再 spawn，也不为了制造迁移强制多轮。
leaf 没有 task 工具是应用角色边界，不能把“拒绝调用后空响应”作为自然 RETURN。
通过真实 callback 和可执行的 CPU stub 集成验证两级 JOIN/状态隔离；再用自然
GPU 运行观察实际深度。没有出现嵌套时如实报告，不把 prompt 设定当成实现证据。

新配置保持 156 个任务、原任务顺序、一张冻结的 Poisson root 到达表和 seed，
不按完成数动态补任务。首先沿用平均 15 秒/root、running 48、Host 200GB、
FULL:Mamba=80:20、HBM mamba/full=0.9、工具 180 秒、输出 8192、
activation 14400 秒。根据实测物理压力再调整，配置改变后双方重跑匹配对照。
旧 V73 继续原冻结流程，新代码与 workload 使用新候选，不能拼接为同一实验。

## 8. 实验与判定

首轮开发先运行新控制器，再运行同配置 native。完成前预测默认不作为新主线启用，
长工具管理和 PREPARE 的增量单独消融。正式阶段补匹配重复、不同到达形态和负载。

至少比较：正确 native；native 加相同终态关闭/回收；agent 计数准入加
yield-on-wait；简单分池 best-fit；程序工作量/亲和性排序；三个机制单独和组合。
移植已有方法时明确版本、差异及可比范围，不把名字贴在简化策略上。

主指标是所有到达任务的质量、完成率、平均 JCT、尾部/公平性和有效完成吞吐。
同时报告相同任务双方的有效工作量，未完成任务的删失及固定窗口完成曲线。
请求/token 吞吐只作诊断，不能通过少完成工作或降低质量取得主指标优势。

机制指标包括：唯一物理状态的等待字节时间；完整状态不足导致的排队；
同一数据首服前重复恢复；重算的已计算前缀；有效 batch；各池容量与控制 CPU。
运行中有 sparse/unknown 数据时不填零，不把累计 CPU 或传输时长直接减去 JCT。

否定条件：真实工作负载缺乏可操作状态压力；强简单基线得到全部收益；改进只来自
修复自身开销/错误 native；牺牲质量、尾部或实际并行度换取平均 JCT；新增控制
开销超过机制收益。满足否定条件时缩减或改变设计，不继续堆参数。

## 9. 实施顺序

研究论证先于代码。随后先实现可独立检查的预算/额度控制器，接入原生 prefill
边界和真实事件生命周期；再实现层级应用与 callback 集成，复用安全终态回收。
新执行模式要能关闭旧预测/高频候选路径，而不只是叠加一个控制器。CPU 正确性、
完整控制周期成本和自然 GPU 净收益分别验收，不能相互替代。

## 10. 当前实现与可证伪验证

开发实现位于 `beliefkv/runtime/workflow_progress.py` 和
`workflow_progress_native.py`，由 `BELIEFKV_WORKFLOW_PROGRESS=1` 启用；
默认保持关闭。新路径在原生 prefill 边界规划，不在每个 decode 步扫描候选，
不启动旧预测 worker、不派发旧 JOIN/tool 预取或 PREPARE。回收、排队和原生数据
依赖仍保留，unknown 和老化请求得到显式原生准入尝试，不伪装成零成本证书。

预算包含下一 chunk、与原生一致口径的 decode 增长估计、请求行、活动 Mamba
及追踪槽。按节点身份/creation_time 去重缺失 FULL 和需保护的可驱逐驻留前缀；
Host Mamba 直接恢复到请求槽时不重复计一个 checkpoint 槽。已由 running 占用的
资源不再次计费。仅支持可观测的静态 FULL/Mamba 两池；其他布局回到原生判断。
这是下一步规划，不是覆盖任意未来增长的物理预留或完成保证。

简单对照入口为 `BELIEFKV_PROGRESS_POLICY=fifo|count|graph|vector`，主策略为
`joint`。所有入口使用相同应用与终态回收；FIFO、count、graph 不做向量状态
普查，graph 单独保留依赖/公平排序，vector 不做 workflow 轮转/续接优先。
最后一个未完成子树的优先信息只在结构变化时更新并缓存到后代，提升受普通
准入额度和 FIFO aging 约束。这一排序本身已有相关工作，不能独立算新贡献。
这些入口只是机制对照，不标作原论文复现。
未知请求的原生回退不属于资源证书，最终批次仍由原生检查。共享状态去重不得
把不同请求的活动/追踪槽合并；child 回收值不得额外加到已经包含释放结果的 free list。

新应用 profile 为 `native_hierarchical`，直接组合 pinned Deep Agents 中的 task
middleware，并在两层使用 private-state isolation。CPU 真 callback 已验证
root→coordinator→leaf、两个 JOIN、三个独立 context、逐级自然 RETURN 与控制
图重放。它证明接线可执行，尚不证明真实模型会自然形成足够的嵌套/状态压力。

最新应用/运行时检查 728 项通过、1 项 Docker 集成检查未运行；独立引擎相关
165 项及 14 个 subtest 通过，包括实际 allocator 的终态回收、共享前缀、
Mamba 请求映射和原生调度 hook。JUnit 见 V1119。早期新 fixture 失败记录保留，
不得将失败或跳过合并成通过。V1120 对完整 V73 predictive 的 156 份客户端
trace 分别逐事件/32 事件一批重放，最终因果状态与原 RCCG 一致；没有物理
visible request 的重放不证明 GPU 资源管理、成本或性能正确。

V1113 首版对 156 个长上下文逐个做精确检查，约 24ms/周期，不宜用于高频
控制。现已按下一批实际空位惰性发现，满 47 running 时只检查一个拟准入对象，
不是扫描完全部队列。V1118 绑定当前控制源码与最新引擎：8/48/156 队列、
47 running 的 joint 中位线程 CPU 约 0.222/0.567/1.580ms；完全空批次下分别
约 0.759/5.921/9.533ms。空批次仍贵，不能宣称控制成本已解决。
该基准保留真实 RadixKey/输入检查及完整空事件维护/规划/选择周期，容量和
session 树仍为 CPU 夹具；活跃图更新另见 V1120，不代表 GPU/JCT。

独立引擎 `sglang-v1116-workflow-progress-20261016` 从冻结 V73 引擎的实际
改动导出，保留原有 GDN、Mamba 映射/追踪和短 prefill 优化，仅追加新准入
hook 与相应 CPU 检查。原生分支的预分配顺序保持；新模式先规划，再仅为已
计费活动槽做批量预分配，unknown 用原生单独分配，不把预分配占用误作短缺。
启动入口为 `scripts/run_workflow_progress_ab.py`，默认只准备可核验计划，明确
使用最新 156 项 manifest、同一 Poisson 时间表、相同资源和应用；新策略先跑，
随后同配置 native。V73 native 已实际启动，不能抢占或热改它。

当前仍待证明的论文级增量是：在正确 native、合理 yield-on-wait、简单分池
best-fit 和程序/图排序之上，联合协议是否减少真实重复恢复与等待状态占用，并
保持 batch 与任务质量。仅凭这份实现不能声称“先前方法无法解决”已经被证实。
