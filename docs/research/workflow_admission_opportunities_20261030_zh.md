# Oracle 准入机会与后续服务审计

本次检查完整 scope18 burst oracle 与保留 Full。两臂相同18个 workflow、
4246个请求和607248个输出，完整停止、fresh drain及所属进程退出已验证。
没有新增 GPU 实验，也没有改变保留 Full 或 paper baseline。

结论是：本轮没有取得可推广收益，但未发现“排序结果没有接入准入/服务”
的断链。当前比较主要测了周期恢复中的类内排序，选择空间很少；它也不是
全局最优调度 oracle。具体限制包括已有 active agent 的连续性、原恢复类别、
按标量排序贪心装入容量，以及仍沿用原规则的其他准入入口。

## 竞争口径与控制漏斗

入口为 `scripts/audit_workflow_admission_funnel.py`，完整证据在
`experiments/reports/workflow_mix_20261029/admission_funnel_r3/audit.json`。
离线复算每次已记录的局部选择，并追踪相同 request/attempt/context/session
的正增量 native work；零增量记录不计服务。

| 完整记录 | 控制次数 |
| --- | ---: |
| 周期控制 | 1067 |
| 有剩余额度但没有 paused 候选 | 750 |
| 无可用预算的空候选控制 | 7 |
| 非空候选控制 | 310 |
| 多个 ready workflow | 152 |
| 不考虑类别时，存在各自放得下、合计放不下的跨 workflow 候选 | 17 |
| 保留原类别后，剩余分数不同的真实容量竞争 | 10 |
| 最终改变准入集合 | 6 |
| 改变选择后获得正增量 native work 的不同请求 | 6 |

这些行并非全部互斥、递进子集。310个非空控制中，154次仅一个ready候选；
171次全部ready候选合计可以容纳；111次连一个ready候选都放不下。
因此不能用1067减10，把其余全部解释为实现漏选或HBM未利用。
这里记录的是逻辑资格和上下文预算，不是同时刻物理独占页的完整可行性。

之前“4次竞争”额外要求同组同时存在按**初始完整工作量**划分的 short、
long 档，是更严格的 workload 诊断；不代表按当前剩余分数只有4次机会。
今后同时报告该指标和剩余分数竞争，避免混用。

`WorkflowSizeWorkingSet._resume()` 只对 paused 集合在原类别内插入rank，
不抢占已有active agent。类别仍优先于rank：已有reasoning续接、第一次
请求、acting依次处理。750次无paused候选时，调整排序不会产生新选择。
111次全部放不下时，则需要完成、真实安全释放额度或调整组合，而不是
交换列表顺序。

## 选择是否传到了服务

6个被改变选择的请求均在选择后23--324ms内得到首个正增量native work，
没有在选择前获得该attempt的正进展，也没有被同次压力处理立即撤销。
8组与局部reference-only候选的比较中，选中请求全部先执行，领先中位数
17.34s，最大45.71s。这是同一实际运行的服务顺序，不是反事实节省JCT。

进一步与完整Full对齐同一request、prompt/output指纹和原到达时刻：

| workflow中的选中请求 | 首输出提前 | 对应完整workflow JCT改善 |
| --- | ---: | ---: |
| game simulation | 92.21s | 25.65s |
| desktop media | 21.32s | 7.47s |
| web CMS | 56.98s | 19.89s |
| data warehouse | -23.02s | -8.36s |
| system networking | 38.42s | 11.21s |
| ML inference | -3.31s | 0.0005s |

局部变化不保证比另一次完整运行更早：队列、工具返回、后续资格与原生
服务的历史已经不同。这也是不能把局部oracle视为最优JCT上界的原因。
六个相关workflow的JCT改善合计55.85s，其余十二个退化合计80.81s；
总体净退化24.96s，平均退化1.387s，与完整报告一致。
不能把这些组间差异全部因果归于六次选择；一组运行也未建立重复收益。

存在明确的容量/类别取舍：最后一次变化选择了剩余分数747.14s、
上下文35149 token的续接，同时使剩余分数173.34s、上下文6884 token的
首次请求及另一较长续接落选。它遵守现有类别规则，说明仅提供更准确的
标量分数并没有取消类别和装箱约束。

下一步应优先检查真实释放边界的ready候选集合、选择后的实际服务和
完整workflow进展，而非只提升排序变化次数。原active连续性保留；
需要单独验证的方向是将有界事件补位纳入同一选择，以及容量感知的
候选组合，不能以强制频繁换出ready agent制造竞争。

## 到达序列与新小样本

用户允许更换随机种子。先固定24--31，按首间隔不大于一个分布均值、
最大间隔不大于三个均值、提交窗口不超过完整对照makespan筛选。
原始各间隔未裁剪，全部候选保留，未读取GPU胜负。
首个满足者seed28的提交窗口仅747.51s，为期望窗口的43.33%，
有限样本到达过于集中。因此 `main_arrivals_r3/review.json` 将其保留但
不接受为下一次持续到达方案。后续筛选还要限制实现窗口为期望的
80%--120%，用预先声明的32--47新种子族；仍只用于开发诊断，
不能称为无条件随机Poisson样本或已证明HBM压力。

该规则现已完成，首个满足者为seed32。保留相同18项目、独立任务排列
seed21和5个初始workflow，名义到达率仍为0.0075349264 workflow/s，
对应平均132.72s。13个后续间隔的实现均值141.38s，首间隔10.69s，
最大384.21s，最后提交1837.95s，为期望提交窗口的106.53%。
它保留持续到达窗口，但最长仍有约6.4分钟间隔；尚未证明持续HBM压力
或跨workflow竞争足够，不能把换种子本身解释为调度改善。

正式准备输出为 `main_arrivals_r5/arrivals.json`，筛选的全部16个候选及
其原始间隔在同目录 `selection.json`。r4先暴露了筛选器与正式生成器
计算相同名义rate时浮点运算顺序不同的问题：时刻差小于1e-12s，
但时间表摘要不同。r4及拒绝原因完整保留；r5统一计算顺序，并在生成后
核对筛选摘要与正式时间表摘要完全相同，未重新选择种子或改变约束。
这只是准备文件的一致性修复，没有影响任何已运行GPU比较。

六项目pilot也已完整完成，CPU收尾及进程退出已确认。实际model-work
P90/P10只有2.151，24个JOIN中18个singleton、6个double、1个嵌套；
child调用中位数24、P90为39.1，六个root均有终态并行委派延期提醒。
仍未形成预期的强异构/高并行结构，保留所有结果，不自动扩到18项目。
新人口变化后，旧到达表仍需匹配新控制重新标定，换种子本身不能保证

新增审计、跨臂传播与到达几何检查及原有真实runtime dispatch相关检查共
58项通过；包含过短提交窗口的拒绝、按相同比例缩放控制速度后种子
选择不变，以及实际准备入口拒绝筛选与正式时间表不一致的回归检查。
本轮未修改线上调度代码。这是CPU诊断，非新的GPU性能资格。

## 后续比较应改变什么

保留active agent的连续性。优先让真正的额度释放事件触发有界候选
选择，将原本分散的首次准入和普通续接机会纳入可观测范围；现有500ms
dispatch提供起点。若启用，两臂必须使用相同补位入口和周期，单独比较
排序，否则不能区分补位改善与剩余工作量排序收益。

候选评估应同时考虑剩余workflow关键路径和完整容量成本。先在少量
ready候选中检查不同组合，处理“一个较大续接挤掉多个更短workflow”
的取舍，并保留真实JOIN依赖、sibling整体进展和原生准入安全条件。
是否调整原恢复类别需要显式声明；只优化类内rank无法改变类别造成的
短任务延后。上述是下一轮待验证的策略边界，本轮未将其作为已实现收益。

每次选择继续追踪完整候选、grant、撤销和正增量native service，最终
统计全部workflow的完整JCT。局部服务提前、更多选择变化和更高迁移量
都不能单独作为成功标准；当前一组oracle/Full对比不足以证明重复收益，
也不能据此否定更广范围的workflow感知准入。
