# 关键请求服务交错的进一步核对

2026-10-28。本文继续核对原始准入前卸载 `716ef9a3` 与分组版
`913e3238` 的 24.981494 秒工具后继服务后增量，不是当前运行中
`a5164fe3` 的性能结果。保留全部 18 workflow、3674 请求、原生停止、
正常长尾及完全一致的关键请求链；没有启动 GPU 或修改生产策略。

## 其他 worker 区间属于哪些阶段

原始核对将 11.067325 秒标为请求未参与的其他 worker 覆盖区间。
新算子按每个请求的真实生命周期及自己的 worker 区间并集先取补集，
再与全局 prefill/decode 并集相交。重叠阶段单独计一次，不把它们
重复相加。原始日志大小、SHA256、时钟、回执及完整关键请求覆盖均核对。

2973 个关键工具后继求和后按 18 workflow 等权平均：

| 请求自己的成员区间之外/s | 准入前卸载 | 分组版 | 增量 |
| --- | ---: | ---: | ---: |
| 仅其他 prefill worker 覆盖 | 141.510561 | 152.699259 | +11.188698 |
| 仅其他 decode worker 覆盖 | 2.842442 | 2.721068 | -0.121374 |
| 其他 prefill/decode 同时覆盖 | 0 | 0 | 0 |
| 所有 worker 并集之外 | 0 | 0 | 0 |
| 合计 | 144.353003 | 155.420327 | +11.067325 |

因此，应优先检查其他 prefill 插入的时机、其批次组成及恢复依赖，
而不能把新增 11.07 秒直接当作控制 CPU 空转。这里的 prefill worker
区间仍可能包含 CPU 提交、依赖等待及传输，不等于有效 GPU kernel
计算；这个分类不能进一步分出其中可消除的等待。

## 关键请求实际获得的 decode 形态

第二个算子只读取同一组 2973 个关键工具后继的实际 decode 成员区间。
每个区间按请求生命周期裁剪，验证同一请求的 decode 区间没有重叠，
并逐项复现原始 decode 区间并集及其 +14.601518 秒增量。

| 关键工具后继观测 | 准入前卸载 | 分组版 |
| --- | ---: | ---: |
| 正生命周期 decode 成员观测数 | 464588 | 464588 |
| decode 成员区间平均/ms | 24.188944 | 24.754665 |
| 按成员区间时间加权的实际 batch | 10.193983 | 10.397393 |
| 同权重 batch 平均上下文/token | 59407.532785 | 59693.858600 |
| decode 区间求和后等权 workflow 均值/s | 624.327388 | 638.928906 |

这些是关键链的成员加权统计，不是全局 worker 的单次批次统计。
同一个 batch 可以同时服务多个 workflow；分别计入它们自己的 JCT
路径不表示该 batch 在 GPU 上被执行了多次。两轮观测数量相同，
不能把差异解释为这些请求多生成了 token。

按照实际 batch、2048-token batch 平均上下文档位及 CUDA Graph 状态
还保留了对称分箱恒等式：共同档的数量/组成项 -12.113765 秒、
共同档内部成员区间项 +2.607385 秒、未共同匹配档项 +24.107898 秒，
三项合计 +14.601518 秒。大量变化落在未共同匹配的档位，因此不能
将它们强行归因为纯 batch 大小效应、控制增量或计算变慢。分箱是
描述性核对；没有相同批次的反事实，也没有独立模块因果估计。

## 对优化判断的影响

24.98 秒现在更明确地表现为：请求自己的 prefill 约少 0.69 秒，
自己的 decode 约多 14.60 秒，其他 prefill 覆盖约多 11.19 秒，
其他 decode 覆盖约少 0.12 秒。它与更大的全局有效 batch、较高的
全局 worker 输出率并不矛盾；关键链可能得到不同的服务时机和批次。

下一步继续检查完整当前 FULL 是否减少这些损失，以及 JOIN 恢复、
预测工具卸载和批次准入如何改变 prefill/decode 的交错。没有据此
提高所有工具后继优先级、引入 ready-agent 轮换或修改正在运行的代码。
历史两轮完整独占控制 CPU 仍未知；新增阶段核对没有填补这个证据缺口。
