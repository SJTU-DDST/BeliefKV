# 短工具执行连续性、JOIN 阻塞与恢复代价

日期：2026-10-22，北京时间。
本文包含最新完成 trace 的离线证据、原论文核查与下一候选设计。
运行中的 V123 普通前沿恢复消融不修改，不宣称新设计已经产生 GPU 收益。

## 1. 重新排队确实形成了大量串行等待

V2750 使用 V122 Full 的 V2726 提交时图快照，以及同轮 JOIN-only/native
已完成的独立工具后继人口。新增审计只聚合这些封存报告，不再次读原始
trace；报告保留全部输入及分析器、统计辅助源码的 SHA256。

同一 agent 以 workflow/invocation 身份分组；相邻轮次必须满足前一后继
request ID 等于后一 origin request ID，才计为连续链。短工具 <=200ms
仅用于离线诊断，不是已经启用的优先级阈值。全部三组的同 agent 队列
区间均没有重叠，累计值与区间并集一致。并行 sibling 的等待不合并为
一条串行关键路径。

| 全程人口统计 | Full | JOIN-only | native |
|---|---:|---:|---:|
| 有首次服务证据的工具后继 | 5804 | 6447 | 7688 |
| 有此类后继的 agent | 155 | 164 | 168 |
| 至少有 10 轮连续短工具的 agent | 115 | 125 | 131 |
| 每 agent 最长连续短工具链 P50 | 17 | 19.5 | 19 |
| 最长连续短工具链 | 257 | 148 | 275 |
| 每 agent 短工具后累计排队 P50 | 242.36s | 198.26s | 257.24s |
| 每 agent 短工具后累计排队 P90 | 837.35s | 693.79s | 879.86s |

Full 的 5649 对相邻工具轮次中，5569 对有精确 request 链接。
其中 1948 个后继在提交时是已观察 JOIN 的唯一剩余 child。
另有 13 个成员关系未证明、6 个工具/委派混合轮次保留为独立状态，
不将它们补成有服务证据的样本。其他两组没有此报告的提交时阻塞者
快照，保持未知，不能解释为零个关键 child。

具体例子：`python_system_automation_hard_062_bug_investigation_expert_01`
的 invocation `deepagents-invocation:aac1de148edec8f9` 有 95 个工具后继，
工具轮次累计仅 0.479s，后继排队累计 1438.75s；74 个提交快照是唯一
阻塞 child。这些队列区间在同一 agent 上串行发生，足以说明短工具往返
不能仅靠隐藏工具运行期间的 H2D 来处理。

但排队本身不是 CPU 调度开销，也不是可以直接删除的时间：GPU 可能正在
公平地服务其他 workflow。提前此 agent 可能推迟别人；程序未来调用图
仍未知，唯一 child 也可能继续运行很多轮。因此这些统计没有给出可节约
JCT 百分比，不用工作量不同的三组之间的差额声称因果收益。

## 2. 已有工作已经认识到这个问题

| 工作与核查位置 | 已覆盖的部分 | 对本项目的约束 |
|---|---|---|
| Agentix，NSDI 2026，§2、§3.2、§4.2 | 多次 LLM 调用的排队会累计到程序响应；PLAS/ATLAS 继承程序服务历史，避免每个新调用都被当作无历史的新程序 | 工具后继保留程序地位不是新问题；需要忠实的程序调度强对照 |
| InferCept，ICML 2024，§3.1 | 中断恢复请求继承原始到达时间，与新请求共同调度；显式讨论保存/恢复成本及恢复请求的队列待遇 | 不能把中断恢复描述为先前全部放到队尾，也不能将原始年龄继承包装为新设计 |
| ThunderAgent，§2--3 | 细粒度无状态调用造成工作集压力；通过 program 级资源与状态管理改善多轮推理 | 工作集局部性和 program 粒度本身已有直接近邻 |
| AgentInfer，公开 scheduling design | 明确指出短工具频繁回到全局 FIFO 会丢失局部性并重复等待；用多队列、时间片与可续期的短期地位处理连续性 | 短工具续接、短期亲和或 TTL 单独不足以构成新贡献；这是作者实现设计，不等于已独立核验其论文级性能 |
| TokenCake v5，§3--5 | 联合 DAG 关键性、时间、空间和资源代价进行 agent 调度及 KV 管理 | “关键路径加 KV 代价”同样不能仅靠机制名称声称新颖 |

因此研究问题应更具体：在同等程序公平与已观察信息下，动态 JOIN 阻塞者
发生变化、程序有长状态且容量紧张时，怎样在保持批次填充的同时，用
有界的执行连续性减少重复排队和状态切换？增量必须超出上述强对照，
不能拿 request FIFO 或只有 parent 优先作为唯一对手。

## 3. 用一个共享服务预算组织三个方向

建议以 root workflow 为服务账户，用当前可执行 continuation 消耗同一
份模型服务预算。实际阻塞依赖决定预算内的先后，恢复代价只在相近服务
地位和等待预算内参与选择，外部等待决定是否暂时让出这次连续执行机会。
不将三种信号简单叠加为一个任意权重分数。

### 3.1 程序地位与短工具连续性

服务账户跨请求、child 和工具调用保留。短工具期间释放 running slot，
其他 workflow 照常填充 batch；工具很快完成且原执行份额尚未耗尽时，
后继可在相同程序优先级内延续顺序，无须重新等待一次完整轮转。

超过连续执行期限、预算耗尽、出现等待过久的其他程序或关键 parent 时，
恢复普通程序队列地位。长工具期间不保留 GPU slot；工具等待不记作模型
服务，也不产生新服务额度。新 child 继承 root 账户，不能靠频繁 spawn
获得额外公平份额。

连续性先作用于下一次自然准入，不中断正在生成的请求。若不接原生运行
请求抢占，它只限制下一请求的连续性优待，不能宣称严格的抢占式时间片
上界。已有模型服务核尚未连接 executor，不用输出 token 或包含排队的
请求墙钟冒充真实服务；接线前先明确 batch 内的服务归属，并对强基线
使用同一规则。

### 3.2 已观察完成依赖决定有限份额内谁先执行

JOIN 已满足的 parent 沿用当前有界优先；实际 WAIT_JOIN 的唯一剩余 child
可以共享同一份有限优先额度。嵌套链不能重复领取多份额度，也不能将
阻塞层数直接乘成 JCT 收益。普通工具结束不自动获得关键地位。

这一步复用事件更新的 JOIN 索引；不每 decode 步重建图、扫描长前缀或
预测未来 spawn。已有独立最后 child 候选可用于先检验这一部分，
必须在 Full 和纯调度强对照同时开启，保持可归因。

### 3.3 恢复服从容量可行性和真实执行机会

在相近程序地位中，比较原生匹配已经提供的必要状态、缺失 FULL 与当前
可用容量。只有排序仍有效、原生准入可以落实的目标，才给予普通需求
恢复；保持 work-conserving，容量不满足时允许其他可执行请求填充。
不为排序反复进行同样的 prefix 匹配，也不为了预取而新增长期驻留保护。

短工具阶段可机会性保留已有 HBM 状态，但保护可在容量压力下撤销；
Host 有效副本与原生引用依赖继续保证正确性。若 EOS parent 需要容量，
不能让普通工具的连续性偏好挡住必要回收。

### 3.4 外部等待仅提供有证据的有限让步

另一必需分支正在等工具并不证明存在 slack。只有经校准的在线剩余等待
保守界足以覆盖让步成本，才允许把有限服务机会让给别的 workflow；
置信不足按普通规则执行。工具真实结束后立即失效，不能使用 trace 中
未来的工具结束时间。

V2726 全部 5804 个后继中只有 19 个提交快照存在另一必需分支的工具等待。
这不是所有决策点的全人口，但不足以支持当前立即加入复杂 slack 预测。
先运行低成本的依赖与连续性候选；外部等待分支暂不进入默认高频路径。

## 4. GiB 级目标有时间和容量时应积极完成传输

用户提出的同空间判断适用于当前实现：FULL token 槽预先整段分配，浅层
和全层恢复占用同一范围的目标槽。因此，在容量已满足、请求确定即将
执行、且没有更紧急 H2D 的情况下，早点完成全部剩余层可以降低后续
layer fence 等待风险，不会再节省 HBM 的浅层传输没有理由刻意停住。

当前 dependency 恢复已经区分这两种情况：

- JOIN/EOS 用 eager：必要 Mamba 状态先行，立即提交全部 FULL 层。
- 普通执行前沿曾用 pipeline：首个 FULL 层先行，原生准入等边界续传尾部。
  V123 已独立关闭这条普通额外恢复路径，原生需求加载继续保留。

因此，低残余等待的 217 个样本不能成为要求 GiB parent 只取首层的依据。
它们混合不同请求，只有 7 个有明确状态归因，也没有关闭预取的反事实。

容量相同不代表提前传输的其他代价相同。大批已提交 H2D 仍可能推迟另一
parent 的必要状态，与模型计算争用 HBM 带宽；目标执行延后或失去驻留
时，提前传完的部分还可能需要重传。继续使用状态先行与传输优先级，
按现有批次边界推进；不声称已经提交的 DMA 可以瞬间抢占。
是否充分隐藏按实际状态/逐层等待和最终 JCT 验收，不按预取 GB 数验收。

## 5. 本轮交付与实验顺序

新增 `scripts/audit_tool_requeue_fragmentation.py` 及 CPU 回归：
精确请求链、漏失轮次断链、长工具断链、跨 sibling 隔离、区间并集、
零长度区间、不完整人口、未知关键性、重复请求及异常时钟。
V2751 的 114 项定向回归全部通过；不据此宣称此前全仓失败已解决，
也不把它替代现有 serving/engine 资格。

正式离线结果为 `experiments/reports/v2750_v122_tool_requeue_fragmentation_20261022.json`。
初版 V2749 保留，存在服务后继总数被同名分布字段覆盖的报告结构缺陷，
不用于新结论；schema2 改为独立的 `served_successor_requests` 并补了回归。

V123 继续只验证普通前沿恢复的删除，不混入本设计。待它完成后，先检验
已有 parent+最后 child 的简单候选及公平的程序连续性对照，再在同一
调度上加入 KV 协调。复杂工具 slack 留待证明机会规模。
所有比较保留任务质量、输出量、请求数、轨迹差异和统一去长尾口径。

创新性验收还包括：服务预算继承和短工具连续性单独已有强近邻；需要用
同信息强对照证明动态完成依赖变化与长状态切换的联合决策确有额外收益。
当前尚未证明这一点，不能将设计草案当作 OSDI/EuroSys 贡献已经成立。
