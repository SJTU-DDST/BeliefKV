## 结论与下一步

复用已经完成的 12 初始 workflow、平均 70 秒到达的匹配对照，不再重跑同一对照，也不同时改变到达方式或 trace 工具时长。运行时 A→B 预测式工具卸载是保留路径，不是待关闭的“长工具替换”。普通合并窗口与完整控制均为两秒；JOIN/EOS、prepare_host 保留，工具预取、普通恢复租约、逐层 handoff 和 mixed chunk 关闭。

本轮 oracle 没有达到预先声明的平均 JCT 至少改善 5% 的诊断目标。下一步先核对剩余时间成本和组合选择，使后续实验回答具体机制问题；不据此开始工作量预测器训练或其他 baseline。

## 选择与实际服务

严格匹配审计先复现本轮实际 oracle 的选择，再在同一观察状态下替换成修复后的关闭排序对照；两边都保留 ready JOIN 保护及观察到的 sibling 邻接，不使用旧的类别/上下文参考来夸大排序影响。

2171 次实际控制中，有 589 次顺序变化、66 次选中集合变化。
73 个新选请求都匹配实际授予、未被同轮压力撤销，并获得后续原生服务；
其中 63 个在下一控制或记录的同 agent 干预前完成有效批次。
共同窗口内仅有 4 次集合变化、7 个新选请求服务、5 个有界有效批次完成。
其余变化主要位于共同窗口之后。

66 次集合变化中，15 次选入更少的 agent、3 次更多、48 次数量相同。
其中存在一个较短的大 KV workflow 替换两个可执行对象，以及拆开等待 JOIN 的 sibling 的局部选择。
这些记录支持检查容量组合与 JOIN 效用，不能证明具体选择造成了全部 JCT 差异，也不等于实际 decode 宽度。

## 成本换算候选

从已完成的关闭排序对照获得 worker 区间代理：

- 加权 decode 步长：23.478283345973637 ms；
- 至少 256 输入 token 的 prefill 批次中，单位输入中位数：
  0.0832252503024952 ms/token；
- 等价 prefill/decode token 权重：0.0035447757860358115；
  原来 0.01 的换算约为此比例的 2.8210528969 倍。

原成本报告还保留 145004 个 decode 批次、8368 个 prefill 批次和
858 次至少 1024 token 的 H2D 复制。Worker 区间可能含停顿与 CPU 提交，
decode 步长不是请求独占 GPU 份额；这不是纯 GPU 时间校准，也未证明成本偏差是回退根因。

`workflow_work_oracle.py` 增加显式 v2 artifact：
`workflow_model_tool_calibrated_cost_oracle_v2`。
它分别声明输入与输出的时间系数，并明确输入成本是在请求完成时移除，
还是在第一次实际观察到正输出进度后移除。零输出或仅请求登记不能移除 prefill。
运行时通常每 128 token 或完成时上报，第一次正进度不等同于物理首 token 时刻。

固有工作量定义仍为 `input_increment + 100 * output_tokens`；
0.01 人口统计、工作量分层、完整请求、源图及工具时间保持原样。
v1 拒绝 v2 成本字段，旧冻结 operator 会拒绝新 kind，避免静默忽略参数。
缓存路径和逐节点参考计算使用相同新参数；默认保留原浮点表达式。

154 项定向 CPU 测试通过，无失败或跳过，包含真实构造入口、工作守恒、
实际输出进度及 80 组随机 DAG 的缓存/参考一致性。
证据：
`oracle_toolaware_initial12_mean70_live_r1/calibrated_oracle_costs_cpu_r2.xml`。
尚未生成 v2 GPU 配置或执行共享回归、GPU 检查和性能实验。
本模块是可选成本候选，不是已验证改善或最优 JCT 上界。

不得静默豁免这些问题或将本轮诊断称为通过稳态验收。

99.4440% / 99.3682%，零利用率样本时长 1.401 / 0.801 秒。
这不能证明计算达到上界，但不支持将本轮主要问题归为持续缺少 ready 工作。
