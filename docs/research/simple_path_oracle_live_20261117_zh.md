# 简化 Oracle 的运行期 CPU 检查

本记录属于当前 Oracle 实验的中途证据，不是新的 GPU 实验或完成结果。
运行注册为
`workflow_original133_host400_mean60_simple_path_oracle_20261117_r4.registration.json`，
服务冻结提交为 `61a55c953063bcdb88a0f34faf3753234c10f34d`。
实际 driver 使用 `--request-timeout-s 3600.0`，保留独立 1800 秒执行兜底。
133 个原项目、20 个初始 workflow、平均 60 秒到达、Host 400 GB、
固定 18 个测量成员均不变。Oracle 完成并实际退出后再启动 D3。

## 局部选择是否传递到服务

证据目录位于 Oracle 开发树的
`experiments/reports/simple_path_oracle_20261117/ready_service_guard_3600/`。
各分析分别封存原始 JSONL 的完整行前缀及哈希，不是原子快照，不能
把不同前缀的分母拼在一起。所有分析均隐藏 CUDA、固定一个 CPU、使用
nice19；没有修改服务冻结代码、运行配置或队列顺序。

- `periodic_live_r1.json`：截至到达原点后约 951.51 秒，
  468 次周期控制中有 86 次跨 workflow 的逻辑容量竞争；
  384 次准入均保留资格并关联到后续精确请求服务，其中 344 次在下一次
  控制或同 agent 干预前获得新的有效服务，343 次在该界限前完成有效批次。
  当前固定共同吞吐窗口只观察了一部分，固定 18 个成员完成 3 个。
- `free_service_live_r1.json`：观察到 24 个去重后的事件准入冲突决策。
  这些事件与周期选择存在联系，不能简单相加成为独立竞争机会。
- `global_choices_live_r1.json`：543 次实际全局 Oracle 选择可由冻结策略
  重放；对同一个局部状态去掉普通剩余工作量排序后，347 次候选顺序变化、
  45 次所选集合变化。49 个新选精确请求均保留资格且最终获得服务，其中
  46 个在下一次控制或干预前获得新的有效服务并完成有效批次。
  该文件绑定了单独封存的更长前缀。
- `paused_live_r1/`：保留 Full 与 Oracle 的 ready/JOIN/tool-paused
  曲线和逐点 CSV。Oracle 此前缀只覆盖到约 914.66 秒，不能把它与
  Full 的完整区间均值直接比较，也不能把未观察尾部填成零。

局部重放保留候选、JOIN 保护、sibling、类别、容量及原规则预算。
它不是另一条 GPU 轨迹，不能证明替代集合在原生物理状态下立即可执行，
也不是完整 JCT 的反事实。当前实验还包含有界工具边界让位和执行兜底，
不能按“只改变排序的严格消融”解释。新增只读入口
`review_global_choices.py` 明确区分这些边界，复用既有逐决策及服务关联检查。
普通事件准入、工具让位的效果没有计入上述周期集合变化次数。

完整结果仍需固定 18 个成员自然完成、原始请求和输出一致、fresh drain、
实际退出后判断。匹配 Full 的平均 JCT 为 1274.833468 秒；降低至少 2%
对应不高于 1249.336799 秒，同时检查共同墙钟窗口吞吐。
以上局部次数不构成达到这一目标的证明。

## 执行兜底的终结批次边界

`cpu_completion_r2/observed.xml` 用未改动的绑定 Oracle fixture，通过
真实 `NativeAdmissionRuntime.on_batch_completed()` 复现了一个边界问题：
非终结服务会清零计时；终结回调先移除 `runtime.visible`，随后 guard
只凭 visibility 判断服务，因此终结批次本身未清零。结果为 1 通过、
1 断言失败，属于缺陷复现，不是服务资格通过报告。

`cpu_completion_r1/` 的初次 fixture 把请求改到另一个 workflow，
被 Oracle 绑定检查拒绝；保留该失败，但不将它作为缺陷证据。
r2 使用原工作流、原 prompt 和原 1000 token 输出长度，排除了此问题。

当前 20,895 个请求最少输出 19 token，没有单 token 请求；
通常已经由此前非终结批次清零，不能据此声称此缺陷导致了当前回退。
Oracle 与待启动 D3 的已绑定源均未为此被热改或重新启动。
最终线性整合时需要补上精确终结请求的服务确认，保留请求对象、
attempt/epoch/session 身份校验，补实际回调顺序与陈旧请求的 CPU 回归。
这项修复不应增加新的排序分数、老化加成或物理容量信用。

## 后续 CPU 准备

终结回调修复已经在独立目录准备为 `49ce22f7`，101 项相关用例通过。
与 D3 的 CPU 预整合候选为 `1356a093`，791 项相关用例实际通过，
包括首次物化许可不能被兜底绕过、真实终结回调同时通知 D3 与兜底的检查。
这些候选尚未合入 main，当前 Oracle 与待启动 D3 的实验身份保持原样。
原缺陷复现报告、初次缺原生路径的跳过报告和预整合的初次失败均保留；
不能把多个执行范围相加成一次更大的新全套执行。

完成后的只读诊断入口为 Oracle 证据目录下的 `finish_diagnostics.py`，
其有效等待计划为 `complete_diagnostics_r2/plan.json`。
observer `112916/start94184665` 已实际运行并持续更新原子状态文件，
使用 nice19、单 CPU、隐藏 CUDA。它等待同一 Oracle 的完整比较与实际退出，
再次核对 fixed18 的 2991 个请求、362157 个输出以及匹配 Full 的精确工作，
然后运行全局选择、周期/事件服务、显式释放到服务、paused 曲线及同步
控制成本分析，并保存原生迁移、前缀丢失/重算和兜底诊断原字段。
这些计数口径仍需分别解释，不把累积计数或局部时延直接当成关键路径收益。
这个 CPU observer 不是 D3 启动依赖，不改变 GPU 队列顺序。

初次 `complete_diagnostics_r1` 的 observer 因重复更新时误用独占创建接口
而退出，没有执行诊断任务；实际进程缺失、原始 traceback、最后状态和
`failure.json` 保留。r2 改为使用现有原子状态发布接口，并已核实多个
心跳与真实活进程。GPU 运行和 D3 等待器均未被重启。

## 完整共同窗口的中途诊断

此节仍不代表 Oracle 的 fixed18 完整 JCT、fresh drain 或退出已完成。
`closed_common_window_r1.json` 封存了已完整观察的原冻结窗口
`[47.736661, 1404.818443)` 秒，按原生批次完成时刻分配输出，包含背景和
prefill 首次输出；窗口、原始任务、到达表和实际池容量均与 Full 一致。

| 指标 | 已完成 Full | 当前 Oracle 的完整共同窗口 |
| --- | ---: | ---: |
| 输出 token/s | 342.209295 | 333.094148 |
| decode token/s | 339.329587 | 330.271916 |
| 输出吞吐相对变化 | 基准 | -2.6636% |
| decode 吞吐相对变化 | 基准 | -2.6693% |

该窗口没有达到预先声明的 98% 吞吐非劣门槛。不能因局部选择次数增加或
尚未完成的 JCT 改善预期而宣布验收成功，也不改变门槛、成员或窗口。

`closed_window_control_r1.json` 使用原有控制成本分析函数，按共同窗口两端
累积计数的前后快照给出边界，不作插值。约计的线程 CPU 秒为：

| 计数 | Full | Oracle |
| --- | ---: | ---: |
| 周期控制含记录 | 0.978 | 1.137–1.138 |
| 工具替换检查 | 24.833 | 43.345 |
| Oracle 路径查询 | 2.574 | 10.811 |
| 新增执行兜底检查 | 未配置 | 0.0495–0.0496 |

工具替换检查增加约 18.51 CPU 秒；路径查询、边界计划与外层替换检查可能
嵌套，不能相加。双方 shared-path 采样均未启用，因此没有完整逐函数分解，
也不能把这些 CPU 秒直接当作暴露 GPU 空闲或可移除的 JCT。

`native_runtime_full_r1/runtime.json` 对原完成 Full 重新验证 2991 个请求、
完整 JCT 与退出后，复用现有原生执行区间分析。
`live_native_common_r1.json` 用相同且源码身份匹配的观测分析函数读取
Oracle 已闭合窗口。decode 组批分解按 forward 开始时刻归属，
与上述按完成时刻归属的输出吞吐分别解释：

| decode 指标 | Full | Oracle |
| --- | ---: | ---: |
| 平均 batch 宽度 | 15.513958 | 14.995651 |
| worker 时间加权 batch 宽度 | 15.863281 | 15.331495 |
| 每批平均 worker 区间 ms | 26.390271 | 26.295705 |
| 平均观测上下文 token | 36818.629 | 37171.305 |
| 需要 CUDA graph padding 的批次 | 0 | 0 |

平均 batch 约收窄 3.34%，每批 worker 区间基本不变，是服务组合发生变化的
证据；还不能证明收窄完全由某个规则或 CPU 开销造成。worker 区间不是纯
CUDA kernel 时间，区间覆盖不能替代 GPU 利用率。

`boundary_markers_common_r1.json` 在同一窗口记录 83 条替换授予标记：
55 条原预测式工具替换、28 条新工具边界替换，后者共列出 29 个 donor。
另有 32 条去重发布的边界计划记录。这些是标记清点，不是独立决策、
已验证有效服务或 JCT 改善次数；完整服务关联仍由收尾审计判断。

## 自然尾部推进

`live_tail_r1.json` 在到达原点后约 3405.49 秒观察到 15/18 完成，
三条剩余 workflow 最近的有效原生服务距观测边界均不足一秒。
`live_tail_r2.json` 在约 4279.93 秒观察到 17/18 完成，剩余 desktop
workflow 正在执行真实的 `root:context-summary:000021` 模型请求，
该边界距最近有效服务约 30.9ms，仍为 active。
这两份前缀都没有执行兜底选择事件，不能将其正常长尾称为 1800 秒饥饿。
继续保留这条内部模型工作及完整自然 JCT，待全部测量成员完成后收尾，
随后按既有队列进入 D3。
