# 简化 Oracle 的运行期 CPU 检查

本记录属于当前 Oracle 实验的中途证据，不是新的 GPU 实验或完成结果。
运行注册为
`workflow_original133_host400_mean60_simple_path_oracle_20261117_r4.registration.json`，
服务冻结提交为 `61a55c953063bcdb88a0f34faf3753234c10f34d`。
实际 driver 使用 `--request-timeout-s 3600.0`，保留独立 1800 秒执行兜底。
133 个原项目、20 个初始 workflow、平均 60 秒到达、Host 400 GB、
固定 18 个测量成员均不变。Oracle 完成并实际退出后再启动 D3。

## 局部选择是否传递到服务

证据目录位于 Oracle 开发树的
`experiments/reports/simple_path_oracle_20261117/ready_service_guard_3600/`。
各分析分别封存原始 JSONL 的完整行前缀及哈希，不是原子快照，不能
把不同前缀的分母拼在一起。所有分析均隐藏 CUDA、固定一个 CPU、使用
nice19；没有修改服务冻结代码、运行配置或队列顺序。

- `periodic_live_r1.json`：截至到达原点后约 951.51 秒，
  468 次周期控制中有 86 次跨 workflow 的逻辑容量竞争；
  384 次准入均保留资格并关联到后续精确请求服务，其中 344 次在下一次
  控制或同 agent 干预前获得新的有效服务，343 次在该界限前完成有效批次。
  当前固定共同吞吐窗口只观察了一部分，固定 18 个成员完成 3 个。
- `free_service_live_r1.json`：观察到 24 个去重后的事件准入冲突决策。
  这些事件与周期选择存在联系，不能简单相加成为独立竞争机会。
- `global_choices_live_r1.json`：543 次实际全局 Oracle 选择可由冻结策略
  重放；对同一个局部状态去掉普通剩余工作量排序后，347 次候选顺序变化、
  45 次所选集合变化。49 个新选精确请求均保留资格且最终获得服务，其中
  46 个在下一次控制或干预前获得新的有效服务并完成有效批次。
  该文件绑定了单独封存的更长前缀。
- `paused_live_r1/`：保留 Full 与 Oracle 的 ready/JOIN/tool-paused
  曲线和逐点 CSV。Oracle 此前缀只覆盖到约 914.66 秒，不能把它与
  Full 的完整区间均值直接比较，也不能把未观察尾部填成零。

局部重放保留候选、JOIN 保护、sibling、类别、容量及原规则预算。
它不是另一条 GPU 轨迹，不能证明替代集合在原生物理状态下立即可执行，
也不是完整 JCT 的反事实。当前实验还包含有界工具边界让位和执行兜底，
不能按“只改变排序的严格消融”解释。新增只读入口
`review_global_choices.py` 明确区分这些边界，复用既有逐决策及服务关联检查。
普通事件准入、工具让位的效果没有计入上述周期集合变化次数。

完整结果仍需固定 18 个成员自然完成、原始请求和输出一致、fresh drain、
实际退出后判断。匹配 Full 的平均 JCT 为 1274.833468 秒；降低至少 2%
对应不高于 1249.336799 秒，同时检查共同墙钟窗口吞吐。
以上局部次数不构成达到这一目标的证明。

## 执行兜底的终结批次边界

`cpu_completion_r2/observed.xml` 用未改动的绑定 Oracle fixture，通过
真实 `NativeAdmissionRuntime.on_batch_completed()` 复现了一个边界问题：
非终结服务会清零计时；终结回调先移除 `runtime.visible`，随后 guard
只凭 visibility 判断服务，因此终结批次本身未清零。结果为 1 通过、
1 断言失败，属于缺陷复现，不是服务资格通过报告。

`cpu_completion_r1/` 的初次 fixture 把请求改到另一个 workflow，
被 Oracle 绑定检查拒绝；保留该失败，但不将它作为缺陷证据。
r2 使用原工作流、原 prompt 和原 1000 token 输出长度，排除了此问题。

当前 20,895 个请求最少输出 19 token，没有单 token 请求；
通常已经由此前非终结批次清零，不能据此声称此缺陷导致了当前回退。
Oracle 与待启动 D3 的已绑定源均未为此被热改或重新启动。
最终线性整合时需要补上精确终结请求的服务确认，保留请求对象、
attempt/epoch/session 身份校验，补实际回调顺序与陈旧请求的 CPU 回归。
这项修复不应增加新的排序分数、老化加成或物理容量信用。
