# 当前系统的新设计机会与筛查结果

2026-11-04，Asia/Shanghai。等待联合实验结果期间，只读检查当前 main、
冻结原生引擎及已完成 original73/Host400 对照；没有修改运行中的代码，
没有增加 GPU 实验。当前联合实验同时验证预测器、组合目标和控制开销变化，
本次机会分析不能替代它的完整结果。

## 判断

两个现有设计已经覆盖“选择谁”和“为所选执行周转 KV”。
后续最有区别的候选是**在驻留和资格保持不变时，决定下一段实际计算推进谁、
推进到什么边界**。它可能连接工作集选择与工具/JOIN 的实际推进，但本轮
只建立局部机会，尚不足以作为已验证的第三个贡献。

另一个值得补强的部分是从 sibling 数量覆盖升级为**真实 JOIN 瓶颈评价**。
它应纳入 D1，不另拆贡献。Host 备份与迁移干扰管理属于 D2 的后续优化；
注意力 kernel、图捕获和低精度 KV 则是独立引擎优化，应同样提供给 baseline。
设计点的数量不能代替各点的必要性、机制差异和端到端证据。

## 1. 驻留工作集内的计算推进

### 当前缺口

冻结引擎 `scheduler.py::get_next_batch_to_run` 在有可执行 prefill 时先选它；
`get_new_batch_prefill` 又先为已有 chunk owner 分配输入预算。
`prefill_decode_interval` 是固定步数控制，当前配置未启用。
已有 `DemandPrefillPipeline` 允许在一份原生 H2D 未完成时推进独立 decode，
并不负责连续计算型 prefill 期间的推进选择。

已有完整关键路径审计中，非排序 Full 平均 JCT 为 1081.531 秒，
首次启动到请求完成约 657.706 秒，占 60.81%。
共同墙钟窗口内 prefill 占两类 worker 时间约 37.50%。
这些是记录 worker 区间，包含主机和依赖开销，不是独占 GPU kernel 时间；
prefill 是必要工作，不能直接删除。

### 新增离线筛查

入口：
`scripts/audit_resident_decode_prefill_frontiers.py`。
复用已验证完整的 18 条测量 workflow、2991 条请求及封闭原生日志。
全部背景工作也参与连续 prefill 段的识别；这不是只在共同吞吐窗口内的统计。

要求连续 prefill 前后均有 decode，比较同一
request/workflow/invocation/context/epoch 的输出报告位置。
排除在该段内又进行自身 prefill 的请求；已知 attempt/session 冲突也排除。
原日志的 decode 样本省略了 attempt/session 字段，不能从 receipt 填回并
宣称观测到了完整物理身份。因此下面是**逻辑连续的计算机会筛查**，
不是未间断驻留、增长容量或原生可执行性的证明。

| 筛查量 | 数值 |
| --- | ---: |
| 全部原生服务样本 | 126133 |
| 前后被 decode 闭合的连续 prefill 段 | 6995 |
| 前后仍有同一未完成 decode 请求的段 | 6989 |
| prefill 段墙钟长度 P50 / P90 / P99 | 59.54 / 234.07 / 2349.19 ms |
| 最长段 | 70.17 s，283 个 prefill batch |

最长段包含预热期，不用它代表测量组的典型等待。
全部段的墙钟跨度合计 1342.669 秒，prefill worker 合计 1217.349 秒；
两者不同，段内还可能存在控制和派发间隔。

局部模型让既有 decode batch 提前推进到某请求完成，用前后实际 decode
worker 时长中较大者乘剩余输出数，支付本地推进成本；之后的 prefill
相应推迟。它没有模拟改变后的成员、图、增长、工具返回和后续关键路径。
前后 batch 也可能不同，所以这不是经过校准的反事实 GPU 成本模型。

| 局部推进成本预算 | 测量关键路径上的不同请求 | 不同 prefill 段 | 每请求取最大值后的局部暴露代理合计 |
| --- | ---: | ---: | ---: |
| 100 ms | 270 | 274 | 78.834 s |
| 250 ms | 361 | 362 | 126.211 s |
| 500 ms | 403 | 400 | 205.906 s |
| 1000 ms | 438 | 424 | 442.216 s |

500ms 行中，按每请求最大局部机会去重，371 条后续是工具开始、
14 条是 SPAWN、16 条是 RETURN、2 条是下次模型提交。
“当前是最后未返回的 child”不等于“当前请求结束就会 RETURN”：
500ms 筛查中满足该在线 JOIN 状态的 236 次观察，有 226 次后续仍为工具。

**这些合计不能除以 18 当作可实现的平均 JCT 改善，也不是严格全局上界。**
多个机会相关，prefill 所属 workflow 会被推迟，提前工具还可能改变供给和竞争。
这里的“本地额外 decode”也不意味着全程工作量增加同样数量：
它可能只是把后续已有工作前移，但实际总成本仍受 batch 组成影响。

### 在线可见性进一步收紧机会

原生 tokenizer 定义了 `<tool_call>` / `</tool_call>`，已经输出的 token
可以作为阶段提示。当前 DeepAgents 事件却明确记录为完整 AIMessage 后
发布动作，没有增量 action boundary；未来需要单独提供有界增量观察。
只能观察已经生成的前缀，不能读取回放中未来输出长度、下一工具或 RETURN。

在测量关键路径上、段前已经输出 `</tool_call>` 的 203 次观察，
涉及 187 条不同请求，剩余输出数 P50/P90 都为 1。
按每请求最大值去重后的局部暴露代理仅约 **27.747 秒**。
相较之下，只有起始 `<tool_call>` 时，仍不知道参数是否很长；
需要预测才可能覆盖更大的机会，不能把“看见工具起始标记”当作即将结束。
多工具输出也可能在第一个关闭标记后继续。

因此，单独增加“工具关闭标记后插一步 decode”尚不足以支撑完整 GPU 对比。
更广的阶段推进候选仍须比较净工作流收益，不能重新包装为固定
每个 prefill 后插一步 decode 的旧方案。

### 若继续，机制如何设计

在原生 batch 边界比较下一段 prefill 与一小段已有 decode：

1. 保留已有 agent 资格和驻留，不为该机制发起迁移或撤销 ready peer。
2. 只用已发布的 workflow 权重、真实 JOIN 状态、已生成动作前缀和
   已观察服务成本；未知阶段回到原生策略。
3. 估计有界推进能否结束模型阶段，以及能提前触发多少真实后续工作。
   同时计入受延后 prefill 所属 workflow 的代价，不能只奖励完成者。
4. 首版让原有 running decode batch 共同推进，避免新增子批选择和抢占。
5. 从已有 batch 元数据维护小型状态，不增加每 token 前缀树遍历、
   同步模型推理或全 agent 扫描。
6. 同时约束 prefill 等待、长任务和完整请求 E2E normalized interactivity，
   不把 token 更平滑等同于完整 workflow JCT 下降。

应先做保持工作量和因果边的双向离线重排检查，至少支付受影响 prefill
的延迟，并比较预测信号覆盖；现有局部模型还不是这项验证。
只有净收益有足够余量，才与其他完成的改动合并到下一次 GPU 候选。

## 2. 用瓶颈与余量改进 JOIN 组合价值

### 当前评分确实缺少分支差异

`beliefkv/policy/workflow_combination.py::_evaluate` 按同组的
`unfinished_members`、`active_ready_members`、selected 数量计算：

```text
incremental_coverage = ((active + selected)^2 - active^2) / unfinished^2
```

同一 workflow 共用一个预测权重。此式表达 sibling 互补覆盖，
没有逐分支剩余模型工作、当前工具等待或 JOIN 完成余量。
当前纯收益目标保留这个分子，取消成本分母并不能补齐这项缺口。

### 实际多成员 JOIN 的尾差

仅统计已观察且完整结束、至少两个直接成员的 ALL-JOIN：

| 范围 | 组数 | 最早到最晚 RETURN 差 P50 | P90 |
| --- | ---: | ---: | ---: |
| 完整日志中所有已结束组 | 68 | 38.146 s | 200.386 s |
| 测量 workflow 所属组 | 19 | 33.790 s | 217.622 s |

测量 19 组在首成员返回后累计尾段为 1307.304 秒。
对应最后 child 与自身 worker 区间重叠 478.810 秒，
与工具等待重叠 559.327 秒；未观察到这些尾段与该 child 的嵌套 JOIN 重叠。
这些是暴露区间，不能未经交集核对直接作互斥分解；
其余时间也不能直接认定为可避免排队。
分支固有工作和工具阻塞就可能产生尾差，1307.304 秒不是调度收益上界。

### 建议机制

将 sibling 共同准入保留为资源允许时的偏好，再补充分支级条件进展：

- 判断谁可能决定已观察 ALL-JOIN 的完成，谁尚有余量。
- 工具已阻塞的分支不获得虚构计算收益；其条件剩余等待影响 JOIN 下界。
- 允许有余量的短分支稍后执行，把当前机会给能更早完成的其他 workflow；
  对确实成为最后瓶颈的 ready 分支，再提高推进价值。
- 仅处理当前已观察 JOIN，不推断未来分支；分支信息不支持时退回现有覆盖式。
- root/child 保持独立 agent 身份，workflow 仍是评价单位；不按 fanout
  获得额外权益，不为尚未 ready 的 sibling 等待或保留空批。

一个直观例子：A 已阻塞工具、还约 8 秒；同 JOIN 的 B 只需 1 秒模型工作；
另一个独立 workflow C 需 2 秒。若 B 具有足够余量，让 C 先完成再做 B，
仍可能在 A 返回前完成 B，同时改善 C 的 JCT。
反之若某 ready 分支已是瓶颈，就不应仅为凑齐 sibling 覆盖而把机会给其他分支。
这个例子说明评价对象应是 JOIN 完成，不能说明未知情况下可准确预测。

先用原轨迹的分支级 oracle 去替换覆盖分子，保留同一容量、候选集、
JOIN 保护、active 连续性和纯收益目标，做 CPU 决策重放；
确认确实改变可行选择后，再评估后续服务与净 JCT。
这属于 **D1 的深化**，不是单独增加一个设计点或现在排队新的 GPU 实验。

## 3. KV 周转还可以改进，但先补收益证据

备份和真实 offload 的优先级、无效备份字节、备份与 attention 的干扰值得检查。
例如，记录某份增量备份在再次修改、退休或回收前是否真的用于释放 HBM，
据此调整可选备份的批次与时机，同时保留真实需求的优先级。

不能将它说成当前缺少 Host 回收：
`HostDemandCapacity` 已为真实 offload 留预算，并有界回收 Device 上仍被
锁定的安全 Host 镜像；`IdleHostMirrorRecycle` 也已处理空闲期重复副本。
下一步需要的是实际字节生命周期与 stall 交集，而非把重复失败计数当作
有用状态丢失，或重复实现既有镜像回收。

如果未来确认备份干扰明显，可让非紧急备份接受计算压力反馈；
真实需求 H2D、必要 D2H 与可选备份分别保留各自优先权。
这属于 **D2 的完善**。没有当前负载上的净收益数据，
不重启已关闭的工具预取或逐层 handoff。

## 优先顺序

1. 完成本轮联合实验，先判断已有工作量选择和控制削减是否改善完整结果。
2. CPU 检查 JOIN 的分支级 oracle 是否能纠正现有覆盖分子的实际选择。
3. 继续计算阶段编排的双向代价分析；仅凭本轮局部机会不启动完整实验。
4. 按实际备份字节生命周期决定是否投入额外 KV 控制。

不追加逐层 handoff、工具预取、简单缩短 tick 或微小参数的独立 GPU 扫描。
内核优化、普通工作集切换、预测器增大和代码去重也不单独包装为新贡献。
