# 同步控制开销审计

2026-11-03，Asia/Shanghai。只读复核 original73、Host400、20 初始加
mean70 到达的非排序 Full、两轮 R5 horizon64 和 ThunderAgent
acting-decay。四轮均重新核对固定 18 个测量成员的完整执行、相同工作量、
fresh drain 和实际 owned-process 退出。没有修改服务策略、冻结目录或
启动 GPU 实验。

## 主要结论

工具阻塞 agent 与 ready-paused 消费者的替换路径，确实分别消耗
117.906983 和 131.919791 秒线程 CPU；两轮合计为 249.826774 秒。
非排序 Full 同一路径为 145.281469 秒。这是此前只列出周期控制几秒时
遗漏的一项较大同步成本，不能将原有周期控制数字解释成全部控制成本。

该路径的有效授予密度低、检查范围较广，值得优先优化。不过，当前
计时只有累计线程 CPU，没有每次调用的 wall、开始结束点和子阶段归因。
它包含原有事件处理和容量管理，不能将全部 118–132 秒称为新增排序
成本、GPU 空转或可消除的 JCT。

另一个重要发现是原生选批与结果处理的 CPU 尖峰较大，ThunderAgent
同样存在；因此不能只检查我方组合枚举和预测器。

## 工具替换的实际工作

| 最后快照计数 | 非排序 Full | R5 首轮 | R5 确认轮 |
| --- | ---: | ---: | ---: |
| 有非空候选的替换轮数 | 29334 | 26685 | 27341 |
| 未找到完整可执行配对 | 29086 | 26463 | 27121 |
| 实际逻辑授予 | 158 | 153 | 155 |
| 发起等待 ACK 的备份尝试 | 88 | 69 | 63 |
| 未找到完整配对 / 非空候选轮 | 99.1546% | 99.1681% | 99.1953% |
| 实际授予 / 非空候选轮 | 0.5386% | 0.5734% | 0.5669% |

“未找到配对”不是预测错误率，也不证明所有失败检查都能删除。容量、
安全副本、锁、工具状态和消费者完整需求都可能合理拒绝。备份尝试与
最终授予不是同一个事件；三项结果计数也没有强行补成互斥分区。
CPU 计时还包含没有找到 keys 的部分调用，因此不能简单用总 CPU 除以
choices，声称得到了严格的单次调用均值。

`ReferenceToolReplacement.run` 在原生 prefill 选批前同步调用，其现有
计时从事件排空前开始，覆盖：

1. 最多 128 个控制消息的 drain，及其中触发的事件应用。
2. 原生容量元数据更新、所有当前请求的流式增长刷新。
3. 最多 512 个 waiting 请求的身份集合、至多 8 个消费者候选。
4. 候选排序；R5 条件分布分支的 A→B 排序实际直接保留输入顺序。
5. 每个消费者的 prefix/reentry 和需求检查，以及每个消费者最多
   8 个 donor 的预测、容量、shadow、释放或备份检查。
6. 实际释放、再次核对需求、逻辑授予及相应日志提交。

当前 source 中的明确改进候选：

- **先做便宜的 donor 筛查。** 现在先对消费者执行
  `demand(refresh=True)`，之后才逐 donor 判断是否存在合格长工具阻塞者。
  无可用 donor 时，消费者的完整前缀观察可能已经白做。
- **复用单次检查内的需求元数据。** `permits → demand`、
  `_eligible → _live_consumer → _demand`、`_worth_offloading` 等多次进入
  同一消费者检查。reentry 本身已有 50ms 缓存，不能说这些全部都会重扫
  token；但预算、free-list 观察和资格检查仍会重复。
  `demand` 取得 headroom 后调用 `_current_residency_budget()`，没有把刚读到
  的 headroom 传进去，也会重新观察。
- **减少不必要的 shadow 构造。** donor 循环先调用
  `_refreshed_shadow_backup_selection`，之后才检查已有 settled 副本的
  release plan 是否足够。已有完整索引、可直接释放的 donor，可以考虑
  先查 settled plan；索引未完整或版本不明时仍必须刷新。
- **重新区分 rearm 的原因。** `rearm()` 清零普通卸载和替换两条 deadline。
  新请求、完成、ACK 会触发；每次接受不同对象的工具 hint 也会触发。
  在线 hint 刷新间隔按预测档位为 150/500/1000ms，所以“200ms 检查间隔”
  不是不可绕过的实际频率上界。应区分新工具/资格变化与同一等待的
  例行刷新，并为没有实质状态变化的失败配对保留有界退避。

这些是源码确认的重复调用与顺序问题，不是已有内层 profile 证明的
118–132 秒组成比例。不得为了缓存结果而跳过动作前的身份、工具返回、
native free、锁、D2H/H2D ACK 和实际容量复核。

## 原生同步阶段的现有采样

使用每 16 个 eligible prefill 采一个的既有探针，按精确 forward、
request IDs、输入增量和 prefix 几何与原生服务匹配。四轮各有一条
6-token、`forward_iter=1` 的探针缺少精确正式服务对应，明确排除；
未将其升级为测量证据。
共同窗口分别保留 325 / 328 / 329 / 312 个完整样本。

| 样本线程 CPU，P50 / P99 / max，ms | Full | R5 首轮 | R5 确认轮 | Thunder |
| --- | ---: | ---: | ---: | ---: |
| 原生选批，含准备与控制 | 14.84 / 699.44 / 776.50 | 11.38 / 659.23 / 759.36 | 12.44 / 639.28 / 689.05 | 10.76 / 808.98 / 1307.32 |
| prefill 结果处理 | 5.28 / 371.75 / 561.90 | 7.11 / 330.88 / 593.10 | 7.04 / 345.50 / 516.43 | 10.50 / 491.12 / 1027.91 |
| post-launch 物理控制 | 0.385 / 30.17 / 489.61 | 0.366 / 32.28 / 49.11 | 0.421 / 33.67 / 64.98 | 0.019 / 0.071 / 0.073 |

这只是已观测样本分布，不能乘以 16 作为整轮总 CPU。选批包括
HiCache 事件处理、chunk 前缀保存、请求整理、原生前缀匹配与内存分配、
自定义控制和最终 batch 准备；结果处理包括原生缓存维护和请求完成回调。
`run_batch` 中的线程 CPU 还包含模型提交，不是纯调度成本。

较大的选批/结果处理尖峰也出现在 Thunder 上，说明存在共享引擎层面
的排查必要；但不同方法的样本不是同一批请求，不能作逐样本因果差值。
缺少细粒度 native profile，暂不能将这些尖峰归因于某一个缓存操作。

## 同步控制路径与覆盖缺口

| 入口 / 工作 | 是否在 scheduler 线程 | 当前完整计时覆盖 |
| --- | --- | --- |
| 控制 socket、JSON、graph 应用、工具事件更新 | 是 | 通用 profile 关闭；部分嵌套在替换等累计计时 |
| 周期工作集衰减、暂停、恢复 | 是 | 已有 inclusive CPU/wall；不是整个 tick 的每个入口 |
| 工具 A→B 事件替换 | 是 | 累计 CPU；无逐次 wall、分位数或内层阶段 |
| 普通 free-dispatch 与 coalescing | 是 | 旧排序或组合选择有计时；整个补位入口未独立计时 |
| JOIN 阻塞预算交接、parent 物理恢复 | 是 | 有动作/拒绝计数，无独立完整 CPU |
| sibling 重试、逻辑共同准入与实际选批 | 是 | 有服务/容量计数，无独立完整 CPU |
| residency 同步、reentry、原生前缀观察 | 是 | 有调用计数与可选 decorator；本轮 decorator 关闭 |
| prepare_host、工具/JOIN prepare、Host 镜像回收 | 是，传输本身异步 | 无独立完整 CPU，部分在 post-launch 采样内 |
| JOIN/EOS H2D 规划、锁/lease、ACK 处理 | 是，传输异步 | 无独立完整 CPU，部分在 post-launch/选批采样内 |
| 请求完成、终态清理、会话缓存维护 | 是 | 结果处理仅有 prefill 采样；无全程细分 |
| 工具条件时间估计、hint 接收及刷新 | 是；可选模型另有 worker | 无独立完整 CPU，部分嵌套于以上入口 |
| 工作量模型编码与推断 | 后台线程 | 有 worker 计时，不能算同步 scheduler CPU |
| opportunity/native JSON 序列化与写盘 | 主要后台线程 | 仅已有抽样；调用方构造大字典的同步 CPU 未独立拆分 |
| 原生选批、缓存/分配与结果处理 | 是 | 已有 prefill 抽样；decode 不能据此外推 |

本轮 `profile_shared_path=false`、`shared_path_timing.phases={}`。
即使以后启用既有 profile，也需补 `ReferenceToolReplacement` 的分阶段
和独立 `dispatch_idle_prepare` 覆盖；不能声称现有 decorator 已经把全部
同步路径无遗漏计时。wall 减线程 CPU 也不能直接识别 GIL 或 GPU 等待。

## 后续优先级

先优化替换路径的无效工作：便宜过滤、版本明确的单轮元数据复用、
settled 副本优先检查、区分 hint 刷新与真实状态变化的 rearm。
保留长工具立即让出容量和最终原生安全检查，不能用整体关闭该机制
换取表面上的低控制成本。

随后补低开销、包含 self/inclusive 区分的阶段采样，并定位原生选批和
结果处理的数百毫秒 CPU 尖峰。微基准只验证本地成本及行为等价；
真正的净收益仍按相同 workload 的完整 JCT、共同窗口吞吐与迁移/重算
验收，不能把此报告换算成确定的 JCT 提升。
