# 剩余工作量预测器的数据扩充与开发验证

用户允许在当前工程验证阶段放宽项目和任务的隔离，并补跑少量 SGLang native
任务收集训练轨迹。这里的结果用于已知项目上的调度开发验证，不声明跨项目泛化。

## 数据边界

- V174 的 24 条自然完成轨迹用于训练，共 9,380 个因果进度快照。
- V171 的 18 条自然完成轨迹用于独立校准，共 6,208 个快照；其余非自然完成
  workflow 保留在导出拒绝记录中。
- V230 的 18 条完整轨迹用于开发评测，共 14,458 个快照，不用评测标签训练模型、
  校准温度或选择训练轮数。
- 相同项目和原任务在不同真实执行中可以重复。所有快照按整次采集分组，
  不把同一次执行的早期和晚期快照拆入不同数据分组。
- 历史执行会复用逻辑 workflow ID，因此用完整事件文件的 SHA256 识别实际执行。
  同一次采集不能跨分组，同一事件轨迹复制到别的目录也不能绕过隔离。
- 原有项目/任务互斥模式继续保留为默认值；放宽规则必须显式选择 `--split-mode capture`。

## 首次扩充训练

使用既有固定训练轮数与种子，不根据开发评测结果选择 checkpoint。训练和校准
工作量标签仍是 `0.01 * 同上下文必要新输入 token + 实际输出 token`，不是实测 GPU 秒。

首次训练得到训练 macro-F1 0.9963、校准 macro-F1 0.5830、开发评测 macro-F1
0.4650。开发评测的长档误判为短档比例为 0.4892，初始档位准确率为 0.4444。
虽然独立校准通过原有数值门槛，这些结果仍不足以支持启用新的调度排序。
本次不注册预测器调度性能实验，先补充当前短 child 预算下的数据。

原始数据、模型和完整混淆矩阵保存在
`experiments/reports/workflow_work_training_20261029/`；不得把校准通过解释为 JCT 改善。

## 新增八任务采集

在已通过真实 root/child 工具执行检查的项目池中，按已有种子顺序取前八个不同项目，
将原始任务类别顺序轮换一次：功能实现到跨文件重构、跨文件重构到集成测试、
集成测试到功能实现。任务来自固定公开数据包，不按观察到的时长或结果筛选。

复用原项目 source commit、上下文快照、容器镜像和工具环境；不修项目代码和测试，
不向模型提供参考答案。每个项目的新任务不同于其已有评测任务。

采集使用 Qwen3-Coder-30B-A3B-Instruct、8 roots、running/decode 上限 24、
child 提醒/软目标 4/8、root 提醒/软目标 8/16、2048-token prefill、mixed off、
种子 21、真实工具时间。使用当前 canonical common native 引擎及其原生 KV 策略，
不启用 agent 准入、工作量排序、prepare_host、工具预取或逐层 handoff。
保留完整自然长尾及所有失败和干预记录。

配置为 `configs/migration/workflow_work_train8_native_20261029.json`，
任务清单为 `configs/workloads/locobench_workflow_work_train8_20261029.json`。
这次 GPU 工作是预测器训练数据采集，不是再次执行旧对比的 native baseline。
启动前须通过绑定当前源码的 CPU 检查和实际 CUDA sampler 检查。

补采结束后只把完整、可审计的执行加入后续明确声明的数据分组；非自然执行保留为诊断
数据。正式跨项目泛化评测留到工程机制有效后另行冻结，当前不能用开发集结果代替该结论。

## 当前配置的校准与小模型对照

32 条扩训并未解决误判：独立旧校准轮次仍通过数值门槛，但当前开发集的
long→short 达到 53.64%。因此不能仅据 `decision_eligible` 声明排序已经可用。

新增显式 `workflow` 划分模式，允许同一次采集中不同完整 workflow 分别用于
训练和校准，仍拒绝相同执行指纹跨组。项目互斥模式及整次 capture 互斥模式保持原语义。
当前 8 条新轨迹按 `SHA256("21:" + workflow_id)` 固定排序，交替取四条校准、
四条训练；不按标签、时长或结果选成员。得到 28 条训练和 22 条校准，当前
18 条开发评测轨迹继续不参与拟合或模型选择。

这是首次失败后的开发调整，不代表一次未接触数据的正式盲测。三个固定容量
对照仅根据校准合格性和 macro-F1 选择，选中 compact16：512 维词表、
16/8 隐层、dropout 0.25、AdamW weight decay 0.1。旧默认参数保持不变。
运行时继续读取同样的便携 JSON 权重，无新增训练库依赖。

## 配置差异与在线输入缺口

`same_task_work_variation_r1.json` 对原任务文本完全匹配的独立执行进行比较：
当前 V230 工作量相对于 V174 的中位比值为 1.4483，旧 V171 校准相对于
V174 的中位比值为 0.9805。标签仍是逻辑模型工作代理。

历史记录证实 V174/V171 使用旧 dynamic_nested 契约，没有现在的并行 JOIN
终态约束和显式软预算；V230/新补采使用 short_workstreams、child 4/8、
root 8/16 及至少两个 child 的 JOIN 规则。原模型输入只含任务文本和已观察进度，
未显式包含这些已知执行条件。该差异与误判相关，不能单凭比例认定唯一原因。

`profile_text_pilot.py` 在相同 28/22 划分及 compact16 参数下，将实际 capture
plan 和 client manifest 中已知的 profile、软目标、最小并行 JOIN、最大深度
加入预测器文本输入；没有未来请求量、输出量或真实总工作量。当前开发集初始
准确率从 44.44% 到 66.67%，但 long→short 仍为 42.97%。
该对照保存在 `profile_text_r1`，**只是 CPU 原型，在线前缀尚未接通，不能部署此权重
后宣称线上使用相同输入契约**。执行指令来自预测器输入，不修改 LLM 工作负载提示词。

## 已观察 paused 候选的排序审计

对完整 2s/no-handoff Full 的 2,217 个状态样本进行只读重建，637 个样本存在
跨 workflow 的 paused 竞争。使用 compact16、保持原类别、同 workflow/category
只计一份，得到 1,027 个真实工作档位不同的成对观察，涉及 242 对不同 request。
它们包含重复观察，不是 1,027 个独立任务。

模型对其中 422 个观察给出不同档位，顺序正确 293、错误 129。相对于原上下文
大小排序，188 次反转中纠正 105 次、破坏 83 次；组合排序正确数为 650/1,027，
原上下文排序为 628/1,027。该改善很有限，尚不支持期待明显 JCT 增益。

审计用已记录的 post-control paused 集合和因果调用边界特征；未复现 partial
decode、200ms 后台缓存、原生容量可行性或真实选批，更不是 JCT 反事实模拟。
真实未来总量只用于离线标签。前述“已知执行指令文本”原型尚未进行这项审计。
证据见 `paused_competition_compact16_r2.json` 和 `paused_rank_decision_review_r1.json`。
保留最初错误访问 wire-only sequence 字段的 CPU 失败，随后改为稳定时间排序。

当前没有注册剩余工作量排序的 GPU 性能实验，整体优于 baseline 的目标仍未完成。
下一步应补齐预测器的执行条件输入契约，并以当前配置下同任务的独立执行检验
工作量漂移和排序稳定性，保留开发性质及所有负结果。

新增 workflow 划分、正则参数和 paused 审计后，`cpu_r2/evidence.json` 实际通过
4,929 项测试及 6 个子测试，保留全部 4,913 个先前测试身份，无失败、错误或跳过；
1,993 个绑定输入及原生引擎在执行中未变化。后来单独执行的 profile 文本 CPU 原型
不在这组源绑定内，也没有 GPU/在线输入资格。

## 在线输入对齐及核算优化

已实现显式 `task_plus_declared_execution_instructions_v1` 输入契约，绑定 profile、
child 软目标、root 阶段软目标、最小并行 JOIN 和最大深度这五项已知条件。共享格式化
函数生成离线和在线前缀；旧模型继续只编码任务文本。模型加载、候选准备及正式
preflight 检查声明条件，条件不同或混入未来工作量字段时拒绝启用该模型。
这些字段不是全部运行环境的指纹，不宣称覆盖未编码的其他环境变化。

`qualify_input_contract.py` 保留原型权重，另存输入绑定后的模型；只修改元数据，不改变
数值权重、温度或校准。`input_contract_r1/parity.json` 对 18 个真实 root 的首次请求，
使用原始 token 尾部和实际 Worker 入口，逐项验证文本、观察特征、投影及概率完全一致。
它是 CPU 入口验证，不是 partial decode、后台缓存时序或 GPU 性能证明。

后台现在统计整个处理周期的 thread CPU/wall，包括事件、任务编码和前缀核算，
不再只统计分类函数。微基准发现 100k 前缀的 Python 逐项比较中位约 5.33ms，
高于动态分类的约 31µs。改为带所有权的连续 int64 历史、批量比较和复制，
并加速 list/tuple 转换后，该微基准约 2.31ms。保留输入增长、编辑、截断及重试
去重语义，历史不引用可变请求缓冲区。它不等同整体 JCT 改善。

`vector_label_parity_r2.json` 检查原 18 workflow 的 14,458 个序列化快照完全不变。
最初直接比较导出 tuple 与 JSON list 的检查失败已记录，修正比较口径后通过；
不是修掉标签差异。

输入对齐后的 paused 审计仍无收益：`paused_profile_r1.json` 的组合排序正确数为
627/1,027，原上下文排序为 628/1,027，纠正 103 次、破坏 104 次。保留这个负结果，
没有据此启动 Full 性能实验。新增连续剩余工作量的成对指标，以便后续训练分位阈值
变化时仍能比较相同工作量代理下的方向；它也不证明容量可行性或 JCT。
