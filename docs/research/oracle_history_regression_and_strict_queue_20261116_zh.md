## 后续 CPU 诊断：组批效率与实际重算

不能把 worker 区间当作纯 CUDA 成本，或把重叠计时相加作全控制成本。

这不覆盖所有请求内撤回，也不排除背景重算的共享服务干扰。
新审计保存实际 source/attempt/session/区间证据，
后续 Host200/55 秒新设计仍需同口径区分测量与背景、首次调用与已有状态续接。

## 策略已经改变

旧 83 项目 Oracle 使用冻结 `631911fb`，当前已跑容量修复版为 `d6d9aa1e`：

| 机制 | 旧含工具路径 Oracle | 最新已跑 Oracle |
|---|---|---|
| 排序量 | 含模型、工具等待的剩余关键路径秒数代理 | 总剩余模型工作量 |
| Oracle 产物 | `workflow_model_tool_critical_path_oracle_v1` | `workflow_continuous_model_work_combination_oracle_v1` |
| 准入选择 | 全局 ready 路径次序、逐个装入 | 有界候选集合的效用加和 |
| 组合开关 | 关闭 | 开启 |
| 效用 | 原路径优先级 | `1/(1+remaining_model_work)` |
| ready 等待老化 | 无此次新增加成 | 30 秒尺度的无上界乘法加成 |
| JOIN 分支 | 保留真实恢复权利和 sibling 支持 | 另有平方覆盖份额影响组合效用 |
| 主动容量累积 | 无此次新增状态 | 最多一个 2 秒普通窗口 |
| 压力暂停工作量偏好 | 通过原工具保留带参与 | model-work-only 模式默认不参与 |
| 普通窗口及完整控制 | 2 秒 | 2 秒 |

源码位置分别为实际冻结树的
`beliefkv/runtime/workflow_oracle_admission.py`、
`workflow_size_admission.py`、`workflow_combination.py` 和实际工作产物。
model-work-only 模式中 `_conditional_distribution` 使普通
`_pressure_preference()` 返回 None；当前产物也没有开启独立 pressure-work 扩展。
因此两种 Oracle 连暂停对象的工作量覆盖范围都不相同，
不能称为同一策略仅把到达间隔从 70 秒改成 60 秒。

最直接的实现偏离是：`shortest_work_first_admission=true` 不保证实际走严格
短优先；`cost_aware_maximal_admission=true` 的分支优先最大化加总效用。
老化又会反转工作量次序。JOIN 平方份额也能使短 workflow 的分支输给较长串行者。
这些是源码和真实选择上的偏离，不是短优先理论收益已被否定。
与此同时，纠正排序本身也不能保证有限 KV、并行依赖与连续 active 服务下的
完整 JCT 一定下降 2%，必须实际配对验收。
