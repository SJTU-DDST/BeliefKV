## Oracle 查询缓存

上一轮 model/tool oracle 每次查询都扫描整个 workflow DAG，完整 GPU 运行的
记录累计约 28.45 秒线程 CPU。本次将结果按已观察到的事件、请求完成和部分
输出进度失效；同一观测状态下，工具经过时间继续实时更新，不采用冻结几百
毫秒分数的 TTL。

对已开始且依赖均完成的外部操作，剩余时间是 `max(0, deadline-now)`；
其下游未开始的工作是固定代价。因此一个观测版本的最长剩余路径可以表示为
`max(constant, deadline-now)`。在观测版本内查询为 O(1)，版本改变后重算。
若观测时间晚于查询时钟，保留原逐节点计算；部分输出、真实工具结束和
workflow 关闭都会正确失效。新增拒绝跨 workflow 的已知事件 ID。

旧完整实验的 18 个 workflow、3,674 次请求和全部工具事件，通过当前缓存与
原逐节点算法的 CPU 对照：

| 项目 | 结果 |
| --- | ---: |
| 记录候选组中的查询 | 13,083 |
| DAG 重算 | 525 |
| 缓存命中 | 12,558 |
| 最大路径差异 | 1.54e-8 秒以内 |
| 局部优先级顺序变化 | 0 |
| 原逐节点查询线程 CPU | 18.3959 秒 |
| 缓存查询线程 CPU | 1.2855 秒 |

证据为 `oracle_cache_r1.json`。这是完整请求边界与记录查询组下的微观对照，
不是完整在线回调重建，也不能从 JCT 中直接减去 17 秒。
单元测试另覆盖部分输出、并行分支切换、时间递减、重复事件、终态和 160 组
随机 DAG。未来 GPU 运行仍须测量实际查询/失效次数及完整控制 CPU。

## 部分进度证据边界

试图直接使用旧重放的全部 native 进度时，严格导出器发现部分正 decode
增量的日志完成时刻晚于客户端结果边界，因而拒绝。共有 2,623 条结果后的
采样行，其中包括零增量残留；示例正增量的差值约 0.74–3.67ms。
这不能单凭时间戳判定额外 GPU 工作，也不满足当前精确部分进度合同。

保留拒绝证据 `oracle_cache_native_progress_rejection_r1.json`，不放宽训练
导出器，不重写原日志，不把这组 native 时间当作准确回调时刻。当前缓存
CPU 对照明确只用完整请求边界；其命中率不能当作未来流式运行命中率。
最初完整 work 签名与二元 token 长度比较的入口错误也单独保留。

## 恢复竞争日志

工作量排序候选现在在授予资格**之前**记录
`logical_ready_paused_before_resume`。观察复用现有请求身份、context epoch、
可见性、工具等待及阻塞 child 检查，保留空预算快速返回。
首次请求可以被观察为 ready，但不会因此获得原先没有的免费续接权限。
该观察值不改变排序、容量、原压力处理或物理恢复权限。

`scripts/audit_workflow_competition.py` 结合完整来源的实际分档，统计同类别
ready-paused 短长候选各自可容纳、合计不可容纳的控制轮；先扣更高类别按
原规则消耗的预算，包括原 buffer。工具或 JOIN 仍阻塞的对象不进入竞争集合。
缺少新快照的旧日志明确报告覆盖不足，不默认所有 paused 都 ready。

脚本沿用选择重演及随后原生服务关联，同时区分选择后压力撤销；逻辑预算
放得下不等于原生 HBM 分配成功，局部集合变化也不是 JCT 的因果反事实。
已补齐 continuous oracle rank 的审计格式，旧 learned bucket 仍严格校验。

本轮完整 CPU 检查通过 5,216 项测试及 12 个子测试，保留此前全部 5,204 项
测试身份，无失败、错误或跳过，原生 engine 字节未改。采集时冻结的
`e7dc71a1` 不包含这些后续更改。
