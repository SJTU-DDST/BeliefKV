# JOIN 余量准入的分支级 Oracle 初筛

2026-11-04，Asia/Shanghai。仅 CPU 分析，没有修改在线策略或启动 GPU。
这是对已提出设计的机会收紧，不是替代集合的端到端回放。

## 直接结论

只依据当前正在执行的工具等待，当前候选窗口里没有出现“这段工具等待就能
覆盖另一个 ready child 到 RETURN 的完整路径”的情况。
依据整个分支剩余路径则能找到一些理想余量，但放入真实竞争者后，
机会从几十次缩小到 8 个一对一替代，其中 1 个涉及测量组竞争者。

因此，不能直接将“工具 A 还有 8 秒、B 只需 1 秒、C 只需 2 秒”的算例推广为
当前负载的主要优化机会。更广的分支预测仍值得研究，但尚无足够净收益
证据为这项机制单独启动完整 GPU 实验。

## 方法

入口为 `scripts/audit_join_branch_oracle.py`：

1. 绑定实际联合实验注册和此前已精确重放的容量选择报告，
   不重新生成候选集合或放宽资源。
2. 从原始 composite73 因果图取得每个 invocation 的显式 RETURN，
   验证完整 oracle 的请求、token、工具 overlay 和源证据。
3. 只保留通往该 RETURN 的祖先，不把整个 workflow 或其他无关 sibling
   的工作量算到某个 child 身上；嵌套 JOIN 保留真实依赖的 max 路径。
4. 沿实际 replay 客户端事件与累计 native 输出更新已完成工作。
   工具剩余时间按已观察开始时间扣除 elapsed，而非使用一次旧 JCT。
5. 在原 46 个有 JOIN 替代集合的窗口计算分支标签。
   客户端公布状态与记录 JOIN 成员数不一致时应保留未知。
6. 仅比较保留其余所有 actual 成员的一对一跨 workflow 替代；
   不把删去多个对象、扩大集合或同 workflow 的 sibling 互换混入计数。

模型秒数沿用绑定历史 token-work 校准，完整源工具时间是显式未来 oracle 标签。
输入在第一次已报告输出后视为 prefill 完成，不估计此前的部分 chunk 进展。
此处没有新校准上下文/batch 执行预测器，也没有运行中的推理模型。

## 结果

| 筛查量 | 数值 |
| --- | ---: |
| 具有替代 JOIN 集合的原决策窗口 | 46 |
| 完整支持的 JOIN 组观察 | 56 |
| 这些组中的候选观察 | 71 |
| 当前工具剩余足以覆盖另一候选完整 RETURN 路径的观察 | **0** |
| 相对其他完整分支路径有正理想余量的候选观察 | 40 |
| 上述正余量候选中实际被选择的观察 | 16 |
| 保留其余实际成员的一对一跨 workflow 替代 | 20 |
| 竞争者完整分支理想路径可放入余量的替代 | 8 |

正完整分支余量 P50 为 19.313 秒，P90 为 304.466 秒。
不同观察相关、可能重复涉及同一分支，合计不能作为 JCT 上界或收益。

8 个放入理想余量的替代来自 4 个 JOIN，为 8 个不同的延后候选与竞争者配对。
它们的 JOIN 所属 workflow 均为非测量任务，其中 **1 个竞争者属于测量组**。
所以“测量 JOIN 的替代数为零”也不能误写成完全没有可能帮助测量组的机会。
其余背景任务仍会影响竞争，但没有对这些间接影响作收益估计。

一个理想例子里，当前选择分支的剩余路径约 40.06 秒，
另一个 sibling 的路径约 378.53 秒，差约 338.47 秒；
可替代的测量 workflow child 路径约 15.18 秒。
该比较说明存在分支长度差与规划可行替代，不说明应当实际延后前者：
竞争者 child 的 RETURN 未必就是其 workflow 完成，当前被选 child
也可能在 RETURN 前的长工具阶段更早让出容量。

## 为什么不把 8 个当作正收益选择

仍未支付或验证：

- C 的真实恢复和可能必要的 donor 备份。
- B 重新准入、KV 恢复与增长约束。
- C 到自然释放相关资格/容量的高侧时间。
- 给 C 计算是否拖慢了本来决定 JOIN 完成的其他 active 分支。
- C 的完成是否推进它自己的 JOIN 或完整 workflow。
- 对余量估计错误的代价，以及后台模型和同步选择的控制成本。

当前工具单独给出的余量为零，较大的完整分支余量依赖未来尚未发生的
模型和工具阶段；未来部署时必须预测这些阶段，不能直接读取录制轨迹。
即使未来 oracle 的固有路径已知，资源竞争下的完成时间也仍需计算。

当前读器只生成标签，没有选择新的集合，没有模拟替代后的资源时间线，
没有计算完整 JCT，也不声明安全的在线延后时限。

## 对下一步的影响

保留本轮已完成的联合版本及其 1.814% 单次 JCT 改善，
优先检查同一纯收益目标下，真实连续 workflow 工作量与当前预测权重
在全部容量竞争里的差异，再决定是否将分支余量纳入完整 oracle。
不为当前 8 个理想局部配对单独追加 GPU 实验。

若继续研究分支机制，下一层应检查“对方自然释放容量的时间”和
“该 competitor 是否推进自己的真实完成 frontier”，并核算受损者；
不能仅提高预测器容量或把正余量候选一律降优先级。
