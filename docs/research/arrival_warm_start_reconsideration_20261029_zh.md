# 短周期到达实验重新定标

2026-10-29。根据用户对有效 KV 压力的质疑，重新检查已完成 FULL 和
ThunderAgent 的全部事件。仅做 CPU 分析，未修改或登记 GPU 实验。
本页替代之前“初始 10 个、后续平均 120 秒”的短周期建议。

## 观测

两侧均为 18 个不同项目、3674 请求、92 个 child、72 个 JOIN，
保留全部正常尾部。以下 child 时间包含当前策略造成的排队和工具等待，
不是任务固有执行时间，也不能直接用于预测新到达方式下的并发。

| 观测 | 最新 FULL | ThunderAgent decay |
| --- | ---: | ---: |
| child 创建至返回 P25 | 90.72 秒 | 93.87 秒 |
| child 创建至返回 P50 | 159.34 秒 | 163.50 秒 |
| 120 秒内返回的 child | 29 / 92 | 27 / 92 |
| 首个 workflow 完成 | 970.24 秒 | 1058.07 秒 |
| 突发完整批次完成率 | 0.468 / 分钟 | 0.459 / 分钟 |

部分 child 会在下一次 root 到达前完成，确实可能降低短期活跃工作集。
但 child 返回不等于 workflow 结束：已有 parent 和后续委派仍可能产生
有效 KV 需求。旧 18-root 突发实验的首个 workflow 在约 16--18 分钟结束，
不能据此断言平均 120 秒到达一定没有迁移压力；初始只有 10 个时，
排队和完成时间又会变化，不能简单搬用旧 JCT。

固定 arrival seed21，初始 10 个、后续 8 个的泊松到达：

| 平均间隔 | 最后到达时刻 | 最长相邻空档 |
| --- | ---: | ---: |
| 120 秒 | 14.39 分钟 | 197.94 秒 |
| 60 秒 | 7.20 分钟 | 98.97 秒 |

对于用现有 18 条轨迹快速验证迁移收益的目的，120 秒过于保守。
它接近旧全程完成率，但后者包含启动和排空，不是已测得的稳态容量。

## 选择

下一轮短到达验证建议保持总数 18、初始 10 个、后续 8 个平均每 60 秒
泊松到达，seed21，running/decode24；其他工作量、容量和政策设置不变。
只调整间隔，先不增加到 24/36 个项目，也不加新的 workflow 入口并发闸门。
每个方法必须使用同一份预生成的外部到达表，完整 JCT 从计划到达算起。
混合到达的运行时契约仍需实现和验证；本页不是可直接提交的到达 manifest。
最新用户指令已取消没有已核验作者代码的 Agentix 复现，允许先运行
这份新到达配置下的工具衰减 ThunderAgent，并与 predictive 的 CPU 优化
并行。原有 Agentix 组件与模型证据保留，不作为正式 baseline 结果。

每分钟一个约为旧突发完整完成率的 2.1 倍，应称有限加压试验，不能称作
可持续稳态流量。固定种子下后续到达只持续约 7.2 分钟，18 条轨迹不足以
同时保证长时间持续到达、稳定压力和很短的完整实验；不作这种保证。

验收同时检查实际 ready 工作、仍有后续用途的独占 KV、Host 命中恢复、
H2D/D2H、暴露恢复等待和旧输入重算。HBM 满载、可回收页总量或未完成
workflow 数都不能单独证明有价值的迁移压力。如果压力仍弱，先判断
是否缺少阻塞冷 KV 或并行就绪工作，再决定是否扩充不同项目并重新采集
匹配轨迹，不靠更密集到达或额外重算制造收益。

原始哈希绑定、完整统计及计算入口：
`experiments/reports/arrival_capacity_20261029/warm_start_reconsideration.json`
和同目录 `reconsider_warm_start.py`。
