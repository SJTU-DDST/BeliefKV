# GPU 暂停期间的新设计筛查：计算阶段与依赖后继

2026-11-04，America/Los_Angeles。用户要求先寻找新的设计点，并明确接下来一段时间
无法运行 GPU 实验。已在中央启动保护中关闭自动恢复，恢复时间留空，必须收到新的
明确释放指令。实际 `check_reservation()` 返回 `HoldChanged: automatic resume was disabled`。
没有注册 GPU 实验、组件检查或自动启动任务；本轮只读既有运行并使用 CPU。

## 结论

优先继续研究**按后继事件安排 prefill 与 decode 的执行次序**。它保持 D1 已有
agent 资格和 D2 的 KV 驻留，在模型计算边界判断是否值得先推进一小段现有 decode，
使真实工具、RETURN 或依赖后继更早启动，并显式支付被推迟 prefill 的代价。

目前仍不能将它认定为第三个已成立的设计点。本轮建立了完整依赖传播下的局部机会，
没有重新执行共享 GPU 队列、准入、批次形状或 KV 增长。机会对成本敏感，实际可用的
在线阶段信号也尚未完成验证。普通缩小 chunk、固定 decode 优先或拆短批次不是新贡献。

另筛查了“部分 child 返回后，提前计算 parent 不变输入前缀”的候选。当前负载中，
多 child JOIN 后 prefill 的直接计算暴露很小，不优先实现。普通工具等待期提前
prefill 与增量工具启动已有相关系统；不能将它们改名作为独立创新。

## 双向依赖投影

入口为 `scripts/audit_compute_frontier_projection.py`。

先将事件和原生请求完成时间绑定至原始因果 DAG。每个节点保留实际相对最晚依赖的
已观察滞后，包含原运行的派发、服务及排队成分。每个局部动作单独从同一基线出发：

1. 找到 prefill 前后仍有输出连续性的原 decode 成员。
2. 用真实剩余输出数乘两侧 decode worker 时长较大值，作为推进到该请求结束的
   成本代理；名义预算为 500ms，且需能在原 prefill 段结束前完成。
3. 将该请求的完成时间前移，同时给该段全部 prefill 请求施加整个推进成本的
   绝对延后。同一依赖链的多个请求不重复累加同一延后。
4. 沿全部已观察依赖传播，而非固定原来的关键路径。JOIN 最后完成分支可改变；
   不在实际尾部的 child 提前返回，可能完全不推进 parent。
5. 统计所有已完成 workflow 的完成时间总和变化，固定测量组只作结果标注。
   直接参与者存在删失的动作单列排除，不把它们的延后成本置零。

这是**保持已观察滞后的依赖投影**，不是全系统离散事件模拟或 token 执行回放。
后续请求保留的排队滞后并不会随 GPU 竞争重新计算；批次分裂、所有受间接影响的
工作、KV 增长与物理可执行性未建模。既非实际 JCT 改善，也非严格全局上下界。
成本倍率敏感性不是概率保证。

7054 个段中有 2339 个满足名义预算与暴露条件的观察，253 个涉及删失直接参与者，
2086 个的直接参与者均已结束。按每个请求首次合格观察去重后为 1918 个。
首轮按不使用收益或测量身份的固定 hash 取 256 个；随后评价全部 1918 个，
不是只保留有利样本或更换任务。两份结果及源码指纹均保留。

| decode 成本代理倍率 | 可推进的局部动作 | 全部已完成 workflow 总和改善为正 | 单次总和改善中位数 |
| --- | ---: | ---: | ---: |
| 0.75 | 1918 | 1408 | +62.029ms |
| 1.0 | 1918 | 1194 | +24.401ms |
| 1.5 | 1911 | 614 | -38.644ms |
| 2.0 | 1771 | 386 | -106.260ms |

较大倍率下不可推进的动作仍属于原来的 1918 个，未改成人群收益率。

### 一个值得继续核对的现场

`native-service-000016706` 后连续 92 个 prefill batch，涉及四个 prefill workflow。
在该段前仍可逻辑连续观察到 security workflow 的 child，录制未来尚余 7 个输出。
名义推进成本为 183.304ms；将它加倍到 366.608ms 后，局部投影中该 workflow
结束可提前 30.429 秒，四个受延后 workflow 各支付约 366.608ms。

这说明少数连续长 prefill 段可能有比典型段更大的推进价值，不能只看中位数。
但此例尚未看到 `</tool_call>`，7 个剩余输出是 oracle 信息；在线不能读取它。
92 个后续 batch 也是回顾观察，在线只能使用已提交输入、当前 chunk 和真实队列。
其提前量还继承了固定后续排队滞后的假设，不能作为实际或可重复收益承诺。

### 可见信号有多大覆盖

1918 个观察中，518 个已输出工具关闭标记；它们在名义成本下 382 个投影为正，
四档成本均正的有 163 个。可见关闭标记与最后未返回 child 同时存在的有 271 个，
其中 100 个四档均正，30 个在双倍成本下同时改善测量均值。
这 271 个录制剩余输出均为 1，但这个未来标签不能变成在线执行权限。

目前只有阶段信号覆盖的描述，没有验证它能稳定选择正收益动作。
下一步可检查已经生成的完整工具 JSON、最终报告协议等更早的可见边界；
不训练新的完整 workflow 工作量预测器，不将工具起始标记等同于即将结束。

## 提前计算后继前缀的成本筛查

入口为 `scripts/audit_dependency_prefill_exposure.py`。
同一完整运行和同一实际最后完成依赖链，对原生 prefill batch 在每条 workflow
内部去重，计算工具或 JOIN 后继实际覆盖的完整 worker 区间：

| 后继类型 | 测量组完整请求 | 位于实际最后完成路径的请求 | workflow 等权 prefill 暴露 |
| --- | ---: | ---: | ---: |
| 所有 JOIN | 78 | 78 | 1.562661 秒 / 0.1472% JCT |
| 至少两个成员的 ALL-JOIN | 19 | 19 | 0.344104 秒 / 0.0324% JCT |
| 普通工具 | 2753 | 2331 | 15.290262 秒 / 1.4399% JCT |

这些是原执行中必要工作所在的区间，不是可删除延迟，也不是全局收益上界。
它们可能包含原前缀重算及共享 batch；工具和 JOIN 人群也不能相加。
即使区间较大，工具新返回内容也未必提前可知、token 化前缀未必稳定；
提前计算还会占用别人的 GPU、请求行和 HBM。

因此，当前不优先实施 JOIN 返回结果的增量 prefill。普通工具后继虽有更多暴露，
尚需证明其中哪些不可变前缀尚未缓存、确实能提前计算，而非重复已有缓存工作。

## 已有研究与独立性要求

- Sarathi-Serve，arXiv:2403.02310：chunked prefill 与 stall-free batching。
  固定 decode 优先、启用 mixed 或更小 chunk 必须作为强控制，不作为新贡献。
- Sutradhara，arXiv:2601.12967：已描述增量工具启动、tool-aware prefill 和
  agent 身份下的缓存处理。普通工具前缀预计算不是新的独立方向。
- HexGenT，arXiv:2605.16637：对异构 GPU 上 agent 工作流的 prefill/decode
  决策与关键路径相互作用已有研究。它与本地单 GPU、资格/KV 保持下的计算推进
  不完全相同，但不能据此宣称通用 workflow 阶段感知调度首次出现。

三篇均核对原始 arXiv 摘要。本轮未完成对全部相关工作的技术新颖性判断。
更强证据应证明：在相同算力、缓存、token 与依赖下，后继事件的推进价值和
被延后阶段的总代价，能比这些简单强控制额外改善完整结果。

## 下一步与停止条件

只继续 CPU 研究，不修改实际 serving：

1. 检查高价值现场能否由已生成的语法/协议状态和已提交输入量识别，
   不依赖录制输出长度、未来工具或未来 RETURN。
2. 对多个动作统一支付额外 forward 与后续 GPU 竞争，验证 token 工作量守恒、
   请求就绪和批次形状变化，保留固定到达、工具时长和完整测量人口。
3. 比较通用 stall 控制与后继事件价值偏好，不能把修复长 prefill 饿死 decode
   单独写成新的工作流设计。
4. 若在线信号只能保留典型的几十毫秒机会，或合理成本扰动即消失，则停止此候选；
   不因需要第三点而增加控制、预测和维护负担。

工作集切换、普通控制检查优化、分支排序、prepare_host 节流等继续按 D1/D2 的真实
边界处理。当前仍是两个已实现设计加一个待验证的计算阶段候选。
