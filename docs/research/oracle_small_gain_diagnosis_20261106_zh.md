# 短 workflow Oracle 小幅收益的诊断

2026-11-06，Asia/Shanghai。复算现有 original73、400 GB Host、20 条初始
workflow 加平均 70 秒到达的 Direct Global Oracle 对照，不启动 GPU、
修改到达表、测量组或主指标。以下区分已完成报告中的事实、源码边界和解释。

## 两种改善率

输入为既有完整配对：

```text
experiments/reports/remaining_original_projects_20261030/useful_token_cost_r1/
  host400_registered_copy_pressure_r1/capacity_review_correction_r1/
    comparison_retry2.json
```

固定 18 成员均完成，2991 个请求、362157 个输出 token；原完成报告核对
完整回执、fresh drain 和实际退出。JCT 口径只复算完成报告，没有额外重跑原始
执行资格；后续新增的同状态准入重放见下文。非排序 Full 平均 JCT 为
1081.530918 秒，Oracle 为 1061.028850 秒。

设同一成员的对照和 Oracle JCT 为 C_i、O_i：

| 汇总 | 公式 | 数值 |
| --- | --- | ---: |
| 完整平均 JCT 下降 | 1 - sum(O_i)/sum(C_i) | 1.895652% |
| 逐 workflow 相对下降率的均值 | mean(1 - O_i/C_i) | 2.597012% |
| 平均绝对提前量 | mean(C_i - O_i) | 20.502068 秒 |
| 完整 P50 JCT 下降 | 1 - P50(O)/P50(C) | 5.189113% |

因此“约 2.5%”与已完成数据中第二个口径吻合，但它不是第一个口径。
平均 JCT 本身对成员等权；其相对下降率等价于用 C_i 加权逐成员相对下降，
所以较长对照 JCT 的小幅相对变化会压低第一个数值。这不是计算错误。
保留完整平均 JCT 为主指标，同时报告逐成员相对变化；不能事后改用较好看的
口径。14 条改善、4 条回退，共同窗口输出变化为 -0.554585%，单对结果不证明
重复性，也不是全系统最优调度收益的上界。

按对照 JCT 从长到短做事后描述，最长 4 条贡献了对照 JCT 总和的
53.977153%，其合计 JCT 改善为 1.287109%；其余 14 条合计改善
2.609373%。全组共提前 369.037221 workflow 秒，最长 4 条贡献其中
135.249785 秒。这说明长尾成员为何会压低完整均值的相对改善，但不能以此
排除它们、重选测量窗口，或把这一事后分组当作预先声明的任务大小分档。

最近 learned R5 对最新关闭版本的 4.807688% 属于另一组配对和策略范围。
不能与这里的 1.895652% 直接比较，推断预测器超过了真实信息 Oracle。

## 并发与有效竞争

同父目录的 `supply.json` 记录共同墙钟窗口中的周期快照：

| 观察 | 数量 | 占同一 1487 个快照 |
| --- | ---: | ---: |
| 有 ready-paused | 1100 | 73.974445% |
| 跨 workflow、各自逻辑可放下但不能全部放下 | 78 | 5.245461% |
| 上述竞争中剩余路径比至少 2 | 47 | 3.160726% |

这些是快照计数，不是时间加权比例、独立决策或物理可执行证明。
ready-paused 多不等于有很多排序可改变的集合：可能全部可放下、全部放不下，
或受 JOIN、工具状态和 active 连续性约束。

完整对照的另一个周期观察器记录 1887 次控制，其中 193 次跨 workflow
逻辑集合竞争；456 次有应用 ready-paused 和剩余额度但没有单体可放下，
360 次有剩余额度但没有应用 ready-paused。这与上述快照人群不同，不能混作
一个漏斗或把百分比连乘为收益。

到达方式仍有局部不足：共同窗口回放后约 956--1556 秒的两段各 300 秒分箱，
ready-paused 平均仅约 0.622、0.548 个，竞争快照分别只有 1/283、4/290。
这里的均值也按快照计，不代表整个执行后半程或全程稳态。
增加后续在途供给值得作为负载敏感性检查，但不能仅增加总数或初始突发：
如果新增的都是大 KV 或工具阻塞对象，可能只扩大不适配队列和 Host 压力。

## Oracle 已生效，但覆盖有限

既有 `oracle_service_audit/complete_first_pair.json` 对实际 Oracle 轨迹核对：

- 1867 次实际选择中，750 次候选顺序变化，104 次最终恢复集合变化。
- 104 次集合变化中，26 次数量更少、6 次更多、72 次数量相同。
- 120 个新选 request attempt 全部真实授予、保留资格并有精确后续服务，
  112 个在下一控制或已记录干预前完成有用批次。
- 新选 episode 中 26 个属于测量组，覆盖其 9 个 workflow；其余属于非测量组。
- 固定共同吞吐窗口内为 45 次集合变化和 51 个新选对象，其中只有 14 个新对象
  属于测量组的 4 个 workflow。

因此没有证据把小收益主要归因于“Oracle 改了顺序但完全没有执行”。
它也没有覆盖所有 native 服务决定。审计中的局部参考为同状态非排序 Full，
没有模拟反事实的后续全局状态或所有压力决策。

## 排序目标的局限

该轮实际配置为 global ready remaining path、组合选择关闭、
workflow_tool_aware 压力保护。Oracle 使用真实未来图和工具时间计算剩余
模型/工具关键路径，但模型工作到秒数采用固定代理，并不知道不同准入组合下
精确的 batch、上下文、迁移和后续竞争成本。

其主要作用仍是 agent 的准入与恢复，也可在既有工具保护带内影响压力受害者
与工具替换消费者。它保留 active agent 连续性和 native 容量权威，不会仅因
新短 workflow 到达就轮换正在推进的 agent，也没有接管所有 prefill/chunk/
decode 选批。不能把它称为完全可抢占的最短剩余处理时间调度。

另外，含工具的剩余墙钟路径最短不保证平均 JCT 最小。一个只用于说明目标
差异的串行 GPU 例子：两个任务同时到达，A 需要 1 秒 GPU 后执行 100 秒工具，
B 需要 10 秒 GPU 后结束。按剩余墙钟路径，B 短于 A：

- B 先执行：B 在 10 秒结束，A 在 111 秒结束，平均 60.5 秒。
- A 先执行：A 在 101 秒结束，B 在 11 秒结束，平均 56 秒。

这个构造不是当前负载收益模拟，也没有改写任何 trace。它说明应区分剩余
模型服务量、外部等待和下一次服务解锁的依赖，而不能把它们压成一个总长度
后假定排序必然最优。只按模型工作量也不自动解决 KV 组合与 batch 成本问题。

## 后续同状态排序目标重放

新增 `scripts/audit_oracle_rank_objectives.py`，使用同一 Oracle 完整执行的
封闭机会日志和回放事件。先逐边界复现实际选择、同状态非排序参考、容量及
原有观察窗口，再只替换排序字段：

- `remaining_path_s`：原含模型、工具及固定延迟的关键路径。
- `model_only_path_s`：去掉外部延迟后，模型工作最长依赖路径的秒数代理。
- `remaining_work`：整个 workflow 剩余模型工作量，合计并行分支。

后两者在聚合方式上不同，不能混称为同一个“去工具 Oracle”。
model-only 和 external-only 分别取最长路径，也不能直接相加当作总关键路径。
真值来自固定轨迹的 token/依赖，服务成本换算仍是代理，不是反事实 GPU 秒数。
原候选、protected JOIN、sibling 分组、类别 tie-break、容量和 buffer 全部保留。
测量成员身份只用于事后统计，不参与选择。

| 同一 1867 个实际边界 | 相对实际顺序变化 | 相对实际集合变化 | 涉及测量组的差异集合 |
| --- | ---: | ---: | ---: |
| 原含工具路径 | 0 | 0 | 0 |
| 模型关键路径 | 297 | 18 | 9 |
| 总剩余模型工作量 | 376 | 19 | 8 |

模型关键路径新增 24、移除 25 个 agent episode；总模型工作量新增 27、
移除 26 个。两种替代评分均涉及 7 个不同测量 workflow，但不是 7 个已加速的
workflow。共同吞吐窗口内，二者各改变 10 个集合，分别 3/2 个涉及测量组。
这些是 Oracle 已产生的轨迹上的局部选择，不能推广为新策略产生的全执行轨迹。

同一批 Oracle 边界可作以下互斥分类：

| 记录候选的逻辑容量结构 | 边界数 |
| --- | ---: |
| 日志未列候选，可能含预算快返 | 468 |
| 有记录候选，但没有单体可放下 | 374 |
| 可放下的候选只来自一个 workflow | 503 |
| 多个 workflow 可放下，且全部可共同放下 | 352 |
| 多个 workflow 各自可放下，但不能全部共同放下 | 170 |

合计 1867；最后一类约占 9.11%。它与上文非排序 Full 的 193 次周期竞争、
以及 1487 个采样快照中的 78 次竞争来自不同观察人群，不能相加或替换分母。
所有分类均是记录边界的逻辑容量，不证明原生物理分配、Host 和锁的即时可行性。

对 468 次“日志未列候选”，按精确 `monotonic_s` 与原服务审计的
`control_observations` 逐条连接，468 条均找到对应控制前观察：

| 控制前的应用 ready-paused 状态 | 边界数 |
| --- | ---: |
| 没有应用 ready-paused | 422 |
| 有应用 ready-paused，但恢复预算不超过 100-token buffer | 41 |
| 有预算且有一个应用 ready-paused，选择日志仍未列候选 | 5 |

这里“没有应用 ready-paused”不表示 GPU 无可执行工作，active agent 仍可
推进。最后 5 条还可能涉及更严格的 request、context、工具状态或恢复过滤，
现有观察不足以定位具体原因，保留为未解释差异，不能直接宣称实现错误。
原始 `agent_periodic_admission_decision` 也确认这 5 条各只有一个这样的
agent，且窗口资格为真。因此，这 5 条观察本身没有遗漏多 workflow 的同时
竞争，不能解释大批跨 workflow 排序机会消失。应用 ready 与完整准入资格
仍不能混为同一指标。

这一结果降低了“只要去掉工具时间就能解决小收益”的优先级。去掉工具确实
会改变部分决定，其中也有测量成员，仍可能具有价值；但绝大多数同状态集合
没有变化。不能把 18/19 次变化折算成 JCT 收益，也不能据此给出全局收益上界。
后续优先确认持续供给和选择覆盖，而不是直接启动一轮“删除工具分数”的 GPU
实验。工具预测卸载、工具 trace 时长和现有 runtime 均未修改。

证据位于原父实验：

```text
host400_registered_copy_pressure_r1/capacity_review_correction_r1/
  rank_objective_diagnostic_r1/
    comparison_final.json
    cpu_final.xml
```

59 项 CPU 检查全部通过，无失败或跳过；涵盖三种目标区别、JOIN、sibling、
容量不能单体适配、同集合重排、真值字段缺失、测量身份不影响选择和历史源码
绑定。初始 `comparison_r1/r2.json` 及相应 CPU 报告保留。
实际选择核心与历史 registration 的 SHA256 相同；已经变动的旧 runtime/
分析脚本输入从其原冻结 checkout 按原哈希验证，不把当前代码冒充历史实现。
机会及回放事件分别重新核对 499137755、57991633 字节的既有封闭前缀。
历史原生服务证据复用原完整审计，不重新声称本读器执行了 GPU 或物理可行性验证。

## 更密集到达的背景覆盖检查

先对同一 73 条任务和固定 18 个测量成员做 CPU 静态检查，不生成新运行结果。
保留初始 20 条、seed 35、精确身份顺序和原始指数随机抽样，将每个原到达
偏移乘以 `新平均间隔 / 70`。schema 6 中已有的完整背景身份替换保持不变；
不能用替换后的身份重新排序再置换，后者会改变任务与到达槽位的对应关系。

为暴露有限背景的风险，暂时固定原对照每个测量成员的已观测完整 JCT：

```text
假定完成偏移_i = 原到达偏移_i × 新平均间隔 / 70 + 原对照 JCT_i
背景覆盖余量 = 最后一条新到达偏移 - max(假定完成偏移_i)
```

| 平均间隔 | 到达率相对原配置 | 最后一条到达偏移 | 最晚假定测量完成偏移 | 背景覆盖余量 |
| --- | ---: | ---: | ---: | ---: |
| 70 秒 | 1.00 | 3966.635 秒 | 3835.586 秒 | +131.049 秒 |
| 60 秒 | 1.17 | 3399.973 秒 | 3776.594 秒 | -376.621 秒 |
| 50 秒 | 1.40 | 2833.311 秒 | 3717.602 秒 | -884.291 秒 |

这不是反事实 JCT 预测：增加并发会改变排队、batch、Host 压力和执行时间，
不能假定原 JCT 在新配置下不变。它只说明当前 73 条有限背景没有很大余量；
直接压缩到达表可能让前段竞争更多、尾段更早失去持续到达。原 70 秒配置的
+131.049 秒来自已完成对照；上述假定完成偏移因原报告时钟表示的舍入，与
记录完成偏移约有亚微秒差异，不据此推断额外完成或缺失到达。

后续若诊断更高到达率，应同时检查实测 ready 候选、可改变集合的竞争、
Host 丢弃/额外重算、实际服务和背景尾部覆盖。若需要延长背景，使用新的
不同原项目完整轨迹，明确作为新负载；不复制已有 workflow，不改写任务、
工具时长，也不根据 Oracle 的收益重新选择测量成员。GPU 暂停期间这里只
准备分析依据，不注册或启动更高并发的实验。

## 到达诊断配置准备

`scripts/prepare_arrival_rate_followup.py` 已补齐当前负载所需的两处准备能力：

- 对 schema 6 的背景身份替换，先在原 schema 4 身份集合上按相同 seed、
  permutation 和新到达率重建槽位，再应用原完整替换记录；保留任务与槽位
  对应关系。到达表的 runtime 验证契约未变。
- 新配置中的 `private_analysis_cohort` 同步更新为新文件与哈希，保留原
  warmup、measured、background 成员和私有属性。原引用未更新、源文件
  被改写或声明要向调度器交付测量成员时，准备失败。

准备入口可复用已完成控制的 sampled supply 报告，检查 registration、
到达表、cohort 哈希及完整共同窗口分箱；此类证据明确不包含 GPU 利用率
或时间加权竞争结论。旧 `--idle-audit` 入口保留。新增可选
`--previous-cohort-report`，把上节固定旧 JCT 的覆盖检查写入准备结果；
检查本身不预测新 JCT，也不接受正式负载。

已实际生成 20 初始、平均 50 秒、仍为相同 73 个项目及 18 个测量成员的
CPU 诊断配置，位于原配对证据目录：

```text
arrival_pressure_followup_r1/
  cpu.xml
  mean50/
    arrivals.json
    analysis_cohort.json
    full.json
    preparation.json
```

独立检查生成文件确认：全部 73 个身份顺序和完整替换记录相同；每个非零
到达偏移为原来的 5/7；测量成员、完整 JCT 终止规则相同；配置除到达与私有
分析引用外逐字段相同。107 项相关 CPU 检查全部通过，无失败或跳过。
本次修复只涉及准备工具，不改变在线调度器行为，不能归因任何 JCT 收益。

该配置的静态覆盖检查明确失败，余量为 -884.291 秒，仍标记
`formal_workload_accepted=false`、`oracle_registered=false`、
`GPU_action=false`；没有改变原 20+70 配置或注册后续 GPU 实验。
按同一 seed 的 50 秒间隔继续生成槽位，第 94 个槽位首次越过上述
3717.602 秒的固定旧 JCT 完成偏移，比当前多 21 个槽位。这只描述到达
时间几何，不证明需要或足够 94 个 workflow，不代表已有 21 个合格的新项目，
也没有复制或追加任何原任务。更高压力的正式比较仍须解决真实背景覆盖，
并实测容量竞争、实际服务、Host 状态丢失和完整 JCT。

## 复用已有轨迹补足持续背景

继续检查已有 capture，发现 `remaining_node_original19_finish_r2/inventory.json`
中的 19 个不同原项目此前未进入上述 81 项目池。该来源有 19 条自然完成、
2492 个请求、原 owned exit 和 fresh drain 记录；本轮重新核对 inventory
绑定的 59 个文件哈希，并确认所记录 watcher、driver、server、scheduler
PID 已不存在。没有重新运行 native capture。

按原六个 inventory 的声明顺序保留第一份项目代表，再加入该 Node 来源，
可得 100 个不同项目，当前 73 条之外有 27 个未使用项目。新的任务多样性
18 采集使用了已有项目的其他任务，不因 task ID 不同算作额外不同项目。
这里复用原有项目 inventory，不需要为了填充背景先采新 trace。

## 下一步的选择

1. 保留完整平均 JCT 和既定 18 成员，补充逐成员相对变化及工作量分层描述。
   不能选择收益更大的窗口、最先完成者或实际受益成员替代原人群。
2. 先检查“共同可执行但容量冲突”的候选与改变选择的覆盖，再决定是否增加
   持续到达强度。若调整，固定 workload、资源和策略；用相同到达表比较各臂，
   同时保留持续背景覆盖；不能仅压缩当前有限到达表后就认定负载已合格。
   后续压力敏感性不能只保留最有利于排序的一档，也不需要为每个 CPU 候选
   单独安排 GPU 实验。
3. 在相同选择范围下区分真实模型剩余工作量与含工具路径分数，先做已有现场
   的局部诊断。若同一候选集上的完美信息也几乎不改集合，优先处理决策覆盖；
   若改了集合但完成目标仍不佳，再处理组合目标与真实服务传递。
4. 增加并发与扩展 native 计算排序是不同改动。后者须同时支付长 chunk、
   active decode、迁移和控制开销的代价，不能凭逻辑 grant 推导收益。

当前判断是：有效竞争稀疏、Oracle 的策略范围和评分代理共同限制收益；
已有数据不能把三者定量拆开。统计口径解释了约 2.60% 与 1.90% 的差异，
没有证据表明完整 JCT 漏算了一个很大的真实收益。
GPU 暂停保持有效；没有注册新实验，也没有将任何假设写成已验证的性能改进。
