## 2. 021 的九千秒不能等同于其固有计算长度

control 的固定 18 条平均完整 JCT 为 **1,854.410 秒**，`021` 为
**9,069.680 秒**，占 18 条 JCT 总和的 **27.1715%**。
其他成员中最长为 4,266.281 秒。`021` 的确显著影响均值和收尾时间，
但它的总模型工作量 67,087.06 与全体另一个 66,970.64 的原项目相近，
不能从实测 JCT 反推它的固有模型工作量高出其他任务数倍。

它的原轨迹有 369 个请求，初始 prompt 241,025 token，最大上下文
249,106 token；24 次上下文摘要贡献 32,083.30 模型工作单位，
占其模型工作量 47.8234%。全体 133 个项目中仅它记录了这些
CONTEXT_COMPACT 事件。这说明其上下文形态特殊，但不等于摘要是本轮
九千秒的主因。

对实际最后完成依赖链做逐节点记账，18 条均精确重建原 JCT。
`021` 链上请求与事件分解为：

| 链上部分 | 秒 |
| --- | ---: |
| 86 个 root 请求，从提交到 native 完成 | 7,472.283 |
| 24 个上下文摘要请求，从提交到 native 完成 | 735.965 |
| 237 个 child 请求，从提交到 native 完成 | 210.678 |
| 工具结束事件的依赖间隔 | 612.950 |
| 其余事件、提交和发布间隔 | 37.804 |
| 完整 JCT | 9,069.680 |

并行 sibling 的时间只沿实际阻塞链计入，没有直接相加全部 child 时长。
表中请求区间包括准入、恢复、prefill、decode 和其他等待，不能称为纯 GPU
计算。root 的客户端首 token 等待合计 **7,306.877 秒**，中位数
0.519 秒，最大 1,856.342 秒；这部分也包括前端、恢复和 prefill，不能
全部叫排队。但几次超长间隔有独立准入证据。

## 3. 三次请求依靠 1800 秒服务兜底

机会日志记录 `021` 在 context epoch24、26、28 的三个 root 后继
分别持续 ready 而未获得 workflow 服务 **1,801.106、1,801.589、
1,801.878 秒**，随后触发现有独立服务兜底。对应客户端 TTFT 为
1,855.928、1,856.342、1,855.291 秒。

给定记录到的普通选择边界：

| epoch | 记录数 | 需求 token | 记录到的最高空余逻辑 token | 个体可放下次数 | 进入评估候选次数 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 24 | 5,306 | 247,811 | 226,506 | 0 | 0 |
| 26 | 3,579 | 247,545 | 199,165 | 0 | 0 |
| 28 | 5,205 | 247,899 | 203,396 | 0 | 0 |

`_strict_candidate_window()` 在排序之前保留 required JOIN，再过滤
当前未折扣逻辑额度放不下的普通候选。这三次请求不是进入短优先比较后
被错误排序，而是未进入评估窗口。root 请求大小接近总物理 KV 池
805,198 token 的三分之一，持续补位可能一直消耗零散释放的额度。
这与非抢占连续性和大对象恢复所需额度有关，不能只调预测器修好。

这些是选择记录的计数，不是独立容量机会数，也不是连续时间采样。
另有 59 条含该 workflow 的早退记录没有逻辑窗口；已明确保留缺失，
没有将其解释成容量不足或成功机会。现有即时工具配对和其他准入入口
不由此表完整覆盖；逻辑能放下也不证明 native 物理页、锁或 DMA 已允许。

后续应核对：等待期间是否存在可安全释放且总量足够的阻塞 KV、既有
工具替换是否只找到不足量的单个 donor、额度释放后是否被其他准入先行
消耗，以及已选集合是否真的获得服务。不能据本表直接启用无条件抢占、
降低 1800 秒门槛、积攒容量或放宽物理安全条件。
