# 已生成工具标记能否驱动计算阶段调度

2026-11-04，America/Los_Angeles。GPU 仍由用户暂停，中央启动保护禁止自动恢复。
本轮只读最新完整 R5 执行，新增 CPU 分析和相关检查，没有修改 serving、预测器、
任务、token、到达、依赖或工具时长。

## 结论

暂不实现“出现工具关闭标记就优先推进一个 decode batch”的 serving 策略。
这个信号在本次执行中通常接近请求结束，但大部分已经来不及改变原来的 prefill
提交；剩余机会还需要支付整个现有 batch 和被推迟 prefill 的代价。

这比先前按请求剩余输出进行的 oracle 筛查更接近可观察边界，但仍是局部依赖投影，
不是新的完整 GPU 调度模拟。不能从它推导 1% 的端到端收益，不能相加局部改善，
也没有证明它比通用的 decode 停顿控制更好。保留两个已有设计，
不把这一简单规则列为第三项贡献。

## 与完整工作集控制问题的关系

用户询问普通免费准入是否应与完整工作集控制合并。源码与既有计数支持以下决定：

- 普通 2 秒窗口和完整控制可以共享一个调度边界，避免先检查未折扣免费额度、
  再等待另一个控制周期。没有正确性要求必须维持两套独立时钟。
- 保留内部快速结束和同一 native 边界内的事件合并；不要求每个 decode 回调、
  工具 hint 刷新都执行一次全量控制。
- 已确认的工具 A→B 配对、JOIN 恢复仍可及时触发，保留连续执行和原生容量、
  锁、ACK 检查。逻辑控制不自动等于物理搬运。

共同墙钟约 1583.262 秒内，最新 R5 开启轮的 770 次完整控制累计线程 CPU
约 1.9336 秒，中位 1.738ms、P90 6.841ms，约占一条 CPU 线程墙钟预算的 0.122%。
这一计数包含内部选择，与其他计数存在重叠；它不是 GPU 停顿或可删除 JCT。
工具替换检查同窗口约 25.47--25.49 秒，属于另一项计数。
不应把此前 118--132 秒工具检查 CPU 误归因于完整控制。

当前 `ce31fcb6` 已在普通窗口到期且有 pending 时提前执行完整协调，
但尚未将架构重写为单入口；该修复没有新 GPU 验证。
本轮不为低占比的控制整理安排单独实验，继续寻找能改变实际模型服务的机会。
计数来源保留在
[完整对照诊断](ranking_disabled_and_prediction_diagnostics_20261104_zh.md)。

## 输入与动作

使用先前完整依赖投影的同一绑定：

```text
ops/workflow_original73_host400_control_refresh_20261104_r1.registration.json
```

73 个原项目、400GB Host、20 初始加平均 70 秒持续到达、固定 18 测量成员。
完整测量请求为 2991 个、输出 362157 token、平均 JCT 为 1061.910742 秒。
输入 JSONL 使用前次封闭字节边界并重新校验 SHA256，前次静态输入也重新校验；
没有重新运行采集或重放。

新增读器 `scripts/audit_visible_compute_frontiers.py`：

1. 先观察 prefill 前一份 decode 实际已发布的输出，只在可见前缀包含
   `</tool_call>` 且尚无 EOS 时标记机会。未来输出仅作事后标签。
2. 以该 decode 的完成时间为信号可见边界。已经提交的 prefill 不可撤回，
   只能从后续第一份尚未提交的 prefill 开始插入动作。
3. 支付前一份完整 decode batch 的 worker 时长代理，不把其中一个请求
   单独拿出来并按人数折算。已经完成的成员按完成边界移除。
4. 核对所有未完成成员在两侧的逻辑身份和输出连续性；当前步需要自己 prefill、
   成员身份改变、完成记录缺失或直接参与者删失时，保留为未知或排除原因。
5. 一步后确实结束的请求获得完成前移，其他成员的 token 进度不计作完成收益。
   原 prefill 后缀中的所有请求支付整步成本，沿原依赖重新传播 JOIN 和结束时间。

动作不使用未来长度来删除误触发。关闭标记也不能保证整个消息结束：
102 个可审计现场中有两个信号请求后来还生成 56、83 个 token，下一边界均为
SPAWN。它们仍留在相同人群，并支付计算代价。

## 机会收缩

| 检查 | 同一完整执行中的段数 |
| --- | ---: |
| 前后由 decode 闭合的 prefill 段 | 7054 |
| 前一 decode 有可见工具关闭标记 | 766 |
| 信号可见时该段 prefill 已全部提交 | 613 |
| 仍有尚未提交的 prefill | 153 |
| 其中直接参与者有删失，单列排除 | 51 |
| 可审计的信号现场 | 102 |
| 同时观察到最后未返回 child 的现场 | 45 |

153 段均已有至少一份 prefill 提前提交。因此不能把整个原 prefill 段都算成
可避免等待。613/766 约 80.0%，只表示这份执行和该信号下的提交时序，
不能外推为所有引擎或所有工具调用的比例。

全部历史 worker 样本仍缺少完整 attempt/session 字段，102 个现场的连续物理
身份都保持未知。逻辑连续和已完成 receipt 不能替代当时的物理驻留证据，
读器不授予执行权限。

## 支付两侧代价后的结果

每个现场分别从同一原执行出发。成本是前一份完整 batch 的 worker 时间代理，
不是新 batch 的实测 GPU kernel 时间；使用四档倍率检查敏感性。

| 成本倍率 | 原 102 个现场中可前移 | 全部已完成 workflow 总和改善为正 | 同时改善测量均值 | 单次总和改善中位 |
| --- | ---: | ---: | ---: | ---: |
| 0.75 | 101 | 78 | 16 | +51.466ms |
| 1.0 | 100 | 67 | 14 | +38.107ms |
| 1.5 | 91 | 53 | 12 | +18.292ms |
| 2.0 | 82 | 36 | 9 | -4.379ms |

大成本下不可前移的现场仍属于原来的 102 个，未改称它们不存在。
四档均正的现场为 36 个。对于可见最后 child 的 45 个现场，
四档均正的为 16 个；双倍成本下有 37 个可前移，16 个总和为正、
5 个同时改善测量均值。其双倍成本的单次总和改善中位数为 -13.326ms。

一个较大的现场为 `native-service-000013255`：第一份 prefill 已提交，
后面还有 44 份，原来未完成的 decode 成员有 22 个。按双倍整批成本
47.935ms 推进，投影中一个测量 workflow 提前约 8.218 秒，
另一个 workflow 支付约 47.935ms，固定 18 条均值降低约 0.454 秒。
它不是最后 child 信号现场，更不是独立的可重复收益。

这些统计不能跨行或跨现场相加。局部动作之间可能竞争同一 batch、容量和后继，
且投影保留了原来的后续排队滞后，没有重算共享 GPU 队列、未来 batch 形状、
KV 增长或其他间接干扰。未给出全局上下界、吞吐预测或净性能结论。

## 实现决定

不启用新的服务策略，也不重启 workflow 工作量预测器训练。
关闭标记单独触发的机会不足以支撑新增机制与控制成本。
如果后续继续研究计算阶段，只考虑可见得更早的状态、实际尚未提交的工作，
并与通用 decode 停顿控制在同样成本下比较；仍需证明全系统而非局部收益。

本轮 36 项 CPU 检查通过，覆盖可见性、提交时序、成员变化、删失、整批成本、
误触发和原依赖传播。前次原始证据不覆写，新证据为：
