# R5 共用选择器的关键路径 Oracle 与匹配实验准备

日期：2026-11-18 UTC，对应美国西部 2026-11-17。
本轮为 CPU 实现、检查和实验准备，尚无新增 GPU 性能结果。

## 1. 补齐的对比缺口

[前一轮候选](r5_joint_choice_prediction_20261118_zh.md)预测整个 workflow
剩余模型＋工具关键路径，但原 strict R5 Oracle 只接受总剩余模型工作量。
旧全局 Oracle 已经包含工具时间，却使用全局恢复入口；它与 strict R5
的候选窗口、容量规划和 sibling 分组不能直接当成同一选择器。

新增显式诊断工件 `workflow_model_tool_path_combination_oracle_v1`，
将原精确路径计算接入现有 strict R5 选择器。原有 Oracle 工件的语义和
约束保持，不能静默把原模型工作量 Oracle 改解释成关键路径 Oracle。
新工件明确使用未来完整轨迹，仅用于诊断，不能部署，也不是最优 JCT 上界。

## 2. 共同决策路径

新 Oracle 与预测 R5 共用：

- 默认六候选、必要时八候选的窗口和相同资源检查。
- required JOIN 权利，以及 workflow 级剩余关键路径短优先。
- 同一真实阻塞 ALL-JOIN 的 ready sibling 跨恢复类别组队，整组能放下
  就共同选择，不能整体放下时推进可行子集。
- 普通两秒边界、事件合并及已确认工具替换的即时响应。
- 现有工具保留权重与原生保护；在既有压力排序允许比较工作优先级时，
  两者调用同一个路径权重函数。
- active 连续性、独立服务兜底及 native KV、槽位、锁和 DMA 最终权限。

R5 预测值和 Oracle 精确值均使用秒数，归一化参考同为
328.548810 秒。接口权重仅单调表达路径长短，不以候选效用和、fanout
或恢复成本比改变短优先顺序。

Oracle 复用原 DAG 扫描和缓存，串行路径累加、并行路径取 max；已等待
工具的过去部分扣除。工作量及观察守恒仍沿用原实现，不新增控制周期。
同一 native 边界内复用预测；新观察使缓存失效，已开始等待的外部时延可
通过已有缓存包络随时钟递减。

同时修正状态口径：strict 选择不再被标成旧的线性 sibling 份额评分；
路径头参与既有压力偏好时如实记录。新 Oracle 的模型状态继续报告
`remaining_model_tool_critical_path_seconds`，另以工件种类和
`shared_R5_path_order` 标记共享选择器，保持现有健康校验接口可验证。
实验登记也记录新路径在既有压力偏好中的未来信息使用范围。

## 3. 三份匹配配置

`scripts/prepare_r5_path_comparison.py` 复用当前 control 的负载和服务
配置，生成：

| 文件 | 工作信息 | 普通准入 |
| --- | --- | --- |
| `full.json` | 保留原连续工作量 worker，省去新路径头 | 关闭排序，使用原参考集合 |
| `oracle.json` | 精确剩余模型＋工具关键路径 | strict 短优先＋真实 sibling 组 |
| `learned.json` | 四折选中的路径预测头 | 同一个 strict 选择器 |

三个实验臂继承相同 133 个原项目、Host200 GB、initial20/mean55 秒、
固定 18 个测量成员，以及原任务、token、工具时长、依赖和到达表。
除工作信息工件、哈希和 provider 外，服务环境逐项相同。测量组文件
只留在实验控制侧，不传给调度器。

Full 省去路径推断，预测 R5 包含其实际推断成本，因此完整方法结果也会
包含这部分开销。不能把三臂 JCT 差额全部解释成纯排序收益；还需核对
选择、原生资格、首次服务和迁移/重算记录。

旧配置里有关效用最大化、老化或“只比较 D3”的说明已清理，旧源码绑定
未冒用到新候选。准备复用正式 `environment()` 组装与真实模型目录，
三个工件均通过实际 runtime 构造预检。

当前预备基座继承 D3 关闭。repaired_r4 的 control 保留旧 R5 排序，
不能复用为这里关闭排序的 Full。等当前 D3 配对结束后，再依匹配结果
确定最终基座并完成线性源码整合、完整来源绑定和冻结，才登记新 GPU
验证；本次准备没有自动启动或排队任何 GPU 实验。

## 4. CPU 证据

最终集成检查 **918 项通过、无跳过**，包括原生 CPU tree/allocator
的 sibling 生命周期与恢复容量用例。原生引擎为当前已验证的
`434c35dd66211d0a230717c88bf1452056769a40`，没有修改引擎源码。
所有作业隐藏 CUDA，CPU0、nice19、单线程运行。

关键用例覆盖工具过去等待扣除、并行 sibling 总模型工作量较大而剩余
关键路径更短、跨恢复类别共同准入、容量不足的部分推进、既有工具替换
与压力偏好、真实 native 候选资格，以及原生实验健康校验。

使用实际 133 个 workflow 的初始未服务状态，精确路径与逐节点参考
全部相等。共扫描 106,830 个节点；各 workflow 随后五次查询共 665 次
缓存命中。最终局部线程 CPU：

| 查询 | 次数 | 中位数 | P90 | 最大值 |
| --- | ---: | ---: | ---: | ---: |
| 首次建图 | 133 | 2.977ms | 5.170ms | 8.852ms |
| 无新观察的缓存命中 | 665 | 8.316µs | 9.059µs | 16.472µs |

这些是初始状态局部 CPU 成本，尚非实际运行的失效频率、完整控制成本
或 JCT。尤其不能仅报缓存命中八微秒而忽略首次建图及后续重新计算。
实际计时继续进入 `path_thread_cpu_us` 和控制器计时。

初始 8,778 对不同 workflow 中，总模型工作量与模型＋工具路径有
1,558 对反序。这只能说明两个目标不同；它不等于实际容量竞争次数、
可改变的服务次数或性能收益。

初次检查中暴露的遗漏均保留：新工件未加入两秒窗口校验、独立构造
fixture 无 `_work`、fixture 缺少上下文绑定/到期窗口，以及旧状态字段
不适配严格分组。初次配置准备误将整份配置当环境，随后又遗漏标准
服务前缀映射；均在 CPU 阶段退出，最终统一复用正式环境组装。
不把失败或原先未指定引擎而跳过的用例算作成功。
