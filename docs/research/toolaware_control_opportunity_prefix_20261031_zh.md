# 12 初始与平均 70 秒对照：运行中选择机会审计

本记录是冻结代码 `9316152914dc` 的修复版对照前缀，不能当作完整 JCT 或 oracle 性能结果。该对照关闭剩余工作量排序，保留相同 oracle 进度记账、工具感知压力、事件驱动预测卸载、JOIN/EOS 和 2000 ms 普通窗口。工具时长映射保持不变。

数据目录：`experiments/reports/remaining_original_projects_20261030/control_toolaware_initial12_mean70_live_r1/`。各报告记录其完整 JSONL 前缀字节数和哈希；多个报告在不同时间采集，不能视作一个原子快照。服务器、回放进程、固定测量组和停机协议均未修改。

## 已发生的选择与实际服务

`periodic.json` 封存前缀包含 258 个周期控制、144 个存在 ready-paused 的边界、6 个跨 workflow 且候选各自能放下而不能全部放下的竞争。109 个周期恢复都验证了后续精确请求的实际服务，93 个还在下一次已观察决策之前完成有效批次。新链路已经有真实消费。

同批供给观察 `supply.json` 的 454 个固定共同窗口状态样本中，217 个包含 ready-paused。该观察仍只覆盖共同窗口前段，不能与旧实验整个共同窗口的比例作单因素因果比较。

稍后的 `selection_replay.json` 精确复现了 706 个对照周期决策，386 个被选请求均有后续实际服务。这是已经发生的对照服务，不是重排后的反事实服务。

## 局部 oracle 比较

现有选择读器原来将关闭排序的控制日志当作整数类别日志，而新控制记录的是浮点常数优先级。已补齐该格式支持，并新增 `scripts/audit_control_oracle_opportunities.py`。读器使用日志中保留的真实剩余关键路径，复用相同冻结策略、候选、预算、100 token buffer、类别及 JOIN 分组；ready JOIN 的零优先级保持保护。

`oracle_opportunities.json` 的结果：

| 项目 | 次数 |
| --- | ---: |
| 精确复现的真实对照周期决策 | 706 |
| 非空候选边界 | 324 |
| 跨 workflow 容量竞争 | 6 |
| oracle 改变局部顺序 | 103 |
| oracle 改变选中集合 | 4 |
| 竞争候选关键路径相差至少两倍 | 6 |

这四次集合变化出现在到达原点后约 120.37、132.65、150.97、197.86 秒。前一次与第三次只替换 warmup；第二次用较短 warmup 替换 measured；第四次用较短 measured 替换 warmup。不能将“选中了更短任务”直接称为测量组 JCT 改善，也不能因为涉及 warmup 就忽略其后续资源影响。

该反事实只覆盖周期恢复选择，未模拟改变选择后的压力对象、物理恢复、组批、后续到达状态或完整 JCT。事件准入与压力暂停的覆盖并不完整。完整 oracle GPU 对比仍然必要。

## 其他路径确实在执行

同一较后前缀记录了：

- 34 次真实 A→B 授予；
- 122 条预测工具 KV 驱逐节点事件；
- 323 条实际 KV 缺失后的资格暂停事件；
- 27 个工作集压力决策；
- 74 次 JOIN 免费额度授予、11 次 JOIN 阻塞额度交接。

这些是不同粒度的事件计数，不能相加为独立 agent 数或调度收益。A→B 的约 4997 次尝试中，4957 次未找到完整可行组合；记录的该路径 CPU 合计约 8.06 秒。这说明路径不是空开关，也留下了减少无效检查的后续空间，但还没有证明它造成可见的 JCT 开销。

## 排查过的容量因素

早期物理采样中 HBM 分配占用约 99.89%，其中可回收 479108 token、不可回收 325244 token；Host 占用约 84.77%。分配占用包括可回收缓存和在途状态，不能据此认定都是有用存活状态。

`demand.json` 的 23 个规则/末事件采样中，下一次可复用的存活前缀并集最大为 HBM+Host 容量的约 64.68%，较后末样本约 47.20%。这是 CPU 存活状态诊断，不代表实际分配或全部并发增长需求；使用未来下一请求只为判断旧状态的实际复用范围，未送入调度器。

`shared_prefix_budget.json` 在 49 个约每分钟的真实周期边界比较完整 active 上下文之和与同原生 namespace 的精确 token 前缀并集。重复计费中位数为 8920 token，最大为 38656 token，约为 805198 token 池的 4.80%。4 个采样边界存在被原预算拒绝、在该影子容量口径下可能放下的候选。影子预算不代表原生页已经共享、存在可用请求行或允许实际准入；这部分差额尚不能作为主要瓶颈。

`residency_granularity.json` 的更后前缀将资格暂停来源分开：27 次来自后继完整 Host-only 前缀检查，144 次来自预测卸载回调，546 次来自原生 parent-pressure 回调。回调可能只记录触发暂停的首个释放节点，不能用其 token 数推断整个 agent 的总卸载量。27 次完整后继检查的缺失量中位数为 125 token，其中 17 次不超过当前提交输入的 1%；这提示小恢复与整 agent 资格转换之间的粒度值得后续单独评估，尚未证明它造成额外 JCT。

## 下一步边界

当前证据说明有效候选与实际服务已经出现，但稳定阶段的竞争仍可能不足。优先完成固定 18 个成员的完整 JCT、共同窗口、后台覆盖和实际退出审计，再在相同条件下验证 oracle。若收益不足，要区分周期恢复、A→B、压力暂停与原生实际组批中的选择机会，不能仅以排序次数判断机制生效，也不能仅靠继续扩大任务工作量差异解决。

读器针对性回归 `reader_cpu.xml` 共 69 个测试通过，没有修改当前 GPU 应用或原生引擎；这不是更新后的整套 GPU 源码资格。正式目标与成功判据保持不变。

## 完整测量组结果的校验入口

旧 `review_sustained_oracle.py` 的命令行入口要求“关闭工作量模块的旧 Full → 开启模块的 oracle”以及事后生成的旧版 provenance。本轮两臂都保留相同进度记账，仅 artifact 中的 `remaining_work_ranking_enabled` 分别为 false/true，不能直接套用旧入口。

新增只读入口 `scripts/review_matched_work_ranking.py`。它要求任务、工具时间、到达表、资源、窗口、策略和指标门槛匹配，校验两份 artifact 的哈希及除排序开关以外的全部内容；两臂均须通过现有测量组完整收据、自然结束、新鲜排空及实际退出验证。比较复用现有固定测量组 JCT 和共同墙钟窗口吞吐实现，不改变测量口径，也不把已完成背景成员当作新的测量组。

工具时长保持当前映射不变，A→B 仍属于预测卸载链路。下一臂应在同一 12 初始、平均 70 秒到达表上开启排序，不再重复运行相同对照，也不同时切换到 80 秒。当前背景已全部到达而测量尾部尚未结束；该覆盖问题必须保留在工作负载判定和最终比较中，即使数值 JCT 改善也不能因此宣称满足稳态验收。

`matched_review_cpu.xml` 中 44 项测试及 11 个子测试通过，并用实际准备好的两份配置验证仅排序开关不同。这里只增加分析入口，没有更新冻结的 `93161529` 服务源码或其 6135 项 CPU 资格。
