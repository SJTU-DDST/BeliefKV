# 工具替换阶段配对与首次准入窗口筛选

## 当前决策

继续使用original56、初始12条及平均70秒持续到达的保留Full。
本轮只读核对工具事件替换及初始准入，没有修改任务、工具时长、到达表、
测量组、服务runtime或原生引擎，没有新增GPU任务。

**阶段配对在当前负载上只有少量已观察的替代机会，尚不进入GPU比较。**
不能将“只有4/144的消费者在donor窗口内最终返回”解释成140次不合理选择：
以更合适的下一释放边界看，已有66/144在窗口内到达潜在释放边界。
12次已发布的可改序逻辑竞争中，6次有乐观阶段配对替换；它们对应5条
不同donor后继请求，donor均为背景workflow，物理替代准入和净JCT收益未证明。

另外检查了已关闭工作量排序、仍保留2秒收集窗口的首次准入。
测量workflow的初始延后区间按各workflow合并后平均5.316秒；
它包括非关键sibling、其他竞争和未知物理条件，不能视为可消除JCT。
当前证据也不足以为首次准入窗口追加一次完整GPU调参实验。
这一初始请求分析不覆盖所有工具后继恢复。

## 下一释放边界的定义

新增`scripts/audit_tool_stage_alternatives.py`，从已有实际事件替换出发，
重新关联同request、attempt、session和generation的已发布选择。
选择的grant必须发生在replacement前0至50毫秒；受保护JOIN、不ready、
完整逻辑预算不能单独放入的候选继续排除。

每个候选从其当前模型请求出发，沿同invocation实际串行事件检查：

- 等待至少2秒的完整工具轮次：以工具开始作为潜在释放边界；
- 实际JOIN完成比JOIN_WAIT晚至少1毫秒：以真实阻塞作为潜在边界；
- 正常RETURN：以终态作为潜在边界。

前面的短工具等待计入阶段成本；同轮并发工具按已有轮次的最晚完成时间，
不逐工具重复累加。同轮重复TOOL_START也不重复计费。
foreground CALL、未知工具轮次、未知JOIN完成、取消或截尾均保留不支持，
不能赋予零剩余工作。

2秒只是这次离线边界筛选值，不替代线上动态卸载门槛。工具开始或RETURN
也不直接证明Host副本settled、原生锁释放、独占页可回收或逻辑额度已归还。

阶段时间代理使用冻结非排序控制已有的完整请求工作量清单：

```text
phase_proxy =
  sum(necessary_input_increment / 100 + true_output_tokens) * frozen_coefficient
  + observed_short_tool_round_waits
```

系数为0.020962694137秒/模型工作单位，保留其原定义与局限。
使用未来输出和未来边界仅为离线机会筛选；服务策略没有获得这些信息。
它不是上下文精确的GPU成本，也没有计入恢复、备份、安全释放及后续重算。
真实墙钟阶段时长包含排队，不能用于替代这一代理或预测另一个策略的执行时间。

## 完整事件替换审计

本轮复现同一144次事件替换，工具轮次、固定测量成员和封存日志均与此前
窗口审计一致。每次消费者阶段及donor后继的首次服务均获得对应：

| 观察 | 数量或时间 |
| --- | ---: |
| 实际事件式替换 | 144 |
| 消费者下一潜在边界为长工具 | 117 |
| 下一边界为正常RETURN | 23 |
| 下一边界为真实阻塞JOIN | 4 |
| 消费者实际在donor工具返回前到达潜在边界 | 66 |
| 乐观阶段成本代理可放入donor剩余窗口 | 71 |
| 已发布、ready且无受保护JOIN的逻辑竞争 | 12 |
| 存在至少一个阶段代理可放入窗口的替代者 | 10 |
| 原消费者代理不适合、替代者代理适合 | 6 |
| 上述6次中donor后继实际服务前等待超过1秒 | 4 |

144次donor后继提交至首次服务的等待P50为1.313秒，P90为8.443秒。
这不是全部由被选消费者造成的等待；其他active agent、prefill、原生容量、
恢复和批次形状都可能参与。

6次乐观替换机会对应：

- 5个不同donor workflow及5条不同donor后继请求；
- donor测量workflow数量为0；
- 适合窗口的替代者涉及2个不同测量workflow；
- 按后继去重的donor服务前等待合计6.639秒。

最后一个数是观察规模，既不能作为可消除JCT，也不是整个方案的全局收益
上界。替代者提早推进可能改变后续依赖，原消费者也会被延迟；
当前只读审计没有重放这些变化。

因此，本轮没有以6次proxy switch登记GPU实验。记录未覆盖所有替换候选，
不能把缺少发布记录当作没有替代者，也不能把12次逻辑竞争当作12次物理可行
切换。原resume类别和替代对象的实际物理准入仍未证明。给某个background
agent更早归还容量，也不自动降低等权workflow JCT。

## 首次准入收集窗口

在调查阶段配对时发现，保留Full虽然关闭工作量排序，仍保留2秒普通准入
收集窗口。因此另用`scripts/audit_free_initial_admission_delay.py`，
核对可能存在的无竞争延后，而没有直接取消窗口。

此处只统计首次agent注册时：

```text
active_after_arrival == false
complete_budget_tokens <= remaining_after_tokens
```

再按相同request/attempt/session身份关联后续实际grant和首次原生worker服务。
周期授予、普通free dispatch及JOIN/sibling授予均可作为真实grant入口。
过滤保留的是注册瞬间逻辑预算，不证明当时已有物理页、请求行或没有竞争者。

| 同一完整Full记录 | 数值 |
| --- | ---: |
| 已观察初始注册 | 397 |
| 初始inactive但单独逻辑可容纳 | 364 |
| 上述记录对应精确后续grant及原生服务 | 364 |
| 属于固定测量workflow的记录 | 115 |
| 注册至grant等待P50 / P90 | 0.972 / 1.820秒 |
| 所有等待区间的时间并集 | 297.529秒 |
| 并集中未被记录worker区间覆盖 | 1.885秒 |
| 各测量workflow合并并行初始等待后的等权均值 | 5.316秒 |

少数等待超过2秒，最大15.564秒，说明不能把整段时长都归给收集timer。
初始资格预算、其他grant、压力和物理条件可能在等待期间改变。
worker覆盖不是CUDA活跃率，不覆盖的时间也不是可直接消除的GPU空闲。
按workflow合并并行sibling区间避免重复累计，但仍包含非关键分支，
不能将5.316秒直接从平均JCT扣除。

这份证据不支持以“364次等待”宣称显著GPU浪费，也不证明所有准入延迟
都很小：普通工具后继恢复不在本项范围内。因此保留当前窗口，不把参数
扫描当成新的调度设计。
