# V330 完整预算与工具卸载审计

本次只读 CPU 审计覆盖已完成的 V330 Full，18 个 workflow、
3674 个请求及全部正常长尾不变。V345 匹配的 ThunderAgent 工具衰减版
仍在运行；这些机制统计不构成性能胜负，也没有修改其冻结代码。

## 逻辑预算不能等同于冷 HBM

`experiments/reports/v349_v330_complete_agent_budgets_20261027.json`
核对全部 2209 个请求区间内预算快照，全部同快照对账。
原生请求跨度为 2279.442 秒，覆盖 2277.917 秒，未覆盖 1.525 秒。
每个快照最多保持 1500ms；没有用无限延长快照来填补采样缺口。

| 全程逻辑 active 预算 token·时间 | 占比 |
| --- | ---: |
| 已提交模型请求，含原生排队与执行 | 72.282% |
| 已知工具或 JOIN 阻塞 | 23.586% |
| 请求之间、未标记阻塞 | 4.132% |

阻塞的三种观测原因分别占全程 active 预算 token·时间：
JOIN 14.604%、已经等待一秒的工具 7.099%、预测长工具 1.883%。
这些是调度资格的逻辑记账，不是物理 HBM 页数、可回收独占页，
也不是对应原因造成的排队时间。

**同时存在已提交 inactive 请求的阻塞预算，只占全程 active
预算 token·时间的 2.974%。**分母仍为全程预算，而不是仅取存在
inactive 请求的时段。inactive 请求不一定因这个阻塞预算被延迟，
也不一定存在物理容量缺口。因此既不能把全部 23.586% 判为浪费，
也不能把 2.974% 当作必然可消除的等待。

V335 的较早前缀中，已知阻塞占比为 7.125%；它不能代替全程值。
最后的多分支等待和活跃集合变化同样需要保留。不能仅为降低预算
占用率而强制撤销阻塞 agent 资格、增加后续 KV 搬运。

## 实际物理释放

`experiments/reports/v350b_v330_complete_tool_offload_and_budget_mechanisms_20261027.json`
逐条聚合原生授权的物理释放事件，并与最后累计计数对账：

| 释放路径 | 事件数 | 累计 FULL 释放量/GB | 不同 invocation |
| --- | ---: | ---: | ---: |
| 实际容量缺口下工具等待驱逐 | 355 | 13.240467456 | 71 |
| 实际容量缺口下 JOIN 等待驱逐 | 559 | 114.284691456 | 18 |
| 预测式提前工具卸载 | 10 | 0.118947840 | 9 |

GB 为十进制单位。前两类检查实际分配缺口、独占 session、
原生无锁条件及已完成 Host 副本；第三类额外检查当前预测与受益
请求。这里不含其他普通 native LRU 动作。
累计事件释放量不是唯一 KV 体积，不能直接解释为省去的传输量或 JCT。

十次预测式实际驱逐的动态剩余时间门槛为 1574.731--2016.770ms，
均通过当时的预测生存概率条件。它不是旧的固定一秒规则，也没有
证明新场景下的预测精度或驱逐净收益。额外预测卸载的量很小，
不能把已有普通压力驱逐计入提前卸载的效果，或者直接认定预测
门槛就是唯一瓶颈。

首次新增审计错误地假设 Device 的已分配字节数可直接除以可用
token 数，校验失败并保留为
`v350_v330_complete_mechanism_geometry_assumption_failure_20261027.json`。
核对冻结原生实现后确认 Device 含一个 padding slot。
最终使用 Host 的精确 FULL 布局单位 98304 bytes/token，
同时验证 Device 的额外分配槽，未改变实际容量或运行结果。

## Prepare 与 Host 压力

后台 idle prepare 记录 9867 次检查，其中 7181 次在 Host 容量门槛处
停止，实际发起 77 个批次、6013 个 FULL token，约 0.591GB。
这些只属于后台 idle 路径，不包含 SPAWN 或工具触发的其他备份。

原生 Host pool 的高水位达到约 200GB，累计 Host 驱逐约 1.104TB。
这支持继续检查 Host 容量和有效副本的竞争；它没有证明压力由
prepare 导致，也没有证明增大 Host 或减少备份就能改善完整 JCT。
历史原生 demand H2D 的 3.223TB 仍按 V339 的请求归因解释，
不能把它全部称为预测卸载造成的重复搬运。

## 下一步的证据条件

先完成 V345 的匹配比较，核对完整 JCT、makespan、decode batch、
恢复流量及暴露等待。如果 Full 的恢复量或等待更高，应先检查
资格借出、返回及实际执行顺序，而不是扩大普通预取权限。
如果主要差距出现在 decode batch 与服务形状，则进一步检查并发
和 agent 连续性；不能通过驱逐 ready agent 来虚增预取覆盖率。

目前不因上述统计新增 GPU 实验，不修改正在执行的 V345，
也不接受已有全局目标为完成。
