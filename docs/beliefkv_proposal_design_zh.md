# BeliefKV：面向动态多智能体工作流的联合执行与 KV 调度方案

更新日期：2026-09-23

## 一、项目目标

本项目面向单 GPU、显存受限的多智能体工作流，研究执行调度与 KV 缓存管理协同优化方法。针对 agent 在运行中动态派生子任务、调用工具、等待消息和汇合等特点，系统从运行时事件中持续识别工作流因果关系，并结合 GPU 与主机内存中的 KV 状态，联合决定请求执行顺序、准入时机及缓存驻留、迁移和恢复策略。

项目目标是在保证任务语义正确和资源安全的前提下，提高 GPU 有效服务能力与工作流完成效率，减少因显存不足造成的等待、重复 prefill 和 KV 重复搬运。系统以工作流吞吐和端到端完成时间为主要指标，同时评估执行等待、缓存复用、传输开销、重算成本和任务公平性。

## 二、总体设计

BeliefKV 将运行时因果状态与物理 KV 状态分开建模，并通过统一的联合计划协调两者。

运行时因果状态描述请求之间的执行依赖和当前阶段；物理状态描述 KV 页的实际驻留位置、共享关系、锁定状态及代际信息。调度器只有在联合评估这两类状态后，才生成执行或迁移动作。SGLang 的 RadixCache、HiCache 和底层 allocator 仍是 KV 物理状态及分配结果的事实来源，BeliefKV 不绕过原生分配器直接修改 KV 张量。

整体流程为：运行时事件采集、因果状态更新、可执行动作识别、需求预测、执行与 KV 联合决策、安全点验证、原生服务执行及结果反馈。

## 三、关键技术方案

### 1. 基于运行时事件的因果状态建模

系统采集请求创建、模型调用、工具开始与结束、子 agent 派生与返回、消息传递及 JOIN 等事件，在线构建和更新运行时因果图。图中记录 invocation 的状态、父子关系、等待条件和状态版本。

与依赖预先给定完整工作流图的方案不同，BeliefKV 面向运行时逐步展开的工作流：尚未派生的子任务不被虚构为已知节点，实际发生的依赖变化通过事件更新。调度器据此形成 action frontier，区分当前可运行请求、等待工具或子任务的请求，以及能够解锁后续工作的请求。

### 2. 面向动作的需求预测

预测模块为调度提供与具体动作有关的概率分布，而不是只给出一个确定的未来时间点。预测对象包括工具或子任务的剩余等待时间、请求后续 decode 需求、prompt 与 KV 增长，以及候选 reentry 是否可能与当前传输窗口匹配。

对于 JOIN，系统依据当前未完成子任务及其状态估计 parent 的重新就绪窗口，并随子任务返回、工作流状态变化或新观测滚动修正。预测结果提供场景和不确定性信息；请求之间的硬因果依赖仍由运行时因果状态决定，预测不能越过未满足的 JOIN 或其他依赖条件。

### 3. 执行与 KV 联合决策

JointPlan 在一个决策过程中共同考虑 runnable 请求顺序、等待请求准入和 KV 动作，而不是先独立决定执行队列、再事后处理显存不足。请求排序综合因果解锁价值、剩余服务需求、KV 恢复成本和等待时间；公平性用于限制长期饥饿，不替代吞吐目标。

系统拟将下一请求的准入与 KV 恢复协同处理：在将请求加入执行集合前，检查其 KV 是否已驻留 GPU；若需要从主机恢复，则根据预测的 reentry 窗口、数据量及传输队列状态提前安排 H2D，使数据传输尽量与当前请求执行或其他传输重叠。

对于工具等待或暂未就绪的请求，系统可提前将 GPU KV 复制到同一 NUMA 节点上的主机内存，形成可恢复副本。该 prepare 操作本身不释放 GPU 空间；只有在物理状态有效且出现相应容量需求时，才提交真正释放 HBM 的操作。对于已终止且没有后续 owner 的上下文，可直接释放其 KV；对于仍可能恢复的上下文，则保留可恢复副本或采用重算回退。

### 4. 分层 KV 状态与物理安全验证

系统分别管理 full-attention KV 与 Mamba 状态池，按照各自的容量、驻留及可驱逐状态进行资源核算，不将两个池的 token 数直接视作可互换容量。第一阶段聚焦 GPU HBM 与同一 NUMA 节点的主机 DRAM；SSD 协同不纳入当前实施范围，以控制系统复杂度。

物理迁移以实际 page 或满足共享闭包约束的物理 bundle 为单位。计划绑定请求及上下文 epoch、页代际、owner、祖先闭包、锁状态、目标池容量和传输状态。逻辑 agent 身份不能单独作为迁移授权依据。

### 5. 安全点与事务式动作执行

联合计划不直接修改物理缓存。调度器在安全点捕获有界状态，并重新验证预测结果和计划绑定的请求、上下文及物理版本；复杂预测与场景计算在后台执行，结果被调度线程消费前必须再次核验。

D2H、H2D 和释放操作通过 SGLang 原生缓存与传输路径执行，并以 ACK 和实际服务状态确认结果。若请求状态、页代际、共享 owner、容量或传输条件发生变化，系统撤销过期计划，释放未提交资源预留，并退回原生调度路径。安全点保留 SGLang 的 PrefillAdder 与 allocator 作为最终准入和容量裁决者。

## 四、预期创新点

BeliefKV 的研究重点不是单独提出 KV offload、prefetch 或关键路径排序，而是研究如何将动态 agent 工作流的运行时因果状态、请求准入和物理 KV 生命周期放入统一的在线决策过程。

预期形成以下方法贡献：一是从运行时事件逐步重建动态工作流的可执行边界；二是使用与具体调度动作相关的需求分布，为执行排序、容量规划和传输窗口判断提供依据；三是联合选择执行对象和 KV 操作，使候选请求的准入与 KV 恢复协同；四是以页级物理状态、版本验证和事务 ACK 约束预测动作，降低错误预测导致的无效迁移及调度阻塞。

上述贡献须通过同一模型、引擎、硬件和工作负载下的对照实验验证，不能仅以预测准确率或迁移次数作为系统收益证明。

## 五、验证方案

实验采用相同工作负载和系统配置，对比 SGLang 原生响应式调度与启用 BeliefKV 后的调度结果。主要指标包括输出 token 吞吐、有效工作流完成速率、工作流完成时间、GPU 服务利用情况、请求排队与首次服务等待、device/host cache 命中、D2H/H2D 数据量与时延、KV 重算量、主机池压力以及任务正确性。

对预测动作进一步记录从触发、计划生成、验证、传输提交、ACK 到首次 GPU 服务的时间链，并检查动作是否在其 latest-start 之前完成。实验应分别报告 KV 与 Mamba 池的 active usage、可驱逐缓存和实际驻留占用，避免以单一“显存使用率”替代容量分析。

## 六、当前实现基础与边界

目前已形成运行时因果状态、action frontier、Observed-State JointPlan、准入排序、物理 KV 镜像及动作安全验证等实现基础。预测式设计已覆盖需求与等待窗口估计、预测性 host shadow、H2D 计划及相关事务接口的部分代码路径。

需要区分代码路径和系统验收状态：Qwen3.5/SGLang 0.5.20 上正在开展 native-reactive 数据采集和迁移适配；新栈的完整预测式物理调度尚未完成端到端验收，单节点 PREPARE/H2D 尚未形成已验证的稳定在线闭环，也尚无新栈下预测调度提升吞吐的结果。因此，申报书可将联合预测调度列为本项目拟突破的关键技术，不宜表述为已在新版推理引擎上实现并验证的性能成果。
